# 기획문서가이드

> 모든 프로젝트가 동일 양식으로 기획문서를 작성해 **일관된 품질**을 내기 위한 표준 가이드.
> 본 가이드를 보고 템플릿에 맞춰 작성하면 G-READY / G-EVIDENCE 검증을 통과한다.
> 판정은 전부 Python checker(LLM 0). 본 문서 자체는 검증 제외(doc_type: ignore).

## 0. 핵심 원칙 (8조)

1. storyboard MD 는 개발/검증 **필수 문서가 아니다**.
2. storyboard PPT 는 **사장님 확인용 참고자료**다.
3. 개발 agent 는 **task(task_spec)** 를 기준으로 개발한다.
4. task(task_spec)는 기존 storyboard 의 화면/흐름/상태 설명을 **흡수**한다.
5. unit_test 는 **task 단위** 검증 기준이다.
6. QA 는 **DAG 단위** 연계 검증 기준이다.
7. Python checker 는 **DAG / task / unit / QA** 를 검증한다.
8. **PPT 는 Python checker 검증 대상이 아니다.**

## 1. 개념 축 (고정)

```text
DAG ≡ 프로그램 ≡ 도메인(로그인)   ≡ QA 1개   (스토리보드는 프로젝트 PPT 1개)
 └ task ≡ 기능(네이버로그인) ≡ 단위테스트 1개  ← 개발자가 보고 개발하는 상세 명세
```

- DAG = 프로그램 = 도메인 1개. 하나의 DAG 안에 여러 task.
- task = 기능 1개 = 단위테스트 1개. task_spec 이 개발 기준.
- QA = DAG 1개 단위 연계(다중 task) 검증.

## 2. 문서/폴더 정의

| 경로 | 정의 | doc_type | 작성주체 | "하나만 보면" |
|---|---|---|---|---|
| `main_plan/plan.md` | 상세기획서 | plan | main | 프로젝트 전체 |
| `main_plan/dag/dag_index.md` | 프로그램 전체 목차 | dag_index | main | 프로젝트 도메인/업무 한눈에 |
| `main_plan/dag/d<n>_<도메인>/task_index.md` | 도메인 task 목차 | program_spec | main | 그 도메인의 기능 목록 |
| `main_plan/dag/d<n>_<도메인>/t<n>_<기능>.md` | 기능 상세명세 | task_spec | main | 개발자가 보고 바로 구현 |
| `main_plan/unit_test/unit_<n>_<기능>.md` | 단위 검증 기준 | unit_test | main | task 1개 검증 |
| `main_plan/qa/qa_<n>_<도메인>.md` | QA 연계 기준 | qa | main | DAG 1개 연계 검증 |
| `main_plan/storyboard/<프로젝트>.pptx` | 시각 자료 | (없음) | main | 사장님 확인용, 검증 제외 |

명명 규칙: 도메인 = `d<숫자>_<도메인명>`, task = `t<숫자>_<기능명>`. 한 DAG 폴더에 task_index 1개 + task 파일 N개.

## 3. 문서 3영역 공통 구조

1. **YAML front-matter** — `key: value  # [owner]` (owner = main/agent/script).
2. **고정 Markdown 표** — 판정/목차/매핑 표(아래 doc_type별 필수 표).
3. **자유 서술** — `## 참고 (판정 제외)` 이후. 판정에서 제외.

판정 컬럼(`자기보고(1차)`/`상태`)은 **strict O/X 문자만** 허용(PASS/✅/0 등 금지).

## 4. doc_type별 필수 양식

> 각 doc_type 상세 양식(필수 키·필수 표·검증 조건)은 **해당 템플릿의 `## 작성 규칙 (양식 — 판정 기준)` 섹션으로 흡수**했다. 양식이 곧 템플릿(단일 진실원). 아래는 위치 인덱스만.

| doc_type | 템플릿 | 비고 |
|---|---|---|
| dag_index | `dag/dag_템플릿.md` | 프로그램 전체 목차 |
| program_spec | `dag/task_index_템플릿.md` | 도메인 task 목차 |
| task_spec | `dag/task_spec_template.md` | 기능 상세명세(필수 6섹션) |
| unit_test | `unit_test/unit_템플릿.md` | task 단위 판정 표 |
| qa | `qa/qa_템플릿.md` | DAG 연계 판정 표 |

> 새 프로젝트는 위 템플릿을 복사 → `<doc>_템플릿.md` 접미를 실제 이름으로 바꿔 작성. 템플릿 파일은 검증/skeleton 대상에서 자동 제외(`_common.is_template`).

## 5. source 표 (개발 결과물 — agent/script 산출)

개발 결과(result/qa_result)는 단일 source 가 아니라 **sources[] 표**로 기준 문서를 대조한다.

- 본문 표(헤더): `source_id | doc_type | path | sha256`
- doc_type별 **필수 source**:
  - `result`(개발 결과) → **task_spec + unit_test**
  - `qa_result`(QA 실행) → **qa**
- 규칙: path 누락 / sha256 누락(path만 있고 sha 없음) / 존재하지 않는 path / sha 불일치 = **BLOCKED**.
- source 표는 `generate_skeletons.py` 가 시드(스크립트 전용). 에이전트 수정 시 sha 불일치로 차단.

## 6. 작성 절차 (프로젝트 공용)

```text
1) plan.md 작성 (상세기획서)
2) dag/dag_index.md 작성 (도메인 전체 목차) — dag/dag_템플릿.md 복사
3) 도메인마다 dag/d<n>_<도메인>/task_index.md (task 목차) — dag/task_index_템플릿.md 복사
4) task마다 dag/d<n>_<도메인>/t<n>_<기능>.md (task_spec, 6섹션) — dag/task_spec_template.md 복사
5) unit_test/unit_<n>_*.md (task별 단위 기준)
6) qa/qa_<n>_*.md (DAG별 연계 기준)
7) storyboard/<프로젝트>.pptx (선택, 참고용)
8) 검증: make schema → make ready (둘 다 PASS여야 개발 진입)
```

## 7. 작성 체크리스트 (G-READY 통과 조건)

```text
[ ] plan.md status: ready
[ ] dag_index.md status: ready + 목차 표 row≥1 (상태 O)
[ ] 각 task_index.md status: ready + task 표(task_spec/unit 문서 열) row≥1
[ ] 각 task_spec status: ready + 필수 6섹션 표 row≥1
[ ] 각 unit_test 판정 표 row≥1
[ ] 각 qa 판정 표 row≥1
[ ] 선언 task ↔ task_spec ↔ unit_test 매핑 완성(orphan 0)
[ ] DAG마다 qa 문서 존재
[ ] storyboard 없어도 PASS (PPT 는 검증 제외)
```

## 8. 검증 명령

```bash
make schema      # 문서 3영역/필수키/표 스키마
make ready       # G-READY (매핑/상세도)
make skeletons   # 기준 문서 → 개발 result skeleton
make canonical   # 정본 테스트(로컬=CI)
```
