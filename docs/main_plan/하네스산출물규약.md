# claude_projects/guide — 11 프로젝트 공통 베이스 표준

> ## 이 문서는 (framework_structure.md 와의 관계)
>
> 이 문서(`STANDARD_LAYOUT.md`)는 **하네스 규약**입니다 — 하네스(AI 파이프라인)로 개발할 때 산출물·DAG·검증이 어디에 쌓이는지(`0dev_haness_agents/`), main 3영역, new-* 16개, RUN 흐름을 정의합니다.
>
> **framework 와 standard 는 "둘 중 하나 고르기"가 아니라 "기반 + 얹기" 관계입니다.**
>
> | 개발 방식 | 적용 문서 |
> |---|---|
> | **하네스 X** (그냥 코딩) | `framework_structure.md` **만** (소스 구조) |
> | **하네스 O** (AI 파이프라인) | `claude_projects/guide/project/docs/framework_structure.md` **+** `STANDARD_LAYOUT.md` (소스 구조 **위에** 하네스 규약 얹기) |
>
> - `framework_structure.md`(소스 구조)는 하네스를 쓰든 안 쓰든 **항상 깔리는 기반**입니다. 앱 코드는 어차피 `apps/ backend/ modules/` 에 살아야 하니까요.
> - 이 문서는 거기에 **하네스 작업 폴더(`0dev_haness_agents/`)를 얹는 추가 규약**입니다. 그래서 아래 "표준 트리"에 `apps/ backend/` 같은 소스 폴더도 같이 그려져 있습니다.
> - standard 를 쓴다 = framework 를 **버리는 게 아니라 포함**합니다.
> - **예약(reservation) 등 하네스 프로젝트 = framework + standard 둘 다 적용** (소스는 framework, 하네스 산출물은 standard).

## 핵심 원칙

1. **모든 에이전트 산출물 + main 작업 폴더는 `{project}/0dev_haness_agents/` 안에 저장** (.gitignore 됨)
   - 옛 위치 `{project}/ai/0dev_haness_agents/`, `{project}/developer/new-*/`, `{project}/docs/developer/{last_report,user_plan}/` 모두 폐기 (이동 완료)
   - new-* 시리즈 16개 sub-agent 폴더 + main 의 3 영역 (`user_plan/`, `main_plan/`, `last_report/`) + `공통양식/` + `task_검증_스크립트/`
2. **전역(~/.claude)에는 프로젝트 특정 정보 저장 금지** — 글로벌 SKILL / hook / agents / settings 만
3. **에이전트 간 소통 방식** = 본 폴더의 산출물(handback / machine_summary / spec_match / scenario_overlay / kickoff / review) read/write
4. **신규 프로젝트 초기화 시** = guide/project 트리를 그대로 복제 + RUN_ID 발급 후 0dev_haness_agents/* 안에 산출물 누적

## 표준 트리

```
{project}/
├── 0dev_haness_agents/            ← ★ git push 제외 (.gitignore — sub-agent + main 작업 폴더 통합)
│   ├── <new-*>/                   ← 16개 sub-agent 산출물 (handback / machine_summary / spec_match 등)
│   ├── 공통양식/                   ← 전 에이전트 공유 양식 (0_task_agents_결과보고 / 1_결과보고_거짓체크검증 / 2_task_결과보고검증요약 / qa_연계결과보고 / 오류보고 _template)
│   ├── task_검증_스크립트/         ← 검증 게이트(validate_*) + 진입점 task_결과진위판정.py + comm_run_harness.sh
│   ├── main_plan/                 ← (main 단독, 2026-05-21 신설, 2026-05-26 dag 표준 갱신) main 이 user_plan 읽고 작성한 정식 S0 산출물
│   │   ├── user_plan/             ← (main 단독, 2026-05-23 main_plan 통합) 사장님 원본 요구 입력 spec
│   │   ├── plan.md                ← 상세기획서
│   │   ├── dag/                   ← ★ 2026-05-26 신설 (Airflow 정합 도메인 DAG, shop 제외 모든 프로젝트)
│   │   │   └── d<N>_<도메인>/     ←   도메인 1개 = DAG 1개 (예: d1_login)
│   │   │       ├── task_index.md  ←     DAG 정의 + task 의존성 + S-XX 매핑
│   │   │       └── t<N>_*.md      ←     task 본문 (예: t001_간편로그인.md)
│   │   ├── task/                  ← legacy (freeze, 보존 의무) — 기존 task_NNN_*.md 그대로
│   │   ├── storyboard/            ← story_NNN_*.md
│   │   ├── unit_test/             ← unit_NNN_*.md
│   │   └── qa/                    ← qa_NNN_*.md
│   └── last_report/               ← (main 단독) new 사이클 완료 후 1개 종합 보고서만 남김
├── apps/                          ← admin / mobile / web
├── backend/                       ← platform / services
├── docs/                          ← 영구 보관 문서 (외부 공개·온보딩용, git push)
├── infra/docker/
├── modules/{identity,main-domain,notification}/
├── packages/{logger,types,ui}/
└── worklog/                       ← /save 스킬 체크포인트 (YYYY-MM-DD_checkpoint.md)
```

## main 의 3 작업 영역 (글로벌 룰 §main 쓰기 범위 정합)

| 영역 | 역할 | 입력 / 출력 |
|---|---|---|
| `user_plan/` | 사장님 원본 요구 입력 | 사장님 발화·아이디어·변경 요구 (입력) |
| `main_plan/` | S0 정식 산출물 (기획서·상세기획서·스토리보드) | user_plan 읽고 사장님과 대화하며 작성 (출력) |
| `last_report/` | 종합 보고서 | new 사이클 완료 후 **1개 문서만** 남김 |

## 에이전트 시리즈

- **new-* (16개)**: 하네스 자동 실행 사이클의 RUN-time 에이전트 (RUN_ID 발급 후 산출물 작성)
  - new-all, new-pm, new-pl, new-bo, new-mobile, new-fe, new-qa, new-verifier, new-judge, new-compound, new-design, new-uiux, new-p1, new-p2, new-p3, new-plan-judge

## RUN 단위 산출물 흐름

1. 사장님 원본 요구 → main 이 받아 `{project}/0dev_haness_agents/main_plan/user_plan/` 에 입력 spec 작성
2. main 이 user_plan 읽고 사장님과 대화하며 S0 산출물 작성 → `{project}/0dev_haness_agents/main_plan/`
   - `plan.md` (상세기획서)
   - `dag/d<N>_<도메인>/task_index.md` + `dag/d<N>_<도메인>/t<N>_*.md` (★ 2026-05-26 dag 표준)
   - `storyboard/`, `unit_test/`, `qa/`
3. 사장님 명시 명령 "/new-all" 또는 "new …" 자연어 → RUN_ID 발급
4. main 이 new-pm dispatch → `{project}/0dev_haness_agents/new-pm/` 에 kickoff / scenario_overlay / spec_match 작성 (입력 spec 위치 = `main_plan/`, dag 구조 인식)
5. chain: new-pl → new-design/uiux → new-fe/bo/mobile → new-qa → new-verifier → new-judge → new-compound (각 에이전트는 본인 폴더 작성)
6. 매 new 사이클 완료 후 main 이 `{project}/0dev_haness_agents/last_report/` 최종 결과 보고서 작성

## 도메인 DAG 룰 (2026-05-26 신설)

글로벌 룰 `~/.claude/CLAUDE.md §도메인 DAG 룰` (DAG.1 ~ DAG.6) 정합.

- **위치**: `{project}/0dev_haness_agents/main_plan/dag/`
- **도메인 = DAG**: `d<숫자>_<도메인명>/` (예: `d1_login`, `d2_결제`)
- **task = DAG 노드**: `t<숫자>_<task한글명>.md` (예: `t001_간편로그인.md`)
- **인덱스**: 도메인 안 `task_index.md` (의존성 + S-XX spec 매핑)
- **적용 범위**: shop 제외 모든 프로젝트 (guide/project 포함)
- **freeze 룰**: 기존 `task/task_NNN_*.md` 보존, 신규는 `dag/` 적용

## 변경 시 동기화 룰 (사장님 핵심 원칙)

- **사장님 변경 요구 1건 = 1 task 사이클 즉시 진행** (누적 X)
- main 이 매 task 진입 전 S0 의 해당 영역만 diff 갱신 (full overwrite X)
- S0 = "현재 진본" 1개 유지, 변경 history 는 RUN_ID 별 산출물에 자연 누적
