# 벤듀어 상태머신 메두사 v2 이식 설계서

작성일: 2026-05-26
대상 메두사 버전: 2.15.3
이식 대상 도메인: Order / Payment / Refund / Fulfillment
설계 단계: Phase 1 (설계만, 구현 없음)

---

## 1. 요약

- 벤듀어는 `FSM<T>` (제네릭 유한상태머신) 기반으로 Order / Payment / Fulfillment / Refund 4 도메인의 라이프사이클을 명시적 전이 그래프로 강제합니다. 모든 상태 전이는 `transitions` 매핑 + `onTransitionStart` 가드 + `onTransitionEnd` 후처리로 검증되어 잘못된 전이 (예: `Cancelled` → `Shipped`) 자체가 컴파일 단계와 런타임에서 차단됩니다 (벤듀어_state-machine_fsm.mdx §11-19, 벤듀어_state-machine_transitions.mdx §13-26).
- 메두사 v2 는 `OrderStatus` / `PaymentSessionStatus` / `ReturnStatus` enum 만 노출하며, 상태 전이의 합법성은 workflow step 안 분기 코드에 흩어져 있어 정합성 게이트가 약합니다 (`@medusajs/utils/dist/order/status.d.ts`, `payment/payment-session.d.ts`). 한국 PG (KCP / 토스 / 카카오페이 / 이니시스 / 나이스) 의 `verify` 단계, 전자상거래법 청약철회, 만 14세 미만 동의 등 한국 특화 state 가 표준에 없습니다.
- 본 설계는 메두사 workflow 패러다임을 보존하면서 벤듀어형 FSM 을 **별도 module 로 이식 (Option B)** 하는 방안을 권장합니다. 메두사 core entity 의 status 컬럼은 그대로 두고, 추가 `state-machine` module 이 각 도메인의 확장 state + 전이 규칙을 관리하며, workflow step 안에서 가드 함수 (`assertCanTransition`) 로 호출됩니다.
- 한국 비즈니스 특화 state 11종 (PG_VERIFICATION_PENDING / PG_VERIFIED / WITHDRAWAL_REQUESTED 외) 을 본 module 의 config 로 정의해 RMA / 환불 / 청약철회 정책을 결정론적으로 검증합니다.
- Phase 3 구현 task 는 P1 (코어 FSM + 4 도메인 default process) / P2 (한국 state 추가 + workflow 연동) / P3 (admin UI + 관측성) 로 분리하며 총 예상 소요 35-45 시간으로 산정합니다.

## 2. 벤듀어 상태머신 4 Process 분석

### 2.1 코어 FSM 구조

벤듀어 `FSM<T extends string, Data>` 은 다음 5개 메서드만 노출합니다 (벤듀어_state-machine_fsm.mdx §10-20).

```ts
class FSM<T extends string, Data = any> {
  constructor(config: StateMachineConfig<T, Data>, initialState: T)
  initialState: T
  currentState: T
  transitionTo(state: T, data: Data): Promise<{ finalize: () => Promise<any> }>
  jumpTo(state: T): void
  getNextStates(): readonly T[]
  canTransitionTo(state: T): boolean
}
```

`StateMachineConfig<T, Data>` 는 `transitions` (전이 그래프) + 3 hook (`onTransitionStart` / `onTransitionEnd` / `onError`) 로 구성됩니다 (벤듀어_state-machine_state-machine-config.mdx §11-17). `onTransitionStart` 가 `false` 또는 `string` 을 반환하면 전이가 차단되며, `string` 은 에러 메시지로 `onError` 에 전달됩니다 (§32-34, §55-67).

`Transitions<State>` 는 `{ [S in State]: { to: Readonly<Target[]>; mergeStrategy?: 'merge' | 'replace' } }` 구조의 단순 매핑입니다. `mergeStrategy` 가 있어 default process 위에 custom process 를 추가 등록할 때 충돌 처리 정책을 지정할 수 있습니다 (벤듀어_state-machine_transitions.mdx §31-37).

### 2.2 Order Process

`OrderState` = `'Created' | 'Draft' | 'AddingItems' | 'Cancelled' | keyof CustomOrderStates | keyof OrderStates` (벤듀어_orders_order-process.mdx §222-228). default process 가 9개 state 를 추가합니다 (§211-219).

| 카테고리 | State |
|---|---|
| 베이스 | `Created`, `Draft`, `AddingItems`, `Cancelled` |
| 결제 단계 | `ArrangingPayment`, `PaymentAuthorized`, `PaymentSettled` |
| 배송 단계 | `PartiallyShipped`, `Shipped`, `PartiallyDelivered`, `Delivered` |
| 수정 단계 | `Modifying`, `ArrangingAdditionalPayment` |

가드는 `DefaultOrderProcessOptions` 의 10개 boolean 플래그로 토글 가능하며 (§69-81), 예를 들어 `arrangingPaymentRequiresStock: true` 는 재고 부족 시 `ArrangingPayment` 진입을 차단합니다 (§121-126). `checkFulfillmentStates: true` 는 `Shipped` 진입 시 모든 Fulfillment 가 `Shipped` 상태인지 검증합니다 (§139-145).

`OrderTransitionData = { ctx: RequestContext; order: Order }` 가 모든 hook 에 주입됩니다 (§236-240).

### 2.3 Payment Process

`PaymentProcess<State>` 인터페이스 (벤듀어_payment_payment-process.mdx §21-28) 는 OrderProcess 와 동일 구조이며, `DefaultPaymentProcess` 가 기본 PaymentState 4종 (`Created` / `Authorized` / `Settled` / `Declined` / `Cancelled` / `Error` — 추가 PaymentState 문서 참조) 의 표준 전이를 제공합니다 (벤듀어_payment_default-payment-process.mdx §1-9).

한국 PG 통합 시 가장 중요한 포인트는 **결제 인증 단계 (vbank deposit / 카카오/네이버 redirect / 토스 secret_key verify) 가 표준 PaymentState 에 없다**는 점입니다. 이는 custom state (`PG_VERIFICATION_PENDING` / `PG_VERIFIED`) 로 추가해야 합니다 (본 문서 §6 참조).

### 2.4 Refund Process

`RefundState = 'Pending' | 'Settled' | 'Failed' | keyof CustomRefundStates | keyof RefundStates` (벤듀어_payment_refund-state.mdx §10).

`RefundProcess<State>` 는 `RefundTransitionData = { ctx; order; refund }` 를 hook 에 전달합니다 (벤듀어_payment_refund-transition-data.mdx §10-15). `Refund` 엔티티는 `state: RefundState` + `items` / `shipping` / `adjustment` / `total` (Money) + `method` + `transactionId` + `metadata: PaymentMetadata` + `paymentId` (FK to Payment) 를 가지며 (벤듀어_entities_refund.mdx §10-32), 결제 1건에 N개 환불이 종속됩니다.

한국 청약철회법은 단순 `Settled` 가 아니라 **요청 → 승인 → 환불 → 완료** 의 4단계 추적이 필요해 custom state 추가가 필수입니다.

### 2.5 Fulfillment Process

`FulfillmentState = 'Created' | 'Pending' | 'Cancelled' | keyof CustomFulfillmentStates | keyof FulfillmentStates` 가 베이스이며, `defaultFulfillmentProcess` 가 `Shipped` / `Delivered` 를 추가합니다 (벤듀어_fulfillment_fulfillment-state.mdx §10-15, 벤듀어_fulfillment_fulfillment-process.mdx §5-17).

`Fulfillment` 엔티티는 `state: FulfillmentState` + `trackingCode` + `method` + `handlerCode` (FulfillmentHandler code) + `lines: FulfillmentLine[]` + `orders: Order[]` (M:N) 구조입니다 (벤듀어_entities_fulfillment.mdx §10-26).

`FulfillmentHandler` 는 외부 배송사 API (예: 우체국 / CJ대한통운 / 한진) 호출을 캡슐화하며, `createFulfillment` (생성 시 tracking code 발급) + `onFulfillmentTransition` (전이 시 외부 API 동기화) 두 hook 을 제공합니다 (벤듀어_fulfillment_fulfillment-handler.mdx §29-80, §103-108).

`FulfillmentService.transitionToState(ctx, fulfillmentId, state)` 가 전이 진입점이며, 성공 시 `FulfillmentStateTransitionEvent` 가 publish 됩니다 (벤듀어_services_fulfillment-service.mdx §15-23, §47-51).

## 3. 메두사 v2 현 상태 분석

### 3.1 Order 상태

`@medusajs/utils` 의 `OrderStatus` enum (`order/status.d.ts`) 은 6개 값만 가집니다.

| State | 의미 |
|---|---|
| `pending` | 신규 생성 |
| `completed` | 완료 |
| `draft` | 임시 |
| `archived` | 보관 |
| `canceled` | 취소 |
| `requires_action` | 추가 액션 필요 |

벤듀어의 `PaymentAuthorized` / `PartiallyShipped` / `Modifying` / `ArrangingPayment` 같은 **중간 단계가 없습니다**. Order 의 결제/배송 진행 상황은 별도 transaction (OrderTransaction) + fulfillment 의 status 를 join 해서 추론합니다.

### 3.2 Payment / Transaction 흐름

메두사는 **PaymentCollection → PaymentSession → Payment → Capture/Refund (Transaction)** 의 4 entity 모델을 사용합니다. `PaymentSessionStatus` 는 6개 값 (`@medusajs/utils/dist/payment/payment-session.d.ts`).

| State | 의미 |
|---|---|
| `authorized` | 결제 인증됨 |
| `captured` | 캡처 완료 |
| `pending` | 진행 중 |
| `requires_more` | 추가 액션 필요 |
| `error` | 에러 |
| `canceled` | 취소 |

전이 그래프가 명시적으로 코드화되어 있지 않고, 각 workflow step (`authorizePaymentSessionWorkflow` / `capturePaymentWorkflow` / `refundPaymentWorkflow` 등) 안 분기로 처리됩니다. 즉 **FSM 형식이 노출되지 않으며 외부에서 custom state 추가가 어렵습니다**.

전자상거래 확장에서 가장 자주 필요한 "PG 인증 대기" (예: 가상계좌 입금 대기, 카카오페이 redirect 대기) state 는 `pending` 단일 값으로 뭉뚱그려져 있어, 한국 PG 통합 시 별도 metadata field 로 구분하거나 별도 state 를 도입해야 합니다.

### 3.3 Fulfillment 흐름

메두사 Fulfillment 는 `created_at` / `shipped_at` / `delivered_at` / `canceled_at` 타임스탬프 컬럼으로 lifecycle 을 추적합니다 (`@medusajs/fulfillment` package). 명시적 `status` enum 컬럼이 없고, "현재 상태" 는 어느 타임스탬프가 채워졌느냐로 추론합니다. 이는 벤듀어의 `state` 컬럼 + FSM 가드 모델과 정반대 접근입니다.

### 3.4 Return / Refund 흐름

`ReturnStatus` enum (`order/status.d.ts`) = `open` / `requested` / `received` / `partially_received` / `canceled`. 환불 자체의 state 가 아니라 반품 신청의 state 이며, 환불 처리는 OrderTransaction 의 음수 amount 로 표현됩니다 (메두사_order_transactions_page.mdx §35-77).

### 3.5 메두사가 상태머신을 노출하지 않는 점 + 한계

| 한계 | 영향 |
|---|---|
| 전이 그래프가 코드 분기로만 존재 | 잘못된 전이 (예: `canceled` → `completed`) 가 런타임에 가능하며 정합성 게이트 부재 |
| custom state 추가 불가 | 한국 PG verify, 청약철회 등 비즈니스 상태를 enum 에 추가하려면 메두사 fork 필요 |
| hook 일관성 부재 | `onTransitionStart` / `onTransitionEnd` 같은 도메인-횡단 hook 표준이 없음. event bus 로 우회 가능하나 동기 가드 불가 |
| 가시성 부족 | "이 order 의 다음 가능한 state 는?" 같은 질의를 표준 API 로 답할 수 없음 |

## 4. 이식 전략 — Option 비교

### Option A — 메두사 workflow 안 inline 상태 검증

각 workflow step 에 `validateOrderStatus(order, expectedFrom, intendedTo)` 류 가드 함수를 직접 박는 방식입니다.

- 장점: 새 module 도입 없음. 구현 가장 빠름 (8-12 시간).
- 단점: 전이 규칙이 workflow 마다 흩어져 정합성이 약함. 한국 특화 state 추가 시 모든 workflow 를 수정해야 함. 가드 누락 회귀 위험 높음.
- 적합도: 단기 임시 방편으로만 적합.

### Option B — 별도 state-machine module + 메두사 module link (**권장**)

벤듀어 `FSM<T>` 와 동등한 제네릭 FSM 을 메두사 module 로 구현하고, Order / Payment / Refund / Fulfillment 4 process 의 default 전이를 본 module 의 config 로 선언합니다. 메두사 core entity 의 status 컬럼은 그대로 두되, 본 module 의 `StateHistory` 테이블이 모든 전이를 audit log 로 기록합니다.

- 장점: 전이 규칙 단일 출처 (single source of truth). 한국 특화 state 를 config 수정만으로 추가 가능. 메두사 update 시 충돌 영역이 본 module 로 격리됨. workflow / subscriber 양쪽에서 호출 가능.
- 단점: 신규 module + DB 테이블 추가. 구현 비용 25-35 시간. core status 와 module state 의 sync 정합성 관리 필요.
- 적합도: **중장기 운영 + 한국 PG / 청약철회 / 만 14세 미만 등 정책 state 다수 필요 시 최적**.

### Option C — 벤듀어 라이브러리 module port

벤듀어 `packages/core/src/common/finite-state-machine` 를 직접 메두사 monorepo 에 포팅하는 방식.

- 장점: 검증된 코드 재사용.
- 단점: 라이선스 검토 필수 (MIT, 가능). 벤듀어 `RequestContext` / `EventBus` / `TransactionalConnection` 등 호환 layer 가 필요해 사실상 self-implement 와 비용이 비슷하거나 더 큼. 벤듀어 upstream patch 추적 부담.
- 적합도: 비권장.

### 권장안 + 사유

**Option B 를 권장**합니다. 근거:

1. 한국 비즈니스 요구 (PG 인증 / 청약철회 / 만 14세 미만 동의) 가 §6 에 나열된 대로 11개 이상 custom state 를 요구하며, 이는 Option A 의 inline 가드로는 유지보수가 불가합니다.
2. 메두사 v2.15.3 의 workflow 패러다임 (compensation function + step retry) 과 FSM 가드는 충돌하지 않고 보완적입니다. workflow 가 "어떤 작업을 어떤 순서로" 를 담당하면, FSM 이 "그 작업 결과 state 가 합법인가" 를 담당합니다.
3. Option C 는 라이선스/호환 오버헤드가 self-implement (200-400 LoC FSM 코어) 대비 이득이 없습니다.
4. Phase 3 에서 RMA / payment-kr 모듈과 통합할 때, FSM module 이 단일 진입점이 되어 정합성 검증이 한 곳에 모입니다.

### 5.3 Service API

```ts
// 의사 코드, Phase 3 에서 정확한 시그니처 확정
class StateMachineModuleService {
  // 전이 가능한 next state 목록
  getNextStates<E extends EntityType>(entityType: E, currentState: StateOf<E>): readonly StateOf<E>[]

  // 전이 가능 여부 boolean
  canTransition<E extends EntityType>(entityType: E, from: StateOf<E>, to: StateOf<E>): boolean

  // 실제 전이 (DB write + history 기록 + event publish)
  transition<E extends EntityType>(input: {
    entityType: E
    entityId: string
    toState: StateOf<E>
    actor: { type: string; id?: string }
    data?: Record<string, unknown>
    reason?: string
  }): Promise<{ fromState: StateOf<E>; toState: StateOf<E>; finalize: () => Promise<void> }>

  // 전이 검증만 (실 write 없음, workflow step 안 가드용)
  validateTransition<E extends EntityType>(entityType: E, currentState: StateOf<E>, toState: StateOf<E>, data?: Record<string, unknown>): Promise<true | { error: string }>

  // history 조회
  getHistory(entityType: EntityType, entityId: string): Promise<StateHistory[]>
}
```

`finalize` 패턴은 벤듀어 `transitionTo` 의 `{ finalize }` 반환 (벤듀어_state-machine_fsm.mdx §15) 을 그대로 답습합니다. transaction 안에서 전이를 미리 검증하고, commit 직전 `finalize()` 로 후처리 (event publish 등) 를 트리거합니다.

### 5.4 Workflow integration

기존 메두사 workflow 에 step 단위로 본 module 의 service 를 주입합니다. 예시 (의사코드):

```ts
// src/workflows/order/place-order-with-state-machine.ts
export const placeOrderWithStateMachineWorkflow = createWorkflow(
  "place-order-with-state-machine",
  (input: { cartId: string }) => {
    // 1. 기존 메두사 cart → order 변환
    const order = createOrderFromCartStep(input)

    // 2. FSM 전이 가드
    const validation = validateTransitionStep({
      entityType: "order",
      currentState: "pending",
      toState: "arranging_payment",
    })
    // validation.error 가 있으면 compensation 발동

    // 3. PaymentSession 생성 + FSM 전이
    transitionStateStep({
      entityType: "order",
      entityId: order.id,
      toState: "arranging_payment",
      actor: { type: "customer", id: input.customerId },
    })

    return new WorkflowResponse({ order })
  }
)
```

이 패턴은 메두사 workflow 의 compensation function (메두사_*_workflows_compensation-function_page.mdx) 와 호환됩니다 — `transitionStateStep` 의 compensation 은 `transition(reverseDirection)` 으로 정의합니다.

### 5.5 Subscriber integration

메두사 event bus (`order.placed` / `payment.captured` / `fulfillment.shipped` 등) 에 subscribe 하여 자동 전이를 수행합니다.

```ts
// src/subscribers/state-machine-sync.ts
export default async function stateMachineSyncSubscriber({ event, container }) {
  const fsm = container.resolve("stateMachineModuleService")
  switch (event.name) {
    case "payment.captured":
      await fsm.transition({
        entityType: "order",
        entityId: event.data.orderId,
        toState: "payment_settled",
        actor: { type: "system" },
      })
      break
    case "fulfillment.shipped":
      await fsm.transition({
        entityType: "order",
        entityId: event.data.orderId,
        toState: "shipped",
        actor: { type: "system" },
      })
      break
    // ...
  }
}
```

### 5.6 메두사 core status 와 module state 의 sync 정합성

메두사 `OrderStatus` (6개) 와 본 module 의 확장 `OrderState` (예: 16개) 는 1:N 관계로 매핑합니다.

| 본 module state | 메두사 core status |
|---|---|
| `created`, `draft`, `adding_items`, `arranging_payment`, `payment_authorized`, `pg_verification_pending` | `pending` |
| `payment_settled`, `partially_shipped`, `shipped`, `partially_delivered`, `delivered` | `pending` (모듈 state 가 진행 단계 추적, core 는 "결제완료 후~배송완료 전" 을 `pending` 유지) |
| `withdrawal_requested`, `withdrawal_approved`, `withdrawal_refunded` | `pending` 또는 `requires_action` |
| `completed` | `completed` |
| `cancelled` | `canceled` |
| `archived` | `archived` |

본 module 의 `transition` 호출 시 매핑 테이블을 통해 core status 도 함께 update 합니다 (한 트랜잭션 내).

## 6. 한국 비즈니스 특화 State 추가

### 6.1 Payment — 한국 PG verify state

KCP / 토스 / 카카오페이 / 이니시스 / 나이스의 공통점 = **redirect 또는 vbank 입금 대기 단계** 가 표준 PaymentSessionStatus.PENDING 에 뭉뚱그려져 있어, 운영자가 "지금 이 주문은 가상계좌 입금 대기인가, 카드 인증 대기인가, 카카오톡 승인 대기인가" 를 구분하기 어렵습니다.

| 추가 State | 진입 조건 | 다음 가능 state |
|---|---|---|
| `pg_verification_pending` | PG 결제창에서 redirect URL 발급 + 사용자가 떠난 직후 | `pg_verified`, `pg_failed`, `cancelled` |
| `pg_verified` | PG 콜백 webhook 수신 + 서명 검증 통과 | `payment_authorized`, `pg_failed` |
| `pg_failed` | 서명 불일치 / 사용자 인증 실패 | (terminal) |
| `vbank_pending_deposit` | 가상계좌 발급 완료, 입금 대기 | `payment_settled`, `vbank_expired`, `cancelled` |
| `vbank_expired` | 입금 기한 (보통 7일) 초과 | (terminal) |

전이 hook 의 `onTransitionStart` 에서 PG 서명 재검증 (`KCP.verifyTraceNo()`, `Toss.verifyByPaymentKey()` 등) 을 수행해 한 번 더 정합성을 보장합니다.

### 6.2 Refund — 청약철회 state

전자상거래 등에서의 소비자보호에 관한 법률 §17 (청약철회) 흐름을 명시적으로 추적합니다.

| 추가 State | 진입 조건 | 다음 가능 state |
|---|---|---|
| `withdrawal_requested` | 고객 청약철회 신청 (storefront API) | `withdrawal_approved`, `withdrawal_rejected` |
| `withdrawal_approved` | 관리자 승인 (자동 또는 수동) | `withdrawal_refunded`, `withdrawal_rejected` |
| `withdrawal_rejected` | 청약철회 거부 (단순변심 후 7일 초과 등) | (terminal) |
| `withdrawal_refunded` | PG 환불 API 호출 성공 + transaction id 수신 | (terminal) |

`onTransitionEnd` 에서 알림 (이메일/SMS) 발송 + RMA module 로 이벤트 publish.

### 6.3 Order — 만 14세 미만 동의

「개인정보 보호법」§22 ② 에 따라 만 14세 미만 회원의 주문은 법정대리인 동의 단계가 필요합니다.

| 추가 State | 진입 조건 | 다음 가능 state |
|---|---|---|
| `age_verification_pending` | 만 14세 미만 사용자가 결제 진입 | `age_verified`, `cancelled` |
| `age_verified` | 법정대리인 동의 완료 (이메일 회신 또는 본인인증) | `arranging_payment` |

본 가드는 `onTransitionStart('arranging_payment')` 에서 검사. 만 14세 미만이면서 `age_verified` 가 아니면 전이 차단.

### 6.4 Fulfillment — 한국 택배사 추적 state (확장)

벤듀어 default = `Created` → `Pending` → `Shipped` → `Delivered` 외에, 한국 택배사 추적 API 의 세분화 단계를 옵션 state 로 추가합니다.

| 추가 State | 진입 조건 |
|---|---|
| `picked_up` | 택배 기사 픽업 완료 |
| `at_hub` | 허브 도착 |
| `out_for_delivery` | 배송 출고 |
| `delivery_failed` | 부재 / 수취 거부 |
| `re_delivery_scheduled` | 재배송 예약 |

이는 운영자 대시보드의 가시성을 위한 옵션이며, default process 에는 포함되지 않습니다 (한국 택배사 통합 task 에서만 활성화).

## 8. 위험 + 대안

### 8.1 메두사 workflow 와 상태머신 동시 사용 시 정합 충돌

- **위험**: workflow 의 compensation function 이 실행될 때 FSM 전이의 finalize 가 이미 commit 되어 rollback 못 함.
- **대안**: FSM `transition` 의 finalize 패턴을 workflow step 의 transaction commit 시점과 정렬. workflow step 의 compensation 에 FSM 의 reverse transition 을 등록. compensation 호출 시 FSM 의 jumpTo (가드 무시 강제 복원) 를 사용하되 history 에 `actor.type = 'compensation'` 명시.

### 8.2 메두사 update 시 호환성

- **위험**: 메두사 v2.16+ 에서 OrderStatus enum 추가 / PaymentSessionStatus 변경 시 매핑 테이블 깨짐.
- **대안**: 매핑 테이블을 본 module config 로 외부화. 메두사 minor version 업그레이드 시 매핑 테이블 회귀 테스트 1회. semver patch (2.15.x) 는 영향 없을 것으로 평가.

### 8.3 다른 module 의존성

- **rma-extension**: 청약철회 4 state 가 RMA workflow 와 결합되므로 state-machine module 이 RMA 의 link 를 정의해 양방향 sync.
- **payment-kr**: 한국 PG handler 가 본 module 의 PaymentProcess hook 을 호출. payment-kr 의 webhook 처리 → FSM transition 호출 패턴.
- **권장**: state-machine module 을 가장 먼저 구현 + 안정화 (P1), 그 후 RMA / payment-kr 가 본 module 에 종속하도록 설계.

### 8.4 동시 전이 race condition

- **위험**: 결제 webhook 과 관리자 수동 cancel 이 동시 발생.
- **대안**: `state_history` insert 시 unique constraint `(entity_type, entity_id, from_state, to_state, transitioned_at)` + DB row lock (`SELECT ... FOR UPDATE`) on current state read. P1 단계 통합 테스트로 검증.
