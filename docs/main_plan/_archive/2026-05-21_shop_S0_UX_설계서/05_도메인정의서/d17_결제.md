## 1. 도메인 개요·책임 범위

- **1줄 책임**: 결제 승인 · 환불 · 정산 · 이상 거래 탐지 · 카드 차단.
- **포지션**: order와 **강결합** (모든 결제는 주문 연동, payment ↔ order 트랜잭션 짝). PG 외부 연동의 유일 창구.
- **PG 정책**: **토스페이먼츠 MCP 모듈 단일** PG, **카드 결제만**. 무통장입금 · 가상계좌 · 에스크로 · 간편결제 · 정기결제 · 해외결제 전면 Out-of-scope (`00_개요.md §2 #1/#2`).
- **회원 전용 정책**: 비회원 주문 불가 → **결제도 회원 한정** (`00_개요.md §2 #8`).
- **환불 단일 경로**: 카드 결제 단일이므로 환불 = **카드사 취소 전표 발행** 단일 경로 (PG API 호출 → 카드사 취소).
- **책임 경계 (out)**: 주문 상태 전이·재고 차감/복구·쿠폰/포인트 차감/복원 실행은 각 도메인 (본 도메인은 이벤트 발행 + 트랜잭션 트리거만). 배송지·운송장은 d18 delivery.

### 2.3 refunds (환불 본체)

| 필드 | 타입 | 제약 |
|---|---|---|
| id | UUID | PK |
| payment_id | UUID | FK → payments.id NOT NULL |
| type | ENUM | NOT NULL (full / partial) |
| amount | DECIMAL(12,0) | NOT NULL CHECK > 0 |
| status | ENUM | NOT NULL DEFAULT 'requested' (requested / approved / processing / completed / failed) |
| requested_by | VARCHAR(20) | NOT NULL (member / admin / system) |
| requested_by_id | UUID | NULL (member_id or admin_id, system은 NULL) |
| reason | TEXT | NOT NULL |
| pg_refund_id | VARCHAR(64) | NULL (PG 환불 거래 ID) |
| pg_refund_receipt_url | TEXT | NULL (카드 취소 전표 URL, PAY-U-033) |
| idempotency_key | VARCHAR(64) | UNIQUE NOT NULL (PG 멱등키, PAY-A-029) |
| idempotency_sub_key | VARCHAR(64) | UNIQUE NULL (Tier1 §3.I — N회 부분 환불 단위 멱등 `{order_id}:{action_type}:{nonce}`, action_type ∈ full_cancel / partial_cancel / return / exchange_refund / admin_refund) |
| requested_at | TIMESTAMPTZ | NOT NULL |
| completed_at | TIMESTAMPTZ | NULL |
| retry_count | INTEGER | NOT NULL DEFAULT 0 |
| error_message | TEXT | NULL |
| version | INTEGER | NOT NULL DEFAULT 0 | 낙관락 |

**인덱스**: `idx_payment_id`, `idx_status`, `idx_requested_at`, `idx_status_requested_at`, `idx_idempotency_sub_key`.

**제약 (DB CHECK)**: `SUM(refunds.amount WHERE payment_id=X AND status IN ('completed','processing')) <= payments.amount` — 초과 환불 방지 (PAY-A-032, B-PAY-012).

**제약 (Tier1 §3.K — N회 부분 환불 누적 무결성)**:
```sql
ALTER TABLE refunds ADD CONSTRAINT idx_idempotency_sub_key UNIQUE (idempotency_sub_key);
ALTER TABLE refunds ADD CONSTRAINT chk_amount_positive CHECK (amount > 0);

-- 누적 환불 검증 트리거 (안전망 — race 차단)
CREATE TRIGGER trg_refund_total_check BEFORE INSERT ON refunds
FOR EACH ROW EXECUTE FUNCTION validate_refund_total_le_payment();
-- validate_refund_total_le_payment: SUM(refunds.amount WHERE payment_id=NEW.payment_id AND status IN ('completed','processing')) + NEW.amount <= payments.amount
```

### 6.5 N회 부분 환불 누적 무결성 (Tier1 §3.K — F-PAY-10·F-PAY-11·F-PAY-12 강화)

> 기존 F-PAY-11 (환불 금액 ≤ 원결제 금액 DB CHECK) + F-PAY-12 (이중 환불 방지 = PG 멱등키 + DB 낙관락) 룰에 N회 부분 환불 race 차단 메커니즘 추가.

**문제 (race 시나리오)**: 부분환불 1 (5,000원) + 부분환불 2 (4,500원) 동시 도달 → 각자 잔여 환불 가능 = 10,000원 검증 통과 → 양쪽 모두 처리 → 9,500원 환불 (현 룰만으로는 race 차단 X).

**해결 — 트랜잭션 격리 + sub_key 멱등 + DB 트리거 3중 안전망**:

| Layer | 메커니즘 | 효과 |
|---|---|---|
| 1. `SERIALIZABLE` 격리 + `SELECT FOR UPDATE on payments` | 다른 환불과 직렬화 | 동시 처리 차단 |
| 2. `refunds.idempotency_sub_key` UNIQUE (§2.3 신규 컬럼) | 같은 액션 재요청 = 캐시 응답 | 클라이언트 재시도 멱등 |
| 3. `trg_refund_total_check` BEFORE INSERT 트리거 (§2.3 신규 제약) | 누적 합 > 원결제 즉시 차단 | 최종 안전망 |

| # | 룰 | 적용 |
|---|---|---|
| F-PAY-11A | **부분 환불 트랜잭션 = SERIALIZABLE + `SELECT FOR UPDATE on payments` 의무** (race 직렬화) | N회 부분 환불 |
| F-PAY-11B | **각 부분 환불 = 별도 Idempotency-Sub-Key** (`{order_id}:{action_type}:{nonce}`) | 멱등 |
| F-PAY-11C | PG 호출 단위 = 부분 환불 신청 단위 1:1 매핑 (Tier1 §3.O — 합산 후 1회 호출 X) | PG 호출 정책 |
| F-PAY-11D | 다건 교환 그룹 환불 = 그룹 1회 PG 호출 (group_id 기준 합산) + refunds N row INSERT (라인별 매핑, 동일 pg_cancel_transaction_id) | 다건 교환 |
| F-PAY-11E | PG 호출 실패 → `refund_retry_queue` + 사용자 안내 ("24시간 내 환불 완료") | 실패 처리 |
| F-PAY-11F | 누적 환불 > 원결제 = 트리거 차단 + 보안 알람 (절대 발생 X) | 안전망 |

### 6.6 PG Webhook 보안 5중 검증 (Tier3 §3.6 — F-PAY-03 강화)

> 기존 F-PAY-03 (PG 콜백 서명 검증) 룰에 IP whitelist + 타임스탬프 윈도우 + dedupe + amount 검증 추가. 본 도메인 컬럼 (`payment_webhooks.signature` / `payment_webhooks.dedupe_key`) + 메타 룰 정의. 실제 검증 코드는 f14 webhook 핸들러.

| Layer | 검증 | 본 도메인 보장 메커니즘 |
|---|---|---|
| 1. HTTPS + IP whitelist (토스 IP 대역만) | 인프라 단 | (인프라 위탁) |
| 2. HMAC 서명 검증 (`Toss-Signature` 헤더) | F-PAY-03 | `payment_webhooks.signature` 저장 + signature_verified=true 조건 처리 |
| 3. 타임스탬프 윈도우 (`Toss-Request-Time` ± 5분) | replay 차단 | webhook 처리 직전 검증, 위반 시 401 |
| 4. dedupe_key UNIQUE (`pg_transaction_id + event_type`) | F-PAY-05 | `payment_webhooks.dedupe_key` UNIQUE 제약 |
| 5. payload amount 검증 (`DB payments.amount == toss payload.amount`) | AMOUNT_TAMPERED 차단 | webhook 처리 트랜잭션 내 비교 |

| # | 룰 | 적용 |
|---|---|---|
| F-WEBHOOK-01 | 5중 검증 의무 (IP·서명·타임스탬프·dedupe·amount) | PG·택배사 webhook |
| F-WEBHOOK-03 | 타임스탬프 윈도우 = ±5분 (replay 차단) | webhook |
| F-WEBHOOK-04 | webhook 응답 = 항상 200 (에러도 200, 내부 큐 적재 후 재시도) | PG 재전송 차단 |
| F-WEBHOOK-05 | 검증 실패 = 즉시 보안 알람 (Slack #security) + admin_audit_logs 박제 | 보안 |

### 6.7 트랜잭션 격리 수준 (Tier2 §3.3)

| 트랜잭션 | 격리 수준 | 사유 |
|---|---|---|
| 결제 webhook 승인 (`/api/payments/webhook/toss`) | SERIALIZABLE | 재고 차감 race + 환불 race 모두 차단 |
