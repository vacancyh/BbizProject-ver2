## 3. 컴포넌트 명세

| 컴포넌트 | 위치 | 데이터 source | 동작 / 상태 |
|---|---|---|---|
| **scope 사이드 패널** | 좌측 | static (12 scope, d21 §2.4) | MEMBER/PRODUCT/CATEGORY/CART/WISHLIST/ORDER/PAYMENT/DELIVERY/REVIEW/COUPON_POINT/ADMIN/SYSTEM. 선택 시 URL `?scope=` |
| **검색·필터** | 본문 상단 | `GET /api/admin/system/policy?scope=&q=&updated_since=` | key·설명 검색 + scope + 최근 변경 |
| **정책 리스트 테이블** | 본문 | `/api/admin/system/policy` | key·설명·현재값(요약)·기본값·마지막 변경자·일자·[상세] |
| **정책 상세 — 메타 (A)** | 상세 | `GET /api/admin/system/policy/{key}` | key·scope·설명·default_value·value_schema (JSON schema viewer) |
| **정책 상세 — 현재값 (B)** | 상세 | (위와 동일) | JSON viewer + 사람 친화 시각 폼 (스칼라는 input, 객체는 form, 배열은 list) |
| **정책 상세 — 변경 폼 (C, SUPER만)** | 상세 | `PUT /api/admin/system/policy/{key}` | 신규값 input + schema 실시간 검증 + 사유 textarea + 이중 확인 (`X-Confirm-Token`) |
| **이중 확인 영역** | 변경 폼 하단 | `X-Confirm-Token` 발급 (서버 30초 만료) | 확인 텍스트 입력 ("CONFIRM" 또는 key 재입력) → 토큰 발급 → 적용 버튼 활성 |
| **정책 상세 — 변경 이력 (D)** | 상세 | `GET /api/admin/system/policy/{key}/history` | before/after diff (JSON diff viewer) + 변경자·사유·시각 |
| **정책 상세 — 영향 메타 (E) + 자동 영향 분석 (Tier 4 §3.9)** | 상세 | `POST /api/admin/system/policy/{key}/preview` | 영향 도메인·캐시 PURGE 대상·실행 환경 (즉시 적용 / 다음 배포 / 배치 다음 실행). **Tier 4 §3.9 정책 변경 영향 분석 표시** = (1) 영향 도메인 (예: `member.signup.bonus_points` → d11 회원 + d20 쿠폰·포인트) (2) 영향 API endpoint (예: `POST /api/auth/signup`) (3) 영향 사용자 추정 (예: 신규 가입자 모두 / 진행 중 주문 영향 X — snapshot 적용) (4) 캐시 PURGE 키 (예: `policy:member:*`) (5) **롤백 절차** (system_policy_history 마지막 N 건 → "이전 값으로 되돌리기" 버튼). 이중 확인 모달에 본 영향 분석 결과를 함께 노출 (사용자 인지 보장) |
| **[점검모드 ON/OFF 액션 — Tier 4 §3.7]** | `maintenance.mode` 정책 상세 | `PUT /api/admin/system/policy/maintenance.mode` | **Tier 4 §3.7 점검모드 운영 표준 5단계** = (1) **사전 공지 1주일 전 (T4-Q04 권장 a)** — 푸터·로그인 페이지·이메일 발송 (마케팅 동의와 무관 — 거래성) (2) **점검 시작** = SUPER 권한 + scope=user 권장 (관리자 영역 정상 — 모니터링 가능). scope=both = **Tier 3 이중 확인 (텍스트 타이핑 "관리자 영역 잠금에 동의합니다")** — 관리자 잠금 위험 (3) **점검 중** = 사용자 영역 503 + 정적 점검 페이지 (`ends_at` 카운트다운) + PG webhook 큐 적재 (Q-11) (4) **점검 종료** = `{enabled: false}` + 큐 처리 (PG webhook 일괄 dispatch) + 사용자 영역 정상 복귀 + 종료 알림 발송 (5) **사후 보고** = 점검 결과 보고서 자동 생성 + SUPER 알림 |
| **[데이터 보정 SOP — Tier 4 §3.10]** | 별도 영역 (audit 불일치 발견 시 트리거) | `POST /api/admin/audit-results/{id}/correct` | **Tier 4 §3.10 데이터 보정 표준 절차** = (1) **발견** = Tier 2 §3.9 audit 배치 결과 자동 알람 (Slack #ops) + `audit_results` 테이블 표시 (2) **분류** = Class A (즉시 — 환불 audit·잔액 음수) / Class B (24h — 포인트·쿠폰 audit) / Class C (주간 — outbox·trace 누락) (3) **조사 + dry-run** = SUPER + 개발 검토 → SQL 스크립트 dry-run (영향 시뮬레이션) (4) **SUPER 승인 → 트랜잭션 실행 + 감사 박제** (5) **재발 방지 patch (§V0 원칙)** = Tier 2~3 표준 보강 + 코드 patch + 테스트 케이스 추가 (6) **사후 보고** = 사용자 통보 (영향 있는 경우) + `audit_postmortem` 박제 |
| **schema 검증** | 변경 폼 | (클라/서버 양쪽) | JSON schema 기반 + custom 룰 (예: max_use_ratio 0~100, expiry_days > 0) |
| **AuditLog 자동 박제** | 변경 시 | 미들웨어 자동 | d21 F6 (admin_id·action=`policy.change`·target_type=`policy`·target_id=key·before·after·reason·result) |
| **캐시 PURGE 트리거** | 변경 후 | 비동기 작업 | Redis 정책 캐시 즉시 PURGE + 결과 토스트 (d21 F10) |
| **system_policy_history INSERT** | 변경 시 | DB 트리거 | 자동 (d21 §2.5) |
| **`policy.changed` 이벤트 발행** | 변경 후 | (각 도메인 캐시 invalidator + 전 SUPER 알림) | d21 §7.2 |
