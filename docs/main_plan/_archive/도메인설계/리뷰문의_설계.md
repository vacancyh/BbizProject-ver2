## 1. 도메인 개요

- **1줄 책임**: 회원의 모든 컨텐츠 기반 CS 채널(상품 리뷰·상품 Q&A·1:1 문의·실시간 채팅)을 통합 관리하고, 컨텐츠 모더레이션(신고·블라인드·스팸 탐지)과 표시광고법 정합(대가성 리뷰 표시·허위 후기 차단)을 책임진다.
- **범위 경계 (in)**: 리뷰 작성·수정·삭제·좋아요·신고·자동 블라인드 / 상품 Q&A(공개·비밀글) / 1:1 문의(상품·주문·일반 카테고리, 비밀글, 첨부) / 관리자 답변·매크로·AI 초안 / 실시간 채팅 세션·운영시간 게이트 / 베스트 리뷰 선정 / CS 케이스 통합 분류·SLA.
- **범위 경계 (out)**:
  - 알림 발송 실행 = `notification` 도메인 (본 도메인은 이벤트 발행만)
  - 포인트 적립·회수 실행 = `coupon_point`(d20) 도메인 (본 도메인은 트리거 이벤트만)
  - 신고 누적 회원 제재 = `member`(d11) 도메인 sanctions
  - 리뷰 작성 전제(구매확정) = `order`(d16) 상태 검증 위임
- **MVP 범위 외 (d19 §8.1)**: 동영상 리뷰, 인플루언서 등급, AI 챗봇 자동 응답, 비회원 Q&A.

## 2. 우리 S0 설계 요약 (d19 + f17 핵심)

### 2.1 핵심 엔티티 (d19 §2)

| 엔티티 | 책임 | 핵심 제약 |
|---|---|---|
| `reviews` | 리뷰 본체 | `UNIQUE(order_item_id)` = 1 주문상품 1리뷰 / rating 1~5 CHECK / status(pending·approved·hidden·reported) |
| `review_likes` | 좋아요 | 복합 PK `(review_id, member_id)` = 1회원 1회 |
| `review_reports` | 신고 | `UNIQUE(review_id, reporter_id)` = 1회원 1회 / COUNT≥3 시 자동 블라인드 |
| `inquiries` | 1:1 문의·상품 문의 통합 | category(product·order·general) / is_secret / status(open·answered·closed) |
| `inquiry_replies` | 관리자 답변 | 답변 시 inquiries.status=answered + `inquiry.answered` 발행 |
| `chat_sessions` | 실시간 채팅 세션 | status(waiting·active·ended·offline) / 운영시간 게이트 |
| `chat_messages` | 채팅 메시지 | sender_type(member·agent·system) |
| `cs_cases` | CS 케이스 통합 메타 레이어 | inbound_channel·priority·SLA·escalation·CSAT |
| `cs_operation_hours` | CS 운영시간 정책 | 복합 PK `(weekday, channel)` |

### 2.2 핵심 룰 (d19 §6 — 시스템 고정 F1~F23 / 정책 변경 P1~P13)

- **시스템 고정(F)**: 리뷰 전제=구매확정(F1) / 1주문상품1리뷰(F2) / 본문 20자↑(F3) / 이미지 최대 5장·5MB·EXIF 제거(F4) / 신고 3회 자동 블라인드(F5) / 비밀글 본인+관리자만(F11) / 비회원 작성 차단(F12) / 답변 시 이메일 알림 기본 ON(F14) / 베스트 리뷰 멱등(F20) / AI 답변 검수 후 발송 의무(F23) / XSS 필터(F18) / 관리자 액션 AuditLog(F19).
- **정책 변경(P)**: 리뷰 작성 기한 기본 7일(P1) / 수정 7일 내 1회(P2) / 텍스트 적립 100P(P3) / 포토 추가 400P=합계 500P(P4) / 자동 승인 vs 검수(P5) / 신고 임계 3회(P6) / 문의 SLA 24h(P7) / 채팅 운영시간 월~금 10~18(P9) / 비활성 타임아웃 10분(P10).

### 2.3 이벤트 (d19 §7) + 미결 (d19 §8.2)

- 발행: `review.submitted/approved/hidden/reported/deleted`, `inquiry.submitted/answered`, `chat.session.started/ended`
- 구독: `order.purchase_confirmed`(7일 카운트다운), `member.suspended`(채팅 종료), `member.withdrawn_completed`(작성자 마스킹)
- 미결: Q1 삭제 시 포인트 회수 잔액 부족 정책 / Q2 채팅 운영시간 외 정책(Q-12) / Q3 자동 블라인드 후 이의신청 / Q4 transcript 보관 기간 / Q5 자동 승인 vs 검수.

## 3. 성숙 플랫폼 패턴 (Spree / Vendure / Medusa 공식)

### 3.1 핵심 발견 — 3개 플랫폼 모두 리뷰·Q&A는 "코어 미포함, 커스텀/플러그인 영역"

| 플랫폼 | 리뷰·Q&A 처리 방식 | 근거 |
|---|---|---|
| **Medusa v2** | 네이티브 모듈 **없음**. 공식 튜토리얼이 `src/modules/product-review` 커스텀 모듈 + `defineLink` 패턴을 권장 | `메두사_..._product-reviews_page.mdx`, `dist/modules/` 실측 |
| **Vendure** | `VendureEntity` 상속 + Plugin `entities[]` 등록 커스텀 엔티티로 구현 (`product-review.entity.ts` 예시 명시) | `벤듀어_..._database-entity_index.mdx` (metaDescription: "store custom data like reviews") |
| **Spree** | 코어에 리뷰 없음. `spree_reviews` 등 외부 gem/extension 영역 | `스프리_docs_*` 내 리뷰 매칭은 모두 PR/plan 문서의 단어 사용일 뿐, 코어 모델 부재 |

→ **결론**: 우리도 리뷰·Q&A·문의·채팅을 **커스텀 모듈**로 구현하는 것이 3개 플랫폼의 일관된 정석이다. 코어 무수정 원칙과도 정합.

### 3.2 Medusa 공식 튜토리얼에서 배울 구체 패턴 (그대로 이식 가능)

`메두사_..._product-reviews_page.mdx` 가 제시하는 검증된 패턴:

1. **데이터 모델(DML)**: `model.define("review", {...}).checks([{ name:"rating_range", expression:(c)=>`${c.rating} >= 1 AND ${c.rating} <= 5` }])` — 우리 d19 rating CHECK 제약을 DML `.checks()` 로 그대로 구현.
2. **모듈 서비스**: `class ProductReviewModuleService extends MedusaService({ Review })` — CRUD 자동 생성(createReviews/retrieveReview/listReviews/updateReviews/deleteReviews).
3. **모듈 정의**: `index.ts` 에서 `Module(PRODUCT_REVIEW_MODULE, { service })` export + `medusa-config.ts` modules 배열 등록.
4. **링크(`defineLink`)**: `src/links/review-product.ts` 에서 `review.product_id ↔ ProductModule.linkable.product` 를 `readOnly:true` 로 연결 (코어 무수정 조회). 동일 방식으로 `review ↔ customer`, `review ↔ order_item` 연결.
5. **워크플로우**: `createReviewWorkflow` = `useQueryGraphStep`(상품 존재 확인) + `createReviewStep`(보상 함수 `deleteReviews` 포함) → 롤백 보장. `updateReviewWorkflow` = 원본 상태 보존 후 복원 가능한 상태 변경(approve/reject).
6. **API route**: `src/api/store/reviews/route.ts`(POST, customer 인증) / `src/api/admin/reviews/route.ts`(GET, 자동 보호) / `src/api/admin/reviews/status/route.ts`(POST approve/reject) + `src/api/store/products/[id]/reviews/route.ts`(승인된 리뷰만 + `getAverageRating`).
7. **미들웨어**: `src/api/middlewares.ts` 에서 `authenticate("customer",["session","bearer"])` + `validateAndTransformBody(zod schema)` + `validateAndTransformQuery`.
8. **Admin UI route**: `src/admin/routes/reviews/page.tsx` — `DataTable` + `createDataTableCommandHelper` 로 일괄 승인/거부 커맨드 바.
9. **평균 별점**: 서비스에 `@InjectManager()` + `@MedusaContext()` 데코레이터로 raw SQL `AVG(rating) WHERE status='approved'`.

> **주의(보안 강화)**: 튜토리얼의 `getAverageRating` 는 `product_id` 를 문자열 보간으로 raw SQL 에 넣음 → 우리 구현은 **반드시 파라미터 바인딩**으로 교체(SQL Injection 차단, f17 §4.2 F-XSS·A-INJ-002 정합).

## 4. 한국 관행 (웹 근거)

### 4.1 구매자 리뷰 vs 일반 리뷰 / 포토 리뷰 차등 보상

- **실 구매자 한정 리뷰**: 카페24는 "실제 구매 고객만 상품 후기 작성" 옵션을 제공 — 우리 d19 F1(구매확정 전제) + F2(주문상품 단위)와 정합. (출처: [카페24 Help — 실제 구매 고객만 후기 작성](https://support.cafe24.com/hc/ko/articles/8462707735193))
- **리뷰 적립금 자동 지급**: 카페24 "레시피" 기능으로 리뷰 작성 시 적립금 자동 지급 설정 가능. 다만 **카페24 기본 레시피는 일반 후기/포토 후기 지급액 구분이 어렵다**는 한계가 명시됨 → 우리는 d19 P3(텍스트 100P)/P4(포토 추가 400P) **차등 지급을 차별점**으로 설계(REV-A-018/019 관리자 설정). (출처: [카페24 Help — 리뷰 작성 적립금 자동 지급](https://support.cafe24.com/hc/ko/articles/8462558072217))
- **포토/동영상 리뷰**: 한국 쇼핑몰 표준은 포토 리뷰 우대(추가 적립). 동영상 리뷰는 우리 MVP 범위 외(d19 O1).

### 4.2 허위·과장 리뷰 규제 (표시·광고법 — 오류 없음 대전제 직결)

- **표시·광고의 공정화에 관한 법률**: 거짓·과장(객관적 근거 없는 '국내 유일' 등), 기만(미사용 후기를 실사용처럼), 부당 비교 광고를 금지. 입증 책임은 사업자. (출처: [국가법령정보센터 — 표시·광고의 공정화에 관한 법률](https://www.law.go.kr/LSW/lsInfoP.do?lsId=002011))
- **공정위 제재 사례**: 빈 상자 발송 후 실구매자처럼 거짓 후기 게재 = 거짓·과장 광고로 시정명령·과징금. (출처: [김·장 — SNS 뒷광고·이용후기 조작 감시 강화](https://www.kimchang.com/ko/insights/detail.kc?sch_section=4&idx=28278))
- **추천·보증 등에 관한 표시·광고 심사지침** (2020-09-01 시행): 현금·**적립금**·할인권·무료 제공 등 경제적 이해관계가 있으면 **반드시 게시물 제목 또는 첫 부분**에 표시 의무. '소정의 수수료 지급 가능' 같은 조건부·불확정 문구 금지. (출처: [공정위 추천·보증 표시·광고 심사지침](https://www.law.go.kr/LSW//admRulInfoP.do?admRulSeq=2100000190311), [공정위 — 경제적 이해관계 표시 안내서](https://www.ftc.go.kr/www/selectBbsNttView.do?key=12&bordCd=3&nttSn=46709))

→ **우리 적립금 리뷰는 "경제적 이해관계 있는 추천·보증"에 해당**. 적립금 지급 리뷰에는 **대가성 표시 라벨**(예: "적립 혜택을 받고 작성한 리뷰입니다")을 리뷰 본문/카드 **상단**에 노출해야 표시광고법 위반을 피한다. (본 도메인 신규 설계 포인트 — d19 미반영분 보강)

### 4.3 상품 Q&A / 1:1 문의 / 채팅 운영 관행

- **올리브영**: 전화 상담 평일 09:00~18:00, 주말·공휴일 전화 불가. **1:1 문의는 24시간 접수**(내역 추적 가능, 행사 기간 전화보다 빠름). 상품 하자 시 **사진 첨부 1:1 게시판** 유도. (출처: [올리브영 FAQ](https://www.oliveyoung.co.kr/store/counsel/getFaqList.do?faqLrclCd=300))
- **무신사**: 1:1 문의 상담 평일 10:00~17:00, "최대한 빠르게 답변". (출처: [무신사 FAQ](https://www.musinsa.com/app/cs/faq/001))

→ 한국 관행 정합: **실시간 채팅은 운영시간 한정**(우리 P9 월~금 10~18), **1:1 문의는 24시간 접수 + SLA 답변**(우리 P7 24h). 운영시간 외 채팅 진입 시 1:1 문의 자동 전환(우리 Q-12 권장안) = 올리브영 패턴과 일치. 상품 하자 첨부 = 우리 inquiries.attachments.

## 5. 종합 설계 결정

위 3개(S0 + 성숙 플랫폼 + 한국 관행)를 종합한 우리 설계.

### 5.1 모듈 분리 결정 (D1)

리뷰·Q&A/문의·채팅·CS케이스를 **3개 커스텀 모듈 + 1개 횡단 모듈**로 분리한다. 코어 무수정, 도메인 응집도, Medusa 모듈 격리 원칙 정합.

| 모듈 | 담당 엔티티 | 근거 |
|---|---|---|
| `product-review` | reviews, review_likes, review_reports | Medusa 공식 튜토리얼 패턴 그대로 |
| `inquiry-qna` | inquiries, inquiry_replies (Q&A와 1:1 문의를 `is_public` 플래그로 통합) | d19 §2.4~2.5 |
| `live-chat` | chat_sessions, chat_messages, cs_operation_hours | d19 §2.6~2.8 — WebSocket 별도 |
| `cs-case` (횡단) | cs_cases | d19 §2.7A — 모든 CS 인입 통합 SLA/에스컬레이션 |

> Q&A와 1:1 문의는 데이터 구조가 거의 동일(작성자·제목·본문·비밀글·답변·첨부) → `inquiries.is_public` boolean 으로 통합. is_public=true = 상품 Q&A(상품 상세 공개), false = 1:1 문의(비공개 CS). d19 의 별도 표현을 단순화한 결정(과설계 회피).

### 5.2 표시광고법 대가성 표시 결정 (D2 — 신규, 법령 직결)

적립금이 지급된 리뷰는 `reviews.points_awarded > 0` 또는 `is_incentivized=true` 일 때 **대가성 표시 라벨을 리뷰 카드 상단에 강제 노출**. 라벨 문구·노출은 시스템 고정 룰로 추가(아래 F24). 표시 위치 = 본문 첫 부분(심사지침 정합).

### 5.3 신규/보강 룰 (d19 F1~F23 + P1~P13 위에 추가)

| # | 룰 | 근거 | 비고 |
|---|---|---|---|
| **F24** | 적립금 지급 리뷰(`points_awarded>0`) = 대가성 표시 라벨 상단 강제 노출 | 표시·광고법, 추천·보증 심사지침 | **신규(법령 직결)** |
| **F25** | 평균 별점 산출 SQL = 파라미터 바인딩 의무(문자열 보간 금지) | A-INJ-002, 튜토리얼 결함 보강 | **보강** |
| **F26** | 리뷰·Q&A·문의 첨부 = `file` 코어 모듈 통해 저장 + 파일명 난수화 + MIME 검증 | d19 S4, Medusa `file` 모듈 | 코어 활용 |

### 6.3 legal-kr 격리 패턴 준수 (코어 무수정 검증)

- 모든 커스텀 모듈은 **코어 entity 직접 FK 금지** → `product_id`/`customer_id`/`order_item_id` 는 `model.text()` 컬럼 + `defineLink(readOnly)` 로만 조회(튜토리얼 §3 + 기존 `order-withdrawal.ts` 패턴).
- 표시광고법 대가성 표시(F24) 같은 한국법 특수 로직은 `product-review` 모듈 내부에 격리(코어 무영향) — `legal-kr` 와 동일 철학. 향후 Medusa 버전 업그레이드 호환성 보존.

### 6.4 ⓒ 마이그레이션 계획

각 모듈별 `npx medusa db:generate {moduleName}` → `npx medusa db:migrate`. 순서: product-review → inquiry-qna → live-chat → cs-case (의존 없음, 독립 가능). 링크 테이블은 readOnly 다수라 별도 테이블 미생성.
