## 1. 엣지케이스 처리 설계표 (12 시나리오)

> 컬럼: 시나리오 · 조건 · 위험 · 처리 설계 · 관련 룰/법령(§17·§18)

### E-01. 수취 거부 (Refusal of receipt)

| 항목 | 내용 |
|---|---|
| **시나리오** | 택배 기사 방문 시 수취인이 인수를 거부 → 상품이 발송처로 반송됨 |
| **조건** | `deliveries.status = shipping`, 추적 이벤트 = 반송(스마트택배 코드: 반송/미배달) |
| **위험** | ① 배송중 상태 고착(delivered 미도달) → 자동확정 미발동 ② 반송비 부담 주체 불명확 ③ 청약철회 7일 기산점 미정(인도일 없음) |
| **처리 설계** | ⓐ 스마트택배 추적이 "반송" 이벤트 수신 → `delivery.return_in_transit`(신규 내부 상태) 전이, delivered 전이 차단. ⓑ 반송 입고 = 물리 입고 확인 후 **반품 라이프사이클 진입(미배송 분기)** → 환불 기산점 = **청약철회일**(L-01 (a) 미공급, 인도 전이므로). ⓒ 반송비: 정당한 사유 없는 단순 수취거부 = **소비자 과실 → 왕복배송비 소비자 부담**(§17③ 정합, deep-research §3 "반송 비용 소비자과실일 경우 부담"). 단 불량·오배송 사전 인지로 인한 거부 = 사업자 부담(검수 결과로 판정). ⓓ 인도가 성립 안 됨 → 청약철회 7일 기산 시작 안 함(법적 안전). | §17③(반송비)·§18①1호(미공급=철회일 기산) |

### E-02. 분실 / 도난 (Loss / Theft)

| 항목 | 내용 |
|---|---|
| **시나리오** | (가) 배송완료 처리 후 문 앞 상품 분실·도난 (나) 배송 중(인도 전) 택배사 분실 |
| **조건** | (가) `status = delivered` + 사용자 미수령 클레임 (나) `status = shipping` + 추적 정지/사고 |
| **위험** | ① 분실 책임 소재 분쟁 ② 인도 성립 여부에 따라 환불·재발송 의무 상반 ③ 무한 클레임 악용 |
| **처리 설계** | ⓐ **배송완료 후 분실/도난(가) = 인도 완료로 소비자 위험부담 이전** → 원칙적 소비자 과실(deep-research §3 "배송완료 후 분실은 소비자 과실"). 다만 사고보고 접수 → 스마트택배 인수 증빙(서명/사진/GPS) 부재 시 운영 검토(보상기준 안내). ⓑ **배송 중(인도 전) 분실(나) = 사업자 위험부담** → 재발송 또는 환불(소비자 선택), 기산점 = 청약철회일(미공급). ⓒ `delivery_incident`(신규 사고 로그: order_id, type[loss/theft], reported_at, resolution) 적재 + 관리자 알림. ⓓ 교환 배송 분실 = UC-DEL-A-22 정합(재발송/환불, 운영 결정). | §18①(미공급 환불)·민법 위험부담(인도 시 이전) |

### E-03. 대리 수령 (Proxy receipt)

| 항목 | 내용 |
|---|---|
| **시나리오** | 수취인 본인이 아닌 가족·경비실·이웃이 대신 수령 |
| **조건** | `status` delivered 전이 + 추적 인수자 ≠ 수취인명 |
| **위험** | ① 사전 동의 없는 대리수령 분쟁(미수령 주장) ② 인도 성립 다툼 |
| **처리 설계** | ⓐ 대리수령 자체는 일반 관행 → delivered 정상 전이, 단 추적 메타(인수자/장소: 경비실/무인함 등) 보관(deep-research §3 "사전 동의 없을 경우 분쟁소지"). ⓑ 인수 증빙(서명/사진) = 스마트택배 추적 payload 90일 보관(d18 shipment_tracking)으로 분쟁 대비. ⓒ 분실 클레임 발생 시 E-02(가) 분기로 위임(인도 증빙 유무 판정). ⓓ 무인택배함/경비실 수령 시 알림에 수령 장소 표기(거래성 알림). | (직접 법령 없음 — 분쟁 대비 증빙·고지) |

### E-04. 배송지 변경 — 준비(상품준비중) 이후

| 항목 | 내용 |
|---|---|
| **시나리오** | 사용자가 결제 후 배송지 변경 요청 (a) 준비중 이전 (b) 운송장 발급/발송 후 |
| **조건** | (a) `status ∈ {paid, preparing}` (b) `status ∈ {shipping, ...}` (운송장 발급됨) |
| **위험** | ① 발송 후 변경 시 물류비·재배송 비용 ② 도서산간 변경 시 추가배송비 재산정 누락 ③ address_snapshot 불일치 |
| **처리 설계** | ⓐ **준비중 이전(a) = 무료 변경 허용** → `deliveries.address_snapshot` 갱신 + region_type 재분류 → **도서산간 변경 시 region_extra 재산정 + 차액 청구/환불**(보강 A-2 항상 부과). ⓑ **운송장 발급 후(b) = 원칙 변경 불가** → 반송 후 재배송 또는 회수-재발송, **추가 물류비 사용자 부담 고지 후 처리**(deep-research §3 "물류비·시간 추가 비용 고지 후 처리", 예시 고지문구). ⓒ 변경 가능 컷오프 = `status` 기반 단방향 게이트(B-03 state-machine 권위). ⓓ 유효주소 검증(zipcode 매핑) 후에만 확정. | (직접 법령 없음 — 추가비 사전 고지 의무 / 다크패턴 회피 §44 정합) |

### E-05. 도서산간 — 무료배송 임계 도달 + 부분취소 잔여

| 항목 | 내용 |
|---|---|
| **시나리오** | (a) 무료배송 임계(50,000) 충족했으나 도서산간 (b) 부분취소로 잔여 < 임계 전락 + 도서산간 |
| **조건** | `region_type ∈ {jeju, mountainous}`, product_amount 임계 경계 |
| **위험** | ① 무료배송이라 추가비 면제로 오인 ② 부분취소 후 base_fee + region_extra 재청구 이중 처리 |
| **처리 설계** | ⓐ **region_extra(제주 3000/도서산간 5000)는 무료배송 무관 항상 부과**(보강 A-2, 카페24 §4.2 근거 박제). 산식 = `(amount≥50000?0:base) + region_extra`. ⓑ **부분취소 잔여 < 50000(b)** = base_fee 추가 청구(f16 §3.2 비례배분) **+ region_extra 유지**(별도, 면제 안 함). ⓒ 결제수단 = 포인트 차감 or 추가 결제(f16-Q07 운영, 사장님 결정 영역). ⓓ FLOOR 절사(보강 A-1 #1) 적용. | (직접 법령 없음 — 배송비 고지 §13 정합) |

### E-06. 반품 회수 지연 — 환불 기산점 (L-01 핵심)

| 항목 | 내용 |
|---|---|
| **시나리오** | 반품 승인·회수 운송장 발급 후 회수가 수일~수주 지연 |
| **조건** | `returns.status = approved/pickup_scheduled`, 재화 미반환 |
| **위험** | ① 통지일 기산 시 사업자가 물건 못 받고 환불(L-01 모순) ② 회수 무한 지연 시 환불 영구 미발동 ③ 법정 3영업일 자동 초과 |
| **처리 설계** | ⓐ **환불 기산점 = 재화 반환받은(검수완료)일**(L-01 (b), 배송완료 후 반품). `requireBusinessDayRefundSLA(orderId, originType=return_received_date)` 호출. ⓑ 회수 지연 동안 SLA 시계 **미시작** → 사업자 모순 해소. ⓒ 회수 장기 미발생(예: N일 경과) = 운영 모니터링 job + 사용자 회수 독촉 알림. ⓓ **미배송 분기(E-01 반송 등)** = 기산점 = 청약철회일(L-01 (a)). ⓔ L-02 연계: due_date(기산점+영업일3) 초과 시 **연 15% 지연이자 자동 산정**(refunds.delayed_interest). | **§18①1호**(미공급=철회일)·**§18①2호**(공급=반환받은날) / 검수 L-01·L-02 |

### E-07. 검수 혼재 (good + defective 라인 혼재)

| 항목 | 내용 |
|---|---|
| **시나리오** | 다건 반품 N라인 중 일부 양호·일부 불량 검수 결과 |
| **조건** | `returns.item_ids` 복수, `ReturnInspection` 라인별 결과 상이 |
| **위험** | ① 단일 inspection_result로 뭉뚱그리면 재고복구·반송비 오판 ② 라인별 환불액 비례배분 오차 |
| **처리 설계** | ⓐ **라인별 분리 처리**(f16-Q09 권장 (a), 보강 미명시→f16 확정 인용). good 라인 = 재고 복구 + 환불 / defective 라인 = 재고 미복구. ⓑ 반송비: good+단순변심 = 소비자 부담 / defective = 사업자 부담(라인별 판정). ⓒ `ReturnInspection.resellable`/`condition`(A/B/C/DISPOSE) 라인 단위 기록(rma-extension). ⓓ 환불액 = 라인별 비례배분(쿠폰·포인트·배송비) FLOOR(보강 A-1 #1). ⓔ 검수완료 = 라인 모두 판정 시 `return.completed` 발행(M-04 환불 체인). | §18(라인별 환불)·검수 L-11(예외사유-검수 매핑) |

### E-08. 교환 일부 품절 (다건 교환 그룹)

| 항목 | 내용 |
|---|---|
| **시나리오** | 다건 교환 그룹의 신옵션 중 일부 SKU 재고 소진 |
| **조건** | `exchange_groups` N라인, 검수/승인 시점 SELECT FOR UPDATE = 0 |
| **위험** | ① 그룹 전체 reject 시 정상 라인까지 무산 ② 부분 진행 시 차액 재계산·회수운송장 1회 정합 깨짐 |
| **처리 설계** | ⓐ **부분 환불 전환 옵션 제안**(f16-Q08 권장 (b)). 품절 라인 = 환불 전환, 가능 라인 = 교환 진행(사용자 동의 기반). ⓑ 그룹 회수 운송장은 **1회 청구 유지**(exchange_groups.pickup_fee_total). ⓒ 신옵션 재고 차감 = 검수 완료 시점 SELECT FOR UPDATE → 0이면 `EXCHANGE_GROUP_PARTIAL_REJECT`(f16 §6) → 사용자 안내. ⓓ 차액 합산 재계산(품절 라인 제외) FLOOR. ⓔ 동가/+차액/-차액 분기는 f16 §3.4 정합. | (직접 법령 없음 — 재고 소진 시 환불 전환은 §15 공급곤란 통지 정합) |

### E-09. 운송장 오등록 (잘못된 번호/택배사)

| 항목 | 내용 |
|---|---|
| **시나리오** | 관리자가 운송장 번호·택배사 오입력 → 추적 불가 또는 타인 배송 추적 |
| **조건** | 정규식 통과했으나 실제 미존재 / 택배사 코드 불일치 |
| **위험** | ① 추적 실패로 배송 상태 미갱신 ② 타인 운송장 매핑 시 개인정보·오배송 추적 노출(IDOR) ③ delivered 오전이 |
| **처리 설계** | ⓐ 등록 시 정규식 검증(d18 F8: CJ 10~12·한진 10·롯데 12·우체국 13 — **정확 자릿수는 스마트택배 코드표로 검증, (추가 확인 필요)**). ⓑ 스마트택배 조회 API 1차 호출로 **운송장 실존 검증**(미존재 시 등록 보류 + 경고). ⓒ 오등록 정정 = 관리자 운송장 재등록(audit log 의무, d18 S4) + 기존 추적 무효화. ⓓ delivered 전이는 추적 webhook 멱등(UNIQUE(order_id,event_at,event_code)) 기반만 허용(수동 강제 전이 차단). ⓔ 본인+관리자만 추적 조회(d18 S2 IDOR 차단). | (직접 법령 없음 — 개인정보보호·IDOR 차단 / d18 F23·S2) |

### E-10. 중복 반품/교환 신청 (동일 라인)

| 항목 | 내용 |
|---|---|
| **시나리오** | 동일 order_item에 반품·교환 또는 반품·반품 중복 신청 (사용자 더블클릭/동시) |
| **조건** | 같은 `order_item_id` 에 진행 중 액션 존재 |
| **위험** | ① 이중 환불·이중 재고복구 ② 라인 상태 충돌 |
| **처리 설계** | ⓐ **라인 단위 분산 락** `line_action_lock:{order_item_id}`(Redis) + **DB UNIQUE(order_item_id, action_type) WHERE status IN (requested, approved, processing)**(f16 §5.2). ⓑ 1건만 성공, 나머지 409 `LINE_ALREADY_IN_PROCESS`(f16 §6). ⓒ 반품 진행 중 다른 라인 교환 = 라인 ID 분리 → 허용(f16 §5.2). ⓓ 멱등키(Idempotency-Sub-Key)로 동일 요청 재시도 차단(f16 §4.2). | (직접 법령 없음 — 이중환불 방지 F-PAY-12) |

## 2. 상태·이벤트 정합 (B-03 / M-04 반영)

### 2.1 신규 내부 상태 (엣지 대응)

| 상태 | 용도 | 진입 엣지 | 권위 |
|---|---|---|---|
| `return_in_transit` | 반송 진행 중(수취거부·미배달 반송) | E-01 | state-machine config (B-03) |
| `delivery_incident` 플래그 | 분실/도난 사고 로그 | E-02 | 신규 사고 테이블 |
| `partially_delivered` | 분할배송 일부 delivered | (기존) | state-machine config |

> **B-03 권위 원칙**: 위 상태는 모두 state-machine `config/fulfillment.ts` 에 등록(주문/배송 각자 정의 금지). 주문 status ↔ 배송 status rollup 매핑표 박제: 전 shipment `delivered` → order `delivered`, 일부 → `partially_delivered`, 반송 → order 측 반품 분기.

### 2.2 환불 체인 이벤트 (M-04 / C-03 통일)

```
배송: return.completed (검수완료, 환불 트리거)
  → 주문: 환불 트랜잭션 시작 (return.completed 구독)
    → 결제: PG cancel 호출 (refund_amount, idempotency_key)
      → 포인트/쿠폰 비례 복원 (FLOOR)
```

- **이벤트명 통일**(C-03): 배송 발행 = `return.completed` / `exchange.completed`. 주문 구독 prefix를 `delivery.return_completed` → **`return.completed`로 통일**(보강 B-05 정합).
- 환불 기산점(L-01)이 이벤트 시점(검수완료=반환받은날)과 일치 → SLA 시계 시작점 명확.
