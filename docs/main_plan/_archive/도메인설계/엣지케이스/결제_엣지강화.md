## 1. 엣지케이스 망라 + 처리 설계 (총 14건)

> 각 엣지: 시나리오 / 조건 / 위험 / 처리 설계(멱등키·재시도·검증) / 관련 룰·법령. PG 호출은 **트랜잭션 외부**(f14 §4.2 F-TXN-01·03, statement_timeout 2초) 원칙을 모든 엣지에 공통 적용합니다.

### E-01. 결제 실패 (카드 거절·승인 거부)

| 항목 | 내용 |
|---|---|
| 시나리오 | 사용자가 토스 결제창에서 카드 입력 후 카드사가 승인 거부(한도·도난·정지카드 등) → `payment.failed` 콜백 또는 Confirm API 실패 응답 |
| 조건 | 토스 Confirm API 4xx/거절 응답, 또는 토스 `PAYMENT_STATUS_CHANGED`(FAILED) webhook 수신 |
| 위험 | (a) 주문 status 고착 (b) 무한 재시도로 카드사 어뷰징 차단 (c) 사용자에게 사유 미고지 |
| 처리 설계 | `payments.status=failed` + `failed_reason` 저장 → `orders.status=pending` **유지**(취소 아님, 재시도 가능). `payment_attempts.attempt_count++`. `payment.failed` 이벤트 → 주문(pending 유지)·notification. **30분 경과 시 미결제 자동취소 배치**(E-04)가 정리. 멱등: webhook dedupe_key(pg_tx+event_type). 응답 = 항상 200(F-WEBHOOK-04). 사용자 안내 = s20 결제실패 페이지 + 잔여 시도 횟수. |
| 관련 룰·법령 | F-PAY-09(30분 자동취소), F-PAY-14(3회→4회 차단), F-WEBHOOK-04, deep-research §3 "결제 실패"(24h 내 미결제 자동취소), f14 §3.3 |

### E-02. 중복 결제 (이중 전송·더블클릭·재시도)

| 항목 | 내용 |
|---|---|
| 시나리오 | (a) 사용자 결제 버튼 더블클릭 (b) 네트워크 오류로 클라이언트가 동일 요청 재전송 (c) 토스가 동일 결제건 콜백 2회 전송 |
| 조건 | 동일 order_id에 대해 2건 이상의 initiate/Confirm/webhook 도달 |
| 위험 | 동일 주문 2회 카드 청구 → 초과분 환불 필요 + 분쟁 |
| 처리 설계 | **3중 멱등 방어**: ① initiate = `payments.idempotency_key` UNIQUE + 24h 응답 캐시(F-IDEM-04/05) → 캐시 hit 시 동일 응답(409 아닌 최초 성공 응답). ② 토스 Confirm/Cancel 호출 = `Idempotency-Key` 헤더 전달(토스 멱등키) → 토스 측 중복 승인 차단. ③ webhook = `payment_webhooks.dedupe_key`(pg_tx+event_type) UNIQUE → 2건째 200 멱등 반환. 프론트 디바운스 보조. `same key 다른 body = 409`(F-IDEM-06, request_hash 비교). **만약 그래도 이중 청구 발생 시**(토스 측 장애): 정기 정합 조회(E-13)가 초과 결제 탐지 → 초과분 자동 부분취소 + `payment.refunded`. |
| 관련 룰·법령 | F-PAY-04(Idempotency-Key 필수), F-PAY-05(dedupe), F-PAY-24(더블클릭), F-IDEM-01~06(f14 §5.4), deep-research §3 "중복 결제" |

### E-03. Webhook 유실 (콜백 미수신)

| 항목 | 내용 |
|---|---|
| 시나리오 | 토스 결제 승인 성공했으나 webhook이 우리 서버에 도달 못함(컨테이너 재시작·네트워크 단절·배포 중) |
| 조건 | 토스 측 승인 완료 + `payment_webhooks`에 해당 pg_tx 레코드 없음 |
| 위험 | 결제는 됐는데 주문이 `pending` 고착 → 사용자 결제했는데 주문 미확정 (CS 폭증) |
| 처리 설계 | **승인 이중화(D-02)**: redirect 후 서버 Confirm API로 **동기 승인**이 1차 경로. webhook은 정합성 안전망(2차). 둘 다 동일 pg_transaction_id dedupe로 1회만 반영. webhook 유실 시: ① Confirm API가 이미 승인 반영했으면 정상. ② Confirm도 유실 시 → **정기 정합 조회 배치**(E-13, 토스 결제 조회 API)가 pending 주문의 실제 PG 상태 조회 → 승인됨이면 승인 트랜잭션 재실행(멱등). ③ 그래도 미복구 시 30분 자동취소 배치가 PG 미승인 확인 후에만 취소. webhook 응답 항상 200(F-WEBHOOK-04). |
| 관련 룰·법령 | D-02(승인 이중화), F-PAY-05(dedupe 멱등), F-PAY-09, f14 §3.3·§5.3(컨테이너 재시작), Medusa webhook-events "프론트 중단 시 webhook 복구" |

### E-04. 결제 중 브라우저 종료 (미결제 pending 잔존)

| 항목 | 내용 |
|---|---|
| 시나리오 | 사용자가 토스 결제창 진입 후 카드 미입력 상태로 브라우저/탭 강제 종료 → redirect 미발생 |
| 조건 | `orders.status=pending` + `payments.status=pending` + PG 미승인(Confirm 미호출) |
| 위험 | (a) 재고/쿠폰/포인트가 주문 생성 시점에 선점됐다면 잔존 (b) pending 영구 잔존 |
| 처리 설계 | **미결제 자동취소 배치**(매 1분 polling): `status=pending AND created_at < now()-30min` → 트랜잭션 내 재확인(`status != pending이면 skip` = 멱등) → 주문 취소 + 재고/쿠폰/포인트 복구(주문 트랜잭션 오케스트레이션, M-03). **PG 미승인 상태면 PG cancel 호출 없음**(`payments.status=cancelled` 직접). 단, 취소 직전 정기 정합 조회로 PG 승인 여부 재확인(승인됐으면 취소 대신 승인 처리 — E-03 경로). 멱등 키 = order_id + payments.version. |
| 관련 룰·법령 | F-PAY-09(30분 자동취소), UC-PAY-U-04, B-PAY-007, f14 §3.4 배치 코드 |

### E-05. Webhook 순서 뒤바뀜 (out-of-order)

| 항목 | 내용 |
|---|---|
| 시나리오 | 토스가 `approved` → `cancelled`(또는 부분취소) 이벤트를 빠르게 연속 전송, 네트워크 지연으로 우리 서버에 **역순 도착**(cancelled 먼저, approved 나중) |
| 조건 | 동일 pg_transaction_id의 복수 event_type이 시간순과 다르게 도착 |
| 위험 | 상태 머신 역행(cancelled 후 approved 덮어쓰기) → 환불됐는데 다시 승인 상태로 오염 |
| 처리 설계 | **state-machine 모듈 config 단일 권위**(B-03)로 **단방향 전이만 허용**. `pending→approved→(cancelled/refunded/partial_refunded)` 외 역전이 차단. webhook 처리 시 `payments.version` 낙관락 + 현재 status 검증: 이미 cancelled/refunded인데 approved 도착 → 전이 불가로 무시(200 반환 + 감사 로그). 각 이벤트는 `payment_webhooks`에 dedupe_key별 INSERT(이력 보존, immutable) → 도착 순서와 무관하게 처리 시점에 status 기반 판정. 토스 payload의 이벤트 timestamp(`Toss-Request-Time`)도 참조하되 권위는 DB status. |
| 관련 룰·법령 | B-03(state-machine 단일 권위), F-OPTLOCK-01~05, F-PAY-28(immutable), F-WEBHOOK-03(타임스탬프), state-machine `config/payment.ts` |

### E-06. 승인 후 재고차감 실패 → 즉시 환불 (오버셀)

| 항목 | 내용 |
|---|---|
| 시나리오 | 토스 결제 승인 완료 후 재고 차감 트랜잭션에서 `UPDATE product_skus SET stock=stock-qty WHERE stock>=qty` 가 0행(동시 구매로 재고 소진) |
| 조건 | webhook 승인 트랜잭션 내 재고 차감 affected_rows=0 |
| 위험 | 결제는 됐는데 줄 물건이 없음 → 사용자 피해 + 오버셀 클레임 |
| 처리 설계 | **F-PAY-07 즉시 자동 환불**: 승인 트랜잭션 ROLLBACK → **별도 환불 트랜잭션**에서 토스 cancel API 전액 호출(PG는 트랜잭션 외부) → `orders.status=cancelled` → `payment.refunded` 이벤트(사용자 안내). M-03 정합: 재고/포인트/쿠폰 복구는 **주문 트랜잭션이 오케스트레이션**, 결제는 PG 환불(외부)만 수행. 멱등: cancel API에 `Idempotency-Key`(`{order_id}:full_cancel:{nonce}`). 동일하게 쿠폰/포인트 차감 실패도 자동 롤백(F-PAY-08). webhook 트랜잭션 = SERIALIZABLE(F-ISO-01), 40001 → 50ms×2 재시도(F-ISO-05). |
| 관련 룰·법령 | F-PAY-07(재고차감 실패 즉시환불), F-PAY-08(쿠폰/포인트 실패 롤백), F-ISO-01/05, M-03, UC-PAY-U-03, ORD-U-037 |

### E-07. 금액 위변조 (amount tampering)

| 항목 | 내용 |
|---|---|
| 시나리오 | (a) 클라이언트가 initiate에 `expected_amount=100` 등 조작값 전송 (b) 공격자가 webhook payload의 `amount`를 조작해 직접 전송 |
| 조건 | 서버 재계산값 ≠ 클라이언트/콜백 amount |
| 위험 | 실제 금액보다 적게 결제 → 매출 손실·사기 |
| 처리 설계 | **4-way 검증(실질 amount 4축)**: 서버 신뢰 축 = DB `payments.amount`. ① initiate 시 서버 재계산(상품금액→쿠폰할인→포인트사용→배송비, FLOOR) == expected_amount, 불일치 422 AMOUNT_MISMATCH(F-PAY-01/02). ② Confirm 호출 시 amount 검증. ③ webhook 처리 트랜잭션 내 `DB payments.amount == toss payload.amount` 재검증, 불일치 시 `failed_reason='AMOUNT_TAMPERED'` + **보안 알람(Slack #security)** + 응답 200(F-WEBHOOK-05). webhook 직접 호출 자체는 5중 검증(IP·HMAC 서명·타임스탬프·dedupe·amount)으로 차단. 금액 산식·반올림 상수는 주문 d16 단일 권위(B-01). |
| 관련 룰·법령 | F-PAY-01/02(4-way·변조 차단), F-WEBHOOK-01~05(5중 검증), B-PAY-001/002, B-01(반올림 단일권위), f14 §3.2 Layer 5 |

### E-08. 부분 환불 N회 (누적 무결성 race)

| 항목 | 내용 |
|---|---|
| 시나리오 | 한 결제건에 부분취소·반품이 여러 번 발생(예: 3개 중 1개씩 3회 환불). 부분환불1(5,000)+부분환불2(4,500)가 거의 동시 도달 |
| 조건 | `SUM(refunds.amount)` 가 결제 금액에 근접한 상태에서 동시 환불 요청 |
| 위험 | 각자 잔여 환불가능 검증 통과 → 양쪽 처리 → **누적 환불 > 원결제**(초과 환불 = 금전 손실) |
| 처리 설계 | **3중 안전망(F-PAY-11A~F)**: ① SERIALIZABLE + `SELECT FOR UPDATE on payments`(race 직렬화). ② `refunds.idempotency_sub_key`(`{order_id}:{action_type}:{nonce}`, action_type ∈ full_cancel/partial_cancel/return/exchange_refund/admin_refund) UNIQUE → 같은 액션 재요청 캐시. ③ `trg_refund_total_check` BEFORE INSERT 트리거(`SUM(completed,processing) + NEW.amount ≤ payments.amount`) = 최종 안전망. PG 호출 단위 = 부분환불 신청 단위 1:1(F-PAY-11C, 합산 1회 호출 금지). 비례 배분(쿠폰·포인트·배송비) = 라인별 adjustment 역산 + **FLOOR 절사**(B-01, A-1 #1). 다건 교환 그룹 = group_id 합산 1회 PG 호출 + refunds N row(F-PAY-11D). 트리거/CHECK = 마이그레이션 raw SQL(단순 CHECK는 DML `.checks()` 우선, 누적 트리거만 raw SQL — Medusa 검수 MINOR). |
| 관련 룰·법령 | F-PAY-11/11A~F, F-PAY-12(이중환불), F-PAY-21(부분취소 비례배분), F-ISO-01, B-01, S-Q14→A-1#1 FLOOR, d17 §6.5 |

### E-09. 환불 3영업일 초과 지연 → 지연이자 (연 15%)

| 항목 | 내용 |
|---|---|
| 시나리오 | 환불 재시도 큐(최대 5회×10분)·PG 장애·검수 지연 등으로 환불이 법정 3영업일을 초과 |
| 조건 | `now() > refunds.due_date`(= 기산점 + 영업일 3) AND status != completed |
| 위험 | **전자상거래법 §18② 위반** — 미지급 지연이자(연 15%) 발생 + 분쟁·과태료 |
| 처리 설계 | **L-02 모델 신설**: `refunds`(payment-kr)에 `due_date` + `delayed_days` + `delayed_interest`(연 15% 일할) 필드. 기산점은 `legal-kr/withdrawal-7day` `requireBusinessDayRefundSLA(orderId, originType)` — **originType 2분기(L-01)**: (a)미배송·미공급=청약철회한 날 / (b)배송완료 후 반품=재화 반환받은(검수완료) 날. **환불 재시도 큐 job이 `due_date` 초과 감지 시**: `delayed_days = 영업일 초과일수` 산정 → `delayed_interest = FLOOR(원금 × 0.15 × delayed_days / 365)` → 환불 실행 시 **원금 + 지연이자 합산** PG 호출 + 관리자 알림. 지연이자도 절사(FLOOR, 고객 유리 — A-1#1과 동일 상수). |
| 관련 룰·법령 | **전자상거래법 §18②(지연이자 연 15%)**, L-01(기산점 2분기), L-02(지연이자 모델), `legal-kr/withdrawal-7day`, D-08(재시도 큐 5회×10분), B-02 보강 |

### E-10. 0원 결제 (포인트/쿠폰 100%)

| 항목 | 내용 |
|---|---|
| 시나리오 | 최종 결제금액이 0원(포인트 100% 또는 쿠폰+포인트로 전액 충당) |
| 조건 | `payment_amount == 0` (point_used == server_amount 등) |
| 위험 | (a) 0원인데 PG 호출 시 토스 오류 (b) PG webhook 안 오니 **주문 pending 고착**(B-02 BLOCKER) (c) 포인트 차감 누락 |
| 처리 설계 | **F-PAY-18**: PG 결제창 **미호출** → 포인트 차감 트랜잭션 직접 실행 → `payments.status` 0원 직접 confirmed → **`payment.zero_payment_confirmed` 이벤트 발행**. **B-02 해소**: 주문 도메인이 본 이벤트를 **구독** → `order.paid` 전이(주문 구독 목록에 추가 — C-01 정합). 응답 = 200 + `{ confirmed: true }`(redirect 없음). 멱등: `payments.idempotency_key` UNIQUE + 포인트 차감 트랜잭션 멱등(point_transactions). 잔액 부족 시 422. 0원 결제도 통계 구분 표시(PAY-A-026). |
| 관련 룰·법령 | F-PAY-18, B-02(0원 이벤트 흐름 명시), C-01(주문 구독 추가), UC-PAY-U-10, PAY-A-026, f14 §3.1 0원 분기 |

### E-11. PG 타임아웃 (Confirm/Cancel API 응답 지연)

| 항목 | 내용 |
|---|---|
| 시나리오 | 토스 Confirm API(또는 cancel API) 호출 후 응답 타임아웃(2초 초과)·5xx |
| 조건 | PG API 호출이 statement_timeout/네트워크 타임아웃 |
| 위험 | (a) 토스는 승인했는데 우리는 실패로 인지 → 결제됐는데 주문 미확정 (b) 환불 타임아웃 시 환불 누락 |
| 처리 설계 | **PG 호출은 트랜잭션 외부**(F-TXN-01·03, 트랜잭션 ≤2초). Confirm 타임아웃 시: 즉시 실패 단정 금지 → 사용자에게 "결제 처리 중, 마이페이지에서 확인"(500 PG_TIMEOUT) → **webhook 또는 정기 정합 조회(E-13)가 실제 PG 상태로 복구**. 모든 PG 호출은 `Idempotency-Key` 헤더 → 재시도해도 중복 승인/환불 없음. 환불 PG 타임아웃 → `refund_retry_queue`(최대 5회×10분, F-PAY-11E/13) + 사용자 "24시간 내 환불 완료" 안내. **재시도가 due_date 초과 시 지연이자(E-09)**. |
| 관련 룰·법령 | F-TXN-01·03(PG 외부·트랜잭션 ≤2초), F-TIMEOUT-01(statement_timeout 2초), F-PAY-11E/13(재시도큐), D-02(webhook 복구), f14 §6 PG_TIMEOUT |

### E-12. 카드 한도초과·결제 시도 어뷰징 (반복 실패)

| 항목 | 내용 |
|---|---|

| 관련 룰·법령 | F-PAY-14(3회→4회 차단 24h), F-PAY-15(이상거래 탐지), F-RATE-01·02(rate limit), UC-PAY-U-05, deep-research §4 로그인 시도 제한 |

## 2. 공통 처리 원칙 (전 엣지 횡단)

| 원칙 | 내용 | 근거 |
|---|---|---|
| PG 호출 = 트랜잭션 외부 | 모든 토스 Confirm/Cancel/조회는 DB 트랜잭션 밖. 트랜잭션 시간 ≤2초, statement_timeout 2초 자동 롤백 | F-TXN-01·03, F-TIMEOUT-01 |

| 트랜잭션 경계 단일 소유 | 재고/포인트/쿠폰 복원 오케스트레이션 = **주문 도메인(d16)**. 결제 = PG 호출(외부)만 | M-03 |

| 반올림 | 모든 비례 배분·지연이자 = **FLOOR 절사**(고객 유리), 산식·상수는 주문 d16 단일권위 `ROUNDING=FLOOR` | A-1#1, B-01 |
| webhook 응답 | 처리 성공/실패 무관 항상 200(PG 재전송 차단), 내부 큐 적재. 검증 실패는 보안 알람 | F-WEBHOOK-04/05 |
| PCI/로그 | 카드번호·CVC·paymentKey 평문 미저장·미로그. 마스킹 + SHA256(card_hash)만 | F-PAY-06, PCI SAQ-A |
| 이벤트 발행 | outbox 패턴(트랜잭션 commit 후 at-least-once), 소비자 멱등(event_id UNIQUE) | F-OUTBOX-01~07 |
