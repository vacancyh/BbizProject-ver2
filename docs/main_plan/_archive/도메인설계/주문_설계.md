# 주문(Order) 도메인 종합 설계

> **대전제**: ① 오류 없음(전자상거래법 청약철회·정산 정합) ② 한국 친화 ③ 코드베이스 수렴(Medusa v2.15.3 native + 기존 커스텀 모듈 재사용). 추측 금지, 출처 명시.
> **격리 패턴 준수**: Medusa core 엔티티 무수정. 확장은 `defineLink` + 별도 커스텀 모듈(`legal-kr/*`, `state-machine`)로만. (기존 `src/links/order-withdrawal.ts` 패턴)

---

## 1. 도메인 개요

- **1줄 책임**: 주문 생성·조회·취소·부분취소·구매확정·정산의 **트랜잭션 경계**를 책임진다.
- **포지션**: payment·delivery와 강결합. 동시성·원자성·멱등성이 가장 중요한 도메인.
- **범위 경계 (in)**: 주문 본체 생성/조회, 원자 트랜잭션 경계 관리(재고·쿠폰·포인트 차감 오케스트레이션), 상태 전이, 전체/부분 취소 트리거, 구매확정, 정산 집계.
- **범위 경계 (out)**:
  - PG 결제 승인·환불 호출 자체 = payment(d17). 본 도메인은 트리거 + 트랜잭션 경계만.
  - 재고 차감/복구 실행 = product(d12). 본 도메인은 이벤트 발행만.
  - 배송지·운송장·반품·교환 라이프사이클 = delivery(d18). 본 도메인은 주문 상태 전이만.
  - 청약철회 7일 기산·예외 판정 = `legal-kr/withdrawal-7day` 커스텀 모듈(기존 구현). 본 도메인은 link로 연결.
- **MVP 정책 고정**: 회원 전용(비회원 주문 불가), 카드 단일 결제(토스 MCP), 무통장/가상계좌/에스크로 미적용. (`00_개요.md §2`)

## 2. 우리 S0 설계 요약

> 출처: `05_도메인정의서/d16_주문.md`, `04_기능정의서/f14_주문_결제.md`

### 2.1 핵심 엔티티 (S0 정의 — 우리 도메인 관점)

| 엔티티 | 책임 | 핵심 필드 |
|---|---|---|
| `orders` | 주문 본체 | order_no(`ORD-YYYYMMDD-XXXXXX`), member_id, status(11종), payment_amount, address_snapshot, idempotency_key UNIQUE, **version(낙관락)** |
| `order_items` | 주문 라인 | sku_id, price_snapshot, option_snapshot, status, **line_status**(라인 단위 진행 추적) |
| `order_status_history` | 상태 전이 이력 | from/to_status, changed_by, **INSERT 전용(UPDATE 금지)** |
| `order_cancellations` | 취소 이력 | type(full/partial), refund_amount, cancelled_items(JSONB), restored_points/coupon |
| `idempotency_keys` | 중복 요청 방지 | key PK, scope, request_hash, response 캐시, expires_at(24h) |
| `exchange_groups` | 다건 교환 그룹(Tier1 §3.A) | total_price_diff, diff_action, pickup_tracking_no(그룹 1회 회수), version |
| `settlement_daily` | 일별 정산 | date PK, sales/refund/pg_fee/net_settlement, held_amount, batch_status |

### 2.2 핵심 룰 (S0 §6 시스템 고정 룰 발췌)

- **F1 원자 트랜잭션**: 주문 생성 = 재고+쿠폰+포인트 차감 + orders INSERT (하나 실패 시 전체 롤백 + 결제 자동 취소·환불).
- **F2 Idempotency-Key 필수**(주문·취소·환불), 응답 캐시 24h.
- **F3 단방향 상태 전이**(역순 차단): pending → paid → preparing → shipping → delivered → confirmed.
- **F4 동시 취소 = 낙관락**(`orders.version`), 1건만 처리.
- **F6 부분취소 비례 배분**(쿠폰·포인트·배송비) 1원 단위.
- **F7 부분취소로 잔여 < 5만원 → 배송비 추가 청구**.
- **F16 주문 시점 가격·옵션·배송지·상품명 스냅샷 보존**.
- **F17 정산 귀속일 = `paid_at` 기준**.
- **F20 주문번호 = `ORD-YYYYMMDD-XXXXXX`**(일별 시퀀스 6자리).
- **격리 수준**: 주문 생성·취소·부분취소·자동취소 = SERIALIZABLE / 정산 = REPEATABLE READ.

### 2.3 상태 머신 (S0 §6.4 — partially_* 4종 확장)

```
pending → paid → preparing → shipping → (partially_delivered) → delivered → confirmed
   │        │        │            └→ partially_cancelled (일부 라인 취소)
   └→cancelled  delivered → partially_returned / partially_exchanged
```

라인 단위 진행은 `order_items.line_status`(active/cancelled/returning/returned/exchanging/exchanged)로 추적.

### 2.4 발행/구독 이벤트 (S0 §7)

- **발행**: `order.created`, `order.paid`, `order.cancelled`, `order.partial_cancelled`, `order.confirmed`, `order.status_changed`, `order.auto_cancelled`, `order.shipping_delayed`.
- **구독**: `payment.approved`, `payment.failed`, `payment.refunded`, `member.blacklisted`, `delivery.return_completed`, `delivery.exchange_completed`.

### 4.2 자동 구매확정 기간 (★ 정책 결정 근거)

- **카페24 톡체크아웃**: 배송완료일로부터 **8일** 후 자동 구매확정.
- **네이버페이/스마트스토어**: 배송완료일로부터 **8일** 째 자동 구매확정(배송추적 가능 택배 기준). 구매확정 요청 시 **5일** 후 자동. 배송추적 불가 시 발송 후 28일.
- **마켓 주문**: 7~14일.
- **우리 결정**: S0 정책값 **배송완료 후 7일**(P4) 유지하되, **관리자 설정 가능 항목으로 노출**(ORD-A-024). 한국 관행(8일)이 더 보수적이므로 운영자가 8일로 조정 가능하도록 기본값만 7일 고정.

  > 출처: [카페24 - 배송 후 자동 배송완료 설정](https://support.cafe24.com/hc/ko/articles/8462460998937), [카페24 - 네이버페이 주문 상태값 매칭](https://support.cafe24.com/hc/ko/articles/8468816039193), [온채널 - 스마트스토어 상황별 자동 구매확정일](https://m.onch3.co.kr/bbs_view.php?num=13&vnum=15479)

### 4.3 정산 기준

- **스마트스토어**: 구매확정·반품완료·교환완료일로부터 **1영업일 후** 정산.
- **우리 결정**: S0 F17(정산 귀속일 = `paid_at` 기준 일별 집계)을 **매출 인식 기준**으로 사용하되, **실 정산금(net_settlement) = sales − refund − pg_fee**(S0 `settlement_daily`)로 PG 정산과 분리. 분쟁/사기 의심 건은 `held_amount`로 보류(ORD-A-010).

  > 출처: [장사왕 - 스마트스토어 정산 가이드](https://www.sellerking.io/blog/스마트스토어-정산-가이드-빠른정산과-제로-수수료-22524), [getm8 - 스마트스토어 구매확정/정산](https://getm8.ai/ko/blog/)

### 4.4 주문번호 체계

- 한국 쇼핑몰 관행: 날짜 기반 + 일별 시퀀스(`YYYYMMDD-NNNNNN`)가 보편(주문 조회·CS 식별 용이).
- **우리 결정**: S0 F20 `ORD-YYYYMMDD-XXXXXX`(일별 시퀀스 6자리) 유지. Medusa native `display_id`(auto-increment)는 내부용, **`custom_display_id`에 한국형 주문번호 저장**(§6 매핑).

### 4.5 부분취소

- 한국 관행: 다품목 주문에서 일부 품목만 취소 시 **비례 배분 환불**(쿠폰·적립금·배송비 안분) + 무료배송 임계 미달 시 배송비 재청구가 표준.
- **우리 결정**: S0 F6·F7 그대로 적용. 반올림 정책(절상/절사/은행원)은 미결(S0 Q4) → §7 단계에서 결정 필요.

## 5. 종합 설계 결정

> 위 3개(우리 S0 + 성숙 플랫폼 + 한국 관행)를 종합. 충돌 시 **① 오류 없음 > ② 한국 친화 > ③ 코드 수렴** 우선순위.

### 5.1 상태 모델 결정 (단일 status 유지 + 파생 2축 표시)

- **결정 D1**: 우리 `orders.status`(11종) 단일 컬럼을 **권위 상태(source of truth)로 유지**.
  - 근거: Spree 6.0은 derived 방향이나 *아직 미구현(implementation not started)*. MVP는 명시적 컬럼이 운영·디버깅 단순. 단, Spree 경고("새 상태 추가는 마이그레이션에서 살아남지 못한다")를 수용해 **상태 추가는 동결**하고 라인 단위 세분화는 `order_items.line_status`로 흡수.
- **결정 D2**: 관리자 목록은 Spree 패턴 차용 — **결제 상태축(paid/balance_due/partially_refunded/refunded/failed) + 배송 상태축(ready/shipping/partial/delivered/cancelled)을 status에서 파생 표시**. DB 컬럼 추가 없이 뷰 레이어 계산(과설계 방지).

### 5.2 취소 모델 결정 (first-class history + 플래그 구동)

- **결정 D3**: `order_cancellations`(이미 append-only) + Spree 패턴 흡수 → 취소 레코드가 **`restock_items`(재고복구)·`refund_payments`(환불)·`notify_customer`(알림)** 의미를 한 SERIALIZABLE 트랜잭션에서 다운스트림 이벤트로 구동. 실패 시 전체 롤백(F1·F12).
- **결정 D4 (취소 사유 표준화)**: 취소 사유를 Spree/Shopify enum 차용 → `customer`(고객요청) / `inventory`(재고소진) / `fraud`(사기의심) / `staff`(관리자) / `expired`(미결제만료) / `other`. CS·정산 분류 용이.

### 5.3 멱등성·동시성 결정 (S0 그대로 + 검증)

- **결정 D5**: 멱등성 2계층(S0 §6.5.2) 그대로 — Level 1(주문생성·전체취소)=client UUID, Level 2(부분처리)=`{order_id}:{action}:{nonce}`.
- **결정 D6**: 낙관락(`orders.version`) + 시스템 race 자동 재시도(50ms×2), 사용자 의도 충돌 즉시 409(S0 §6.6). SERIALIZABLE serialization_failure(40001) 자동 재시도(S0 F-ISO-05).
- **결정 D7**: 라인 단위 락 — `UNIQUE(order_item_id, action_type) WHERE status IN (requested,approved,processing)`로 동일 라인 반품·교환 중복 차단(409 `LINE_ALREADY_IN_PROCESS`).

### 5.4 구매확정·정산 결정 (한국 법규 정합)

- **결정 D8 (구매확정)**: 수동 확정 + 자동 확정(배송완료 + N일, 기본 7일 관리자 조정 가능). 확정 시 `confirmed_at` + `order.confirmed` 이벤트(포인트 적립·등급 갱신 트리거). 멱등(이미 확정 시 skip, F11).
- **결정 D9 (청약철회와 분리)**: 한국 전자상거래법 §17 청약철회(배송완료 7일)는 **`legal-kr/withdrawal-7day` 모듈(기존 구현) 책임**. 주문은 `order.delivered` 발행만 → 모듈이 `WithdrawalEligibility`(eligible_until = delivered_at+7일) 자동 생성. 구매확정과 청약철회는 별개 라이프사이클(확정 후에도 §17 기간 내 철회 가능).
- **결정 D10 (정산)**: 일별 정산 배치(매일 03:00, `paid_at` 귀속, REPEATABLE READ) + 월 마감. net = sales − refund − pg_fee. 멱등(date PK UPSERT, F18). 보류(held_amount) = 분쟁/사기.

### 5.5 다건 교환 그룹 결정

- **결정 D11**: S0 `exchange_groups`(§2.6A) 유지 — Medusa native `Exchange`는 단건 중심이므로 **그룹 단위 일괄 처리·1회 회수 운송장·차액 합산**을 커스텀 모듈로 보강. Medusa `Exchange` N건을 group에 묶음(d18 `exchanges.group_id` FK).

## 6. Medusa 코드 매핑

> 격리 원칙: Medusa core(`@medusajs/order`) 엔티티 **무수정**. 확장 = `defineLink` + 커스텀 모듈. (기존 `src/links/order-withdrawal.ts` / `legal-kr/withdrawal-7day` / `state-machine` 패턴 준수)

### 6.1 ⓐ 활용할 Medusa native 모듈

| 우리 S0 요소 | Medusa native | 매핑 방식 |
|---|---|---|
| `orders` 본체 | `Order`(order_, display_id, version, status 6종, currency_code, metadata) | native 사용. 한국 status 11종은 `state-machine` 모듈로 별도 관리(§6.2), Order.status는 native 6종(pending/completed/canceled/draft/archived/requires_action) 유지. |
| order_no(`ORD-YYYYMMDD-XXXXXX`) | `Order.custom_display_id` | native 필드 활용 — 주문 생성 워크플로에서 일별 시퀀스 생성 후 set. native `display_id`는 내부 PK 보조. |
| `order_items` | `LineItem`(title/product_title/variant_sku/unit_price/compare_at_unit_price 스냅샷) | native 스냅샷 필드가 F16과 정합. `line_status`는 metadata 또는 커스텀 link로 보강. |
| 금액 합산 | `OrderSummary`(version별 totals) | native 사용 — 부분취소 시 버전 증가로 재계산. |
| 취소 | `cancelOrderWorkflow` + `Order.canceled_at` | native 워크플로 트리거. 상세 사유·플래그는 커스텀 `order_cancellations`(§6.2). |
| 변경 이력 | `OrderChange`/`OrderChangeAction` | 부분취소·교환을 OrderChange로 버저닝(adjustment versioning 패턴). |
| 반품/교환/클레임 | `Return`/`Exchange`/`Claim` + `createReturnWorkflow`/`createExchangeWorkflow` | native 사용. 다건 교환 그룹은 커스텀 `exchange_groups`로 묶음(§6.2). |
| 결제 트랜잭션 | `Transaction` | native — 결제 이력. PG 호출 자체는 payment 모듈(d17). |

### 6.2 ⓑ 필요한 커스텀 모듈 / defineLink / API route

**(1) state-machine 모듈 (★ 기존 구현 재사용 — 신규 작성 불필요)**

- 위치: `src/modules/state-machine/`(기존). `config/order.ts`에 ORDER_STATES + ORDER_TRANSITIONS 정의됨.
- **현 config가 S0 한국 status와 부분 정합** — Vendure 상태군(adding_items/arranging_payment/payment_authorized/payment_settled/partially_shipped/partially_delivered) + 한국 PG verify + 청약철회 4종 포함. **단, S0의 `preparing`/`confirmed`/`partially_cancelled`/`partially_returned`/`partially_exchanged`가 누락** → §7에서 config 보강 필요.
- 상태 전이 이력 = `StateHistory`(domain="order", entity_id=order.id). 우리 S0 `order_status_history`를 이 모듈로 흡수(중복 테이블 방지).

**(2) legal-kr/withdrawal-7day 모듈 (★ 기존 구현 재사용)**

- 위치: `src/modules/legal-kr/withdrawal-7day/`(기존). `WithdrawalEligibility`(delivered_at, eligible_until, is_eligible, disqualified_reason) + `order-delivered.ts` subscriber + `withdrawal-deadline-check.ts` job.
- link: `src/links/order-withdrawal.ts`(기존) — order ↔ WithdrawalEligibility(1:1) + WithdrawalReasonRecord(1:N).

**(3) order-settlement 커스텀 모듈 (신규)**

- 위치: `src/modules/order-settlement/`(신규). 모델: `SettlementDaily`(date PK, sales/refund/pg_fee/net_settlement, held_amount, batch_status).
- job: 일별 정산 배치(03:00) + 월 마감(매월 1일). `paid_at` 귀속 집계.
- link: order ↔ SettlementDaily(N:1, 집계는 date 단위이므로 직접 FK 아님 — query로 조회).

**(4) order-purchase-confirm 커스텀 모듈 (신규)**

- 위치: `src/modules/order-purchase-confirm/`(신규). 모델: `PurchaseConfirmation`(order_id, confirmed_at, confirm_type[manual/auto], policy_days).
- subscriber: `order.delivered` 수신 → 자동확정 예약. job: 배송완료+N일 자동확정 polling.
- link: order ↔ PurchaseConfirmation(1:1).

**(5) order-exchange-group 커스텀 모듈 (신규 — Tier1 §3.A)**

- 위치: `src/modules/order-exchange-group/`. 모델: `ExchangeGroup`(§2.6A — total_price_diff, diff_action, pickup_tracking_no, version).
- link: order ↔ ExchangeGroup(1:N), ExchangeGroup ↔ Medusa `Exchange`(1:N, exchanges.group_id).

**(6) order-idempotency (신규 — 인프라 공통)**

- 모델: `IdempotencyKey`(key PK, scope, request_hash, response, expires_at). middleware로 write API 전처리.
- *주: payment(d17)와 공유 가능 — 도메인 중복 방지 위해 공통 `infra-idempotency` 모듈로 추출 권장.*

**(7) API route (커스텀)**

| 종류 | route | 매핑 |
|---|---|---|
| Store | `POST /store/orders`(또는 cart complete 확장) | createOrderWorkflow + 한국형 4-way 검증·멱등 미들웨어 |
| Store | `POST /store/orders/:id/cancel` / `cancel-items` / `confirm` / `reorder` | 커스텀 워크플로(native cancelOrderWorkflow 래핑) |
| Admin | `/admin/orders/*`(목록·상세·status·force-cancel·bulk·memo·export) | native admin route 확장 + 커스텀 |
| Admin | `/admin/settlement/*`(daily·monthly·hold·export) | order-settlement 모듈 |
| Admin | `/admin/policies/order`(최소금액·자동취소·반품기간·구매확정·알림) | 정책 저장 모듈 |

### 6.3 ⓒ 마이그레이션 계획

| 단계 | 작업 | 영향 |
|---|---|---|
| M1 | state-machine `config/order.ts` 보강(preparing/confirmed/partially_* 추가) + seed UPSERT | core 무영향(커스텀 모듈 내) |

### 7.2 immediate (Phase 우선 — 주문 핵심 트랜잭션)

1. **state-machine config 보강**: `config/order.ts`에 `preparing`/`confirmed`/`partially_cancelled`/`partially_returned`/`partially_exchanged` 상태 + 전이 추가, seed 재실행. (M1)
2. **주문 생성 워크플로**: createOrderWorkflow 확장 — SERIALIZABLE + 4-way 금액 검증 + 재고/쿠폰/포인트 SELECT FOR UPDATE 차감 + `custom_display_id` 생성 + idempotency. (F1·F2·F20)
3. **idempotency 미들웨어**: write API 전처리(Level 1/2). (F-IDEM-01~06)
4. **전체/부분 취소 워크플로**: cancelOrderWorkflow 래핑 + `order_cancellations` 기록(사유 enum) + 비례 배분(F6) + 잔여 배송비 재청구(F7) + 낙관락. (D3·D4·D6)

### 7.3 다음 단계 (Phase 후속)

5. **order-purchase-confirm 모듈**: 수동/자동 구매확정(배송완료+7일 job) + `order.confirmed` 이벤트. (D8)
6. **order-settlement 모듈**: 일별/월별 정산 배치 + 보류 + 엑셀. (D10)
7. **order-exchange-group 모듈**: 다건 교환 그룹 + 1회 회수 운송장. (D11)
8. **관리자 API/화면**: 목록(파생 2축 표시 D2) + force-cancel + bulk + 정책 설정 + 대시보드.
