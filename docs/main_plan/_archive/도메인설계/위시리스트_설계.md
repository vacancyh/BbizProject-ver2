## 1. 도메인 개요

- **1줄 책임**: 회원의 상품 찜(wishlist) · 품절 상품 재입고 알림 구독 · 위시 → 장바구니 일괄 이동 · 위시리스트 공유.
- **포지션**: member·product 단순 연결 + product 도메인의 `product.restocked` 이벤트를 구독해 notification 도메인의 발송을 트리거하는 **저위험 보조 도메인**. 결제·재고 트랜잭션 위험 없음.
- **범위 경계 (in)**: 찜 추가/해제·목록 조회(실시간 재검증)·재입고 알림 구독/해제·장바구니 일괄 추가 호출·공유 링크 생성/조회·관리자 통계.
- **범위 경계 (out)**:
  - 알림 채널 선택·실제 발송 = **notification 도메인** 책임 (본 도메인은 발송 트리거만).
  - 재입고 감지(`product.restocked`) 이벤트 발행 = **product 도메인** (본 도메인은 구독만).
  - 장바구니 합산·재고 검증 = **cart 도메인** (본 도메인은 일괄 추가 호출만).
- **회원 전용 정책**: 위시리스트는 회원 전용(`00_개요.md §2 #8`). 비회원 하트 클릭 시 로그인 모달. (재입고 알림은 후술 §4 한국 관행에 따라 비회원 신청 허용 여부를 미결로 분리.)

## 2. 우리 S0 설계 요약 (d15 핵심)

### 2.1 엔티티 (4개)

| 엔티티 | 핵심 | 키 제약 |
|---|---|---|
| `wishlists` | 회원당 1건(1:1). `item_count` 캐시 | PK = member_id |
| `wishlist_items` | 위시 라인 = **상품 단위**(옵션 무관) | `UNIQUE(member_id, product_id)` |
| `restock_alerts` | 재입고 알림 구독. `sku_id` NULL 시 상품 전체 | `UNIQUE(member_id, product_id, COALESCE(sku_id, ...))` + 부분 인덱스(notified_at IS NULL) |
| `wishlist_share` | 공유 링크. `share_token`(32자 난수) + 30일 TTL | UNIQUE(share_token) |

### 2.2 핵심 룰 (S0 §6 발췌)

- F1 회원당 위시 1건 / F2 위시 = 상품 단위(옵션은 재입고 알림에서만 분리) / F3 중복 차단 + 하트 재클릭 = 해제.
- F4 회원당 최대 **200개**(P1, 2026-05-23 1,000→200 조정) / F7 목록 진입 시 실시간 단가·재고·상태 재검증.
- F6 **위시 해제 ≠ 재입고 알림 해제**(별도 row) / F9 발송 트리거 = `product.restocked` 이벤트, sku_id 매칭 우선·NULL 구독은 상품 단위 매칭.
- F10 채널 우선순위 = 알림톡 > 이메일 > SMS(P4) / F11 발송 완료 시 `notified_at` SET(멱등) / F12 비활성 회원 skip / F13 채널 동의 모두 OFF 시 구독 차단.
- F14 공유 토큰 난수 + 본인 식별자 미노출 + 30일 TTL / F15 공유 조회 = 읽기 전용 / F16 카트 일괄 이동 시 옵션 미선택 라인 = 옵션 선택 모달.

### 2.3 이벤트 (S0 §7)

- **발행**: `wish.added` / `wish.removed` / `wish.restock_subscribed` / `wish.restock_notified` / `wish.shared` / `wish.bulk_to_cart`.
- **구독**: `product.restocked`(핵심 트리거) / `product.sold_out` / `product.status_changed` / `member.withdrawn`(PII cascade) / `member.suspended` / `notification.send_failed`(notified_at 롤백·재시도).

### 2.4 미결 (S0 §8.2) — 본 설계에서 §5에 결정안 제시·잔여는 §7 이관

Q-WIS-01(200개 적정성)·Q-WIS-02(채널 우선순위)·Q-WIS-03(공유 TTL·짧은 URL)·Q-WIS-04(수동 발송 한도)·Q-WIS-05(카트 이동 옵션 처리)·Q-WIS-06(NOT-* QA ID 정식 부여).

## 3. 성숙 플랫폼 패턴 (외부참조)

> 위시리스트·재입고 알림은 Spree/Vendure/Medusa **모두 코어 native 미제공** = 커스텀/플러그인/확장으로 구현하는 것이 업계 표준입니다.

### 3.1 Medusa 공식 패턴 (가장 강한 근거 — 본 설계 직접 적용)

출처: `외부참조문서/메두사/메두사_www_apps_resources_app_plugins_guides_wishlist_page.mdx` (위시리스트 플러그인 가이드), `..._recipes_commerce-automation_restock-notification_page.mdx` (재입고 알림 레시피).

**(가) 위시리스트 — 플러그인 + 커스텀 모듈 패턴 (Medusa 공식 예제 그대로)**

- `Wishlist` 모델: `id` / `customer_id` / `sales_channel_id` / `items` hasMany. **`UNIQUE(customer_id, sales_channel_id)`** → 판매 채널당 위시 1건.
- `WishlistItem` 모델: `id` / `product_variant_id` / `wishlist` belongsTo. **`UNIQUE(product_variant_id, wishlist_id)`** → 중복 차단.
- **핵심 차이점**: Medusa 예제는 위시를 **variant(SKU) 단위**로 저장. 우리 S0 는 **상품 단위(F2)**. → §6에서 우리 룰(상품 단위) 우선 채택하되 Medusa 모델 필드명만 정합.
- **격리 방식**: `defineLink(..., { readOnly: true })` 로 Customer·SalesChannel·ProductVariant 와 링크. **링크 테이블 미생성**(readOnly) → 코어 무수정 격리. ← 우리 `legal-kr` 패턴과 동일 철학.
- **Workflow 패턴**: `createWishlistWorkflow`(중복 검증→생성, 보상함수 deleteWishlists) / `createWishlistItemWorkflow`(위시 존재·sales_channel·variant 중복·sales_channel 가용성 검증 → 생성 → 재조회). 각 step에 **compensation(롤백) 함수** 표준.
- **API 표준 경로**: `POST/GET /store/customers/me/wishlists`, `POST /store/customers/me/wishlists/items`. `/store/customers/me/*` = **인증 고객 전용**(`req.auth_context.actor_id`). publishable API key의 sales_channel 강제.
- **검증**: Zod 스키마 + `validateAndTransformBody` 미들웨어 (`@medusajs/framework/zod`, v2.13.0+).

**(나) 재입고 알림 — `restock-notification` 레시피 (Medusa 공식)**

- `RestockSubscription` 모델: `id` / `variant_id` / `sales_channel_id` / `email` / `customer_id`(nullable=게스트 허용). **`UNIQUE(variant_id, sales_channel_id, email)`**.
- **variant(SKU) + sales_channel 단위 구독** ← 우리 S0 `restock_alerts.sku_id` 와 정합(옵션별 알림).
- `createRestockSubscriptionWorkflow`: `getVariantAvailability` 로 **품절 검증**(재고>0이면 에러) → 기존 구독 있으면 update / 없으면 create (upsert).
- `sendRestockNotificationsWorkflow`: `getUniqueSubscriptions`(distinct variant+sc) → `getRestockedStep`(getVariantAvailability 재확인) → `useQueryGraphStep`(구독자 조회) → `sendRestockNotificationStep`(Notification 모듈 `createNotifications`, template `variant-restock`) → `deleteRestockSubscriptionStep`(발송 후 삭제, 보상함수=재생성).
- **스케줄 발송**: `src/jobs/check-restock.ts`, cron `0 0 * * *`(매일). ← 우리 S0 배치(UC-WIS-A-07) 와 정합.
- **Notification 모듈**: SendGrid/Resend(이메일) 또는 local(로그) provider. 한국은 알림톡/SMS provider 추가 필요(§6 후술).

> **중요 차이 — 발송 후 삭제 vs notified_at SET**: Medusa 레시피는 발송 후 **구독 row 삭제**. 우리 S0 F11 은 **`notified_at` SET(보존)**. 우리 안이 한국 관행(신청 내역 조회·CS 대응·재구독 이력)에 더 부합 → §6 에서 우리 안 채택.

### 3.2 Spree / Vendure (참고)

- **Spree**: 위시리스트 자체 가이드는 외부참조에 없음. 재고 관리는 `stock-levels`·`typed-stock-movements` 로 분리(출처: `스프리/스프리_docs_user_manage-products_stock-levels.mdx` 등). 재입고 알림 전용 도메인 문서는 외부참조 셋에 미수록 = **(추가 확인 필요)**.
- **Vendure**: 위시리스트는 `customer-accounts` storefront 가이드에서 고객 계정 부속 기능으로 언급(출처: `벤듀어/..._storefront_customer-accounts_index.mdx`). DB 엔티티 확장 패턴은 `database-entity` 가이드(출처: `벤듀어/..._database-entity_index.mdx`) = custom entity + plugin 확장 = Medusa 와 동일 철학.
- **공통 시사점**: 3개 플랫폼 모두 위시/재입고를 **코어 외부 확장**으로 둠 → 우리도 `legal-kr` 처럼 **커스텀 모듈 격리**가 정답.

## 5. 종합 설계 결정 (S0 + 성숙 플랫폼 + 한국 관행 종합)

### 5.1 엔티티·관계 최종안

S0 d15 §2 엔티티 4개를 **그대로 유지**하되, Medusa 모델 정합을 위해 아래를 확정합니다.

| 결정 | 내용 | 근거 |
|---|---|---|
| **D1. 위시 = 상품 단위** | `wishlist_items.product_id`(S0 F2). Medusa 예제의 variant 단위는 **미채택** | S0 F2 + 한국 찜 관행(상품 토글) |
| **D2. sales_channel 컬럼 추가** | `wishlists`/`restock_alerts` 에 `sales_channel_id` 추가 (Medusa 가용성·가격이 채널별) | Medusa wishlist/restock 공식 모델 (UNIQUE에 포함) |
| **D3. 재입고 = SKU 단위** | `restock_alerts.sku_id`(NULL=상품 전체). SKU 단위 = 한국 표준 | S0 §2.3 + 식스샵/무신사 관행 |
| **D4. 발송 후 보존(삭제 X)** | 발송 시 `notified_at` SET(S0 F11). Medusa 레시피의 row 삭제는 미채택 | 한국 신청 내역 조회·CS·재구독 이력 |
| **D5. 채널 우선순위 재정의** | **알림톡 > SMS > 이메일** (S0 F10 의 알림톡>이메일>SMS 에서 SMS·이메일 순서 교체) | 한국 관행(알림톡·SMS가 주, 이메일 부차) — §4.1 |

### 5.2 도메인 룰 최종 (S0 §6 + 한국 관행 조정)

- **유지(변경 없음)**: F1~F3, F6~F9, F11~F18 (S0 그대로).
- **F4 (최대 200개)**: 유지(P1, 운영 후 재조정 — Q-WIS-01).

- **신규 F19**: 재입고 자동 발송 시 **관리자 발송 허용 시간대(quiet hours) 적용** — 야간 발송 차단(카페24 PRO 관행). P7 정책 신설.
- **신규 F20**: 수동 일괄 발송 시 **일 발송 한도** 적용(스팸 방지, Q-WIS-04 결정 대기 → 기본 무제한, P8 정책).

## 7. 현 코드와의 관계 + 구현 단계

### 7.1 현 코드와의 관계

- **wishlist/restock 코드 = 미존재(green field)**. 코드베이스 확인 결과 `apps/backend/apps/backend/src/modules/` = `legal-kr` / `option-template` / `rma-extension` / `state-machine` 만 존재. → 신규 구현.
- **재사용할 패턴**: `legal-kr/withdrawal-7day` 의 (모듈 격리 + `defineLink` readOnly + `medusa-config.ts` resolve + `subscribers/` + `jobs/` + `migrations/`) 구조를 **1:1 답습**. 새 pattern이 아니라 검증된 패턴 복제 → 리스크 최소.
- **의존 도메인 선행 필요**: notification(알림톡/SMS provider) · product(`product.restocked` 이벤트 발행) · cart(bulk UPSERT) · member(status·채널 동의). 이들 미구현 시 본 도메인 일부 stub 필요.

### 7.2 구현 단계 (immediate / 다음 분리)

**[immediate — 본 도메인 자족 범위]**

1. `wishlist` 모듈 (Wishlist/WishlistItem 모델 + service + index) + `db:generate/migrate`.
2. `defineLink` 5종(readOnly) — 코어 무수정 검증.
3. `createWishlistWorkflow` / `createWishlistItemWorkflow`(F4 200개·중복 검증 포함) / `removeWishlistItemWorkflow` + `/store/customers/me/wishlists/*` API + Zod 미들웨어.
4. 목록 조회 시 실시간 단가·재고·상태 재검증(F7) — `useQueryGraphStep` + `getVariantAvailability`.
5. 단위 테스트(integration-tests 의 legal-kr `playwright` 패턴 참조).

**[다음 단계 — 의존 도메인 연동]**

6. `restock` 모듈 + `createRestockSubscriptionWorkflow`(품절 검증) + `/store/restock-subscriptions` API. (member 채널 동의 F13 의존.)

10. 관리자 API(통계·수동 발송·엑셀·CS 조회) + 감사 로그(S3).
11. `member-withdrawn` / `notification-send-failed` subscriber(PII cascade·발송 롤백).
