## 1. 도메인 개요

- **1줄 책임**: 결제 승인 · 환불 · 정산 · 이상 거래 탐지 · 카드 차단. 외부 PG(토스페이먼츠) 연동의 유일 창구.
- **범위 경계 (in)**: 결제 시작(initiate)·PG 결제창 호출·webhook 콜백 검증·승인 확정·멱등성 보장·환불(전체/부분)·이중 환불 방지·정산 배치·이상 거래 탐지·카드 블랙리스트·PG 수수료/할부 정책.
- **범위 경계 (out)**: 주문 상태 전이·재고 차감/복구·쿠폰/포인트 차감/복원 **실행**은 각 도메인 책임 (본 도메인은 이벤트 발행 + 트랜잭션 트리거만). 배송지·운송장은 d18 delivery. 청약철회 7일 환불 기산점은 `legal-kr/withdrawal-7day` 모듈이 산정(본 도메인은 환불 실행만).
- **핵심 정책 (S0 확정)**:
  - PG = **토스페이먼츠 단일**, 결제수단 = **카드 단일** (무통장·가상계좌·에스크로·간편결제·정기·해외 전면 Out-of-scope).
  - **회원 전용** (비회원 결제 불가).
  - 1 주문 1 결제 (분할 결제 없음).
  - 환불 = **카드사 취소 전표 발행 단일 경로** (PG cancel API → receipt_url 보존).

## 2. 우리 S0 설계 요약

> 출처: `05_도메인정의서/d17_결제.md`, `04_기능정의서/f14_주문_결제.md`

### 2.1 엔티티 (8개, 모두 커스텀 — Medusa native와 별도 운영. §6에서 매핑)

| 엔티티 | 책임 | 핵심 무결성 |
|---|---|---|
| `payments` | 결제 본체 (1 주문 1 결제) | `order_id` UNIQUE, `idempotency_key` UNIQUE, `version`(낙관락), 카드번호 마스킹+SHA256 해시만 저장 |
| `payment_webhooks` | PG 콜백 수신 로그 | `dedupe_key`(pg_transaction_id+event_type) UNIQUE, payload·signature INSERT 후 immutable |
| `refunds` | 환불 본체 (전체/부분) | `idempotency_key` UNIQUE, `idempotency_sub_key`(N회 부분환불 멱등) UNIQUE, `SUM(amount) ≤ payments.amount` CHECK + 트리거 |
| `payment_attempts` | 결제 시도 카운터 | 3회 실패 → 4회째 `blocked_until` 24h 차단 |
| `card_payment_blocks` | 카드 차단(블랙리스트) | `card_hash` 활성 1건 UNIQUE |
| `payment_anomalies` | 이상 거래 탐지 큐 | pattern(multi_cancel_24h/chargeback/large_amount/repeated_failure) |
| `pg_fee_rules` | PG 수수료 정책 | (method,pg) effective_to IS NULL 1건만 활성 |
| `installment_settings` | 할부 정책 | 단일 row 전역 설정 |

### 2.2 핵심 룰 (시스템 고정 — PCI/B-PAY 강제, 변경 금지)

- **F-PAY-01 4-way 금액 검증**: 장바구니 = 주문서 = 토스 결제창 = DB payments.amount. 불일치 422.
- **F-PAY-03 PG 콜백 5중 검증**: IP whitelist + HMAC 서명 + 타임스탬프 ±5분 + dedupe + amount.
- **F-PAY-04 Idempotency-Key 필수** (결제 시작·환불), 24h 응답 캐시.
- **F-PAY-05 webhook dedupe** (pg_transaction_id + event_type) UNIQUE.
- **F-PAY-06 카드번호·CVC 원문 절대 미저장·미로그** (마스킹 + SHA256만).
- **F-PAY-07 재고 차감 실패 → 즉시 자동 환불 + 주문 자동 취소** (원자).
- **F-PAY-08 쿠폰/포인트 차감 실패 → 결제 자동 롤백** (원자).
- **F-PAY-10 환불 트랜잭션 = 재고 복구 + 포인트 복구 + 쿠폰 복원 + PG 환불 원자성**.
- **F-PAY-11 환불 금액 ≤ 원결제 금액** (DB CHECK + BEFORE INSERT 트리거).
- **F-PAY-11A~F N회 부분 환불**: SERIALIZABLE + `SELECT FOR UPDATE on payments` + sub_key 멱등 + 누적 검증 트리거 3중 안전망.
- **F-PAY-12 이중 환불 방지**: PG 멱등키 + DB 낙관락.
- **F-PAY-18 포인트 100% 결제 → PG 미호출** (0원 직접 확정).
- 트랜잭션 격리: 결제 승인·환불 = **SERIALIZABLE**, 40001 serialization_failure → 50ms×2 자동 재시도.

### 2.3 발행 이벤트

`payment.approved` / `payment.failed` / `payment.refunded` / `payment.refund_failed` / `payment.anomaly_detected` / `payment.card_blocked` / `payment.card_unblocked` / `payment.zero_payment_confirmed`.

### 2.4 미결 (사장님 결정 필요)

S-Q11(점검 모드 콜백) · S-Q12(현금영수증) · S-Q13(세금계산서) · S-Q14(부분취소 반올림) · S-Q15("토스 MCP" 의미) · S-Q16(차지백 회원 자동 블랙리스트) · S-Q17(환불 SLA) · S-Q18(카드 OFF 정책).

## 3. 성숙 플랫폼 패턴

### 3.1 Medusa (코드베이스 본체)

> 출처: `외부참조문서/메두사/메두사_www_apps_resources_app_commerce-modules_payment_*`, `정의서/결제_09정의서.md`

- **PaymentCollection → PaymentSession → Payment → Capture/Refund** 흐름. 결제 컬렉션 1개가 cart/order 1개에 연결되고, 그 안에 N개의 결제 세션(시도 단위)이 있으며 승인 시 Payment 생성.
- **PaymentProvider 추상화**: `AbstractPaymentProvider`(`@medusajs/framework/utils`) 를 상속해 PG를 모듈로 등록. 다중 provider service를 한 모듈에 둘 수 있고, 각각 `pp_{identifier}_{id}` 형태 ID로 등록됨. (출처: `payment-provider/page.mdx`, `node_modules/@medusajs/utils/dist/payment/abstract-payment-provider.d.ts`)
- **authorize/capture 2단계 분리**: 승인(authorize)과 캡처(capture)가 분리되어 있어, 토스의 "승인=즉시 캡처" 단일 단계 카드 결제에 매핑 시 `authorizePayment`에서 바로 captured 상태를 반환하거나 webhook에서 `captured` action 반환.
- **Webhook 표준 라우트**: `/hooks/payment/{identifier}_{provider}` (out-of-the-box). 라우트가 main service의 `getWebhookActionAndData` → provider의 동명 메서드 호출. 반환 action이 `authorized`/`captured`면 Medusa가 세션 상태 전환 + cart 미완료 시 완료 처리. (출처: `webhook-events/page.mdx`)
- **Refund metadata**: v2.15.0부터 `refundPayment`에 `metadata`(reason·return_id 등) 저장 가능 → 한국 카드 취소 전표 URL·환불 사유 보존에 활용.
- **AbstractPaymentProvider 필수 구현 메서드 (확인)**: `initiatePayment` / `authorizePayment` / `capturePayment` / `cancelPayment` / `refundPayment` / `deletePayment` / `getPaymentStatus` / `retrievePayment` / `updatePayment` / `getWebhookActionAndData`.

### 3.2 Vendure

> 출처: `외부참조문서/벤듀어/벤듀어_docs_docs_guides_core-concepts_payment_index.mdx`

- **Authorization & Settlement 2단계** 개념 명확화. 단일 단계(authorize+capture 동시) vs 2단계(checkout 시 authorize, 배송 시 settle). → 본 프로젝트 카드 결제는 **단일 단계** (토스 승인 = 즉시 매출 확정) 채택 근거.
- **PaymentMethodHandler** (`createPayment`/`settlePayment`/`cancelPayment`) — Medusa의 AbstractPaymentProvider와 동형 패턴. createPayment 반환 state로 `Authorized`/`Settled`/`Declined` 분기.
- **Hosted payment page 패턴**: 카드 정보가 가맹점 사이트를 거치지 않고 PG가 직접 수집 → PG가 success/failure URL로 redirect POST → 사전 공유 secret으로 서명 검증. **토스 결제창(리다이렉트/SDK) 방식과 정확히 일치** → 가맹점은 카드 원문을 절대 보지 않음(F-PAY-06 자연 충족, PCI-DSS SAQ-A 수준).
- **Custom PaymentProcess (상태머신 확장)**: 새 Payment 상태("Validating") 추가 가능 → 본 프로젝트는 기존 state-machine 모듈(`src/modules/state-machine/config/payment.ts`)에 한국형 상태 전이를 정의하는 근거.

### 3.3 Spree

> 출처: `외부참조문서/스프리/스프리_docs_integrations_payments_stripe.mdx`, `스프리_docs_user_orders_refunding-orders.mdx`, `스프리_docs_user_settings_payments.mdx`

## 4. 한국 관행 (웹 근거)

> 본 절은 한국 PG·전자금융 실무 관행. 출처 URL은 토스페이먼츠 개발자 문서를 1차 기준으로 명시(2026-05 기준 일반 공개 문서). **세부 파라미터/IP 대역/서명 알고리즘은 연동 시점 공식 문서 재확인 필요** (추측 금지 — "(연동 시 확인)" 표기).

### 4.1 토스페이먼츠 연동 (1차 PG)

- **결제 위젯/SDK 방식**: 프론트가 토스 결제창(SDK `@tosspayments/payment-sdk` 또는 결제위젯)을 호출 → 사용자가 카드 입력 → 토스가 `successUrl`/`failUrl`로 리다이렉트하며 `paymentKey`·`orderId`·`amount` 전달. 출처: 토스페이먼츠 개발자센터 결제 연동 가이드 (`https://docs.tosspayments.com/guides/v2/payment-widget/integration`).
- **승인(Confirm) API**: 리다이렉트로 받은 `paymentKey` + `orderId` + `amount`를 서버가 `POST https://api.tosspayments.com/v1/payments/confirm` 으로 **서버 승인** 호출. 이때 **클라이언트 amount와 서버 DB amount 일치 검증이 필수**(4-way 검증의 핵심). 출처: `https://docs.tosspayments.com/reference#결제-승인`.
- **인증 헤더**: `Authorization: Basic base64(secretKey:)` (Basic 인증, secretKey 뒤 콜론). 출처: 토스페이먼츠 API 레퍼런스 인증 섹션.
- **멱등성**: 토스 승인/취소 API는 `Idempotency-Key` 헤더 지원 → 네트워크 재시도 시 중복 결제/환불 방지. 출처: `https://docs.tosspayments.com/reference/using-api/authorization` (멱등키 섹션). → 본 도메인 F-PAY-04·F-PAY-11B 정합.
- **카드 할부/무이자**: 승인 시 `cardInstallmentPlan`(할부 개월), 무이자는 카드사 이벤트 또는 가맹점 부담. 출처: 토스 결제 승인 응답 `card.installmentPlanMonths`. → `installment_settings`, `payments.installment_months`/`is_interest_free` 매핑.

### 4.2 PG Webhook (콜백) 보안

- **Webhook 이벤트**: 토스는 결제 상태 변경 시 등록된 webhook URL로 이벤트 전송(`PAYMENT_STATUS_CHANGED` 등). 출처: `https://docs.tosspayments.com/guides/webhook`.
- **서명 검증**: 토스 webhook은 본문 + 서명을 통해 위변조 검증(연동 시 정확한 헤더명/알고리즘 공식 문서 확인). 본 설계는 **방어적으로 5중 검증**(IP·서명·타임스탬프·dedupe·amount) 적용 → 서명 메커니즘이 약하더라도 amount 재검증·dedupe로 보강. → F-PAY-03 / F-WEBHOOK-01~05.
- **응답 200 원칙**: webhook 수신 측은 처리 성공/실패와 무관하게 빠르게 200 반환 + 내부 큐 재처리 → PG의 공격적 재전송 방지. (업계 표준, F-WEBHOOK-04 정합)

### 4.3 환불·부분취소

- **카드 취소 전표**: 카드 결제 취소 시 카드사 취소 승인 + 취소 전표(영수증) 발행. 토스 `POST /v1/payments/{paymentKey}/cancel` (`cancelAmount` 지정 시 부분 취소, 미지정 시 전체). 출처: `https://docs.tosspayments.com/reference#결제-취소`. → F-PAY-19 / `refunds.pg_refund_receipt_url`.
- **부분 취소 N회**: 토스는 한 결제건에 대해 누적 취소 금액이 결제 금액을 넘지 않는 한 N회 부분 취소 허용. 각 취소가 별도 거래로 기록. → F-PAY-11C(PG 호출 단위 = 부분 환불 신청 단위 1:1) 정합.
- **PG 수수료 처리**: 결제 후 익일(D+1) 부분 취소 시 PG 수수료 차감 정산 이슈 발생 → `pg_fee_rules` + PAY-A-024/025 정산 즉시 차감.

### 4.4 전자금융거래법·정산·세무 (한국 법령)

- **전자금융거래법**: PG는 전자금융업자 등록 의무 — 가맹점은 등록 PG(토스) 사용으로 충족. 결제·환불 기록 보존 의무(분쟁 대응). → `payment_webhooks` immutable + `refunds`/`payment_anomalies` 변경 이력 보존(S-PAY-04/05).
- **전자상거래법 §18 청약철회**: 재화 수령 후 7일 이내 청약철회 가능, 철회 시 3영업일 이내 환불. → `legal-kr/withdrawal-7day` 모듈이 기산점·기한 산정, 본 도메인은 환불 **실행**만. (출처: `정의서/결제_09정의서.md §6`)
- **PCI-DSS**: 토스 결제창(hosted) 방식 → 카드 원문이 가맹점 서버를 거치지 않음 → SAQ-A 수준. 마스킹+해시만 저장(F-PAY-06).
- **현금영수증/세금계산서**: 카드 결제 단일이라 현금영수증 의미 축소(미결 S-Q12/S-Q13). 카드 매출전표가 지출증빙 대체.

## 5. 종합 설계 결정

> 위 3개(S0 + 성숙 플랫폼 + 한국 관행)를 종합한 우리 설계. 근거 명시.

### 5.1 결제 흐름 (확정)

```
[주문 생성/결제 시작] POST /api/payments/initiate (Idempotency-Key 필수)
  → 4-way 금액 검증 1차 (DB amount == expected_amount)
  → 0원 결제(포인트100%)? → PG 미호출, 직접 confirmed (F-PAY-18)
  → 아니면 토스 결제 세션 생성 → toss_payment_url 응답 (201)
[사용자] 토스 결제창에서 카드 입력 → successUrl 리다이렉트 (paymentKey/orderId/amount)
[서버 승인] 토스 Confirm API 호출 (Idempotency-Key) → 승인 확정
[Webhook] POST /api/payments/webhook/toss
  → 5중 검증 (IP·서명·타임스탬프·dedupe·amount)
  → SERIALIZABLE 트랜잭션: payments.approved + 재고차감 + 쿠폰/포인트차감 + orders.paid
  → 실패 시 즉시 자동 환불 (F-PAY-07/08)
  → payment.approved 이벤트 (outbox)
```

**결정 D-01 (단일 단계 결제 채택)**: Vendure의 2단계(authorize/settle) 개념 중 **단일 단계**(승인=즉시 매출 확정) 채택. 근거 — 토스 카드 결제는 Confirm 시점에 매출 확정되며, 본 프로젝트는 배송 시 캡처 같은 2단계 운영 불필요(d17 §6.4 O-PAY). Medusa의 `authorizePayment`가 곧바로 `captured` 처리 또는 webhook `captured` action 반환.

**결정 D-02 (승인 이중화 — Confirm + Webhook)**: 토스 redirect 후 서버 Confirm API로 동기 승인하되, webhook을 **정합성 안전망**으로 병행. redirect 유실(브라우저 종료)·Confirm 타임아웃 시 webhook으로 복구. 둘 다 동일 `pg_transaction_id` dedupe로 1회만 반영. 근거 — f14 §3.3 컨테이너 재시작/콜백 유실 시나리오 + Medusa webhook-events "프론트 중단 시 webhook이 주문 없이 결제 처리됨" 경고.

**결정 D-03 (4-way → 실질 3축 + amount 4축)**: 장바구니/주문서/토스창은 프론트 표시, **서버 신뢰 축은 DB payments.amount**. Confirm 호출 시 amount 검증 + webhook payload.amount 재검증으로 변조 차단. 근거 — 토스 Confirm API의 amount 불일치 검증 권고 + B-PAY-001.

### 5.2 멱등성·동시성 (확정)

| 지점 | 메커니즘 | 근거 |
|---|---|---|
| 결제 시작 | `payments.idempotency_key` UNIQUE + 24h 캐시 + 토스 `Idempotency-Key` 헤더 전달 | F-PAY-04, 토스 멱등키 |
| Webhook | `payment_webhooks.dedupe_key`(pg_tx+event) UNIQUE | F-PAY-05 |
| 환불 | `refunds.idempotency_key` + N회 부분환불 `idempotency_sub_key`(`{order_id}:{action}:{nonce}`) | F-PAY-11B |
| 동시 환불 | SERIALIZABLE + `SELECT FOR UPDATE on payments` + `version` 낙관락 + 누적 트리거 | F-PAY-11A/12 |
| 재고 race | webhook 트랜잭션 내 `UPDATE ... WHERE stock>=qty` 원자, 0행 시 자동환불 | F-PAY-07 |

### 5.3 보안 결정

- **D-04 5중 webhook 검증**: 토스 서명 검증을 신뢰하되, IP whitelist(토스 IP 대역 — 연동 시 확인) + 타임스탬프 ±5분(replay) + dedupe + **amount 재검증**을 추가. amount 재검증이 최종 방어선. 근거 — F-WEBHOOK-01~05.
- **D-05 카드 데이터 격리**: 토스 hosted 결제창으로 카드 원문이 서버 미경유 → 저장은 마스킹(`****-****-****-1234`) + SHA256 해시(`card_hash`, 블랙리스트 매칭용)만. 로그에 카드번호·CVC·paymentKey 평문 미기록. 근거 — F-PAY-06, PCI-DSS SAQ-A.
- **D-06 관리자/사용자 JWT 분리**: 관리자 환불·카드차단 = admin JWT, PG webhook = 서명 검증(JWT 무관). 근거 — S-PAY-03.

### 5.4 환불·정산 결정

- **D-07 환불 단일 경로**: 모든 환불 = 토스 `cancel` API → 카드사 취소 전표(`receipt_url`) 보존. 부분 환불은 `cancelAmount` 지정 N회 호출, 각 호출 = 1 refunds row. 근거 — F-PAY-11C/19, 토스 cancel API.
- **D-08 환불 원자 트랜잭션**: PG 환불 성공 후 재고복구+포인트복구+쿠폰복원 원자 처리, 일부 실패 시 전체 롤백 + 관리자 알림. PG 환불 실패 시 재시도 큐(최대 5회, 매 10분) + 재고 복구 보류. 근거 — F-PAY-10/13.
- **D-09 정산 배치**: 매일 03:00 `settlement_daily` UPSERT (매출 − 환불 − PG수수료 = 순정산), d16 정산과 연동. 멱등(date PK). 근거 — F-PAY-22.

### 5.5 미결 처리 방침

미결 8건(S-Q11~18)은 **설계 보류 항목**으로 명시하고 기본 동작(가장 안전한 보수적 정책)으로 구현 후 사장님 결정 시 토글. 예: S-Q17 환불 SLA = 우선 "영업일 기준 3일 이내"(전자상거래법 하한) 표시. S-Q14 반올림 = 우선 "절사(고객 유리)" + d16 통합 결정 대기.

### 7.2 구현 단계

**immediate (Phase 1 — 결제 핵심 경로)**
1. `payment-toss` Provider 모듈 골격 + `AbstractPaymentProvider` 10개 메서드 stub + 토스 client(confirm/cancel).

7. 환불(전체/부분 N회) — SERIALIZABLE + sub_key 멱등 + 누적 트리거(F-PAY-11A~F) + 카드 취소 전표 보존.
