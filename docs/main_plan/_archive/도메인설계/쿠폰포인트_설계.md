## 1. 도메인 개요

- **1줄 책임**: 쿠폰 발급/사용/복원 + 포인트 적립/사용/소멸을 회계 원장(INSERT-only) 기반으로 무결하게 관리합니다.
- **범위 경계 (in)**:
  - 쿠폰 정책 마스터 CRUD · 발급(가입/생일/등급/이벤트코드/일괄) · 결제 직전 할인액 산출 · 주문 취소 시 원자적 복원 · 만료 배치 · 강제 회수
  - 포인트 적립(구매확정/리뷰/가입/생일/출석/추천) · 사용(결제) · 소멸(FIFO) · 관리자 수동 지급/차감 · 잔액 정합성 감사
- **범위 경계 (out)**:
  - 결제 승인·환불 PG 호출 = d17 payment (본 도메인은 `coupon.used` / `point.used` 이벤트만 발행)
  - 주문 상태 전이 = d16 order
  - 알림 발송 = notification 도메인
  - 환금·송금·양도·선물 = 전자금융거래법 규제 영역 (MVP out, d20 §8.1 O3/O4)
- **핵심 불변식 3중 방어** (f18 §1.비즈니스 목적 인용):
  1. 회계 원장(point_transactions = INSERT only, balance 직접 UPDATE 금지)
  2. 잔액 음수 금지 (DB CHECK `balance >= 0`)
  3. 멱등성 보장 (`idempotency_key UNIQUE`)

## 2. 우리 S0 설계 요약

### 2.1 엔티티 (d20 §2)

| 엔티티 | 책임 | 핵심 제약 |
|---|---|---|
| `coupons` | 쿠폰 정책 마스터 | code 16자 UNIQUE, type=AMOUNT/PERCENT, target=ALL/CATEGORY/PRODUCT, issue_trigger=SIGNUP/BIRTHDAY/GRADE_UP/MANUAL/EVENT_CODE |
| `coupon_issues` | 개별 발급 이력 | status=issued/used/expired/cancelled, UNIQUE(coupon_id, member_id, issued_at), used 시 discount_amount 박제 |
| `points` | 회원 포인트 잔액 캐시 | PK=member_id, balance CHECK>=0, version(낙관락) |
| `point_transactions` | 포인트 원장(INSERT only) | type=EARN/USE/EXPIRE/CANCEL/ADMIN_ADJUST, balance_after, expires_at, idempotency_key UNIQUE |
| `coupon_codes` | 이벤트 코드(1코드 N회) | PK=code, max_uses/used_count 낙관락 |
| `point_policies` | 정책 스냅샷(d21 미러) | key/value JSONB (적립률·소멸기간·max_use_ratio·보너스) |

### 2.2 핵심 룰 (d20 §6 / f18 §4.2 — F1~F20 발췌)

- **쿠폰**: F1(16자 랜덤 code) · F2(1발급 1사용) · F3(stackable=false 1주문 1쿠폰) · F4(전체취소 시 만료 전만 복원) · F5(만료 쿠폰 미복원) · F6(만료 배치 00:30 KST) · F7(per_user_limit) · F8(usage_limit 낙관락)
- **포인트**: F10(balance 직접 UPDATE 금지) · F11(NEVER 음수 DB CHECK) · F12(적립 멱등) · F13(소멸 FIFO) · F14(사용 = USE INSERT + 낙관락 단일 트랜잭션) · F15(100% 사용 시 PG 미호출) · F16(취소 시 CANCEL INSERT 복원)
- **결합**: F19(사용·환불·취소·회수 = 주문/결제와 단일 DB 트랜잭션, 분산 트랜잭션 X) · F20(산출 순서: 상품금액→쿠폰→포인트→배송비→최종)
- **격리**: 결제 차감/적립/복원/소멸 = SERIALIZABLE, 조회 = READ COMMITTED + SELECT FOR UPDATE (d20 §6.5)

### 2.3 이벤트 (d20 §7)

- **구독**: member.signed_up/birthday_today/grade_changed, order.purchase_confirmed/cancelled, review.approved/deleted

## 3. 성숙 플랫폼 패턴

### 3.1 Medusa Promotion Module (native, v2.15.3)

출처: `외부참조문서/메두사/..._promotion_concepts_page.mdx`, `..._application-method_page.mdx`, `..._campaign_page.mdx`, 실제 패키지 `node_modules/@medusajs/promotion/dist/models/`

- **데이터 모델 (실측)**: `promotion`, `promotion-rule`, `promotion-rule-value`, `application-method`, `campaign`, `campaign-budget`, `campaign-budget-usage`
- **Promotion**: type=`standard`/`buyget`, `code`(쿠폰코드), `status`, `limit`(v2.12.0+ 전체 사용 한도)
- **ApplicationMethod**: `type`=fixed/percentage, `target_type`=items/shipping_methods/order, `allocation`=each/across/once(v2.11.0+), `max_quantity`
- **PromotionRule**: `attribute`(예: customer_group_id, customer_id) + `operator`(eq/in 등) + `PromotionRuleValue`(값 N개). 카트 속성과 매칭하여 적용 여부 결정 → **카테고리/상품/첫구매 한정** 구현 가능 (`target_rules`)
- **Campaign + CampaignBudget**: `spend`/`usage` global budget + `use_by_attribute`(customer_id/customer_email) attribute budget(v2.11.0+) → **선착순 한도·계정당 한도** 구현 가능
- **배울 점**: 정률/정액·카테고리한정·중복(stackable)·전체한도·계정당한도·VIP그룹한정이 **모두 native 모델로 표현 가능** → 우리 `coupons` 정책 마스터는 Promotion으로 매핑.

### 3.2 Medusa Loyalty Points 패턴 (커스텀 모듈 튜토리얼)

출처: `..._how-to-tutorials_tutorials_loyalty-points_page.mdx`

- 포인트는 native 미존재 → **커스텀 `loyalty` 모듈** 권장 (`model.define`, `MedusaService` CRUD + `addPoints`/`deductPoints`/`getPoints`)
- 포인트 사용 = **동적 promotion 생성**(customer_id rule) → 카트에 적용 → `order.placed` 구독자가 차감/적립, 충돌 방지 위해 **`acquireLockStep`/`releaseLockStep`** 사용
- step **compensation 함수**로 실패 시 자동 롤백 (포인트 복원/차감 되돌림) → 우리 F19(단일 트랜잭션 원자성) 정합
- **배울 점**: 커스텀 모듈 + 워크플로우 + 구독자 + step compensation 패턴이 우리 적립/사용/복원 흐름과 1:1 대응. 단, 튜토리얼은 단순 `points` 단일 컬럼 → 우리는 **원장(transactions) + 잔액 캐시 + 소멸(expires_at)** 으로 강화 필요.

### 3.3 Medusa Store Credit / Spree Store Credit (loyalty plugin)

출처: `..._store-credit_concepts_page.mdx`, `스프리/..._assign-store-credits.mdx`

- **`StoreCreditAccount` + `AccountTransaction`(type=credit/debit, reference/reference_id)**: 잔액을 DB에 직접 저장하지 않고 **transaction SUM으로 실시간 계산** → 우리 `point_transactions` 원장 + 정합성 감사(balance vs SUM) 설계의 권위 있는 선례
- Spree store credit = 환불·보상·로열티 리워드, customer 종속·양도 불가 → 우리 "회원 전용 · 환금 불가" 정책과 정합
- **배울 점**: "잔액 = 원장 합계" 원칙은 성숙 플랫폼 공통. 우리는 **잔액 캐시(`points.balance`) + 원장(`point_transactions`)** 이중 구조 + 일 1회 감사로 정합성 보강 (캐시는 성능, 원장은 진실의 원천).

### 3.4 Medusa First-Purchase Discount

출처: `..._first-purchase-discounts_page.mdx`

- 첫구매 할인 = promotion(code) + **커스텀 validation**(구매 이력 검증) + 첫주문 여부 카트 체크

## 5. 종합 설계 결정

> 3개 출처(S0 / 성숙 플랫폼 / 한국 관행)를 종합한 우리 설계. 근거 명시.

### 5.1 쿠폰 = Medusa Promotion native 활용 + 한국 확장 래퍼

- 우리 `coupons` 정책 마스터를 **Medusa `Promotion`** 으로 매핑:
  - `type=AMOUNT` → application_method.type=`fixed`, `type=PERCENT` → `percentage`
  - `target=ALL` → target_type=`order`, `target=CATEGORY/PRODUCT` → target_type=`items` + `target_rules`(PromotionRule attribute=product.categories.id / variant.product_id)
  - `min_order_amount` → PromotionRule attribute=`items.total` operator=`gte`
  - `max_discount`(정률 상한) → 한국 관행 필수이나 Medusa application_method에 native 상한 없음 → **커스텀 hook으로 산출 단계에서 min() 적용** (§6 매핑)
  - `usage_limit` → Promotion `limit` 또는 Campaign global `usage` budget
  - `per_user_limit` → Campaign attribute budget `use_by_attribute=customer_id`
  - `stackable` → 우리 코어 검증(stackable=false 시 1주문 1쿠폰, Medusa는 기본 다중 적용 → 적용 단계 가드)
  - `issue_trigger` → 우리 커스텀 발급 워크플로우(promotion은 정책, 발급 인스턴스는 우리 `coupon_issues`)
- **`coupon_issues`(개별 발급 이력)는 커스텀 모듈 유지**: Medusa promotion은 "정책 + 사용 카운트"만 관리하고, "누가 언제 발급받았고 어느 주문에 썼는지"의 한국형 쿠폰함 모델(보유/사용됨/만료됨 탭)은 native 미흡 → 우리 `coupon_issues` 원장으로 보강.

### 5.2 포인트 = 커스텀 `loyalty-point` 모듈 (원장 기반)

- Medusa loyalty 튜토리얼 + store-credit 원장 패턴을 결합한 **커스텀 모듈** (native 미존재):
  - `points`(잔액 캐시 + version 낙관락) + `point_transactions`(INSERT-only 원장 + expires_at + idempotency_key)
  - store-credit식 "잔액 = SUM(transactions)" 진실 원천 + 성능용 캐시 컬럼 + 일 1회 정합성 감사(F-AUDIT)
  - 적립/사용/복원/소멸 = 워크플로우 step + compensation(롤백) — 단, F19에 따라 **주문/결제 도메인과 단일 DB 트랜잭션** 내 호출(분산 트랜잭션 회피)
- **소멸 FIFO**: EARN row별 remaining 추적(EARN 후 USE/EXPIRE/CANCEL 차감 합산) → 가장 오래된 expires_at 우선 EXPIRE INSERT (d20 f18 §3.6 의사코드 채택)

### 5.3 무료배송 쿠폰 (한국 관행 추가 결정)

- 한국 표준(카페24 6종 혜택)에 무료배송 쿠폰 존재 → 우리 S0 `type` ENUM은 AMOUNT/PERCENT 2종
- **권장**: `coupons.type`에 `FREE_SHIPPING` 추가 또는 별도 target_type=`shipping_methods` promotion 활용. Medusa는 shipping_methods target native 지원 → **Medusa promotion target_type=shipping_methods로 매핑, 우리 ENUM 확장 불필요**. 단 S0 ENUM 미정의 항목이므로 **사장님 확인 필요(신규 미결)**.

### 5.4 포인트 사용 단위·비율 정합 (S0 내부 불일치 정리)

- **불일치 발견**: d20 §6.2 P6 = "10P 단위", f18 §2.4/§4.1 = "10P 단위" 이나 d20 §3.1 UC-CPN-U-14 = "최소 1,000P, 100P 단위" 로 단위가 10P vs 100P 혼재.
- 한국 관행(CJ ONE) = 최소 1,000P + 10P 단위.
- **권장**: 최소 사용 1,000P + **10P 단위** 로 통일(P6 기본값 10P 채택, 정책 변경 가능). UC-CPN-U-14의 "100P 단위"는 오기로 판단 → **사장님 확인 필요(S0 정합 미결)**.

### 5.5 max_use_ratio (Q1 권장 박제)

- §4.3 한국 표준 = 50% → `point.max_use_ratio` 기본값 **0.5** 권장. 검증: `point_used <= payment_amount * max_use_ratio`. F15(100% 사용 PG 미호출) 예외 경로 보존.

### 5.6 정합성·동시성 (오류 없음 대전제)

- 포인트 사용/적립/복원/소멸 = SERIALIZABLE + `points` SELECT FOR UPDATE + version 낙관락
- 멱등키 표준(f18 §5.5): `{order_id}:EARN`, `{order_id}:USE`, `{order_id}:CANCEL_USE`, `{order_id}:CANCEL_EARN`, `{member_id}:SIGNUP`, `{member_id}:BIRTHDAY:{year}`, `review:{review_id}:EARN`, `earn:{earn_row_id}:EXPIRE`
- serialization_failure(40001) → 50ms × 2회 자동 재시도 (F-ISO-05)
- 일 1회 정합성 감사: 포인트 03:00 KST (balance==SUM), 쿠폰 03:30 KST (used 시 used_order_id NOT NULL), 불일치 시 알람 + 검토 큐

## 6. Medusa 코드 매핑

> `legal-kr/withdrawal-7day` 격리 패턴 준수 = **Medusa 코어 entity 무수정**, 커스텀 모듈 + `src/links/` defineLink + subscriber + workflow + api route 로만 확장.

### ⓐ 활용할 Medusa native 모듈

| native | 활용 | 비고 |
|---|---|---|
| **Promotion Module** (`@medusajs/promotion` v2.15.3) | 쿠폰 정책 마스터(정률/정액/카테고리한정/무료배송/VIP그룹한정) | `createPromotionsWorkflow`, `updatePromotionsStep`, PromotionRule/ApplicationMethod |

### ⓒ 마이그레이션 계획

1. `loyalty-point` 모듈 모델 정의 → `npx medusa db:generate loyalty-point` → `db:migrate`
2. `point_transactions`에 `idempotency_key UNIQUE` + `expires_at` 부분 인덱스(type=EARN), `points.balance CHECK >= 0` DB 제약 명시 (DML default 외 raw SQL 보강 필요 가능)
3. `medusa-config.ts` modules 배열에 `{ resolve: "./src/modules/loyalty-point" }` 추가
4. `src/links/order-coupon-point.ts` 추가 후 `db:migrate`(link 테이블 생성)
5. 시드: point_policies 기본값(적립률·소멸365·max_use_ratio 0.5·보너스) + 샘플 promotion(신규가입/생일/이벤트)

## 7. 현 코드와의 관계 + 구현 단계

### 7.1 현 코드와의 관계

- **현재 상태**: backend `src/modules/`에 쿠폰·포인트 관련 커스텀 모듈 **없음**(legal-kr/rma-extension/state-machine/option-template만 존재). 본 도메인은 **신규 구현**.
- **격리 선례**: `legal-kr/withdrawal-7day`가 모델+service+migrations+subscribers+jobs+utils 구조 + `src/links/order-withdrawal.ts` defineLink로 코어 무수정 확장을 이미 구현 → **동일 패턴 그대로 적용**.
- **native promotion**: 코어 자동 로드되므로 별도 등록 불필요. 단 쿠폰 "발급 이력/쿠폰함" 한국형 요구는 커스텀 모듈로 보강(promotion만으로 부족).
- **포인트**: native·plugin 모두 미설치 → 자체 원장 모듈 필수.

### 7.2 구현 단계

**immediate (1차 — 포인트 원장 코어)**:
1. `loyalty-point` 모듈 골격(point-account / point-transaction 모델 + service CRUD) + 마이그레이션 + DB CHECK/UNIQUE 제약
2. 적립 워크플로우(order.purchase_confirmed 구독, 등급별 적립률, 멱등키) + 사용 워크플로우(결제 차감, SERIALIZABLE, FOR UPDATE)
3. 사용자 조회 API(`store/points`, `store/points/transactions`) + 잔액 캐시 정합

**다음 단계 (2차 — 쿠폰 + 복원 + 배치)**:
4. coupon-issue / coupon-code 모델 + Promotion native 매핑(정책 생성 워크플로우) + 발급 트리거 구독자(SIGNUP/BIRTHDAY/GRADE_UP/EVENT_CODE)
5. `store/coupons/*` + 결제 적용(applicable 산출, max_discount min() hook, stackable 가드)
6. 복원 워크플로우(order.cancelled 구독, 만료 전만 쿠폰 복원 + 포인트 CANCEL/EARN 회수) + 소멸/만료/감사 배치 jobs
7. `src/links/order-coupon-point.ts` defineLink

**3차 (관리자 + 정합성)**:
8. 관리자 API + admin widget(일괄발급 dry-run·진행률, 포인트 수동지급 사유필수, 강제회수 409 가드, SUPER 이중확인)
9. 정합성 감사 배치(balance vs SUM) + 알람/검토 큐 + AuditLog

**미결 선결 의무 (사장님 결정 필요 — 구현 전 확정)**:
- Q1 max_use_ratio (권장 0.5) / Q2 리뷰삭제 회수 잔액부족(권장 가능한 만큼) / Q3 소멸포인트 환불복원 / Q4 발급후 정책수정 영향(권장 신규분만) / Q5 본인 쿠폰폐기 / Q6 만료 알림
- §5.3 무료배송 쿠폰 ENUM/매핑 / §5.4 포인트 단위 10P vs 100P 정합 — **S0 내부 불일치 → 사장님 확인 필요**
