## 1. 현재 상태 (2026-05-31)
- 상품 등록 화면(`/app/product-mgmt`)에서 **클라이언트 검증**은 구현됨: 게시(published) 시 상품군(분류)의 고시 필수항목 누락 → 등록 차단 + 토스트. (라이브 검증 완료)
- **한계**: 클라이언트 검증은 admin API를 직접 호출(curl/스크립트)하면 우회 가능. 전자상거래법 정합(대전제 ①오류없음)을 위해 **서버사이드 강제**가 필요.

## 2. 목표
상품이 `status=published`(공개)로 생성·수정될 때, **서버에서** 해당 상품군(분류)의 고시 필수항목(`product_type_disclosure_field.required=true`)이 `product.metadata.kr_disclosure`에 모두 채워졌는지 검증하고, 누락 시 **422로 차단**.

## 3. 구현안 (택1, 권장 = A)

### A. API 미들웨어 (권장)
- `src/api/middlewares.ts`에 `POST /admin/products`·`POST /admin/products/:id`(및 `/admin/products/:id` PATCH) 대상 미들웨어 등록.
- 로직: 요청 body의 `status==='published'`(또는 기존 draft→published 전이)일 때
  1. `metadata.kr_product_type_id`로 상품군(분류) 조회 → `product-type` 서비스 `listProductTypeDisclosureFields({type_template_id})`.
  2. `required=true` 필드 중 `metadata.kr_disclosure[field_key]`가 빈 값이면 → `MedusaError(INVALID_DATA)` throw → 422.
- 장점: 생성·수정 모두 단일 지점 차단. 코어 라우트 로직 무수정(미들웨어만 추가).

### B. 구독자(subscriber) 보정 (보조)
- `product.created`/`product.updated` 구독 → published인데 고시 누락이면 status를 draft로 되돌리고 관리자 알림.
- 단점: 사후 보정이라 순간적으로 노출될 수 있음(차단 아님). A의 보조로만.

## 4. 검증 시나리오
- curl로 `metadata.kr_disclosure` 없이 `status=published` POST → **422** 확인.
- 정상(전 필수 채움) → 201.
- draft 생성은 검증 면제(작성 중 저장 허용).

## 5. 주의
- 상품군(분류) 미지정(`kr_product_type_id` null) 상품의 published 허용 여부 = 정책 결정 필요(권장: 경고만, 차단 X — 기존 상품 호환). 추후 전 상품 상품군 필수화 시 강제.
- Medusa product 생성은 워크플로우 기반이라, 미들웨어에서 body 검증이 가장 단순·확실.
