> 표준 템플릿: `_README_설계템플릿.md` 의 7개 표준 섹션 순서 고정.

## 1. 도메인 개요·책임 범위

- **1줄 책임**: 주문 이후 실물 처리 — 배송지 관리 · 운송장 발급·추적 · 배송비 정책 · 자동 구매확정 · 반품/교환 라이프사이클 (전자상거래법 청약철회 포함).
- **포지션**: order 도메인의 "배송" 단계를 전담. payment 와는 독립이나 반품·교환 시 환불 트리거 이벤트를 발행. 재고 복구는 product 도메인이 처리 (본 도메인은 이벤트 발행).
- **회원 전용**: 배송지·반품·교환 신청은 회원 전용. 비회원 송장 조회 미적용 (`d18 §1`).
- **책임 경계 (out)**: ⓐ 환불 PG 호출 = payment 도메인 ⓑ 재고 복구 = product 도메인 ⓒ 주문 상태 전이 최종 확정 = order 도메인 (본 도메인은 트리거 발행).
- **범위 (in)**: 배송지 CRUD · 운송장 단건/CSV/분할(1주문 N운송장) 등록 · 택배사 webhook·풀링 추적 · 배송비 산정(지역별/조건부 무료) · 자동 구매확정 배치 · 반품·교환·청약철회 처리 · 검수·환불 트리거.

## 2. 우리 S0 설계 요약

> 출처: `05_도메인정의서/d18_배송.md` · `04_기능정의서/f15_배송_추적.md` · `f16_취소_반품_교환.md`

### 2.1 엔티티 (d18 §2)

| 엔티티 | 역할 | 핵심 |
|---|---|---|
| `addresses` | 회원 배송지 | 회원당 활성 10건 한도(P1), 기본 배송지 부분 UNIQUE, region_type 자동 분류(normal/jeju/mountainous), 소프트 삭제 |
| `deliveries` | 주문별 배송 (1:1) | order 단위 status 집계, address_snapshot(JSONB), courier/tracking_no, auto_confirm_due_at |
| `shipments` / `shipment_items` | 1주문 N운송장 (분할 배송) | 실 운송장 단위 추적, `UNIQUE(order_item_id) WHERE active`, 합계 qty = order_items.quantity 검증 |
| `shipment_tracking` | 택배사 추적 이력 | `UNIQUE(order_id, event_at, event_code)` webhook 멱등, webhook_payload(JSONB) 90일 보관 |
| `returns` | 반품 | item_ids, reason enum, status 머신, inspection_result(good/defective), return_shipping_fee_charged |
| `exchanges` / `exchange_groups` | 교환(+다건 그룹) | new_sku_id, price_diff, 그룹 1회 회수 운송장 |
| `delivery_fee_policy` | 배송비 정책 (싱글톤) | free_threshold 50000 / base 3000 / jeju 3000 / mountainous 5000 / return 3000 |

### 2.2 핵심 룰 (d18 §6 / f15 §4 / f16 §4)

- **F8/F9**: 운송장 택배사별 정규식 검증 → 등록 시 preparing→shipping + `delivery.shipping_started` 발행.
- **F10**: 배송 상태 단방향 전이 (preparing → shipping → delivered → confirmed). 역순 차단.
- **F12/F13**: webhook 멱등 (UNIQUE) + 서명 검증 실패 401 / 중복 200 OK.
- **F14**: 배송완료 webhook → delivered + auto_confirm_due_at = delivered_at + P3 + `delivery.delivered` 발행.
- **F16/F17**: 반품 가능 기간 = delivered_at + P2(기본 7일), 단순변심 = 회수 배송비 소비자 부담.
- **F18**: 검수 양호 = 재고 복구 / 불량 = 미복구 + `return.completed` 발행 (환불 트리거).
- **F25~F29**: 1주문 N운송장 분할 배송 + partially_delivered 상태.
- **F31~F38** (v4 신규): 동시성·일괄·원자성 8종 — 동시 반품 독립 트랜잭션, 검수→환불→재고 3단계 원자성(PG 실패 시 롤백·"환불대기"), 교환 재고 소진 처리 등.

### 2.3 핵심 이벤트 (d18 §7)

발행: `delivery.shipping_started` · `delivery.delivered` · `delivery.delayed` · `return.requested/approved/completed/rejected` · `exchange.requested/completed` · `delivery_policy.changed`.
구독: `order.paid`(deliveries INSERT) · `order.partial_cancelled`(배송비 재청구) · `member.withdrawn`(배송지 정리).

### 2.4 미결 (사장님 결정 필요 — d18 §8.2 / f15 §9 / f16 §9)

- **Q-DEL-08 / f15-Q01 / f16-Q02**: 자동 구매확정 + 반품 기간 (P3) — 7일 vs 14일 (사장님 verbatim 권장 = 14일 + D-3 알림).
- **Q-DEL-09 (P4-A)**: 무료배송 임계 도달 시 도서산간 추가비 면제 여부 → **§4 한국 관행으로 해소: 면제 안 함** (권장).
- **Q-DEL-02**: 도서산간 zipcode 룰셋 출처 (자체 vs 외부 API).
- **f16-Q08/Q09**: 다건 교환 일부 품절 처리 / 검수 혼재(good+defective) 라인별 분리.

## 4. 한국 관행 (웹 근거)

> 모든 항목 출처 URL 명시.

### 4.1 택배사 연동 (CJ대한통운 등)

- CJ대한통운 자체 API 는 외부 연동용으로 설계되지 않아 로그인/토큰/세션 처리가 택배사별 상이하고 동시 로그인 제한이 있음. 대리점에 "상품추적전달 등록" 요청 필요. → **직접 연동 난이도 높음**. ([CJ대한통운 배송조회](https://www.cjlogistics.com/ko/tool/parcel/tracking), [택배API 블로그](https://www.deliveryapi.co.kr/blog/courier-account-api))
- **권장**: 운송장 발급/접수는 솔루션 연동(카페24/고도몰형 또는 택배API), 배송추적은 **스마트택배(Sweet Tracker) 통합 조회/추적 API** 사용.
  - 조회 API = 실시간 단건 조회, 추적 API = 주기적 자동 추적(연간 계약·후불). RESTful, 택배사 코드 + 운송장 번호 파라미터. ([스마트택배 API](https://tracking.sweettracker.co.kr/), [API Doc](https://info.sweettracker.co.kr/apidoc))
- **설계 반영**: 택배사별 개별 webhook(d18 §5.3) 은 이상적이나 **현실은 스마트택배 단일 추적 API 풀링/통합 webhook 권장**. → **Q-DEL-07 (webhook 미지원 택배사 대응) 의 권장안 = 스마트택배 통합 API** 로 박제.

### 4.2 배송비 정책 (도서산간 / 조건부 무료)

- **핵심 발견**: 카페24 — 지역별(도서산간) 배송비를 설정하면 **무료배송·조건부 무료배송·등급 무료 혜택이 적용된 상품이라도 항상 도서산간 추가 배송료가 적용됨**. ([카페24 배송비 설정](https://serviceguide.cafe24.com/ko_KR/SH.DH.SR.html), [지역별 배송비 가이드](https://support.cafe24.com/hc/ko/articles/8469011970585))
  → **Q-DEL-09 (P4-A) 해소: 무료배송 임계 도달 시에도 region_extra(제주/도서산간) 는 면제하지 않음** (d18 §6.1 F6 의 "정책 P4-A 추가비 부과 유지" 와 정합).
- 지역별 배송비 = 특수지역명 + 우편번호 범위 + 추가 금액. → 우리 region_type 자동 분류(zipcode 범위)와 정합. ([imweb 지역별 배송비](https://imweb.me/faq?mode=view&category=29&category2=40&idx=71455))

### 4.3 묶음배송

- 카페24 묶음배송 = 2건 이상 서로 다른 주문을 한 번에 배송. **수령자명·우편번호·주소·연락처가 모두 동일**해야 가능. ([카페24 묶음배송](https://support.cafe24.com/hc/ko/articles/8465860034457))
  → 우리 MVP 는 묶음배송 out-of-scope (d18 §8.1 O2). 단, **반대 방향인 1주문 N운송장 분할 배송은 in-scope** (shipments 1:N). 추후 묶음배송 확장 시 본 동일성 검증 룰 채택.

### 4.4 전자상거래법 — 청약철회·반송비 (오류 없음 대전제)

- **§17 ①**: 소비자는 재화 인도일로부터 **7일 이내** 청약철회 가능. ([국가법령정보센터 전자상거래법](https://www.law.go.kr/lsInfoP.do?lsId=009318), [찾기쉬운 생활법령 반품·환불](https://www.easylaw.go.kr/CSP/CnpClsMain.laf?csmSeq=835&ccfNo=4&cciNo=1&cnpClsNo=2))
- **반송비 부담**: 단순변심 청약철회 = **왕복 배송비 소비자 부담**. 표시·광고와 다르거나 계약과 다르게 이행(상품불량/오배송) = **사업자 부담**. ([찾기쉬운 생활법령](https://www.easylaw.go.kr/CSP/CnpClsMain.laf?csmSeq=835&ccfNo=4&cciNo=1&cnpClsNo=2))
- **§18 ①**: 사업자는 청약철회 통지받은 날부터 **영업일 3일 이내** 환불 의무. ([LBOX §18](https://lbox.kr/v2/statute/전자상거래등에서의소비자보호에관한법률/본문%20%3E%20제2장%20%3E%20제18조))
  → 우리 `legal-kr/withdrawal-7day` 모듈의 `withdrawal_deadline`(delivered_at+7일) + `requireBusinessDayRefundSLA`(영업일 3일) 와 **정합 확인**.

## 5. 종합 설계 결정

> 위 §2~§4 종합. 근거 명시. 추측 금지.

### D1. 배송비 산정 (Internal provider 패턴 + 도서산간 항상 부과)

- 산식: `배송비 = (product_amount ≥ free_threshold ? 0 : base_fee) + region_extra`.
- **region_extra (제주/도서산간) 는 무료배송 적용과 무관하게 항상 가산** (§4.2 카페24 근거 + d18 F6). → **P4-A = 면제 안 함** 확정.
- region_type 자동 분류 = zipcode 범위 매핑 (Spree DeliveryZone postal_code 패턴 §3.1 차용). 도서산간 룰셋 출처는 Q-DEL-02 미결 유지 (자체 관리 권장 — 소급 미적용 B-DEL-006).
- 정책 변경 시 카트 캐시 무효화 + `delivery_policy.changed` 발행 (d18 F24).

### D2. 운송장·추적 = 스마트택배 통합 API + 분할 배송

- 택배사별 직접 연동 난이도(§4.1) 고려 → **스마트택배(Sweet Tracker) 통합 추적 API 단일 채널** 권장 (Q-DEL-07 해소). 택배사 개별 webhook 은 향후 확장.
- 운송장 등록: 단건(`deliveries`) + 분할(`shipments` 1:N, Vendure 부분 이행 §3.2 정합) + CSV 일괄(각 라인 독립 트랜잭션).
- 추적 멱등: `UNIQUE(order_id, event_at, event_code)`. 추적 누락 보완 배치 (마지막 추적 N시간 경과 시 풀링, P10 기본 12시간).
- 운송장 정규식 택배사별 (CJ 10~12 / 한진 10 / 롯데 12 / 우체국 13 — d18 F8). 단, 정확 자릿수는 **(추가 확인 필요)** — 운영 시 스마트택배 택배사 코드표로 검증.

### D3. 배송 상태 머신 (Vendure 확장 패턴)

- 기본 5종 (created/pending/shipped/delivered/canceled — 코드 `state-machine/config/fulfillment.ts` 확인). 단방향 전이 (d18 F10).
- **partially_delivered** = 분할 배송 일부만 delivered (d16 §6 확장). order-level rollup = 모든 shipment delivered 시 delivered.
- 한국 택배사 세분화(picked_up/at_hub/out_for_delivery/delivery_failed/re_delivery_scheduled) = **P2 단계 추가** (Vendure 커스텀 state §3.2 + 코드 주석 명시).

### D4. 자동 구매확정

- `delivery.delivered` → auto_confirm_due_at = delivered_at + P3. 배치 매시간 매칭 → order confirm 트리거(멱등).
- **P3 기본값 = 14일 + D-3 알림** 권장 (사장님 verbatim, f15-Q01). 단 최종 확정은 사장님 결정 영역 (Q-DEL-08).

### D5. 반품·교환 = Medusa RMA + rma-extension + legal-kr (이미 구현됨)

- Medusa `Return`/`OrderClaim`/`OrderExchange` first-class 사용 (이식설계 §3.1, 평탄화 불필요).
- 한국 정책 = `rma-extension`(ReturnsPolicy/ReimbursementType/ReturnInspection/ReturnShippingFeePolicy) + `legal-kr/withdrawal-7day`(WithdrawalReason/WithdrawalEligibility). **defineLink 코어 무수정 격리**.
- 반송비 부담: 단순변심=소비자(§4.4 법령) / 불량·오배송=사업자. `ReturnShippingFeePolicy.payer` enum 으로 자동 판정 (이미 모델 존재).
- 검수: `ReturnInspection.resellable`/`condition`(A/B/C/DISPOSE) → 양호=재고복구 / 불량=미복구 (d18 F18 정합).
- 환불 SLA: 영업일 3일 (§4.4 §18). `legal-kr` 의 `requireBusinessDayRefundSLA` + business-day util 존재.

### D6. 동시성·원자성 (v4 F31~F38)

- 검수→환불→재고 복구 3단계 원자성: PG 실패 시 재고 복구 롤백 + "환불대기" 유지 + 재시도 큐 (d18 F33). PG 호출은 **트랜잭션 외부** (f16 §5.1, 트랜잭션 ≤ 2초).
- 동시 반품·교환·취소 = orders.version 낙관락 + 라인 단위 분산 락 + `UNIQUE(order_item_id, action_type) WHERE status IN (...)`.
- 일괄 처리 = 각 건 독립 트랜잭션, 부분 실패 시 성공/실패 분리 리포트 (d18 F37).
