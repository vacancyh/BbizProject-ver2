## 0. 한 장 요약 (연동 핵심 결정)

1. **연동 모델 = Medusa native `product_category` N:N pivot 1개 + `product.metadata.primary_category_id` 1개**. 신규 테이블 0. 카페24의 "대표 분류 1 + 추가 진열 분류 N" 과 1:1 대응. (출처: 카페24 "여러 개의 분류에 같은 상품을 노출")
2. **등록/수정 UX = 진열 카테고리 "다중 선택" + primary "라디오 1개" 지정**. 현 코드의 단일 Select(`categoryId` 1개)를 다중 트리 선택 + primary 라디오로 교체. 상품유형 Select(옵션·고시 결정)는 그대로 유지(독립 축).
3. **상품군(상품유형) → 진열 카테고리 = "추천" 매핑(강제 X)**. `product_category.metadata.suggested_product_type_id` 역방향 또는 상품유형 → 카테고리 추천. 등록 시 상품유형 선택하면 진열 카테고리를 추천 하이라이트만. 권위는 분리.
4. **카테고리 이동/병합/비활성 시 상품 처리 = N:N 기준 자동 정합**. 이동(parent 변경) = 상품 연결 불변(트리 위치만 변경). 병합 = 상품 재배치 + primary 갱신. 비활성 = "전 진열 카테고리가 모두 비가시일 때만" 사용자 노출 제외(F12).
5. **native API 매핑 = `POST/GET /admin/products`(코어) + `/admin/product-categories`(코어) 조합 + 우리 `metadata`**. 카테고리 트리 CRUD admin route(`/admin/categories`)는 미구현이므로 본 연동의 사전 작업으로 식별(체크리스트 §5).

### 2.3 상품군(상품유형) ↔ 진열 카테고리 추천 매핑

- **목적**: 등록 UX 보조. 상품유형(의류/악세서리)을 고르면 어울리는 진열 카테고리를 추천 하이라이트. **강제 아님** — 관리자가 자유 선택·해제 가능.
- **권위 분리(절대)**: 옵션·고시 = 상품유형 단일 권위 / 진열 = 카테고리. 추천은 UI 편의일 뿐 데이터 정합에 관여 안 함.
- **저장 방향(MVP 권장)**: `product_type_template.metadata.suggested_category_ids: string[]`. 상품유형이 "나를 고르면 이 진열 카테고리들을 추천" 보유. (역방향 `product_category.metadata.suggested_product_type_id` 도 가능하나, 상품유형이 적고 카테고리가 많으므로 상품유형 측 보유가 관리 단순)
- **주얼리 MVP 예시**:

| 상품유형(상품군) | 추천 진열 카테고리 | 근거 |
|---|---|---|
| 악세서리(주얼리) | 반지 / 목걸이 / 귀걸이 / 팔찌 | `카테고리_재설계 §3.3` 매핑표 |

- **동작**: 상품유형 Select 변경 → 진열 카테고리 트리에서 `suggested_category_ids` 노드에 "추천" 뱃지 + 자동 펼침. 자동 선택은 안 함(관리자 확인 후 체크).

### 3.3 저장 페이로드 (createProduct/updateProduct 변경안)

현 `CreateProductInput.categoryId: string | null` → 아래로 교체:

```
categoryIds: string[]            // N:N 진열 집합 (≥1, 게시 시)
primaryCategoryId: string | null // metadata 저장. categoryIds 부분집합
```

- `createProduct` body 변경:
  - `categories: input.categoryIds.map(id => ({ id }))`  (현 단일 → 배열)
  - `metadata: { ...기존, primary_category_id: input.primaryCategoryId }`  (신규 키 추가, 기존 `kr_product_type_id`·`kr_disclosure` 유지)
- **하위호환**: 기존 단일 `categoryId` 데이터(metadata에 primary 없음) = 마이그레이션 시 그 1건을 primary 로 backfill(§5 체크리스트).

## 4. 카테고리 관리 화면(s39) ↔ 상품 연동

> s39는 트리 CRUD가 본체. 본 절은 그 CRUD 액션이 **상품 연동에 미치는 처리**만 명세(트리 룰 자체는 `카테고리_재설계 §3.5` 권위).

### 4.1 관리 액션별 상품 처리

| s39 액션 | 상품(N:N) 처리 | 사용자 영향 | 근거 |
|---|---|---|---|
| **생성** | 영향 0 (빈 카테고리) | — | s39 §3.2 |
| **수정(name/slug/thumb)** | N:N 연결 불변. slug 변경 = 캐시 PURGE + 구 URL MVP 404 | 목록 캐시 갱신 | F16, F4 |
| **이동(parent 변경, 드래그)** | **N:N 연결 불변** — 상품은 그 카테고리에 그대로. 트리 위치만 변경(빵부스러기·메뉴 경로 갱신) | primary 경로(빵부스러기) 재계산 | F13, `카테고리_재설계 §3.5` |
| **비활성 토글** | 연결 불변. 단 "상품의 전 진열 카테고리가 모두 비가시"면 사용자 노출 제외(다른 활성 진열 있으면 노출 유지) | F12 — 다중 진열 보호 | `카테고리_재설계 §3.5 F12` |
| **병합(A→B, MVP 수동)** | A 진열 상품을 B 로 재배치 + **A 가 primary 인 상품은 primary 를 B 로 갱신** + A 삭제 | 무중단 | F14 |
| **삭제** | 진열 상품 0 **AND** 자식 0 일 때만(409 차단). 상품 있으면 s39 "상품 관리로 이동" 유도 | — | F15, s39 §2.1·§5 |

### 4.2 s39 화면의 연동 요소 (현 s39 문서 → 4단/다중 정합 갱신점)

| s39 위치 | 현 문구 | 연동 갱신점 |
|---|---|---|
| §3.1 매핑 상품 카운트 | `product_count` 클릭 → `/admin/products?category_id={id}` | **N:N 기준 카운트**(primary 무관, 진열된 전 상품). 링크 필터도 N:N |
| §4.1 "트리 2단까지" 토스트 | "트리는 2단까지만 지원해요" | **"4단까지"** 로 갱신(`카테고리_재설계 §3.1`) |
| 삭제 차단 모달 | "매핑된 상품 N개" | N:N 진열 상품 수 기준. **병합 안내 추가**(B로 재배치 유도) |
| 비활성 토글 안내 | E-014 정합 | **"다른 활성 분류에도 진열된 상품은 계속 노출됩니다"** 안내 추가(F12 다중 보호) |

### 4.3 캐시 무효화 연동 (F4)

- 카테고리 CRUD/활성/reorder/병합 → `category.*` 이벤트(d13 §7.2) 발행 → product 도메인 구독 → (a) 트리 캐시(헤더·홈·s02) (b) 목록 캐시(s03 cat별) (c) 검색 인덱스(E-014) PURGE.
- Medusa native event(`product-category.created/updated/deleted`) subscriber 로 구현 — `카테고리_재설계 §4` 정합.

### 5.1 상품 등록 시 카테고리 연동 (코어 product API 활용)

### 5.2 카테고리 트리 연동 (코어 product-category API + 우리 admin route)

| 연동 동작 | 사용 API | 비고 |
