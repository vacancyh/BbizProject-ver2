## 1. 도메인 개요

- **1줄 책임**: 가입·로그인·소셜인증·프로필·멤버십 등급·동의 이력·제재/블랙리스트·탈퇴를 담당하는 **모든 도메인의 인증·권한 기반**.
- **범위 경계 (in)**: 회원 식별/인증, 프로필·주소록, 등급(멤버십), 동의 이력, 세션, 비밀번호 재설정, 제재/블랙리스트, 탈퇴·PII 마스킹, 알림 설정 저장.
- **범위 경계 (out)**:
  - 알림 **발송 자체** = notification 도메인 (본 도메인은 설정 저장/조회 + 이벤트 발행만).
  - 쿠폰·포인트 **발급/적립 로직** = coupon_point 도메인 (본 도메인은 `member.signed_up`/`grade_changed`/`birthday_today` 등 이벤트 발행만).
  - 등급 판정의 **구매액 원천** = order 도메인 (`order.purchase_confirmed` 이벤트 구독).
- **핵심 정책**: 비회원 주문 불가(`00_개요.md §2 #8`). 비회원 장바구니(localStorage)는 결제 진입 시 **로그인 강제 게이트**로 전환.

## 2. 우리 S0 설계 요약 (d11 + f11)

### 2.1 엔티티 (S0 정의 8개)

`members`(본체) / `member_oauth`(소셜) / `member_consent`(동의 이력, INSERT-only) / `member_sanctions`(제재) / `member_blacklist`(영구차단) / `auth_sessions`(Refresh·Token Rotation) / `password_resets`(30분·1회) / `member_notification_settings`(채널×카테고리).

### 2.2 핵심 룰 (d11 §6 — 시스템 고정 F1~F18, 정책 P1~P14)

- **인증**: 비번 8자↑(영문+숫자+특수)(F1) · JWT Access 15분 + Refresh Token Rotation(F2) · 비번 변경 시 전 세션 revoke(F3) · 정지/블랙 시 세션 즉시 revoke(F4).
- **법령**: 만 14세 미만 가입 차단(F5) · 탈퇴 후 PII 마스킹·삭제(F15) · 탈퇴/블랙 식별자는 email/phone 해시로 보존하여 재가입 차단(F16).
- **토큰**: 재설정 토큰 30분·1회(F6) · 이메일 인증 토큰 1시간(F7) · 재설정 IP 30분 5회 제한(F8) · OAuth state CSRF(F9).
- **정책값(관리자 변경 가능)**: 가입 포인트 3,000P(P1) · 등급 기준금액(실버 10만/골드 30만/VIP 50만)(P3) · 등급 적립률(일반1%/실버2%/골드3%/VIP5%)(P4) · 잠금 5회/30분(P7·P8) · 자동로그아웃 30분(P9) · 탈퇴 유예 30일(P10) · 소셜 ON/OFF(P11) · 등급 집계 연간(P13) · 알림 채널 글로벌 ON/OFF(P14).

### 2.3 PII 영향평가 (d11 §6.4)

수집 항목 × 보관·암호화·마스킹 전수표 존재. 민감정보 3등급(Level S=평문 미저장 / A=AES-256 컬럼 암호화 / B=평문+응답 마스킹 / C=마스킹X). 보존 자동화(탈퇴+30일 마스킹 / 접속로그 1년 / cold 7년 삭제).

### 2.4 이벤트 (d11 §7)

- **발행**: `member.signed_up` / `email_verified` / `grade_changed` / `points_adjusted` / `suspended` / `password_changed` / `withdrawn_pending` / `withdrawn_completed` / `blacklisted` / `birthday_today`.
- **구독**: `order.purchase_confirmed`(등급 가산) / `order.partial_cancelled`(등급 하락).

### 2.5 QA 추적

사용자 MEM-U-001~055(55) + 관리자 MEM-A-001~035+029B(36) + 비기능 A-AUTH(22)·A-LOG(5) = **118건**.

## 3. 성숙 플랫폼 패턴 (Vendure / Spree)

### 3.1 Vendure — Customer ↔ User 분리 + AuthenticationStrategy

- 출처: `외부참조문서/벤듀어/벤듀어_docs_docs_guides_core-concepts_auth_index.mdx`, `..._customers_index.mdx`, `..._user-management_index.mdx`
- **배울 점 1 — 인증/프로필 분리**: `Customer`(프로필) 와 `User`(인증·인가) 를 분리. 게스트 체크아웃은 `User` 없는 `Customer`. → 우리 설계의 `members`(프로필) + `auth_sessions`/`password_resets`(인증) 분리와 동일 철학. **Medusa 도 동일하게 `Customer` 모듈(프로필) ↔ `Auth` 모듈(자격증명) 을 분리** (§6 참조).
- **배울 점 2 — Strategy 플러그형 소셜로그인**: `shopAuthenticationStrategy: [NativeAuthenticationStrategy, FacebookAuthenticationStrategy, GoogleAuthenticationStrategy]` 처럼 인증 전략을 배열로 끼워 넣음. 외부 인증은 `ExternalAuthenticationService` 가 공통 처리. → Medusa 의 Auth Module Provider(emailpass/google + 커스텀 kakao/naver) 패턴과 1:1 대응(§6.2).
- **배울 점 3 — CustomerGroup**: 가격·프로모션 적용 단위. → 우리 등급(membership_grade)을 Medusa `CustomerGroup` 으로 매핑할지(§5.3 결정) 검토 근거.

### 3.2 Spree — CustomerGroup 세분화 + 운영 흐름

- 출처: `외부참조문서/스프리/스프리_docs_user_customers_customer-groups.mdx`, `..._customer-profile.mdx`, `스프리_docs_plans_6.0-platform-auth.md`
- **배울 점 1 — 그룹 기반 비즈니스 룰**: CustomerGroup 으로 Price List Rule·Promotion Rule·접근 제한을 건다(VIP/wholesale/B2B). → 등급별 적립률·쿠폰을 그룹 규칙으로 거는 방식의 근거.
- **배울 점 2 — 운영 UX**: 관리자 그룹 화면에서 검색→선택→일괄 추가/제거. → 관리자 회원 목록(MEM-A-001) + 등급 수동 조정(MEM-A-006) UI 패턴.

> **종합**: 성숙 플랫폼 2종 모두 "인증(자격증명) ↔ 프로필(고객) 분리 + 그룹 기반 세그먼트 + 플러그형 외부 인증" 으로 수렴. 이는 Medusa 의 Auth/Customer 모듈 분리 구조와 정확히 일치하므로, 우리 등급/소셜/동의/제재는 **커스텀 모듈 + defineLink** 로 격리하는 것이 정합(§6).

## 4. 한국 관행 (웹 근거)

> 모든 항목 출처 URL 명시. 확인 못한 값은 "(추가 확인 필요)".

### 4.1 소셜로그인(카카오·네이버·구글 OAuth)

- 카페24는 SNS 로그인을 **OAuth 2.0 기반**으로 제공하며, 관리자 `쇼핑몰 설정 > 고객 설정 > 회원 가입·로그인 > SNS 로그인 연동 관리` 에서 **Client(App) ID/Secret 발급 후 입력**하여 공급자별 ON/OFF 한다.
  - 출처: <https://support.cafe24.com/hc/ko/articles/7751406614809>, <https://serviceguide.cafe24.com/ko_KR/PM.SN.LI.html>
- **최초 SNS 로그인 = 회원가입** 으로 간주하고, 이때 **추가정보·약관 동의 페이지를 노출**해 부족한 회원정보(연락처·생년월일 등)와 필수 약관을 보완 수집한다.
  - 출처: <https://support.cafe24.com/hc/ko/articles/8460781731865>, <https://support.cafe24.com/hc/ko/articles/8467406173721>
- 추세: **카카오싱크/네이버 연동으로 "1초 회원가입"** 이 일반적. 카카오싱크 가입 후 별도 PASS 본인인증 단계를 둘 수 있다.
  - 출처: <https://ppcle.com/blog/social-login/>, <https://devtalk.kakao.com/t/pass/140819>
- **설계 반영**: 소셜 콜백 시 신규면 약관·추가정보 동의 화면을 강제하고 그 시점에 `member_consent` 를 INSERT. provider 는 kakao/naver/google 3종.

### 4.2 휴대폰 본인인증

- 통합 본인인증(PASS·네이버·토스·카카오·금융인증서 등)은 **KG이니시스**, 휴대폰 본인인증은 **다날**, 종합은 **NICE아이디**(PASS App/QR/SMS 3종) 가 대표 공급자.
  - 출처: <https://blog.portone.io/authorization-payment-2/>, <https://www.niceid.co.kr/prod_mobile.nc>, <https://blog.portone.io/authorization-payment/>
- 본인인증 용도: **스팸 회원 차단, 14세/19세 연령 제한 상품 판매, 법적 본인확인** 충족.
  - 출처: <https://www.codemshop.com/shop/nice/>
- **설계 반영**: MVP 가입은 이메일+비번 / 소셜 중심(S0 정의). 휴대폰 본인인증(PASS)은 만 14세 검증·연령제한 상품·블랙리스트 강화의 **선택적 보강 레이어**로 위치 — S0 에 별도 엔티티가 없으므로 **(추가 확인 필요)**: 도입 시점·공급자(NICE/다날) 사장님 결정.

### 4.3 회원 등급(멤버십) 체계

- 카페24는 `고객 설정 > 회원정책 설정 > 회원등급 관리` 에서 등급을 설정하고, **등급별 배송비 무료·할인** 등을 부여. 등급 할인과 상품 할인 중복 정책을 별도 설정.

## 5. 종합 설계 결정

> 위 3개(성숙 플랫폼·한국 관행·법령) + Medusa 구조를 종합한 우리 설계. 근거 명시.

### 5.1 인증 구조 — Medusa Auth/Customer 분리 채택

- **결정**: 우리 `members` 본체 = Medusa **`Customer`**(프로필·email·phone·`has_account=true`·`metadata`) 에 매핑. 자격증명(비번·소셜·MFA·세션) = Medusa **`Auth` 모듈**(`AuthIdentity` + `ProviderIdentity`) 에 위임.
- **근거**: Vendure(Customer↔User)·Spree(platform-auth)·Medusa 3종 모두 인증/프로필 분리 구조. 우리 S0 의 `auth_sessions`/`password_resets`/`member_oauth` 는 Medusa `provider_identity`(provider+entity_id 유니크)·세션 관리로 흡수 가능.
- **세션·토큰**: Medusa 는 `session`/`bearer`/`api-key` 인증 미들웨어 제공. JWT Secret/Cookie Secret 분리(F14)는 이미 `medusa-config.ts` `jwtSecret`/`cookieSecret` 로 구분, `cookieOptions`(httpOnly·sameSite=lax·secure)도 설정됨(F12 정합 — 실제 코드 확인).

### 5.2 소셜로그인 — Auth Provider 플러그형

- **결정**: 구글 = `@medusajs/auth-google`(설치 확인) 그대로. **카카오·네이버 = 커스텀 Auth Module Provider** 2개 신규 구현(`AbstractAuthModuleProvider` 확장, phone-auth 튜토리얼 패턴).
- **근거**: Medusa auth-providers 문서 + phone-auth 튜토리얼(`identifier`/`DISPLAY_NAME`/`authenticate`/`validateCallback`). 카카오/네이버는 표준 OAuth2 라 GoogleProvider 와 동형. 최초 콜백 시 신규면 약관·추가정보 동의(한국 관행 §4.1) 강제.
- `authMethodsPerActor` 로 `customer: [emailpass, google, kakao, naver]`, `user(관리자): [emailpass]` 분리.

### 5.3 회원 등급(멤버십) — 커스텀 Tier 모듈 + defineLink

- **결정**: 등급은 Medusa `CustomerGroup`(일반/실버/골드/VIP 4개 그룹)으로 **세그먼트 표현** + **커스텀 `member-grade` 모듈**(기준금액·적립률·집계기간 정책 + `total_purchase_amount` 누적)로 **판정 로직** 보유. order 도메인의 구매확정 이벤트 구독 subscriber 로 누적·재평가.
- **근거**: customer-tiers 튜토리얼(Tier/TierRule 모듈 + order 구독 subscriber 로 tier 갱신) + Spree/Vendure 그룹 기반 + 한국 관행(연간 누적 자동 산정). `CustomerGroup` 매핑으로 향후 등급별 가격/프로모션(PriceList) 연동 확장 가능.

### 5.4 동의·제재·블랙리스트·탈퇴 — legal-kr 격리 커스텀 모듈

- **결정**: `member_consent`/`member_sanctions`/`member_blacklist`/`member_notification_settings`/탈퇴 메타 = **커스텀 모듈에 격리**(코어 Customer 무수정), `Customer`↔커스텀 모델은 `defineLink` 로 연결.
- **근거**: 본 백엔드에 이미 동일 격리 패턴이 가동 중 — `src/modules/legal-kr/withdrawal-7day`(청약철회 7일) + `src/links/order-withdrawal.ts`(defineLink). 회원 동의/제재도 동일 구조로 일관. INSERT-only 동의 이력(MEM-A-012)·사유 필수(F18)는 모델 제약으로.

### 5.5 PII·법령 정합

- **휴면계정**: 신설하지 않음(2024 폐지법 정합, 과설계 방지). 미접속 안내는 향후 옵션.
- **만 14세**: 단순 차단(F5) 유지 + 보호자 동의 흐름은 미결(d11 §8 Q2). 2025 개정(18세 확대) 모니터링.
- **암호화/마스킹**: Level A(이름·휴대폰·생년월일) AES-256 컬럼 암호화는 Medusa `Customer` 기본 평문 컬럼이므로 **응답 마스킹 미들웨어 + 저장 시 암호화 레이어**를 커스텀으로 추가(F-PII-01·02). Level S(비번·토큰)는 Auth 모듈이 해시 처리(직접 저장 안 함).

### 5.6 2FA(MFA)

- **발견**: Medusa Auth 모듈에 **MFA 네이티브 모델 존재**(`auth_mfa_factor`·`auth_mfa_recovery_code` — node_modules 실측). → d11 §8 Q1(2FA) 도입 시 커스텀 없이 네이티브 활용 가능. MVP 범위는 사장님 결정 미결 유지하되, **관리자(user) MFA 는 네이티브로 즉시 가능**함을 박제.

## 6. Medusa 코드 매핑

### 6.1 ⓐ 활용할 Medusa native 모듈 (설치 확인 완료)

| Medusa 모듈/패키지 | 버전 | 활용 | 우리 S0 대응 |
|---|---|---|---|
| `@medusajs/customer` | 2.15.3 | 회원 본체(프로필·email·phone·metadata·addresses·groups) | `members`(본체) + 주소록 |
| `@medusajs/auth` | 2.15.3 | `AuthIdentity`·`ProviderIdentity`(provider+entity_id 유니크)·MFA·세션 | `auth_sessions`·`password_resets`·`member_oauth` 자격증명부 |
| `@medusajs/auth-emailpass` | 2.15.3 | 이메일+비번 인증 (bcrypt) | F1 비번 정책·로그인 |
| `@medusajs/auth-google` | 2.15.3 | 구글 OAuth | MEM-U-017 |
| `@medusajs/user` | 2.15.3 | 관리자 계정(User·Invite) | MEM-A-030 관리자 CRUD, A-AUTH-017 |
| `@medusajs/rbac` | 2.15.3 | 역할 기반 접근 제어(설치됨) | 관리자 권한 등급(SUPER 등) |
| `@medusajs/notification` (+`-sendgrid`/`-local`) | 2.15.3 | 인증/재설정 메일 발송 | F7·F6, `auth.password_reset` 이벤트 구독 subscriber |

- **모델 실측(node_modules)**: `Customer{id(cus_),company_name,first_name,last_name,email,phone,has_account,metadata,created_by,addresses,groups}` / `AuthIdentity{id(authid_),provider_identities[],mfa_factors[],mfa_recovery_codes[],app_metadata}` / `ProviderIdentity{entity_id,provider,user_metadata,provider_metadata,UNIQUE(entity_id,provider)}` / `AuthMfaFactor{provider,status,...}`.
- **비번 재설정**: Medusa 가 `auth.password_reset` 이벤트 발행 → notification subscriber 가 메일 발송(reset_url) → Reset Password API 로 확정. 우리 F6(30분·1회)·F8(IP 5회/30분)은 토큰 만료·rate limit 미들웨어로 보강.

### 6.2 ⓑ 필요한 커스텀 모듈 / Provider / defineLink / API route

**커스텀 Auth Provider (2종 신규)**
- `src/modules/auth-kakao/` — `AbstractAuthModuleProvider` 확장, `identifier="kakao"`, `authenticate`/`validateCallback` 구현(카카오 OAuth2). state CSRF 검증(F9).
- `src/modules/auth-naver/` — 동형, `identifier="naver"`.
- `medusa-config.ts` 의 auth 모듈 providers 배열에 등록 + `http.authMethodsPerActor.customer = ["emailpass","google","kakao","naver"]`.

**커스텀 도메인 모듈 (legal-kr 격리 패턴 준수, 코어 무수정)**
- `src/modules/member/grade/` — `MemberGrade`(member_id·grade·total_purchase_amount·집계기간) + `GradePolicy`(기준금액·적립률 — P3·P4). customer-tiers 패턴. CustomerGroup(일반/실버/골드/VIP) 동기화.
- `src/modules/member/consent/` — `MemberConsent`(type·agreed·changed_at·ip·ua, INSERT-only — MEM-A-012).
- `src/modules/member/sanction/` — `MemberSanction`(level·reason·expires_at·issued_by) + `MemberBlacklist`(member_id|email_hash|phone_hash 최소1, reason). 사유 필수(F18).
- `src/modules/member/notification-pref/` — `MemberNotificationSetting`(channel×category×enabled, 복합 PK).
- `src/modules/member/withdrawal/` — 탈퇴 유예(grace_until)·PII 마스킹 상태. (legal-kr 하위 배치 권장 — 개인정보보호법 격리.)

**defineLink (`src/links/`, 코어 무수정)**
- `customer-member-grade.ts`: `CustomerModule.linkable.customer` ↔ `MemberGradeModule.linkable.memberGrade` (1:1).
- `customer-member-consent.ts`: customer ↔ memberConsent (1:N, isList).
- `customer-member-sanction.ts`: customer ↔ memberSanction (1:N).
- `customer-notification-pref.ts`: customer ↔ memberNotificationSetting (1:N).
- (참조 본보기: 기존 `src/links/order-withdrawal.ts`.)

**Subscriber (`src/subscribers/`)**
- `order-purchase-confirmed.ts`: order 구매확정 → `total_purchase_amount` 누적 → 등급 재평가 → `member.grade_changed` 발행(coupon_point 구독).
- `auth-password-reset.ts`: `auth.password_reset` 구독 → 한국어 재설정 메일(notification).
- `member-signed-up.ts`: 가입 완료 → `member.signed_up` 발행(coupon_point: 가입 포인트·쿠폰).
- `member-suspended.ts`: 제재 시 활성 세션 즉시 revoke(F4).

**API route (`src/api/`)**
- `src/api/store/auth/oauth/[provider]/...` (kakao/naver url·callback), `src/api/store/me/consents`·`notification-settings`·`withdraw`(+cancel), `src/api/store/me/grade`.
- `src/api/admin/members/[id]/{suspend,release,grade,points,password-reset-link,consents}`, `src/api/admin/blacklist`, `src/api/admin/withdrawals`, `src/api/admin/policies/member/{signup-benefit,grade,global}`.
- **미들웨어**: `authenticate("customer", ["session","bearer"])` (사용자), `authenticate("user",["session","bearer","api-key"])` (관리자) — 관리자/사용자 actor 분리(F14).

**Admin UI (`src/admin/routes/`)**
- 회원 목록/상세, 제재/등급/포인트 조정, 블랙리스트, 탈퇴 신청, 정책 설정 — 기존 `src/admin/components`(admin-data-table·admin-page 등) 재사용.

### 6.3 ⓒ 마이그레이션 계획

- 각 커스텀 모듈은 자체 `migrations/`(MikroORM, 기존 withdrawal-7day·rma-extension 패턴) 보유 → `npx medusa db:generate <module>` 후 `db:migrate`.
- Customer 코어 테이블 **무수정**. 등급/동의/제재/알림설정/탈퇴는 별도 테이블 + link 테이블.
- Level A(이름·휴대폰·생년월일) 암호화는 Customer 평문 컬럼 위 **애플리케이션 레이어 암복호화 + 응답 마스킹 미들웨어**로 처리(스키마 변경 최소화). 생년월일은 Customer 에 없으므로 `member` 커스텀 모델 또는 `metadata` 에 보관(암호화).

## 7. 현 코드와의 관계 + 구현 단계

### 7.1 현 코드 관계

- **회원 전용 커스텀 코드 = 현재 없음**(grep 확인: member/grade/blacklist/membership 매칭 0건 — RMA 오탐 제외).
- **가동 중 격리 패턴 본보기**: `src/modules/legal-kr/withdrawal-7day`(모듈) + `src/links/order-withdrawal.ts`(defineLink) + `src/subscribers/*` + 자체 `migrations/`. 회원 도메인도 **이 패턴을 그대로 복제**.
- **인증 인프라 기반 마련됨**: `medusa-config.ts` 에 jwtSecret/cookieSecret 분리(F14), cookieOptions(httpOnly·sameSite=lax·secure 토글)(F12) 설정. auth-emailpass·auth-google·rbac·notification 패키지 설치 완료.
- **legal-kr 격리 원칙 준수**: 코어 Customer/Auth 무수정, 커스텀은 별도 모듈 + defineLink — 본 설계 전체가 이 원칙을 따름.

### 7.2 구현 단계

**immediate (Phase 1 — 인증·프로필 기반)**
1. emailpass 가입/로그인/로그아웃 + 이메일 인증(notification) + 비번 재설정(`auth.password_reset` subscriber).
2. `member` 커스텀 모듈(생년월일·gender 등 Customer 미보유 필드 + 만14세 검증 F5) + Customer link.
3. 응답 마스킹 미들웨어 + Level A 암호화 레이어.
4. 약관/동의 모듈 + INSERT-only consent + 가입 시 필수 동의 검증.

**다음 단계 (Phase 2 — 소셜·등급·운영)**
5. auth-google 연동 + 카카오/네이버 커스텀 Provider 2종 + 콜백 시 신규 약관/추가정보 동의 화면.
6. member-grade 모듈 + order 구매확정 subscriber + CustomerGroup 동기화 + 등급 정책 admin.
7. sanction/blacklist 모듈 + 제재 시 세션 revoke subscriber + 블랙리스트 가입/로그인 차단.
8. 탈퇴(grace 30일) + PII 마스킹 배치(job) + email/phone 해시 보존(F16) + 관리자 탈퇴/정책 화면.
9. 알림 설정(채널×카테고리) + 관리자 글로벌 ON/OFF.

**보류 / 사장님 결정 (d11 §8 미결)**
- 2FA(네이티브 MFA 모델 존재 — 관리자 즉시 가능, 사용자 옵션): Q1.
- 만 14세 보호자 동의 흐름: Q2 (2025 개정 18세 확대 모니터링).
- 정지 회원 탈퇴 정책: Q3. 친구추천: Q4. 비번 룰 관리자 변경: Q5.
- 휴대폰 본인인증(PASS/NICE/다날) 도입 시점·공급자: **(추가 확인 필요)**.

## 8. 핵심 설계 결정 요약

1. **인증/프로필 분리 — Medusa Auth(자격증명) + Customer(프로필)** 채택. Vendure/Spree/Medusa 3종 공통 구조에 우리 S0 의 `auth_sessions`/`password_resets`/`member_oauth` 를 흡수.
2. **소셜로그인 = google 네이티브 + 카카오/네이버 커스텀 Auth Provider 2종**(phone-auth 튜토리얼 패턴, `authMethodsPerActor` 로 actor별 제한). 최초 콜백 시 약관·추가정보 동의 강제(한국 관행).
3. **등급·동의·제재·블랙리스트·탈퇴 = legal-kr 격리 커스텀 모듈 + defineLink**(코어 무수정). 기존 `withdrawal-7day` 패턴 그대로 복제. 등급은 customer-tiers 패턴 + CustomerGroup 동기화.
4. **법령 정합 확정**: 휴면계정 분리보관은 2024-01-01 폐지법 → **신설 안 함(과설계 방지)**. 만14세 단순차단 유지(보호자 동의·18세 확대는 미결). 탈퇴 후 PII 마스킹 + 주문 5년 보존은 전자상거래법 정합.
5. **2FA 네이티브 발견**: Medusa Auth 에 `auth_mfa_factor`/`auth_mfa_recovery_code` 모델 실재 → 관리자 MFA 는 커스텀 없이 즉시 가능(사용자는 옵션, 사장님 결정).
