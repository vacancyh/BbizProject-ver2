## 1. 도메인 개요

- **1줄 책임**: 관리자 계정·권한(RBAC)·공지/배너/팝업·마케팅 발송·시스템 정책·감사 로그를 단일 통제실에서 관리하는 **횡단(cross-cutting) 백오피스 도메인**.
- **범위 경계 (in)**:
  - 관리자 인증(MFA TOTP)·세션(사용자와 완전 분리)·IP 차단
  - RBAC(역할/권한) — 메뉴별·기능별 접근 통제
  - 공지사항·FAQ·배너/팝업/상단 띠 CRUD
  - 마케팅 세그먼트·발송(이메일/SMS/카카오) 정책·이력 (실 발송 모듈은 notification 위탁)
  - 시스템 정책 저장소(`system_policies`) — d11~d20 정책의 통합 진입점
  - 모든 write 액션의 감사 로그(`admin_audit_logs`) — INSERT only
  - 시스템 헬스·점검모드·일괄 처리(bulk job)·이중 확인(confirm token)
- **범위 경계 (out)**:
  - 각 도메인의 비즈니스 룰 실행 자체 = 해당 도메인 (본 도메인은 정책 저장 + 변경 API + 감사 박제만)
  - 실 알림/메일 발송 = notification 도메인 (Medusa Notification 모듈 위탁)
  - 상품·주문·결제 등 운영 CRUD 화면 = 각 도메인 admin route (본 도메인은 권한·감사 인프라만 제공)
- **포지션**: 다른 11개 도메인(d11~d20)이 본 도메인을 **역방향 의존** — 정책·감사·권한 인프라를 소비. d21 짝 정의서 §1 "모든 도메인의 정책 변경 1차 진입점" 정합.
- **대전제 정합**: ①오류 없음(접근통제·감사 무결성·법령) ②한국 친화(대표운영자/운영자/CS 등급, 메뉴별 권한, IP 제한, 5년 보관) ③코드베이스 수렴(Medusa user/auth native + 커스텀 모듈 격리).

### 2.2 핵심 룰 (d21 §6 F1~F23 요약)

- **인증/세션**: F1 별도 JWT secret · F2 별도 DB pool(sensitive_pool) · F3 Access 15분/Refresh 8시간 · F4 MFA 필수 · F5 5회 실패 30분 차단+잠금 · F17 비번 12자+ 4종 · F18 90일 만료 · F19 쿠키 HttpOnly+Secure+SameSite=Strict · F20 `/admin` robots.txt 차단.
- **감사**: F6 모든 write = 감사 INSERT(failure 포함) · F7 INSERT only + 5년 보관 · F8 PII 마스킹 · F14 로그인 success/failure 박제.
- **정책**: F9 SUPER + 이중 확인 + 사유 · F10 변경 시 즉시 캐시 PURGE + history INSERT · F11 SUPER 최소 1명 · F12 본인 정지/강등 차단.
- **운영**: F13 점검모드 scope=user 권장 · F15 헬스 30초 polling · F16 down/degraded 슬랙·이메일 알람 · F21 배너 SVG 악성 스크립트 검증 · F22 마케팅 [광고] prefix + List-Unsubscribe + 야간 차단 + 동의자만 · F23 약관 수정 즉시 반영.

### 2.4 마케팅 (f21) 핵심

## 3. 성숙 플랫폼 패턴

### 3.1 Vendure RBAC (★ 본 도메인 권한 설계의 1차 참조)

> 출처: `외부참조문서/벤듀어/벤듀어_docs_docs_guides_core-concepts_roles_index.mdx` · `..._permissions_index.mdx` · `..._developer-guide_custom-permissions_index.mdx` · `..._user-guide_settings_administrators-roles.mdx`

- **Role = Permission 묶음**: Administrator는 1+ Role을 가지며, 요청 시 **role의 permission 합집합(union)** 으로 검사. 다중 role 조합 가능 ("Order Manager" + "Catalog Manager" = 둘 다 허용).
- **CRUD 단위 권한**: 엔티티별 `Create/Read/Update/Delete` 4종. **도메인 단위로 그룹** (예: `Catalog` 도메인 = Products+Variants+Collections+Facets+Assets). 본 프로젝트의 `scope` ENUM(MEMBER/PRODUCT/ORDER/...)과 정확히 동형.
- **built-in 도메인**: Catalog / Customer / Order / Promotion / Settings / **System**(글로벌 설정·Jobs·관리자 계정·Roles). → 본 도메인의 `ADMIN`/`SYSTEM` scope에 매핑.
- **특수 권한**: `SuperAdmin`(전 권한 bypass, 수정·삭제 불가, 최초 관리자에 부여), `Owner`, `Public`. → d21 SUPER role + F11(SUPER 최소 1명)과 정합.
- **Deny-by-default**: `@Allow()` 명시 없으면 접근 불가. → 본 도메인 권한 미들웨어 기본값으로 채택.
- **배울 점 1**: role을 enum 고정(4-role)이 아닌 **"권한 묶음 + 조합"** 으로 설계하면 Q7(3-role vs 4-role) 충돌이 해소됨 — MARKETER는 "마케팅 권한만 가진 custom role"로 표현 가능. (§5 종합 결정에 반영)
- **배울 점 2**: 권한을 코드 enum이 아닌 **DB 저장 Role + Permission** 으로 두면 메뉴별 접근권한(카페24 관행)과 자연 정합.

### 3.2 Vendure Settings Store (정책 저장소 참조)

> 출처: `벤듀어_docs_docs_guides_developer-guide_settings-store_index.mdx`

- 스코프(global/per-user/per-channel/custom) + 권한 제어 + 검증 함수 + 자동 정리 배치 + GraphQL API를 갖춘 **임의 JSON config 저장소**. 엔티티에 종속되지 않음.
- → 본 도메인 `system_policies` 설계와 동형 (key/value JSONB + scope + value_schema + version). 차이: 본 프로젝트는 **변경 시 즉시 캐시 PURGE + history 박제**를 추가 (F10).

### 3.3 Spree Admin Auth (관리자 인증/세션 패턴 참조)

> 출처: `스프리_docs_plans_5.5-admin-auth-cookie-refresh.md` · `5.5-admin-api-key-scopes.md` · `sso-mfa-social-login_admin-dashboard.mdx`

- **관리자 JWT TTL = 5분** (스토어프론트 토큰과 분리, `admin_jwt_expiration` 별도 config). → d21 F3(Access 15분)과 비교: Spree가 더 공격적. 본 프로젝트 15분은 운영 편의 절충값으로 합리적.
- **Refresh = HttpOnly 서명 쿠키**(`Path=/auth`로 스코프 한정, localStorage 금지), Access = JS 메모리만. → d21 F19(HttpOnly+Secure+SameSite) 정합. 본 프로젝트는 SameSite=Strict(Spree는 Lax/None) — 더 엄격.
- **CSRF = SameSite + CORS allowlist 조합** (별도 CSRF 토큰 미발급). → 관리자 영역 CORS allowlist 운영 룰로 채택 권장.
- **API Key Scopes (fail-closed)**: secret key는 `read_<resource>`/`write_<resource>` scope 보유, `write_*`가 `read_*` 함의, 기본 `[]`(아무것도 못함). JWT 관리자 user는 CanCanCan(role) 유지. → 본 프로젝트가 외부 연동/API key 도입 시 참조 (MVP 외).
- **MFA/SSO**: Spree는 enterprise SSO(Entra/Okta) + MFA를 별도 스코핑 통합으로 제공. → 본 프로젝트 MVP = 이메일+비번+TOTP MFA(O2 SSO는 범위 외)와 정합.

### 3.4 Medusa native (코드베이스 기반)

> 출처: `메두사_..._commerce-modules_user_*` · `..._auth_*` · `..._notification_*` · `..._customize-admin_*` · `정의서/사용자인증_14정의서.md`

- **User 모듈** = 관리자 프로필(first_name/last_name/email/avatar_url/metadata)만. 비번/role 없음 (Auth 모듈이 자격증명 관리).
- **Auth 모듈** = AuthIdentity(actor_type + provider + entity_id). `actor_type="user"` → 관리자, `="customer"` → 고객. `app_metadata.{actor_type}_id`에 user id 저장.
- **Invite** = 초대 토큰 기반 관리자 가입 (token + expires_at + accepted). → 카페24 "운영자 초대" 관행과 정합.
- **커스텀 actor type** = `create-actor-type` 가이드로 신규 actor("manager" 등) 추가 가능. → 본 프로젝트 role은 user 모듈 확장 또는 커스텀 모듈로 처리.
- **Admin customization** = `src/api/admin/<resource>/route.ts`(API route) + `src/admin/routes`(UI route) + widget injection zone. core 무수정 확장 패턴.
- **Notification 모듈** = workflow step에서 `notificationModuleService.createNotifications({to, channel, template, data})`. → 마케팅/알람 발송 위탁 경로.

## 4. 한국 관행 (웹 근거)

### 4.1 관리자 권한 등급 — 대표운영자 / 부운영자 (카페24)

> 출처: [운영자 계정 관리 – 카페24](https://support.cafe24.com/hc/ko/articles/33948723673113) · [부운영자 계정 등록 및 권한 설정](https://support.cafe24.com/hc/ko/articles/18280025795865) · [부운영자 권한 FAQ](https://support.cafe24.com/hc/ko/articles/17498047886233)

- **대표운영자(1명) / 부운영자(N명)** 구조. **운영자 계정 관리 메뉴 자체는 대표운영자만 접근** — 부운영자는 접근 불가. → d21 F11(SUPER 최소 1명) + 계정 CRUD = SUPER 전용 정합. **대표운영자 = SUPER** 매핑이 한국 운영자에게 가장 자연스러움.
- **메뉴 접근 권한 + 상세 권한(기능별, 읽기/쓰기)** 2계층 설정. 메뉴별 체크 + 화살표로 세부 권한. → Vendure CRUD permission(§3.1)과 동형. 본 프로젝트 권한 모델 = "메뉴(scope) × CRUD(action)" 매트릭스로 설계해야 한국 관행 + 성숙 플랫폼 동시 충족.
- **전체 권한 부여** = 모든 메뉴 체크 + 전체선택. → SUPER에 해당.

### 4.2 관리자 접속 IP 제한 + 접속 시간 제한 (고도몰/카페24)

> 출처: [고도몰 관리자 IP접속제한 설정](http://guide.godo.co.kr/season4/board/view.php?id=basic&no=35) · [상점/보안 설정 – 카페24](https://support.cafe24.com/hc/ko/articles/7751558333081)

- **허용 IP 등록 + 와일드카드(`*`) 대역 설정** + 허용/차단 모드. 미인가 IP 접속 시 **403 또는 리다이렉트**. **관리자 페이지 로그인에만 적용** (스토어프론트 무관). → d21 `admin_ip_blocks`는 "5회 실패 자동 차단"만 박제 → **한국 관행 정합을 위해 "허용 IP allowlist(화이트리스트)" 정책 추가 권장** (§5.4).
- **부운영자 접속 허용 시간** 설정 — 시간 외에는 관리자 접속 불가(스토어프론트는 가능). → 운영 시간 제한 정책(`admin.access.allowed_hours`) 추가 검토 권장.
- **정보통신망법**: 관리자 로그인 추가 인증수단(SMS/IP 제한) 미조치 시 법적 처벌 가능. → 본 프로젝트 MFA TOTP + IP 제한으로 충족.

### 4.3 관리자 활동 로그 / 접속기록 보관 (ISMS-P)

> 출처: [ISMS-P 2.9.4 로그 및 접속기록 관리 – IT위키](https://itwiki.kr/w/ISMS-P_%EC%9D%B8%EC%A6%9D_%EA%B8%B0%EC%A4%80_2.9.4.%EB%A1%9C%EA%B7%B8_%EB%B0%8F_%EC%A0%91%EC%86%8D%EA%B8%B0%EB%A1%9D_%EA%B4%80%EB%A6%AC) · [ISMS 2.6 접근통제 – CELA](https://www.cela.kr/ISMS_2_6)

- 개인정보처리시스템 접속기록은 **위·변조/도난/분실 방지** 안전 보관 의무 — 상시 백업 + 보조저장매체 또는 **덮어쓰기 방지 매체(WORM/CD-R)**. → d21 F7(INSERT only + UPDATE/DELETE 금지)이 이 요건을 직접 충족. **WORM/append-only 스토리지 또는 SIEM 위탁(S4)** 으로 강화.
- 접속기록 보관 기간 (개인정보보호법 시행령 — 통상 **최소 1년, 5만명 이상/민감 시 2년**). → 본 프로젝트 d21 F7 = 5년(전자상거래법 거래기록)은 더 보수적. 감사 로그 = 5년, 단순 접속기록(로그인) = 최소 1~2년 분리 보관 가능 (§5.3).

### 4.4 공지/배너/팝업 관리 (쇼핑몰 공통 관행)

- 공지사항: 노출 기간(시작/종료) + 노출 순서 + 긴급 고정(상단). FAQ: 카테고리 + 노출 순서.
- 배너/팝업: 메인 배너 슬롯 + 팝업("오늘 하루 안 보기" 쿠키) + 상단 공지 띠. **SVG 업로드 시 악성 스크립트(XSS) 검증** (d21 F21).
- → 한국 쇼핑몰 어드민 표준 메뉴 구조. ADM-N(공지 5) / ADM-F(FAQ 5) / ADM-B(배너 7) QA 정합.

## 5. 종합 설계 결정

> §3(성숙 플랫폼) + §4(한국 관행) + §2(우리 S0)를 종합. 추측 금지 — 근거 명시.

### 5.1 RBAC 모델 — Role + Permission 분리 (Q7 해소안) ★ 핵심 결정

**결정**: 역할 enum 고정(3-role vs 4-role 충돌)을 폐기하고, **Vendure 패턴(§3.1) + 카페24 메뉴별 권한(§4.1)** 을 결합한 `역할(role) + 권한(permission)` 2-테이블 구조 채택.

- `admin_roles`: 역할 정의 (시스템 role + custom role). 시스템 role = `SUPER`(전권, 수정·삭제 불가) + 기본 제공 `OPERATION`(=운영자) + `CS` + `MARKETER`.
- `admin_permissions`: `scope(메뉴) × action(CRUD)` 단위 권한 마스터 (Vendure CRUD 동형).
- `admin_role_permissions`: role ↔ permission 매핑 (M:N).
- `admin_accounts.role_id` (단일) 또는 `admin_account_roles`(다중, Vendure union 패턴) — **MVP는 단일 role**(한국 운영자 멘탈모델 단순), 후속 다중 role 확장 여지.

**근거**:
- Q7의 4-role(MARKETER 분리)·3-role(OPERATION 통합)이 모두 "권한 묶음" 으로 표현 가능 → enum 충돌 소멸. MARKETER = "마케팅 scope write만 가진 role".
- 카페24 "메뉴 접근 권한 + 상세 권한" 2계층(§4.1)이 `scope × action`에 정확 매핑.
- Vendure deny-by-default(§3.1) → 권한 미명시 = 거부 (대전제 ①오류 없음).
- **사장님 Q7 결정 필요**: 시스템 role 기본 셋을 `SUPER/OPERATION/CS/MARKETER`(권장)로 시드할지. 4개 role을 권한 묶음으로 시드하면 v4 QA(3-role)·d21(4-role) 양쪽 모두 수용.

### 5.2 관리자 인증·세션 (사용자 완전 분리 유지)

**결정**: d21 F1~F5/F17~F19 유지 + Spree 패턴(§3.3) 보강.
- 별도 JWT secret + 별도 DB pool(sensitive_pool). Access 15분 / Refresh 8시간.
- MFA TOTP 필수 (mfa_enrolled_at NULL → 진입 차단). 백업 코드 10개(bcrypt). secret AES-256.
- Refresh = HttpOnly+Secure+SameSite=Strict 쿠키, Access = 메모리. (Spree 패턴: refresh 쿠키 Path를 `/admin/auth`로 스코프 한정 권장 — XSS 시 결제 라우트에 미전송.)
- 5회 실패 → 30분 IP 차단 + 계정 잠금. 비번 12자+ 4종, 90일 만료.

### 5.3 감사 로그 (ISMS-P 정합 강화)

**결정**: d21 F6~F8/F14 유지 + ISMS-P(§4.3) 보강.
- `admin_audit_logs` = **append-only** (DB 권한에서 UPDATE/DELETE revoke + WORM 또는 SIEM 실시간 스트림(S4)). 위·변조 방지 충족.
- 보관: **감사 로그(업무) = 5년**(전자상거래법) / **로그인 접속기록 = 최소 2년**(개인정보보호법) 분리. (현 d21은 5년 단일 — ISMS 1~2년 최소 요건은 충족, 비용 시 분리 권장 = Q4 SIEM 위탁 연계.)
- 모든 admin write 액션 자동 박제 (미들웨어, f20 §3.3). PII 마스킹(비번/카드/토큰/MFA secret 평문 금지). failure/partial도 박제(보안 상관 분석 입력).

### 5.4 IP 제한 — allowlist 추가 (한국 관행 정합)

**결정**: d21 `admin_ip_blocks`(자동 차단)에 더해 **`admin_ip_allowlist`(화이트리스트)** 정책 추가 (고도몰/카페24 §4.2 관행).
- `system_policies` key = `admin.ip.allowlist`(IP/CIDR 배열) + `admin.ip.allowlist_enabled`(bool). enabled=true 시 allowlist 외 관리자 로그인 → 403.
- 와일드카드/CIDR 대역 지원. 미인가 IP = 403 + 감사 박제.
- (선택) `admin.access.allowed_hours` 운영 시간 제한 — 부운영자 한정 적용 (카페24 관행).
- 본 정책은 **system_policies로 관리** (코드 배포 없이 변경) — 운영 유연성.

### 5.5 정책 저장소 (Vendure Settings Store 정합)

**결정**: d21 `system_policies` 유지 (Vendure Settings Store §3.2와 동형 검증 완료).
- key(도트) + value JSONB + scope(12) + value_schema(JSON schema 검증) + version(낙관락).
- 변경 = SUPER + 이중 확인(confirm_token) + 사유 + **즉시 캐시 PURGE + history INSERT + SUPER 전원 알림**(F9/F10, f20 §3.2).
- d11~d20 모든 도메인 정책의 **단일 진입점** (`/admin/system/policy?scope=X`).

### 5.6 공지/배너/마케팅/시스템설정

**결정**:
- 공지/FAQ/배너 = 커스텀 모듈(`content` 또는 `cms`)로 CRUD. 배너 SVG = 업로드 시 sanitize(악성 스크립트 제거, F21).
- 마케팅(f21) = 별도 도메인 권장(O5)이나 권한·감사·정책은 본 도메인 인프라 사용. 발송 = notification 모듈 위탁. 광고성 표기·야간 차단·동의 필터 다중 방어선 유지.
- 시스템설정(약관/캐시/점검/출석/매출리포트/CS통합) = `system_policies` + 전용 커스텀 모듈 혼합.

### 5.7 강제 조치·이중 확인·일괄 처리

**결정**: d21 §6.4 강제조치 매트릭스 + `confirm_tokens`(Tier1~4) + `bulk_jobs`(dry-run+rate limit) 유지. 모든 강제 조치 = 사유 NOT NULL + 감사 박제 + 사용자 통보 + 트랜잭션 무결성.

## 6. Medusa 코드 매핑

> 코어 무수정 격리 원칙 (`legal-kr/withdrawal-7day` 패턴 = 커스텀 모듈 + `src/api` route + workflow). 기존 `state-machine` 커스텀 모듈(`apps/backend/apps/backend/src/modules/state-machine/`)이 정확한 격리 선례.

### 6.1 ⓐ 활용할 Medusa native

| Medusa native | 활용 |
|---|---|
| `@medusajs/user` (User 모델) | 관리자 프로필(first_name/last_name/email/avatar_url/metadata). 단 **role/MFA/잠금 필드는 native에 없음** → 커스텀 확장 또는 별도 모델 (§6.2). |
| `@medusajs/user` (Invite) | 관리자 초대(token+expires_at) — 카페24 운영자 초대 관행 직접 충족. |
| `@medusajs/auth` (AuthIdentity, actor_type="user") | 관리자 자격증명. emailpass provider. `app_metadata.user_id` 매핑. |
| `authenticate("user", ["session","bearer"])` 미들웨어 | `/admin/*` actor type 보호. |
| Notification 모듈 | 헬스 알람·정책 변경 알림·마케팅 발송 위탁(`createNotifications`). |
| Admin customization (UI route / widget zone) | s35/s36/s47/s48/s49 관리자 화면 = `src/admin/routes` + widget. |
| 기존 커스텀 `state-machine` 모듈 | 관리자 강제 상태 전이(주문 강제취소 등) 시 `transition()` 호출 → StateHistory 자동 박제. **본 도메인 감사 로그와 보완**(state-machine = 상태 전이 audit, admin_audit_logs = 행위 audit). |

> **주의**: Medusa native User에는 비밀번호 정책·MFA·failed_login_count·locked_until·role이 없음 (Auth 모듈이 자격증명, RBAC는 feature-flag `rbac` 미확정 — `사용자인증_14정의서.md §4-5` "추가 확인 필요"). 따라서 d21의 강한 요건(MFA 필수·5회 잠금·5년 감사)은 **native만으로 불충족 → 커스텀 모듈 필수**.

### 6.2 ⓑ 필요한 커스텀 모듈 / API route / admin route (코어 무수정)

**커스텀 모듈** (`src/modules/` — state-machine 격리 패턴 동일):

| 모듈 | 모델 | 책임 |
|---|---|---|
| `admin-rbac` | `AdminRole` · `AdminPermission` · `AdminRolePermission` · `AdminProfile`(MFA/잠금/role_id — User 보완) | RBAC + MFA + 계정 상태. §5.1 결정. |
| `admin-audit` | `AdminAuditLog`(append-only) | 모든 write 액션 감사. `transition()` 유사 `record(action, target, before, after, reason, result)` 메서드. INSERT only 서비스. |
| `system-policy` | `SystemPolicy` · `SystemPolicyHistory` | 정책 저장소 + 이력. UPDATE 시 history 자동 INSERT + 이벤트 발행. |
| `system-ops` | `SystemHealth` · `MaintenanceMode` · `AdminIpBlock` · `AdminIpAllowlist` · `ConfirmToken` · `BulkJob` | 헬스·점검·IP·이중확인·일괄. |
| `cms-content` | `Notice` · `Faq` · `FaqCategory` · `Banner` · `Popup` | 공지/FAQ/배너/팝업 CRUD. SVG sanitize. |
| `marketing`(별도 도메인, f21) | `MarketingSegment` · `SegmentRun` · `SegmentRunTarget` · `Send` · `SendLog` · `MarketingWebhookEvent` | 세그먼트·발송·KPI. |

> 각 모듈 = `index.ts(Module 정의) + models/ + service.ts(MedusaService 확장) + migrations/ + seed.ts`. state-machine 모듈과 동일 구조.

**커스텀 actor type / 인증**:
- 옵션 A (권장): `@medusajs/auth` emailpass + `admin-rbac` 모듈의 `AdminProfile`로 role/MFA 보강. MFA = `/auth` 위에 커스텀 2-step route(temp_token → TOTP verify).
- 옵션 B: 커스텀 actor type 신설 (create-actor-type 가이드) — User와 분리. MVP는 옵션 A(User actor type 재사용 + 보강)가 변경 최소.

**API route** (`src/api/admin/` — 코어 무수정):
- `src/api/admin/auth/*` (login/mfa/verify/refresh/logout) · `admins/*`(계정 CRUD) · `audit-logs/*` · `system/policy/*` · `system/health` · `system/maintenance` · `system/ip-blocks` · `system/ip-allowlist` · `dashboard` · `cms/*`(공지·FAQ·배너) · `marketing/*`(세그먼트·발송·KPI·webhook).

**미들웨어** (`src/api/middlewares.ts`):
- `authenticate("user", ...)` + 커스텀 `requirePermission(scope, action)`(deny-by-default, Vendure 패턴) + `adminAuditMiddleware`(write 자동 박제, f20 §3.3) + `maintenanceGuard`(scope=user 시 사용자 라우트 503) + `ipAllowlistGuard`.

**defineLink**: `AdminProfile` ↔ `User`(1:1) · `AdminAuditLog` ↔ `AdminProfile`(N:1) · `SystemPolicy` ↔ `AdminProfile`(updated_by).

**Admin UI route**: `src/admin/routes/{login,dashboard,system/policy,system,marketing,content}` + widget injection.

### 6.3 ⓒ 마이그레이션 계획

- 각 커스텀 모듈 = `npx medusa db:generate <Module>` → `db:migrate`. zero-downtime = d21 F-MIG-01(ADD→BACKFILL→SWITCH→REMOVE) + `CREATE INDEX CONCURRENTLY`.
- seed: `admin-rbac` = 시스템 role 4종(SUPER/OPERATION/CS/MARKETER) + permission 마스터(scope×CRUD) + role-permission 매핑 시드 (state-machine `seed.ts` 패턴). `system-policy` = d11~d20 default 정책 시드. `system-ops` = 헬스 component 9종 등록.
- 최초 SUPER 관리자 = seed 또는 부트스트랩 스크립트 (Vendure "최초 관리자 = SuperAdmin" 패턴).

### 6.4 코어 무수정 격리 검증

- ✅ 모든 신규 모델 = `src/modules/` 커스텀 모듈 (User/Auth core 테이블 무변경, AdminProfile로 보완).
- ✅ 모든 신규 API = `src/api/admin/*` route (core route 무수정).
- ✅ 감사 자동 박제 = 미들웨어 (core 비침습).
- ✅ state-machine 모듈 격리 선례와 100% 동일 패턴 (index/models/service/migrations/seed).

## 7. 현 코드와의 관계 + 구현 단계

### 7.1 현 코드 관계

| 현 코드 | 관계 |
|---|---|
| `@medusajs/user` + `@medusajs/auth` (native) | 관리자 프로필·자격증명 기반. role/MFA/잠금/감사는 커스텀 보완 필요 (native 미제공). |
| `src/modules/state-machine` (커스텀, 기존) | **격리 패턴 선례** + 보완 관계. 관리자 강제 상태 전이는 `transition()` 위임 → StateHistory(전이 audit) + admin_audit_logs(행위 audit) 이중 박제. |
| `legal-kr/withdrawal-7day` (코어 무수정 격리 패턴) | 본 도메인 커스텀 모듈 격리 원칙의 표준. |
| 기존 admin route (없음 확인됨) | 본 도메인이 admin 인증·권한·감사 인프라를 신규 제공. |

### 7.2 구현 단계 (immediate / 다음)

**immediate (MVP P1 — 보안 기반)**:
1. `admin-rbac` 모듈 (AdminProfile + Role + Permission + 시드 4-role) — **Q7 사장님 결정 후 시드 확정**.
2. `admin-audit` 모듈 (append-only) + `adminAuditMiddleware`.
3. 관리자 인증 route (login → MFA verify → 세션) + `authenticate` + `requirePermission` 미들웨어.
4. `system-policy` 모듈 + d11~d20 default 시드 + 정책 변경 route(SUPER+confirm+사유+PURGE).
5. `admin_ip_blocks` 자동 차단 + `admin_ip_allowlist`(한국 관행, §5.4).
6. s35(로그인)·s36(대시보드)·s48(정책)·s49(계정·감사·헬스) admin UI route.

**다음 (P2+)**:
7. `system-ops` 헬스 30초 잡 + 알람(notification) + 점검모드 가드.
8. `confirm_tokens`(Tier1~4) + `bulk_jobs`(dry-run+rate limit) + 강제조치 매트릭스.
9. `cms-content` (공지/FAQ/배너 — SVG sanitize 포함).
10. `marketing` 도메인 (세그먼트·발송·KPI·webhook 5중 검증) — f21.
11. SIEM 연동(S4) + WORM 보관(ISMS-P) + Tier4 외부 승인(Slack) + outbox/DR/SLO 운영 메타.

### 7.3 결정 필요 (사장님)

- **Q7 (★)**: 시스템 role 시드 = `SUPER/OPERATION/CS/MARKETER` 4종(권장 — 권한 묶음으로 v4 3-role도 수용) 확정 여부.
- Q1 점검모드 scope=both 허용 / Q3 비민감 정책 MANAGER 허용 / Q4 감사 SIEM 위탁 + 접속기록 보관기간 분리(5년 vs 2년) / Q5 MFA 백업코드 운영 / Q6 헬스 알람 임계.
- §5.4 IP allowlist + 운영 시간 제한 도입 범위 (전 관리자 vs 부운영자 한정).
