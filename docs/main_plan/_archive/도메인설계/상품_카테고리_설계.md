## 1. 도메인 개요
상품을 **3개 축**으로 분류한다. 한국 대부분 쇼핑몰(카페24·스마트스토어·고도몰)과 성숙 플랫폼(Spree 6.0)이 동일하게 분리하는 정답 패턴이다.

| 축 | 명칭 | 역할 | 성격 |
|---|---|---|---|
| ① | **진열 카테고리** (Display Category) | 네비게이션·필터·진열·SEO | 계층 트리·수동 |
| ② | **상품유형** (Product Type) | **옵션 템플릿 + 상품정보제공고시 필수항목**을 정의 → 등록폼 자동생성·검증 | 스키마 템플릿 |
| ③ | **컬렉션** (Collection) | 기획전·시즌·세일·신상 등 마케팅 묶음 | 평면·큐레이션 |

> 핵심: **"무엇을 파는가(유형)"가 옵션·법정고시를 결정**하고, **"어디에 진열하는가(카테고리)"는 별개**다. 둘을 분리해야 오류가 없고 관리가 쉽다.

## 2. 우리 S0 설계 요약
- **d12 상품**: `products.category_id` = **단일 FK(NOT NULL)** → 한 상품 = 1차 분류 1개. `product_options.type` = color/size 고정(주얼리 MVP), `product_skus.option_combo`(JSONB) + stock(CHECK≥0).
- **d13 카테고리**: 계층 트리(`parent_id`, 1-2단 MVP), name(한글)/slug(영문)/is_active/display_order/thumb_url. 진열·필터·SEO 책임. 비활성 시 미노출·필터 제외·404.
- **deep-research §5 (★법령)**: **상품 카테고리(상품군)별 법정 필수 고시 상이** — 의류=원산지·소재·세탁 / 화장품=용량·사용기한·주성분·제조국 / 전자=KC인증. 전자상거래법 「상품정보제공 고시」.

→ S0는 **1상품=단일 category_id**. 본 설계는 이를 **primary 분류 1개(필수) + 진열 카테고리 다중(선택)**로 확장하고(권장안 확정, §C), **옵션·고시 결정 권위는 카테고리가 아니라 상품유형(§5.2)**으로 분리한다. (검수 A2 self-contradiction 해소 — `_보강설계_결정반영.md §C` 참조)

## 3. 성숙 플랫폼 패턴 (Spree 6.0)
출처: `외부참조문서/스프리/스프리_docs_plans_6.0-product-types.md`, `6.0-replace-taxons-with-categories.md`

- **Category** — 계층(nested set) 분류, 상품의 1차 진열 홈. 수동.
- **Collection** — 평면, 수동/룰기반(시즌·세일·신상). 머천다이징.
- **ProductType** = **라이브 템플릿**:
  - **OptionTypes** 정의 → 해당 유형 전 상품에 전파(additive floor: 유형 옵션은 제거 불가, 상품은 추가 가능)
  - **MetafieldDefinitions**(`required`+`sort_order`) 정의 → **상품 속성 스키마 강제** = 우리의 **상품정보고시 필수항목**과 정확히 일치
  - 등록폼 자동 생성, 게시 전 required 검증
  - 유형 변경은 metafield 값 무효화 → 값 할당 후 immutable

## 4. 한국 관행 (웹 근거)
- **진열 카테고리**: 대>중>소>**상세 (최대 4단)** 트리, 드래그 정렬, 하위분류 진열 옵션 — 카페24 표준. (출처: 카페24 상품 분류 관리)
- **상품정보제공고시**: 전자상거래법 고시, **약 40종 표준 품목**(의류·신발·가방·악세서리·화장품·향수·농/수/축산물·가전·음향·영상·모바일/컴퓨터·가구·서적 등). 품목별 필수항목 상이. 의류=소재·세탁·원산지 / 화장품=용량·사용기한·주성분·제조국 / 전자·향수=KC인증. **모든 한국 몰이 상품등록 시 "고시 품목 드롭다운" 제공**. (출처: 고도몰 상품정보제공 고시 가이드)
- **옵션**: 상품별 색상/사이즈 정의 + 카테고리/유형 기반 옵션 제안(스마트스토어 등).

→ 한국 관행도 **진열 카테고리(4단)와 상품유형(고시 품목)을 분리**. 사장님 조건("우리나라 대부분 쇼핑몰 체계") 충족.

## 5. 종합 설계 결정

### 5.1 ① 진열 카테고리 (Display Category) — 권장안 확정
- 계층 트리 **대>중>소>상세(최대 4단)** (카페24 표준). name 한글/slug 영문/is_active/display_order/thumb.
- 상품 = **primary 분류 1개(필수)** + **진열 카테고리 다중(선택)** (예: "신상" + "원피스"). primary가 1차 분류 권위.
- ※ **S0 갱신 필요**(사장님 권장안 승인): d13 `1-2단 → 4단`, d12 `category_id 단일 → primary_category_id + product_category 다대다 진열`. Medusa native `product_category`(N:N) 활용. (`_보강설계_결정반영.md §A-1 #4·§C`)

### 5.2 ② 상품유형 (Product Type) — 본 설계의 핵심
- 상품유형 = **옵션 템플릿 + 고시 필수항목 정의**를 가진 라이브 템플릿. 한국 "상품정보제공고시 품목"을 기반으로 구성.
- 상품은 **유형 1개**에 귀속(1:1, nullable). 유형이 (a)기본 옵션 (b)법정 고시 필수항목을 결정.
- 등록 시 유형 선택 → 옵션폼 + 고시폼 자동 생성. 게시 전 **고시 필수값 검증(누락 차단 = 대전제①)**.

### 5.3 ③ 컬렉션 (Collection)
- 시즌·기획전·세일·신상. 평면. 수동/룰. (타임세일은 d12 time_sales 연계)

### 5.4 엔티티(개념)
```
product_type (상품유형)
  - id, name(예: 의류), disclosure_code(고시 품목코드, 예: clothing), rank
product_type_option (유형 옵션 템플릿)
  - product_type_id, option_title(사이즈/색상/손가락 호수), option_values(json), rank
product_type_disclosure_field (유형 고시 필수항목 정의)   ← 2단계
  - product_type_id, field_key(소재/세탁방법/제조국…), label, required(bool), sort_order, input_type
product_disclosure_value (상품별 고시 입력값)              ← 2단계
  - product_id, field_key, value
```

## 6. Medusa 코드 매핑 (코어 무수정 · legal-kr 격리 패턴)

| 축 | Medusa native | 커스텀(우리) |
|---|---|---|
| ① 진열 카테고리 | `product_category`(계층 N:N) 그대로 활용 | (없음) — d13 정합 |
| ② 상품유형 | `product.type_id` → `product_type`(라벨만) | **신규 모듈 `product-type`**: 옵션 템플릿 + 고시 필드 정의를 Medusa product_type.id 에 연결(defineLink 또는 type_id 참조). 등록폼 자동생성·검증은 admin route + API. |
| ③ 컬렉션 | `product_collection` 활용 | 룰기반/타임세일은 커스텀(d12 연계) |

- 옵션/variant/SKU = Medusa native(`product_option`/`product_variant`) 그대로. 유형 템플릿이 등록폼에 주입.
- 고시값 저장 = `product.metadata` 또는 별도 `product_disclosure_value` 모듈(2단계). 검증 = 게시 전 API hook.
- 모든 커스텀은 `src/modules/` 격리(코어 엔티티 무수정), 기존 `legal-kr/withdrawal-7day` 패턴 준수.

## 7. 현 코드와의 관계 + 구현 단계

### 현 상태(2026-05-31 오전 구현)
- `src/modules/option-template` (category_id 기준 옵션 템플릿) + `/admin/option-templates` API + `/app/product-mgmt` 등록 화면. **축이 "카테고리"로 한 칸 어긋남.**

### 진화 계획
| 단계 | 내용 | 상태 |
|---|---|---|
| **1 (immediate)** | `option-template` → **`product-type`** 모듈로 진화. 키 `category_id` → `product_type_id`. 옵션 템플릿을 **상품유형**에 귀속. 시드(의류·신발·악세서리·가방 → 상품유형). 등록 화면 = 진열 카테고리 선택 + **상품유형 선택→옵션 자동**. | 진행 |
| **2** | 상품유형에 **고시 필드 정의**(`product_type_disclosure_field`) 추가 + 등록폼 고시 입력 + 게시 전 필수 검증. 고시 품목 ~40종 시드. | 다음 |
| **3** | 진열 카테고리 4단 트리 관리 화면(d13/s39) + 상품의 진열 카테고리 다중 배치 + primary 지정. | 다음 |

### 마이그레이션 주의
- 현 `category_option_template` 테이블 → `product-type` 스키마로 이전(데이터 적어 재시드 가능). 기존 시드 카테고리(의류·신발·악세서리·가방)는 **진열 카테고리로 유지**하되, **동명의 상품유형**을 신설해 옵션을 그쪽으로 귀속.
