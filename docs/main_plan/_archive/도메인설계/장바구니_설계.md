## 1. 도메인 개요

- **1줄 책임**: 회원 카트 보관·옵션/수량 관리·쿠폰 미리 적용·실시간 가격/재고 재검증·주문서 진입 게이트 — 결제 직전까지 수정 가능한 **임시 가변 상태 버퍼**.
- **범위 경계 (in)**: 담기 UPSERT, 라인 수량/옵션 변경, 단일/선택/전체 삭제, 카트 단일 쿠폰 미리 적용, 카트 진입 실시간 재검증(단가·재고·옵션·쿠폰), 합계 실시간 계산(무료배송 기준 안내), 비회원→회원 카트 병합, 주문서 진입 페이로드 생성, 장기 미결제 리마인드/자동 정리 배치, 관리자 통계·CS 조회.
- **범위 경계 (out)**:
  - 재고 차감 **실행** = product 도메인(d12). 본 도메인은 실시간 **조회·재검증 호출**만.
  - 쿠폰 발급·잔여 검증 = coupon_point 도메인(d20). 본 도메인은 **적용 시도/해제**만.
  - 결제 트랜잭션·주문 INSERT = order 도메인(d16). 본 도메인은 **주문서 진입 페이로드 생성**까지.
  - 배송지 CRUD = member 도메인(d11). 본 도메인은 주문서 진입 시 **직전 배송지 매칭 힌트**만.

## 2. 우리 S0 설계 요약

### 2.1 엔티티 (`d14 §2`)
- **carts** (PK = `member_id`, 회원당 1:1) — `created_at`, `updated_at`, `last_seen_at`, `abandoned_notified_at`.
- **cart_items** — `id`(PK), `cart_id`, `product_id`, `sku_id`, `qty`(CHECK 1~min(stock,99)), `added_at`, `selected`(체크 결제), `price_at_add`(담기 시점 단가 스냅샷, 변동 감지용), `version`(last-write-wins 보조). **`UNIQUE(cart_id, sku_id)`** — 동일 옵션 중복 금지(합산).
- **cart_coupon_applied** (PK = `cart_id`) — 카트당 쿠폰 1건(`coupon_id`, `applied_amount`, `applied_at`).
- **guest_cart** — 서버 미저장. 클라이언트 localStorage `shop_guest_cart_v1`(TTL 30일). 로그인 직후 서버 병합 후 초기화.

### 2.2 핵심 룰 (`d14 §6` / `f13 §4`)
- **F1** 회원당 카트 1건 / **F2** 동일 sku_id UPSERT 합산 / **F3** 1≤qty≤min(stock,99) / **F4** 1인당 수량 = 카트+주문 합산 / **F5** 라인 최대 50.
- **F6** 카트 진입 시 실시간 재검증(단가·재고·옵션·쿠폰) / **F7** 가격·옵션·품절 변동 배지 / **F8** 동시 수량 변경 = **last-write-wins**(낙관락 재시도 X) / **F9** 카트 쿠폰 1건 / **F10** 카트 변경 시 쿠폰 조건 재검증→실패 자동 해제 / **F11** 결제 진입 시 쿠폰 → `orders.coupon_id` 이관 + 삭제.
- **F12** 비회원 = localStorage, 서버 미저장, 결제 진입 시 로그인 게이트 강제 / **F13** 로그인 직후 병합(sku 합산, `min(server+guest, stock, 99)` 상한) / **F14** 세션 만료 시 회원 카트 영속 보존 / **F15** 단종/hidden 라인 노출하되 결제 시 자동 제외 / **F16** 주문서 페이로드 = `selected=TRUE` 라인만 + 1단계 재검증 / **F18** 합계 = 상품합 + 쿠폰 차감 + 무료배송 기준 안내 / **F20** 가격 인하 라인 "가격이 내렸어요" 배지 + 즉시 신단가 / **F21** 주문서 진입 시 직전 배송지(`addresses.last_used_at`) 자동 선택 / **F22** 카트→위시 이동.
- **정책(관리자)**: P1 자동 정리 7일 / P3 전체 삭제 90일(P6 = 7~365일 설정 가능) / P4 라인 50 / P5 무료배송 기준(본문 정합 50,000원, `f13-Q06` 미결) / P7 리마인더 지연 24h.
- **보안**: S1 IDOR 차단(본인 카트만) / S2 관리자 조회 = 읽기 전용 + 감사 로그 / S3 일괄 작업 = 사유 필수 + 감사.

### 2.3 이벤트 (`d14 §7`)
- **발행**: `cart.item_added/quantity_changed/item_removed/coupon_applied/coupon_removed/abandoned/merged_from_guest`.
- **구독**: `product.sold_out/restocked/price_changed/option_changed/status_changed`, `timesale.closed`, `order.created`, `coupon.expired/consumed`.

### 2.4 QA 범위
- 사용자 CRT-U-001~020 (20건) + 관리자 CRT-A-001~006 (6건) + 비기능 4건 = **30건**(`d14 §9`).

## 3. 성숙 플랫폼 패턴

### 3.1 Vendure — "Cart = AddingItems 상태의 Order" (단일 모델)
출처: `외부참조문서/벤듀어/벤듀어_docs_docs_guides_core-concepts_cart_index.mdx`, `.../storefront_active-order_index.mdx`

- **별도 Cart 엔티티 없음**: 카트 = `AddingItems` 상태의 Order. 동일 테이블·동일 상태머신이 카트→이행까지 관장.
- **active order 패턴**: 세션(게스트/인증 무관)당 활성 주문 1건. `addItemToOrder/adjustOrderLine/removeOrderLine`가 세션 컨텍스트로 활성 주문 자동 해석(주문 ID 불필요).
- **동일 variant 재담기 = 기존 OrderLine quantity 증가**(중복 라인 생성 X) → **우리 F2(UPSERT 합산)와 동일 철학**.
- **Order Interceptors**: 카트 수정 시점에 커스텀 검증(상품당 최대 수량, 재고 확인, 비즈니스 룰)을 내장 mutation 오버라이드 없이 주입 → **우리 F3/F4/F5 검증 훅과 매핑**.
- **게스트→인증 병합**: 게스트 로그인 시 익명 카트 + 계정 카트 병합으로 손실 방지 → **우리 F13와 동일**.
- **AddingItems → ArrangingPayment 전이 검증**: 최소 1개 라인 + 배송 방법 설정 필수 → **우리 F16 결제 진입 게이트(최소금액·품절 차단)와 매핑**.
- **배울 점**: 카트와 주문의 라인 스냅샷 일관성, 세션 기반 활성 카트 해석, 검증 훅(interceptor) 패턴.

### 3.2 Spree 6.0 — Cart/Order 분리 + copy-on-completion
출처: `외부참조문서/스프리/스프리_docs_plans_6.0-cart-order-split.md`

- **Cart와 Order를 별도 모델로 분리**(6.0 설계 확정), LineItem은 polymorphic `owner`(Cart 또는 Order).
- **copy-on-completion**: 체크아웃 완료 시 카트 아이템을 주문으로 **복사**(`cart.complete!` → `Spree::Carts::Complete`). Order 레벨 상태머신 제거, status는 파생.
- **배울 점**: 우리 설계가 채택한 **"카트는 임시 버퍼, 주문 생성 시 라인 복사·이관"** 방향(F11·F16)과 정확히 일치. Vendure(단일 모델)와 Spree 6.0(분리 모델) 중 **우리는 Spree 방향(별도 carts/cart_items 테이블)** = 회원 전용 영속 카트 + 주문은 별도 트랜잭션이라는 우리 도메인 경계와 정합.
- **주의**: Medusa는 Vendure보다 Spree에 가까운 "별도 Cart 모델 + `complete_cart`로 Order 변환" 구조 → 우리 카트 모델(별도 테이블)이 Medusa 코드 매핑 시 자연스럽게 수렴(§6).

### 3.3 종합 — 우리 채택 방향
| 항목 | Vendure | Spree 6.0 | Medusa | **우리 채택** |
|---|---|---|---|---|
| 모델 구조 | Order 단일 | Cart/Order 분리 | Cart/Order 분리 | **분리(별도 carts)** |
| 동일 항목 재담기 | quantity 증가 | line 합산 | line 추가 | **UPSERT 합산(F2)** |
| 카트→주문 | 상태 전이 | copy-on-completion | `complete_cart` | **쿠폰/라인 이관(F11/F16)** |
| 게스트 병합 | 익명+계정 병합 | — | `transfer-cart-customer` | **localStorage→서버 병합(F13)** |
| 카트 수정 검증 | Interceptor | — | refresh hooks | **재검증 훅(F6)** |

## 4. 한국 관행 (웹 근거)

### 4.1 비회원 장바구니 + 회원 전환
출처: [카페24 주문 시 설정](https://support.cafe24.com/hc/ko/articles/7751230009113), [비회원 구매 내역 회원 적용](https://support.cafe24.com/hc/ko/articles/18812256498201)
- 카페24는 **비회원 장바구니 담기 허용** + 비회원/회원 구매 정책을 관리자에서 설정. 비회원 구매 내역을 **회원가입 후 아이디에 연결**하는 동선이 표준.
- **우리 정합**: 우리는 회원 전용 서버 카트 + 비회원 localStorage(F12) + 로그인 시 서버 병합(F13). 카페24의 "비회원→회원 연결" 관행과 동일 목적이나, 우리는 **결제 진입 시 로그인 강제 게이트**(`00_개요 §2 #8`)로 더 단순화 = 비회원 서버 카트(O1) 미지원.

### 4.2 옵션별 재고·수량·가격, 품절·재입고 알림
출처: [스마트 스토어 상품 옵션 설정](https://talk.cashnote.kr/article/CONTENT/39500), [상품 품절 처리(품고)](https://guide.poomgo.com/96f830ee-b9e7-457a-aba2-2cead5d34784), [재입고 알림(위사 스마트윙)](https://help.wisa.co.kr/document/article/2439)
- **옵션별 재고**: 조합형 옵션 사용 시 **옵션(SKU)별 재고**가 곧 상품 재고. → 우리 `cart_items.sku_id` 단위 재고 검증(F3)과 정합.
- **판매상태**: 준비중/판매중/품절 상태 + 품절 아이콘 노출. → 우리 F7(품절 배지) / F15(단종·hidden 노출 후 결제 제외)와 정합.
- **재입고 알림**: 재고관리 사용 상품에 한해, 옵션별 허용 품절방식 설정, 잔여 0 이하 시 신청. → 우리 `product.restocked` 구독(배지 해제·재검증)과 정합(단, 카트 도메인은 알림 구독만, 발송은 notification 도메인).
- **가격 할인**: 정액/정률 + 특정기간 한정 판매(타임세일). → 우리 `price_at_add` 스냅샷 + `product.price_changed`/`timesale.closed` 구독(F7/F20)과 정합.

### 4.3 장바구니 만료
- 카페24/스마트스토어 공개 문서에서 **명시적 "장바구니 만료 기간" 표준값은 확인 불가**(추가 확인 필요). 업계 통념상 회원 카트는 장기 영속, 비회원 카트는 쿠키/세션·로컬 기반 단기.
- **우리 정합**: 회원 카트 영속(F14) + 관리자 설정 가능 만료(P3=90일 기본, P6=7~365일 / `f13-Q08` 미결) + 비회원 localStorage TTL 30일(F19). 이는 한국 관행의 "회원 영속 / 비회원 단기"를 정책화한 합리적 기본값.

## 5. 종합 설계 결정

> Vendure(검증 훅·병합·active order) + Spree(분리 모델·copy-on-completion) + 한국 관행(옵션별 재고·품절 배지·회원 영속) + 우리 S0를 종합. 우리 S0가 이미 한국 친화·법령 정합으로 정교하므로 **S0를 권위 기준으로 확정**하고, 외부 패턴은 구현 시 차용할 메커니즘으로 정리.

### 5.1 엔티티·관계 (확정 = S0 d14 §2 그대로)
```
carts (PK=member_id, 1:1 members)
  └─ 1:N ── cart_items (UNIQUE(cart_id, sku_id))
  └─ 1:1 ── cart_coupon_applied (카트당 쿠폰 1건)
guest_cart = localStorage shop_guest_cart_v1 (서버 미저장, TTL 30일)
```
- **결정 D1**: 모델은 **분리형**(별도 carts/cart_items) 채택 — Spree 6.0/Medusa 방향. Vendure 단일 모델(Order=Cart)은 우리 "회원 영속 카트 + 별도 주문 트랜잭션" 경계와 충돌하므로 미채택.

### 5.2 동시성 (확정)
- **결정 D2**: 카트는 임시 버퍼 → **last-write-wins(F8)**, 낙관락 충돌 재시도 X(`d14 §6.6`). 단, **담기 UPSERT는 `UNIQUE(cart_id, sku_id)` + `ON CONFLICT DO UPDATE qty=qty+EXCLUDED.qty`로 원자 합산**(`f13 §5`). **병합만 SERIALIZABLE**(1인당 한도 race 방지, `d14 §6.5`).

### 5.3 가격·합계 (확정)
- **결정 D3**: `price_at_add`는 **변동 감지(배지)용 스냅샷**일 뿐, **결제 금액은 항상 실시간 단가**(F6/F18/F20). 가격 인하 = 즉시 신단가 + "가격이 내렸어요" 배지. 가격 인상 = 배지 + (`f13-Q07` 미결: 30%↑ 변동 시 확인 모달 도입 여부). 합계 = 상품합 + 쿠폰 차감 + 무료배송 기준 안내(P5).

### 5.4 비회원 병합 (확정 = F13 + d14 §6.4 3단계 한도)
- **결정 D4**: 로그인 직후 `POST /api/cart/merge`. 한도 합산 3단계 — ① `final_qty=min(server+guest, stock, 99)` ② 1인당 구매 한도(`purchase_limit_per_member`) ③ 카트 라인 50(초과 시 신규 sku skip). 응답 `{merged[], adjusted[], skipped[]}`(사유: stock_limit/purchase_limit/cart_line_limit_50).

### 5.5 결제 진입 게이트 (확정 = F16)
- **결정 D5**: `POST /api/cart/checkout-payload {item_ids}` → `selected=TRUE` 라인만 + 1단계 실시간 재검증(3단계 재고 검증 중 1단계, d12 §F3). 전부 품절 → 409 ALL_UNAVAILABLE, 최소금액 미만 → 409 BELOW_MIN_ORDER_AMOUNT, 단종/hidden 라인 자동 제외(F15).

## 6. Medusa 코드 매핑

> 코드 확인 경로: `apps/backend/node_modules/.pnpm/@medusajs+cart@2.15.3.../@medusajs/cart/dist/models/` (모델), `@medusajs+core-flows@2.15.3.../@medusajs/core-flows/dist/cart/workflows/` (워크플로우). 격리 패턴 출처: `apps/backend/apps/backend/src/modules/legal-kr/withdrawal-7day/` + `src/links/order-withdrawal.ts`.

### 6.1 ⓐ 활용할 Medusa native (코드 확인 완료)

**Cart 모델** (`models/cart.js`, prefix `cart_`): `id, region_id, customer_id, sales_channel_id, email, currency_code, locale, metadata, completed_at, created_at, updated_at` + 다수 computed bigNumber(`item_total, total, subtotal, tax_total, discount_total, shipping_total` 등). relationship: `hasOne address`(shipping/billing), `hasMany items/credit_lines/shipping_methods`.

**LineItem 모델** (`models/line-item.js`, prefix `cali_`): `id, cart_id, title, quantity, product_id, variant_id, variant_sku, variant_title, variant_option_values(json), unit_price, compare_at_unit_price, is_discountable, is_tax_inclusive, requires_shipping, metadata` + computed total들. 그 외 모델: `address(cart_address), line-item-adjustment, line-item-tax-line, credit-line, shipping-method(+adjustment/tax-line)`.

**워크플로우** (`core-flows/dist/cart/workflows/`, 코드 확인):
| 워크플로우 ID | 활용 |
|---|---|
| `createCartWorkflow` (`create-carts`) | 카트 생성(회원 로그인 시) |
| `addToCartWorkflow` (`add-to-cart`) | 담기 → 내부적으로 `refreshCartItemsWorkflow` 호출(가격 재계산) |
| `updateLineItemInCartWorkflow` (`update-line-item-in-cart`) | 수량 변경 |
| `deleteLineItemsWorkflow` | 삭제 |
| `refreshCartItemsWorkflow` (`refresh-cart-items`) | **가격·프로모션·세금 재계산** — `setPricingContext` hook 제공 → 우리 F6 실시간 재검증의 native 기반 |
| `confirmVariantInventoryWorkflow` (`confirm-variant-inventory`) | 재고 확인 → 우리 F3/F16 재고 검증 |
| `transferCartCustomerWorkflow` (`transfer-cart-customer`) | **게스트→회원 소유권 이전** — `cart.customer.id !== customer.id`면 `customer_id` 갱신 + `CUSTOMER_TRANSFERRED` 이벤트 발행. 우리 F13 병합의 native 기반(단, 우리는 localStorage→DB 합산이라 커스텀 합산 로직 추가 필요) |
| `updateCartPromotionsWorkflow` | 쿠폰/프로모션 적용 → 우리 카트 쿠폰(F9) |
| `completeCartWorkflow` (`complete-cart`) | 결제 완료 → Cart→Order 변환(Spree copy-on-completion과 동일). 우리 F11/F16 카트→주문 이관의 native 기반 |

**한국 세금/로케일 native** (`정의서 §7`): `currency_code="krw"`, `LineItemTaxLine.rate=10`(부가세 10%), `is_tax_inclusive=true`(소비자가 부가세 포함 표시), `locale="ko-KR"`. → 우리 합계 표시에 그대로 활용.

### 6.2 ⓑ 필요한 커스텀 (legal-kr 격리 패턴 = 코어 무수정)

> 우리 S0 카트는 Medusa native와 **필드·정책이 다름**(회원당 1:1 / `price_at_add` 스냅샷 / `selected` / `version` / `last_seen_at` / `abandoned_notified_at` / localStorage 병합 / 7·90일 배치). 코어 cart 모델을 **수정하지 않고**, `legal-kr/withdrawal-7day`와 동일한 격리 모듈 패턴으로 **별도 커스텀 모듈 + defineLink**로 한국형 메타데이터를 격리한다.

**커스텀 모듈 `cart-kr`** (`src/modules/cart-kr/`, legal-kr 패턴 복제):
- `index.ts` — `Module(CART_KR_MODULE, { service })`, 등록명 `cartKr`.
- `models/` — 다음 모델로 native cart 부족분 격리:
  - `cart_kr_meta` (cart_id 1:1) — `last_seen_at`, `abandoned_notified_at` (장기 미결제/정리 배치 기준).
  - `cart_item_kr_meta` (line_item id 1:1) — `price_at_add`(변동 감지 스냅샷), `selected`(선택 결제), `version`(last-write-wins), `added_at`. (native LineItem `metadata` JSON으로 대체 가능하나, 인덱스·쿼리 성능 위해 별도 모델 권장.)
  - `cart_coupon_kr` (cart_id 1:1) — 카트당 단일 쿠폰 정책(F9) + `applied_amount` 캐시. (native는 LineItemAdjustment 다중 → 우리 정책은 카트당 1건이므로 격리.)
  - `cart_policy_kr` (싱글톤/정책 저장소) — P1·P3·P4·P5·P7(만료·정리·라인한도·무료배송·리마인더). 관리자 설정(CRT-A-006).
- `service.ts` — UPSERT 합산, 병합 한도 3단계, 쿠폰 조건 재검증/자동 해제, 합계 계산, 배치 멱등 로직.
- `subscribers/` — `product.sold_out/restocked/price_changed/option_changed/status_changed`, `timesale.closed`, `coupon.expired/consumed`, `order.created` 구독 → 라인 배지/쿠폰 자동 해제/카트 정리.
- `jobs/` — ① 카트 자동 정리(매일 04:00, P1 7일/P3 90일, 멱등) ② 장기 미결제 리마인드(매일 10:00, `abandoned_notified_at` SET 멱등).

**defineLink** (`src/links/cart-kr.ts`, order-withdrawal.ts 패턴):
- `CartModule.linkable.cart ↔ cartKr.linkable.cartKrMeta` (1:1)
- `CartModule.linkable.lineItem ↔ cartKr.linkable.cartItemKrMeta` (1:1)
- `CartModule.linkable.cart ↔ cartKr.linkable.cartCouponKr` (1:1)

**커스텀 API route** (`src/api/store/cart/...`, `src/api/admin/cart/...`):
- 우리 S0 API 면(`d14 §5`)을 그대로 구현하되 **내부적으로 native 워크플로우 호출 + cart-kr 서비스 합성**:
  - `GET /api/cart` → `refreshCartItemsWorkflow` + cart-kr 재검증(배지·쿠폰·합계).
  - `POST /api/cart/items` → 재고/단종/1인한도 검증(`confirmVariantInventoryWorkflow`) → `addToCartWorkflow`(UPSERT 합산) → cart-kr 메타 갱신.
  - `PATCH /api/cart/items/{id}` → `updateLineItemInCartWorkflow` + version last-write-wins.
  - `PATCH /api/cart/items/{id}/option` → 신 SKU 라인 전환(delete+add 합성).
  - `DELETE` / `bulk-delete` → `deleteLineItemsWorkflow`.
  - `POST /api/cart/coupon` / `DELETE` → `updateCartPromotionsWorkflow` + cart-kr 단일 쿠폰 정책.
  - `POST /api/cart/merge` → `transferCartCustomerWorkflow` + cart-kr 병합 한도 3단계.
  - `POST /api/cart/checkout-payload` → 1단계 재검증 + `selected` 라인 페이로드(complete는 d16에서).
  - 관리자: `/api/admin/cart/stats`, `/members/{member_id}`(읽기+감사), `/abandoned-notify`, `/cleanup-soldout`(사유), `/policies/cart`(P1~P7).

**defineLink 미스매치 주의**: native cart는 `customer_id`(nullable, 게스트 허용)지만 우리 carts PK는 `member_id`. → 우리는 **회원 카트만 DB 저장**(F12)이므로 native cart 생성 시 `customer_id` 필수화는 API 레이어 게이트로 처리(코어 무수정).

### 6.3 ⓒ 마이그레이션 계획
1. `cart-kr` 모듈 모델 마이그레이션 생성(`cart_kr_meta`, `cart_item_kr_meta`, `cart_coupon_kr`, `cart_policy_kr`). legal-kr와 동일하게 `migrations/` 디렉토리에 격리.
2. `medusa-config.ts`에 `cartKr` 모듈 resolve 등록.

5. **코어 cart 테이블 무수정** — 모든 한국형 필드는 link 테이블로 분리(legal-kr 검증된 패턴).

## 7. 현 코드와의 관계 + 구현 단계

### 7.1 현 코드 관계
- **현재 백엔드 상태**: `apps/backend/.../src/modules/`에 **`legal-kr/withdrawal-7day`만 존재**(청약철회 7일). **카트 커스텀 모듈은 아직 없음** — Medusa native `@medusajs/cart`(v2.15.3) + core-flows만 설치된 상태.
- `src/links/`에 `order-withdrawal.ts`, `order-return-rma.ts` 존재 → **cart-kr link도 동일 디렉토리·동일 패턴**으로 추가.
- 프론트(`apps/web/`)는 별도 — 본 설계는 백엔드 도메인 한정. localStorage 비회원 카트(F12/F19)는 프론트 구현 영역(스키마 `shop_guest_cart_v1` v1 검증).

### 7.2 구현 단계

**immediate (Phase 2 task 단위 진입 시)**
1. `cart-kr` 모듈 스캐폴딩(legal-kr 복제) + 4개 모델 + 마이그레이션 + defineLink + 정책 시드.
2. `GET /api/cart`(refresh + 재검증 배지·합계) / `POST /api/cart/items`(UPSERT 합산 + 재고/단종/1인한도) — 카트 핵심 경로 우선.
3. `PATCH` 수량(last-write-wins) / 옵션 변경 / `DELETE`·bulk-delete.
4. `POST /api/cart/coupon`·`DELETE`(단일 쿠폰 + 자동 해제) — d20 의존.
5. `POST /api/cart/merge`(병합 3단계 한도, SERIALIZABLE) + `transferCartCustomerWorkflow` 합성.
6. `POST /api/cart/checkout-payload`(selected 라인 + 1단계 재검증) — d16 주문서 진입 연결.

**다음 단계 (의존 도메인 완료 후)**
7. 구독 subscribers(product/coupon/order/timesale 이벤트) — d12·d20·d16 이벤트 확정 후.
8. 배치 jobs(자동 정리 04:00 / 리마인드 10:00) — notification 도메인 연결 후(`Q-CRT-02` 채널 미결).
9. 관리자 API(stats·CS 조회·abandoned-notify·cleanup·policies) + 감사 로그(S2/S3).
10. 미결 반영: `f13-Q06` 무료배송 기준(50,000원 정합), `f13-Q07` 가격 인상 확인 모달, `Q-CRT-01/03` 정리 기간·라인 한도 운영 데이터 후 조정.
