## 0. 현황 요약

`apps/web`는 Medusa Next.js 스타터 기반으로 **핵심 구매여정 골격은 존재**한다.

- 라우트: `app/[countryCode]/(main)/{store,products/[handle],categories,collections,cart,order/[id],account}` + `(checkout)/checkout`
- API 연동: `lib/data/{products,categories,collections,variants,cart,payment,fulfillment,orders,customer,regions,locales}`
- 도메인 컴포넌트: `modules/{account,cart,categories,checkout,collections,common,home,layout,order,products,shipping,skeletons,store}`

**비어 있는(관리자엔 있으나 프런트 미구현) 한국형 기능**: 리뷰·상품문의·1:1문의, 적립금/포인트·멤버십 등급·쿠폰·위시리스트, 상품정보고시 표시, 타임세일, 본인인증·소셜로그인, 무통장/간편결제, CMS(배너/팝업/공지/FAQ), 약관/동의관리, SEO.

> ⚠️ 일부 기능은 **백엔드 store API도 미구현**(리뷰·포인트·본인인증·PG 등). §6 참조.

## 1. 분담 원칙 — 도메인 수직 분할

라우트 그룹 / `lib/data` / `modules`가 도메인별로 분리돼 있어 **사람마다 디렉터리를 통째로 소유**하면 파일 충돌이 최소화된다. 레이어(마크업/로직)로 자르지 말고 **기능 세로로** 자른다.

### 담당자별 소유 영역 (관리자 ↔ 프런트 매핑)

| 담당 | 소유 라우트 | 소유 `lib/data` | 소유 `modules` | 관리자 대응 |
|---|---|---|---|---|
| **A · 카탈로그** | `(main)/store`, `products/[handle]`, `categories`, `collections`, 검색 | `products`, `categories`, `collections`, `variants` | `store`, `products`, `categories`, `collections` | 상품·카테고리·기획전·타임세일·큐레이션·상품정보고시 |
| **B · 주문/결제** | `cart`, `(checkout)/checkout`, `order/[id]` | `cart`, `payment`, `fulfillment`, `orders` | `cart`, `checkout`, `order`, `shipping` | 주문·배송·환불/취소·반품/교환·구매확정·결제수단 |
| **C · 회원/마이페이지** | `(main)/account/*` | `customer` | `account` | 회원가입·본인인증·소셜로그인·주문내역·적립금/등급·쿠폰·위시리스트·동의 |
| **D · 콘텐츠/CS/공통** | `home`, `layout`, 신규 `reviews`·`cs`·`legal` | (신규) `reviews`, `cs`, `cms` | `home`, `layout`, `common`, `skeletons` + 신규 | 홈진열·배너/팝업/공지/FAQ·리뷰·문의·약관·SEO |

> **D는 `common`/`layout`(디자인시스템·네비·푸터) 게이트키퍼 겸임** → 공통 컴포넌트 중복/충돌 방지.

## 2. 마일스톤

| 마일스톤 | 기간(목표) | 내용 | 비고 |
|---|---|---|---|
| **M0 · 공통 기반** | 1~1.5주 | KRW 통화·한국 리전, i18n, `countryCode` 라우팅 규약, 인증/세션 패턴, `lib/data` 호출 규약, 공통 디자인 토큰+핵심 UI, **API 계약(시그니처+타입) 합의** | 2명 집중, 전원 합의. 충돌 방지 핵심 |
| **M1 · 핵심 구매여정** | 2~3주 | 상품 탐색 → 장바구니 → 체크아웃 → 주문완료 (실거래 가능) | 4인 병렬 |
| **M2 · 회원·마이페이지·리뷰** | 2주 | 포인트/등급/쿠폰/위시리스트 + 리뷰/문의 | C·D 주도 |
| **M3 · CS·CMS·SEO·확장** | 2주 | CMS·CS·SEO + 본인인증·소셜로그인·결제수단 확장 | 백엔드 로드맵 Phase 1·2와 동기화 |

각 마일스톤 종료 시 **통합 브랜치 + Playwright E2E**로 검수(테스트 인프라는 admin에 기구축).

## 3. 브랜치 전략

- **trunk-based**: `main` 보호(직접 push 금지), 짧은 수명의 feature 브랜치.
- 브랜치 네이밍: `feature/<도메인>-<작업>` (예: `feature/catalog-pdp-disclosure`), 수정 `fix/<요약>`.
- **PR 규칙**: 작게 자주, **상호 리뷰 1인 이상 필수**, CI(빌드/lint/타입체크/E2E) 통과 후 머지.
- **CODEOWNERS**로 §1 표대로 디렉터리별 리뷰어 자동 지정 → 타 영역 변경 시 자동 리뷰 요청.
- 공통 파일(`layout`, 네비, `types`, 디자인 토큰) 변경은 **사전 공지 + 초소형 PR**.

---

## 4. 계약 우선(contract-first) 개발

병렬성을 막는 가장 큰 요인은 의존성이다. 다음을 먼저 못 박는다.

1. **`lib/data` 함수 시그니처 + `types`/`packages/types`** 를 인터페이스 PR로 먼저 확정 → 이후 화면 병렬 구현.
2. 백엔드 미구현 기능은 **`lib/data`에 mock + 타입만 먼저** 작성(런타임 mock 플래그) → 백엔드 준비 시 구현 교체.
3. **데이터 정합 단일 출처**: 기존 `revalidate-contract`(백엔드)↔`revalidate-tags`(프런트) 패턴을 따라, 관리자 변경 → 프런트 캐시 무효화 계약을 공유 유지.

## 5. 협업 메커니즘

- **동기화**: 데일리 15분 스탠드업 + 주 1회 통합/데모.
- **디자인**: 공통 토큰/`@medusajs/ui-preset` 기준, 프로토타입(있으면) 단일 기준. 컴포넌트는 `common`에서 재사용.
- **DoD(완료 정의)**: 화면 구현 + 반응형(모바일 우선) + 로딩/에러/빈상태 + 접근성 기본 + E2E 1개 이상 + PR 리뷰 통과.
- **PR 템플릿**: 변경 범위 / 관련 도메인 / 테스트 방법 / 스크린샷 / 백엔드 의존성 명시.

## 6. 백엔드 의존성 (중요)

프런트 일부 기능은 **백엔드 store API 자체가 없음** — 갭 분석/로드맵과 연동 필요.

| 프런트 기능 | 백엔드 상태 | 전략 |
|---|---|---|
| 리뷰·상품문의·1:1문의 | admin 모듈만 존재(store API 없음) | store 라우트 신설 또는 mock 선개발 |
| 적립금/등급/쿠폰(고객 조회) | admin 라우트만 존재 | store 라우트 신설 |
| 본인인증·소셜로그인 | 미구현(로드맵 Phase 2) | 계약/목업 후 연동 |
| 무통장/간편결제·PG | 미구현(로드맵 Phase 1) | PG 연동 일정과 동기화 |
| 상품정보고시 표시 | 데이터 존재(catalog_type/disclosure) | 조회만 연결 |

→ 선택: (권장) 4명 중 1명 **풀스택 겸임**으로 store API 동반 구축, 또는 **순수 프런트 + mock 계약**으로 진행 후 로드맵 단계에 맞춰 교체.
