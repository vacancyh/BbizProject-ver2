## Phase 1 — 결제 기반 (최우선)

> 실거래·정산·구매확정의 전제. 단독몰 운영의 출발점.

### 1-1. 실 PG 결제연동  · 난이도 **L** · 설계문서 ✅
- **권장 1차**: 토스페이먼츠(문서/SDK 정비 우수) → 이후 카카오페이·네이버페이·KG이니시스 확장
- **구현 위치**:
  - 백엔드: Medusa **Payment Module Provider** 신규 (`src/modules/payment-toss` 등) — `authorizePayment`/`capturePayment`/`refundPayment`/`getWebhookActionAndData` 구현
  - 결제 위젯/리다이렉트: `apps/web` 결제 단계 + 콜백 라우트(`/api/payment/callback`)
  - 웹훅 수신: `src/api/hooks/payment/[provider]/route.ts`
- **연계**: 기존 D7 결제원장·정산 모듈이 PaymentCollection→Payment 흐름을 그대로 받도록 결선
- **체크포인트**: 결제 멱등성(d13 t001 이미 설계됨)·부분취소 환불(d13 t003)과 정합

### 1-2. 무통장입금 / 가상계좌 + 입금확인 + 미입금 자동취소 · 난이도 **M** · 설계문서 ✅
- **구현 위치**:
  - 백엔드: 가상계좌 발급(PG 연동) 또는 무통장 계좌 안내용 커스텀 payment provider
  - 입금확인: PG 웹훅(가상계좌 입금통보) → 주문 상태 전환 / 무통장은 관리자 수동확인 화면
  - 미입금 자동취소: **스케줄드 잡**(`src/jobs/`) — 입금기한 경과 주문 자동 취소(정책값은 기존 policy 모듈 `payment.deposit_deadline_hours`)
  - 관리자: `apps/admin` 주문 목록에 "입금대기" 상태 + 입금확인 처리 액션

### 1-3. 결제수단별 정산/부가세 분리(기존 정산 보강) · 난이도 **S~M** · 설계문서 ➖
- settlement-payout 스냅샷에 결제수단 차원(카드/가상계좌/간편결제) 추가 집계 컬럼

## Phase 2 — 회원/법적 (병렬 진행 가능, 법적 우선)

### 2-1. 휴면회원 관리 · 난이도 **M** · 설계문서 ✅  ⚠️법적 의무
> 개인정보보호법: 1년 미접속 시 휴면 전환 + 사전 고지 + 분리보관/파기.
- **구현 위치**:
  - 백엔드: 커스텀 모듈 `src/modules/dormant`(또는 membership 확장) — 마지막 로그인 추적, 휴면 상태, 분리보관 테이블
  - **스케줄드 잡**: 휴면 D-30 고지 발송(기존 알림 모듈 재사용) → D-day 휴면 전환 → 보관기한 경과 시 파기 로그(기존 audit 모듈 연계)
  - 로그인 추적: `auth` 흐름에 last_login_at 기록
  - 관리자: 휴면 목록/수동 전환·해제 화면
- **재사용 가능 자산**: customer-consent(동의이력)·audit(파기 로그)·알림(고지 발송) 이미 존재

### 2-2. 본인인증(휴대폰/아이핀) · 난이도 **L** · 설계문서 ✅
- **권장**: NICE아이디 또는 PASS(통신사 본인확인) 연동
- **구현 위치**:
  - 스토어프론트: 가입/주문 시 본인인증 팝업 + 콜백
  - 백엔드: 인증결과(CI/DI) 검증·저장 API, 중복가입 방지(CI 기준)
  - 주의: CI/DI는 민감정보 — 암호화 저장 + audit PII 마스킹 정책 적용

### 2-3. SNS 간편로그인(카카오·네이버) · 난이도 **M** · 설계문서 ➖
- **구현 위치**: Medusa **Auth Module Provider** 신규(`auth-kakao`, `auth-naver`) — 코어에 google/github 레퍼런스 존재(`docs/.../auth-providers`) → 동일 패턴
- 스토어프론트: 소셜 로그인 버튼 + OAuth 콜백

## Phase 3 — 주문 완결 (Phase 1 이후)

### 3-1. 구매확정(자동확정 D+day / 수동확정) · 난이도 **M** · 설계문서 ✅
> 결제완료·배송완료 기준이 있어야 동작 → Phase 1 결제 + 기존 배송완료 흐름 선행.
- **구현 위치**:
  - 백엔드: 커스텀 모듈 또는 order-ops-kr 확장 — 구매확정 상태 + 확정 시점 기록
  - **스케줄드 잡**: 배송완료 + D+N(정책값) 경과 → 자동 구매확정 → **적립금 지급 트리거**(기존 customer-point) + **정산 확정 트리거**(기존 settlement)
  - 관리자/스토어프론트: 수동 확정 버튼
- **재사용 가능 자산**: customer-point·settlement-payout·state-machine 이미 존재 → 트리거 결선 위주

## Phase 4 — 마케팅/유입 (대부분 병렬)

| 항목 | 난이도 | 구현 요지 |
|---|---|---|
| 네이버쇼핑/가격비교 피드(EP) | M | 상품 XML 피드 생성 라우트(`/feed/naver.xml`) + 갱신 잡 |
| 리타게팅 픽셀(카카오·메타·네이버) + GA/UTM | S~M | `apps/web`에 스크립트 주입 + 전환 이벤트, 관리자에 픽셀 ID 설정 |
| 접속/전환 통계(UV·PV·유입경로·퍼널) | M | GA4 연동 또는 자체 이벤트 수집 → 통계 화면 |
| SEO(메타/OG/사이트맵) | S~M | `apps/web` 메타데이터 + `sitemap.xml`/`robots.txt` |
| 마케팅 자동화(장바구니 이탈·재구매·생일쿠폰) | M | 트리거 잡 + 기존 알림/쿠폰 자동발급 결합 |

## Phase 5 — 운영 편의 (백로그)

추가상품/사은품·세트, 번들·장바구니 금액대별 할인, 재입고 알림 신청, 예치금,
브랜드/제조사·원가마진 리포트, 발주/입고(안전재고 경고)·묶음배송, 주문서/거래명세서/배송라벨 출력,
일반 게시판·채팅상담 연동, 관리자 2FA·IP 제한·사업자정보(통신판매업 신고번호) 표기.
