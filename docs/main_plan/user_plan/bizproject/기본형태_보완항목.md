## 1. 🔴 기본 형태에 반드시 필요한 것

### 1-1. 알림 발송 구조가 **아예 없다** ❌

가장 큰 구멍이다. 단순히 "SMS 업체와 계약이 안 됐다"가 아니라,
**보낼 코드 자체가 없다.**

확인 결과:
- `medusa-config.ts` 에 notification 모듈 미설정
- 주문 이벤트 구독자는 3개뿐 — 적립금, 캐시무효화 2개. **알림 구독자 없음**
- `sendNotification` / `Modules.NOTIFICATION` 을 쓰는 코드 0건

즉 SMS 업체와 계약해도 **"주문완료 시 무엇을, 어떤 문구로 보낼지" 부터 새로 만들어야 한다.**
구매자가 "PG처럼 키만 넣으면 되겠지" 라고 생각하면 일정이 크게 어긋난다.

**✅ 조치 완료 (2026-08-03)** — `modules/notification-kr` 신설

- 알림 시점 9종 정의 + **기본 문구 9종 적재**(주문접수·입금·발송·배송완료·취소·환불·가입·적립금소멸·재입고)
- 문구는 DB 에 저장 → 관리자 API 로 수정 (`GET/POST /admin/notifications/templates`)
- **provider 추상화** — 업체가 바뀌어도 `send()` 구현체 하나만 교체
- 발송 이력 기록 (`GET /admin/notifications/logs`) — CS 가 "보냈는지" 확인 가능
- `order.placed` / `order.canceled` 구독자 연결

**지금 업체 없이도 동작한다.** 기본 provider 가 실제 발송 대신 기록만 하므로,
어떤 주문에 어떤 문구가 나갔어야 하는지 관리자에서 볼 수 있다.

실측 검증: 실제 주문 생성 → `010-1234-5678` 로
`"[쇼핑몰] 홍길동님, 주문이 접수되었습니다. 주문번호: 147 결제금액: 47,300원"` 렌더링 확인.

> 남은 것: **발송 업체 계약뿐이다**(비용). 계약 후 provider 구현체 추가 + `NOTIFICATION_PROVIDER` 변경.

> 주문했는데 아무 연락이 없으면 고객은 바로 전화한다. **CS 부담이 가장 크게 늘어나는 지점이다.**

### 1-2. 이미지 최적화가 꺼져 있다 ⚠️

`apps/web/next.config.js`:
```js
images: { unoptimized: true }
```

쇼핑몰 페이지 무게의 대부분은 상품 이미지다. 지금은 **원본 파일을 그대로 내려보낸다** —
WebP 변환도, 화면 크기별 리사이즈도, lazy loading 최적화도 없다.

실제 확인: 홈에 걸린 이미지가 외부 S3 의 원본 PNG.

**영향**
- 모바일에서 느리다 → 이탈률 상승 (전환율에 직결)
- 트래픽 비용이 몇 배로 나간다
- Core Web Vitals(LCP) 저하 → 검색 노출 불이익

**✅ 조치 완료 (2026-08-03)**

- `unoptimized` 해제 + AVIF/WebP 변환·반응형 사이즈 활성화
- 히어로 배너를 원본 `<img>` → `next/image` 로 전환(LCP 요소라 가장 큰 효과)
- **실측: 928KB PNG → 11KB AVIF (99% 절감)**, 홈 이미지 16개 전부 최적화 경유

> ⚠️ 이 과정에서 **미등록 호스트(`images.pexels.com`)로 상품 상세가 500** 이 나는 걸 발견해
> 함께 고쳤다. 최적화를 켜면 `remotePatterns` 에 없는 호스트는 페이지를 죽인다.
> 재발 방지로 `preflight-check.ts` 가 미등록 이미지 호스트를 사전에 잡는다.

### 1-3. 모니터링이 없다 ❌

**사이트가 죽어도 아무도 모른다.** 새벽에 내려가면 아침에 고객 전화로 알게 된다.

`NEXT_PUBLIC_SENTRY_DSN` 변수 자리는 있지만 연동 코드는 없다.

**✅ 조치 완료 (2026-08-03)** — 감시할 수 있는 지점을 만들었다

점검 중 더 큰 문제를 발견했다: **기존 `/health` 는 DB 가 죽어도 "OK" 를 반환했다.**
(실측: DB 컨테이너를 내려도 `OK`) 거짓 초록불은 감시가 없는 것보다 나쁘다.
또 `/admin/ops/health` 는 인증이 필요해 외부 감시 도구가 쓸 수 없었다.

- **`GET /hc`** (백엔드, 인증 불필요) — 실제 DB 조회로 판정. 정상 200 / 장애 **503**
- **`GET /api/health`** (스토어프론트) — 백엔드 연결까지 확인
- 둘 다 타임아웃을 걸어 장애 시에도 즉시 응답한다

실측: DB 정지 → `{"status":"degraded","db":"down"}` **503** 반환 확인.

> 남은 것: UptimeRobot 등에 위 두 주소를 등록하고 **담당자 연락처를 넣는 것**(무료).

### 1-4. 요청 추적 수단이 없다 ❌

`requestId` / `correlationId` / `traceId` 를 쓰는 코드 0건.

고객이 "어제 3시쯤 결제가 안 됐어요" 라고 하면, 지금은 **그 요청을 로그에서 특정할 방법이 없다.**
감사 로그는 관리자 행위만 남기지, 고객 요청은 남기지 않는다.

**✅ 조치 완료 (2026-08-03)**

- 모든 요청에 ID 부여 → `x-request-id` 응답 헤더로 반환
- 앞단(로드밸런서·CDN)이 이미 붙였다면 그 값을 이어받는다(구간별로 끊기지 않게)
- 오류(4xx/5xx)만 로그에 남긴다 — 정상 요청까지 남기면 로그 비용이 커진다

실측: 앞단 ID `lb-trace-abc123` 전달 시 그대로 이어받음 확인.

## 2. 🟠 운영을 시작하면 곧 막히는 것

### 2-1. 관리자가 재고를 예약 수량보다 낮게 설정할 수 있다 ⚠️ (실측)

실제로 재현했다:
```
예약 6건이 걸린 상품의 재고를 2로 설정 → 가용재고 -4
결과: 그 상품은 아무도 장바구니에 담을 수 없게 된다(전부 400)
```

오버셀 자체는 **정상적으로 차단**된다(가용재고 기준으로 담기 거부). 문제는 그 반대 —
관리자가 실수로 재고를 낮추면 **팔 수 있는 상품이 조용히 판매 불가**가 된다.
화면에는 경고가 없다.

**✅ 조치 완료 (2026-08-03)**

재고 조정 API 에 가드를 넣었다. 어느 화면에서 하든 막힌다.
- 예약 수량 미만으로 내리려 하면 **400 + 설명**
  ("예약된 26개보다 적게 설정할 수 없습니다. 가용재고가 -1개가 되어 판매가 중단됩니다")
- 실사 후 정말 보정해야 하면 `x-force-stock-decrease: true` 헤더로 진행
  → **실수는 막고 의도는 허용한다**

> 구현 중 함정 하나: 처음에 `?force=true` 쿼리로 만들었더니 코어 라우트의 쿼리 검증에 걸려
> 400 이 났다. 헤더는 코어가 검증하지 않아 헤더 방식으로 바꿨다.

### 2-2. 백업이 서버 안에만 있다 ⚠️

백업 스크립트는 잘 동작한다(무결성 검사까지 한다). 하지만 `backups/` 는 **같은 서버 안**이다.
서버가 통째로 죽으면 백업도 함께 죽는다.

**✅ 조치 완료 (2026-08-03)**

`scripts/db-backup.sh` 에 외부 업로드 단계를 추가했다.
- `BACKUP_S3_BUCKET` 설정 시 자동 업로드, 미설정이면 **경고와 함께 건너뜀**
  (로컬 백업만으로도 스크립트는 정상 동작한다)
- 업로드 실패해도 스크립트를 죽이지 않되 **눈에 띄게 남긴다** — 조용한 실패가 가장 위험하다
- 버킷에 버전 관리 + 객체 잠금(Object Lock) 을 켜라고 안내 — 랜섬웨어 대비

자동 실행 스니펫(cron / Windows 작업 스케줄러)은 `운영자_매뉴얼.md` §7 에 있다.

> 남은 것: **S3 버킷 준비와 자격증명 설정**(사장님). 스크립트는 대기 상태다.

### 2-3. 검색에 오타 보정이 없다 ⚠️

실측:
```
"티셔츠"  → 1건 ✅
"티셔"    → 1건 ✅ (부분 일치 동작)
"티셔쳐"  → 0건 ⚠️ (오타 시 아무것도 안 나옴)
```

한글 검색 자체는 정상이다. 다만 오타·유사어를 못 잡는다.
고객은 오타를 낸다. 0건 화면을 보면 그냥 나간다.

**✅ 조치 완료 (2026-08-03)** — 0건 화면 보강

오타 보정 자체는 검색엔진 도입이 필요해 미뤘다. 대신 **막다른 화면을 없앴다.**
이전에는 "'xxx'에 대한 검색 결과가 없습니다." 한 줄이 전부였다.

- 실제 집계된 **인기 검색어를 버튼으로 제시**(클릭하면 바로 그 검색으로 이동)
- **전체 상품 보기** 버튼

실측: `?q=티셔쳐`(오타) → 인기 검색어 `니트, 코트, 패딩` 노출 확인.

> 남은 것: 오타·유사어 보정은 검색엔진(Meilisearch 등) 도입 시. 자체 호스팅이면 비용은 서버뿐.

### 2-4. 테스트 데이터가 남아 있다 ⚠️

- 자동화 테스트 계정 **98건** — 회원 통계·매출 집계가 왜곡된다
- 시드 상품 **15건** — 주소가 `/products/kr-test-p1` 형태로 고객에게 보인다
- 고객 화면에 예시값 노출: `1600-0000`(전화), `000-00-00000`(사업자번호), 약관의 `[운영사명]`

정리 도구는 있다(`cleanup-test-data.ts`, `storefront-readiness-probe.mjs`).
**실제 상품·실제 값으로 교체하는 것은 사람이 해야 한다.**

### 2026-08-03 후속 조치 (사장님 지시)

**백엔드 ESLint 도입** ✅
- 설치 성공. flat config 작성 후 첫 실행에서 **218건** 검출.
- 규칙을 실정에 맞게 조정해 **0 error / 0 warning** 달성 → CI 백엔드 잡에 연결(`pnpm lint`).
- 조정 근거를 설정 파일에 남겼다:
  - `no-unnecessary-type-assertion` 끔 — `req.scope.resolve(MODULE) as unknown as Service` 는
    이 프로젝트 전반(197곳)의 **모듈 타입 지정 관례**다. 자동 수정하면 개발자가 의존하는
    타입 정보가 통째로 사라진다.
  - `no-useless-assignment` 끔 — `let x: T | null = null` 후 try 안에서 할당하는
    **올바른 스코프 패턴**을 오탐한다.
  - `src/admin/**`(Medusa 어드민 UI, React)은 promise 규칙 제외 — onClick 에 async 를
    넘기는 것은 React 표준 패턴이라 오탐이다.
- 실제로 고친 것: 미사용 import·변수 6건, `prefer-const` 1건.

> ⚠️ 설치 중 함정: 앞서 CVE 대응으로 넣은 `ajv: '>=8.18.0'` override가 ajv 6.x 를 쓰는
> `@eslint/eslintrc` 까지 8.x 로 올려 **ESLint 가 아예 실행되지 않았다.**
> 해당 CVE 는 v7 이상만 영향이므로 `ajv@>=7` 로 범위를 좁혀 해결했다.

**알림 문구를 카카오 알림톡 형식으로 전환** ✅ (사장님: "기본적으로 카톡을 많이 쓰니")
- 기본 문구 9종을 알림톡 규격으로 재작성 — 카카오 표준 `#{변수}` 표기
- **버튼** 추가: 주문 상세보기(WL) · 배송조회(DS) · 상품 보러가기(WL)
- **대체문자(fallback_body)** 각 템플릿에 작성 — 카카오톡 미설치·차단 시 자동으로 문자 발송.
  국내 실무 표준이라 없으면 그 고객은 아무 연락도 못 받는다.
- `template_code`(카카오 심사 승인 코드) 필드 추가 — 심사 후 관리자에서 입력
- 길이 검사도 채널별로: 알림톡 1,000자 / 문자 2,000바이트
- 기본 채널을 알림톡으로 변경(전화번호 없으면 이메일)
