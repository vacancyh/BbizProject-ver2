## 1. 🔴 심각 — 실제 금전 손실 (전부 수정 완료)

세 건 모두 **같은 뿌리**다. `검사 → (락 없음) → 집행` 사이에 다른 요청이 끼어든다(TOCTOU).
단위 테스트로는 절대 잡히지 않는다. 실제 서버에 동시 요청을 던져야 드러난다.

### 1-1. 적립금 이중 사용 — 보유액의 N배 할인

**실측 결과 (수정 전)**

```
보유 10,000P · 카트 3개 생성 후 각각 10,000P 사용을 동시 요청
  카트1: 200 {"applied":10000}
  카트2: 200 {"applied":10000}
  카트3: 200 {"applied":10000}
→ 30,000원 할인 적용, 잔액 -20,000P
```

병렬 요청 수만큼 무한 증폭된다. 카트는 얼마든지 만들 수 있으므로 **사실상 무제한**이다.

**원인** — `src/api/store/carts/[id]/points/route.ts`

- 락 키가 `points-cart:{cartId}` 였다. **적립금 잔액은 카트가 아니라 고객 단위 자원**이다.
  카트가 다르면 서로 다른 락을 잡으니 상호배제가 아예 없었다.
- 잔액 검사(`points > balance`)가 락 **밖**에 있어, 동시 요청이 모두 통과했다.
- 2026-07-27 점검에서 "per-cart 락으로 이중차감 방지"라고 주석까지 달았지만 **락 단위 선택이 틀렸다.**

**수정** — 락 키를 `points-customer:{customerId}` 로 바꾸고, 잔액 검사를 락 안으로 옮겼다.

**수정 후 검증**

```
10 동시 요청 × 각 2,000P (보유 10,000P) → 성공 정확히 5건, 잔액 0
3 동시 요청 × 각 10,000P               → 성공 1건, 잔액 0, 음수 없음
```

### 1-2. 환불 이중 집행 — 요청액의 3배 환불

**실측 결과 (수정 전)**

```
동일 nonce 로 1,000원 환불을 동시 3회 요청 → 3건 모두 200
DB: refund 레코드 3행 (각 1,000원, 4ms 이내 생성)
→ 1,000원 요청했는데 3,000원이 실제로 빠져나감
```

순차 재요청은 409(cached)로 잘 막혔다. **동시 요청만 뚫렸다** — 그래서 지금까지 발견되지 않았다.

**원인** — `src/api/admin/orders/[id]/refund/route.ts`
멱등키 조회 → PG 환불 집행 → 멱등키 저장이 락 없이 실행됐다.
동시 요청이 모두 "멱등키 없음"을 보고 각자 환불을 집행한다.

**수정** — 멱등키 단위 분산 락(`refund:{idempotencyKey}`)으로 임계구역 전체를 직렬화.

**수정 후 검증**

```
동일 nonce 동시 5회 → 성공 1건 / 409(중복) 4건
DB: refund 레코드 1행, 합계 1,000원  ← 정확히 요청한 만큼만
```

### 1-3. 강제취소 이중 집행 + 만료 멱등키 재실행

`cancel` 라우트는 환불과 같은 구조인데 **문제가 하나 더 있었다.**

- 락 없음 → 동시 취소 이중 집행 (취소는 `cancelOrderWorkflow` 가 자동 환불까지 수행 = 금전 영향)
- **만료된 멱등키를 "새 요청"으로 통과**시켜 재집행을 허용했다.
  환불 라우트는 2026-07-28 에 정확히 이 이유로 fail-closed 로 고쳤는데, **취소에는 반영되지 않았다.**

**수정** — 주문 단위 락(`cancel:{orderId}`) + 만료 무관 fail-closed.
락 키를 멱등키가 아니라 주문 id 로 잡은 이유: 이 라우트는 nonce 가 **선택값**이라
멱등키로 잡으면 nonce 없는 동시 요청이 그대로 통과한다.

**수정 후 검증**: nonce 없이 동시 4회 → 성공 1건, `order_cancellation` 1행.

### ⚠️ 운영 전제 — 이 수정이 무효화되는 조건

분산 락은 **Redis 가 있을 때만** 프로세스 간에 유효하다.
`LOCKING_REDIS_URL`(없으면 `REDIS_URL`)이 **둘 다 없으면 in-memory 락으로 떨어지고**,
API 인스턴스를 2대 이상 띄우는 순간 위 세 결함이 그대로 되살아난다.
→ `.env.template` 에 경고와 함께 명시해 두었다. **운영 배포 시 반드시 확인할 것.**

### ✅ 실제 피해 여부 확인

DB 를 직접 조회한 결과 **실제 고객 중 적립금 잔액이 음수인 계정은 0건**이다.
(음수였던 1건은 이번 점검에서 취약점을 실증하려고 만든 `@kr-audit.local` 계정이며, 정리했다.)
운영 배포 후에도 아래 쿼리로 주기 점검을 권한다.

```sql
SELECT customer_id, SUM(amount) AS balance FROM point_ledger
WHERE deleted_at IS NULL GROUP BY customer_id HAVING SUM(amount) < 0;
```

## 2. 🟠 높음 (수정 완료)

### 2-1. "멱등" 적립이 실제로는 멱등이 아니었다

`earnFromPurchaseIdempotent` 는 **원장 적립을 먼저 하고 멱등 로그를 나중에** 기록했다.
동일 주문 이벤트가 동시에 두 번 처리되면 둘 다 중복 검사를 통과해
**원장에 2행 적립**되고, 나중 것만 UNIQUE 제약에 걸려 실패했다. 즉 포인트는 이미 두 배 지급된 뒤였다.

**수정** — 멱등 토큰을 **원장보다 먼저** 선점한다. 중복 요청은 DB 제약에 막혀 원장에 도달하지 못한다.
원장 적립이 실패하면 선점 토큰을 반납해 재시도가 가능하도록 했다(적립 누락 방지).

**검증**: 동일 주문에 동시 5건 적립 시도 → 적립 1건 / skip 4건, 원장 1행, 잔액 정확.

### 2-2. 멤버십 누적이 비멱등 — 등급 부풀리기

`recordAccrual` 은 읽고-더하고-쓰는 구조라 `order.placed` 재발행 시 누적금액이 중복 가산됐다.
등급은 적립률·혜택과 직결되므로 금전 영향이 있다.
코드 주석에도 *"별도 구독 이벤트 재발행 차단 없음 — 향후 보강 deferred"* 라고 남아 있었다.

**수정** — 멤버십 누적을 적립 멱등 토큰에 종속시켰다. 토큰 선점에 성공한 처리만 누적을 반영한다.

### 2-3. Next.js high CVE 3건 — SSRF ×2, DoS

| CVE 성격 | 영향 |
|---|---|
| Server Actions SSRF (커스텀 서버) | 서버가 임의 내부 주소로 요청하도록 유도 |
| rewrites SSRF (공격자 제어 호스트명) | 동일 |
| App Router Server Actions DoS | 서비스 중단 |

스토어프론트는 Server Actions 를 광범위하게 쓴다 = **런타임 노출 경로**.
**15.5.18 → 15.5.21** 로 올렸다(같은 마이너 내 패치라 회귀 위험 낮음).

**검증**: 프로덕션 빌드 성공(248 페이지 생성), 전 페이지 200, E2E 30/30 통과.

### 2-4. sharp(libvips) CVE 4건 — 이미지 처리 런타임

`next` 가 이미지 최적화에 쓰는 런타임 의존성. override 로 `>=0.35.0` 상향.

**의존성 취약점 최종 상태**

| 대상 | 점검 전 | 점검 후 |
|---|---|---|
| 스토어프론트 | high 9 · moderate 5 | **0 · 0** |
| 어드민 | high 7 · moderate 5 | **0 · 0** |
| 백엔드 | high 7 · moderate 15 | high 4 · moderate 11 (아래 §5 수용) |

## 3. 🟡 보통 (수정 완료)

### 3-1. 장바구니 수량에 정수 검증이 없었다

```
quantity=0.4 → 200. 수량 0짜리 라인아이템 생성, 총액 0원 (주문에 유령 항목)
quantity=1.5 → 2로 반올림. 소수 누적분이 섞여 재고·정산 수치가 어긋남
```

UI 는 정수만 보내지만 **API 는 공개**돼 있어 누구나 직접 호출할 수 있다.
→ 양의 정수(1~1000)만 허용하는 가드를 추가. 7개 경계값 케이스 전부 통과 확인.

### 3-2. 초대형 요청 본문이 500 을 유발

~100KB 초과 본문 → `An unknown error occurred` 와 함께 **500**.
본문 파싱이 라우트 미들웨어보다 먼저 실행돼 미들웨어로는 잡을 수 없었고(보안 헤더조차 안 붙었다),
공격자가 손쉽게 오류율을 올려 **진짜 장애 로그를 파묻을 수 있었다.**

→ 전역 `errorHandler` 로 페이로드 초과는 **413**, 깨진 JSON 은 **400** 으로 응답.
기존 오류 응답 형식(404 등)은 그대로 유지됨을 회귀 확인했다.

### 3-3. CSP `connect-src` 에 `https:` 와일드카드

```
이전: connect-src 'self' http://localhost:9000 https: ws: wss:
```

`https:` 는 **모든 HTTPS 호스트**를 허용한다. XSS 가 한 번 성공하면 공격자 서버로
데이터를 그대로 실어 보낼 수 있어 connect-src 방어가 사실상 무의미했다.
게다가 `http://localhost:9000` 이라는 개발 값이 박혀 있었다.

→ **운영 빌드에서만** `NEXT_PUBLIC_MEDUSA_BACKEND_URL` 오리진으로 좁혔다(개발은 기존 유지).
프로덕션 빌드로 E2E 9/9 통과 확인 — 기능 손상 없음.

> ⚠️ 운영에서 외부 서비스(분석·결제 SDK 등)를 붙이면 **반드시 여기에 오리진을 추가**해야 한다.
> 누락 시 브라우저가 조용히 차단한다.

### 3-4. 스토어프론트가 `X-Powered-By: Next.js` 노출

백엔드는 이미 지우고 있었는데 스토어프론트만 그대로였다 → `poweredByHeader: false`.

### 3-5. 환경변수 25개 중 19개가 템플릿에 없었다

운영 배포 시 **조용히 기본값으로 동작**하는 위험. 특히:

| 변수 | 누락 시 |
|---|---|
| `LOCKING_REDIS_URL` / `REDIS_URL` | 분산 락 무력화 → §1 취약점 3건 부활 |
| `COOKIE_SECURE` | HTTPS 인데 세션 쿠키에 Secure 플래그 없음 |
| `SECURITY_GUARD_FAIL_CLOSED` 외 2 | 보안 강화 플래그가 꺼진 채 운영 |
| `PII_ENCRYPTION_KEY` / `ADMIN_2FA_SECRET_KEY` | (운영에서는 fail-fast 하도록 이미 잘 되어 있음) |

→ `.env.template` 을 25개 전부 + 필수/선택 구분 + 누락 시 동작까지 적어 재작성. 현재 누락 **0건**.

## 4. ⚪ 점검했고 이상 없었던 것

추정이 아니라 **실제 요청을 던져 확인**한 결과다. 총 **52개 검사 전부 통과**
(1차 프로브 27 + 2차 19 + 동시성 6).

| 영역 | 확인 내용 |
|---|---|
| **RBAC 커버리지** | admin 라우트 77개 전수 대조. 미매핑 8건은 전부 정당(2FA·logout 은 의도된 예외, `ops/maintenance` 는 라우트 내부 SUPER 이중검증, `ops/health` 는 시크릿 미노출) |
| **IDOR / 소유권** | store 라우트 28개 전수 확인. 타인 주문·카트·적립금 접근 전부 차단(404/403) |
| **토큰 위조·혼용** | `alg=none` 위조, 서명 변조, 고객↔관리자 토큰 교차 사용 — 전부 401 |
| **권한 상승** | 고객이 관리자 적립금 발행/등급 상향 시도, id 주입, 리뷰 검수 우회 — 전부 차단 |
| **인젝션** | SQL, 경로순회(`../../etc/passwd`), 널바이트, 쿼리 필터 주입 — 전부 안전 |
| **CORS** | 와일드카드 없는 명시적 allowlist. 임의 Origin 자격증명 반사 없음 |
| **PII 암호화** | DB 직접 조회: 사업자번호 **8/8 암호화(`pii1:`), 평문 0건** |
| **개인정보 노출** | 공개 엔드포인트 11개 응답을 이메일/전화/주민번호 패턴으로 스캔 — **0건** |
| **데이터 정합성** | 재고 음수 0 · 적립금 음수 0 · 멤버십 음수 0 · 주문총액 음수 0 · 고아 적립로그 0 |

**성능**: API 응답 9~80ms(양호). 동시 30요청에 5xx·429 없음.
SSR 페이지 1.3초는 **dev 서버 측정치라 대표성이 없다** — 프로덕션 빌드에서는 페이지 전환이
1.2초로 약 5배 빨랐다(E2E 실측). 운영 판단은 프로덕션 빌드 기준으로 다시 재야 한다.

## 5. 📌 수용한 위험 (근거 기재)

의도적으로 **고치지 않은** 것들이다. 이유를 남긴다.

| 항목 | 이유 |
|---|---|
| OpenTelemetry high 3건 | **도달 불가**를 실측 확인 — 프로메테우스 exporter 포트(9464/9090/9091) 전부 닫힘, `/metrics` 404, 텔레메트리 설정 없음 |

## 6. 회귀 방지 — 자산화한 것

이번에 찾은 결함이 **다시 생기면 즉시 잡히도록** 프로브를 남겼다.
동시성 결함은 단위 테스트로 잡히지 않으므로 **실제 서버를 상대로** 돌려야 한다.

## 7. 사장님이 하셔야 하는 것

제가 대신 할 수 없는 항목만 추렸다.

### 배포 전 필수

1. **`REDIS_URL` 또는 `LOCKING_REDIS_URL` 설정 확인** — 없으면 §1 취약점 3건이 되살아난다. 가장 중요하다.
2. **`COOKIE_SECURE=true`** (HTTPS 환경)
3. **보안 강화 플래그 3종을 운영에서 켤 것**
   `SECURITY_GUARD_FAIL_CLOSED` · `ADMIN_2FA_REQUIRED` · `ADMIN_MONEY_ACTIONS_SUPER_ONLY`
4. **시크릿 신규 발급** — `JWT_SECRET` · `COOKIE_SECRET` · `PII_ENCRYPTION_KEY` · `ADMIN_2FA_SECRET_KEY` · `REVALIDATE_SECRET`
   (현재 `REVALIDATE_SECRET` 은 `supersecret-revalidate` 라는 개발용 값이다)
5. **C2 시크릿 로테이션 + git 히스토리 스크럽** — 이미 노출된 값이라 발급처 폐기가 먼저다

### 정책 결정 (값만 정해주시면 반영)

무료배송 기준 · 기본 배송비 · 도서산간 추가비 · 인기검색어 노출기준 · 베스트 집계기간 ·
적립금 과세기준(`POINTS_DISCOUNT_POST_TAX`)

### 운영 중 주기 점검

```sql
-- 적립금 음수 계정(경합 결함 재발 감지)
SELECT customer_id, SUM(amount) FROM point_ledger WHERE deleted_at IS NULL
GROUP BY customer_id HAVING SUM(amount) < 0;

-- 동일 주문에 환불 레코드가 여러 건인지(이중 환불 감지)
SELECT payment_id, count(*), SUM(amount) FROM refund GROUP BY payment_id HAVING count(*) > 1;
```

## 8. 남은 한계 — 확인하지 못한 것

정직하게 적는다. "점검했다"와 "이상 없다"는 다르다.

- **결제 PG 실연동 미검증** — 현재 결제는 수동/시스템 provider 다. 실제 PG 연동 시
  환불 경로는 **다시 검증해야 한다**(락은 유효하지만 PG 응답 지연·타임아웃 시나리오는 다르다).
- **다중 인스턴스 환경 미검증** — 분산 락은 단일 프로세스 + Redis 조건에서만 확인했다.
  2대 이상 띄운 뒤 `audit3` 프로브를 다시 돌려볼 것을 권한다.
- **백엔드 ESLint 부재** — 신규 의존성 설치가 필요하고 사내 TLS MITM 환경에서 설치 검증이
  선행돼야 해 손대지 않았다. 현재 품질 방어선은 `tsc --noEmit` + 유닛 408건이다.
- **SSR 성능은 dev 기준 측정치** — 운영 판단에 쓰지 말 것.
- **체크아웃 E2E 간헐 실패 1회 관찰**(2026-07-30) — 이후 재현되지 않았다. 재발 시 스펙 간
  상태 격리가 필요하다.
