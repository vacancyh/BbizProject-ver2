## 1. 분담 요약 (대메뉴 기준)

상세 메뉴(대>중) 구조와 백엔드 매핑은 06 업무분담 참조. 큰 그림만:

| 담당 | 소유 대메뉴 | 소유 디렉터리(예) |
|---|---|---|
| **A · 카탈로그** | ① 홈, ② 상품 | `modules/{home,store,products,categories,collections}`, `lib/data/{products,categories,collections,variants}` |
| **B · 구매/결제** | ③ 장바구니·주문·결제 | `modules/{cart,checkout,shipping}`, `lib/data/{cart,payment,fulfillment}` |
| **C · 회원/마이** | ④ 마이페이지, ⑤ 회원/인증 | `modules/{account,order}`, `lib/data/{customer,orders}` |
| **D · 공통/CS** | ⑥ 고객센터, ⑦ 공통/시스템 | `modules/{common,layout,신규 reviews/cs/cms}`, `styles` |

원칙: **대메뉴 단위로 라우트+`lib/data`+`modules`를 통째 소유** → 파일 충돌 최소화. **D가 공통(⑦)·디자인시스템 게이트키퍼** 겸임.

## 2. 마일스톤 (canonical)

| 마일스톤 | 기간 | 내용 | 종료 기준 |
|---|---|---|---|
| **M0 공통기반** | 1~1.5주 | ⑦ 공통/디자인시스템/KRW, 인증·데이터 호출 규약, 타입 계약 확정 | 공통 컴포넌트·규약 합의, 로컬 전원 구동 |
| **M1 구매여정** | 2~3주 | ② 상품 → ③ 카트/결제 → ④ 주문내역 | 실거래 가능 + E2E 통과 |
| **M2 회원·마이·CS** | 2주 | ⑤ 회원, ④ 적립금/등급/쿠폰/위시, ⑥ CS/리뷰 | 마이페이지·리뷰 동작 |
| **M3 진열·확장** | 2주 | ① 홈/기획전/타임세일, CMS/SEO, 결제수단·본인인증 확장 | 진열·SEO·확장 결제 |

각 마일스톤 종료 = 통합 브랜치 + Playwright E2E 검수.

## 3. 브랜치 전략

- **trunk-based** — `main` 보호(직접 push 금지), 짧은 수명 feature 브랜치에서 작업.
- 브랜치 네이밍
  - 기능: `feature/<대메뉴>-<작업>` (예: `feature/catalog-pdp-disclosure`, `feature/checkout-payment`)
  - 수정: `fix/<요약>` / 잡무: `chore/<요약>`
- **PR 규칙**: 작게 자주, 제목은 의도 중심, **상호 리뷰 1인 이상 필수**, CI 통과 후 머지(Squash 권장). (현재 CI `.github/workflows/ci.yml`는 **타입체크·린트** 게이트. E2E·전화면 스윕은 로컬 `pnpm test:sweep`/`test:e2e`로 운영.)
- 공통 파일(`layout`, 네비, `types`, 디자인 토큰) 변경 = **사전 공지 + 초소형 PR**.

> 현재(팀 분할 전)는 `main` 직접 작업 허용. **팀 분할 착수 시점부터 위 브랜치 전략으로 전환.**

## 4. CODEOWNERS (분담 확정 후 추가)

회의 §5 분담 확정 → 레포 루트 `CODEOWNERS`에 디렉터리별 리뷰어 지정(예시):
```
/apps/web/src/modules/products/      @A
/apps/web/src/modules/checkout/      @B
/apps/web/src/modules/account/       @C
/apps/web/src/modules/common/        @D
/apps/web/src/modules/layout/        @D
```
→ 타 영역 변경 시 자동 리뷰 요청 → 무단 충돌 방지.

---

## 5. 계약 우선(contract-first)

병렬성을 막는 1순위 요인은 의존성. 다음을 먼저 못 박는다.
1. `lib/data` 함수 시그니처 + `types`/`packages/types`를 **인터페이스 PR로 먼저 확정** → 화면 병렬 구현.
2. 백엔드 미구현 기능(06 업무분담의 ❌/⚠️ 항목: 리뷰·포인트·본인인증·PG 등)은 **`lib/data`에 mock + 타입 먼저** → 백엔드 준비 시 구현 교체.
3. 관리자→프런트 캐시 무효화는 기존 `revalidate-contract`(백엔드)↔`revalidate-tags`(프런트) 패턴 유지.

## 6. 협업 메커니즘

- **동기화**: 데일리 15분 스탠드업 + 주 1회 통합/데모.
- **디자인**: 디자인 소스(Figma/프로토타입) 단일화, 공통 토큰(`@medusajs/ui-preset`) 기준. 컴포넌트는 `modules/common` 재사용.
- **완료 정의(DoD)**: 화면 구현 + 모바일 우선 반응형 + 로딩/에러/빈상태 + 접근성 기본 + (가능 시) Playwright E2E 1개 + 리뷰 통과.
- **PR 템플릿**(권장 항목): 변경범위 / 관련 대메뉴 / 테스트 방법 / 스크린샷 / 백엔드 의존성.

## 7. 백엔드 의존성 관리

프런트 일부는 백엔드 store API가 없음(06 업무분담 상태 ❌/⚠️). 택1:
- (a) 4인 중 1명 **풀스택 겸임** — 해당 store 라우트 동반 구축
- (b) **mock 계약 선개발** → 로드맵(Phase 1 결제 / Phase 2 회원)에 맞춰 교체

대표 의존: 결제수단/PG(③), 본인인증·소셜로그인(⑤), 리뷰·포인트·쿠폰·위시 store API(④⑥), 상품 큐레이션 테이블(현재 누락 — 백엔드 마이그레이션 재적용 필요).
