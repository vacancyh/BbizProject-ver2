# 12. 다국어(영어) 가이드

> 📄 **문서 #12** · 2026-08-05 신설 · 영어 지원이 **어디까지 되고, 무엇을 누가 관리하는지**.

---

## 한 줄 요약

**두 갈래로 나뉩니다.**

| | 무엇 | 누가 관리 | 어디서 |
|---|---|---|---|
| **콘텐츠** | 상품명·설명·카테고리·공지·FAQ·배너 | **운영자** | 관리자 화면의 언어 탭 |
| **UI 라벨** | 버튼·안내문·에러 문구 | 개발자 | 코드 (`lib/i18n/messages.ts`) |

이렇게 나눈 이유는 단순합니다. **상품을 올릴 때마다 개발자를 부를 수는 없기 때문**입니다.
반대로 "장바구니에 담기" 같은 버튼 문구는 운영자가 바꿀 일이 없고, 바꾸면 화면이 깨집니다.

---

## 언어 스위치는 하나입니다

고객이 언어를 바꾸면 **상품명과 화면 문구가 함께** 바뀝니다.

```
주소 /en/kr/...
   ├─→ 백엔드에 x-medusa-locale: en-US → 상품명·카테고리·공지가 영어로
   └─→ 스토어프론트 UI 사전 → 버튼·안내문이 영어로
```

전환 UI 는 스토어프론트 **헤더 우측의 언어 버튼**(`KO ▾`)입니다.
데스크톱·모바일 모두 같은 자리에 있습니다.

> 2026-08-10 에 사이드메뉴 안에서 헤더로 옮겼습니다 — 메뉴를 열어야만 보여 찾기 어려웠습니다.

## 언어는 **주소**가 정합니다 (2026-08-12 변경)

```
/kr/store        → 한국어   (기본 언어는 접두사 없음)
/en/kr/store     → 영어
```

### 왜 바꿨나 — 검색엔진이 영어를 볼 수 없었습니다

전에는 언어가 `_medusa_locale` 쿠키에만 있었습니다. 사람에게는 편했지만:

| | 문제 |
|---|---|
| 검색엔진 | **쿠키가 없습니다** → 영어 페이지를 아예 못 봅니다(색인 불가) |
| 링크 공유 | 영어로 보다 링크를 보내면 받는 사람은 한국어로 열립니다 |
| CDN | 한 언어로 만든 응답이 다른 언어 방문자에게 나갈 수 있습니다 |

기본 언어에 접두사를 안 붙인 이유: 기존 주소(`/kr/...`)가 그대로 살아야
이미 색인된 페이지와 공유된 링크가 안 깨집니다.

### 규칙 — 주소가 쿠키를 이깁니다

- `/kr/...` 은 쿠키에 영어가 남아 있어도 **한국어**입니다. 그래야 링크가 공유 가능합니다.
- 쿠키는 "마지막에 고른 언어"를 기억할 뿐이고, **국가코드가 없는 주소로 들어올 때만**
  반영됩니다(`/` → `/en/kr`).

### 동작 방식

라우트를 언어별로 복제하지 않습니다. 미들웨어가 `/en` 을 떼어내고 rewrite 한 뒤
언어를 요청 헤더(`x-ui-locale`)로 넘기고, `getUiLocale()` 이 그걸 읽습니다.

```
요청  /en/kr/store
  ↓  middleware: 접두사 분리 → rewrite(/kr/store) + x-ui-locale: en
  ↓  getUiLocale() → "en"      (헤더 → 쿠키 → 기본 순)
  ↓  getLocaleHeader() → x-medusa-locale: en-US   (콘텐츠 번역도 같은 판단)
```

> ⚠️ **링크는 반드시 `LocalizedClientLink` 를 쓰세요.** 접두사를 안 물고 가면
> 한 번 클릭할 때마다 한국어로 되돌아갑니다. `next/link` 직접 사용처는
> 그 컴포넌트 하나뿐입니다 — 새로 만들지 마세요.
> 주소를 손으로 만들 때(`router.push`)는 `withLocalePrefix(locale, path)` 를 쓰세요.

> ⚠️ **언어 전환은 전체 페이지 로드입니다.** 클라이언트 이동으로는 루트 레이아웃이
> 다시 안 그려져 `<html lang>` 과 버튼 문구가 이전 언어로 남습니다 —
> 한 화면에 두 언어가 섞입니다(2026-08-12 실측).

### 검색엔진에 알리는 것

- `hreflang` — 각 페이지에 `ko-KR` · `en` · `x-default` 3종
- `canonical` — 보고 있는 주소 그대로
- `sitemap.xml` — 모든 경로를 **언어 수만큼** 펼치고 서로를 alternates 로 연결
- `Vary: Cookie` — 국가코드 없는 주소의 진입 리다이렉트가 쿠키를 보기 때문

**기본값은 한국어**입니다. 접두사가 없으면 한국어로 렌더되고, 모르는 언어 코드가 들어와도 한국어로 떨어집니다.

## 운영자가 하는 일 — 콘텐츠 번역

### 상품

관리자 → 상품 → 상품 클릭 → **기본 정보**에 언어 탭(`KR` / `US`)이 있습니다.

1. `US` 탭을 누른다
2. 상품명·부제·상세 설명에 영어를 넣는다 (입력칸 아래에 한국어 원문이 흐리게 보입니다)
3. **변경사항 저장**

> 탭에 **점(•)** 이 붙어 있으면 그 언어에 아직 아무것도 안 넣은 것입니다.
> 신규 등록 화면에는 언어 탭이 없습니다 — 저장한 뒤 상세에서 넣습니다.

### 그 밖에 번역할 수 있는 것

| 대상 | 관리자 위치 |
|---|---|
| 카테고리명·설명 | 카테고리 → 카테고리 클릭 |
| 공지사항 | 설정 → 고객센터 → 공지 |
| FAQ | 설정 → 고객센터 → FAQ |
| 배너 문구 | 설정 → 배너 |

**번역을 안 넣으면 한국어 원문이 그대로 나갑니다.** 화면이 비지 않으니 안심하고 하나씩 채우면 됩니다.

### 기본 영어값은 이미 들어 있습니다

빈 화면에서 시작하지 않도록 **확인용 영어 번역을 시드해 뒀습니다.**

```bash
cd backend/services/api
npx medusa exec ./src/scripts/seed-content-en.ts   # 상품 15 · 카테고리 5 · 컬렉션 2 · 배너 7 · 공지 3 · FAQ 4 …
npx medusa exec ./src/scripts/seed-legal-en.ts     # 약관 · 개인정보처리방침 영문본
```

**이미 번역이 있으면 덮어쓰지 않습니다** — 운영자가 고친 값을 스크립트가 지우면 안 되니까요.
기본값으로 되돌리려면 `SEED_EN_OVERWRITE=true` 를 붙입니다.

> 실제 판매 문구가 아니라 **확인용 기본값**입니다. 운영 전에 관리자에서 바꾸세요.

### 저장하면 고객 화면에 바로 반영됩니다

상품·카테고리를 고치면 Medusa 가 이벤트를 쏘고 백엔드 구독자가 스토어프론트 캐시를 지웁니다.
그런데 **번역 저장은 이벤트를 발행하지 않습니다.** 그래서 영어 상품명을 넣어도 화면이
한동안 예전 값을 그대로 보여줬습니다(상품 목록은 `force-cache` 라 시간이 지나도 안 바뀝니다).

→ 관리자 화면이 저장 직후 `POST /admin/translations-revalidate` 를 부르도록 했습니다.
캐시 무효화가 실패해도 저장은 유지됩니다(저장이 되돌아가면 더 나쁩니다).

### 아직 안 되는 것

| 대상 | 이유 |
|---|---|
| 약관 편집 화면 | 영문본은 시드로 들어가 있고 고객 화면에도 나옵니다. 다만 **관리자에 개별 문서 편집 화면이 없어** 운영자가 직접 고칠 수는 없습니다("새 버전 작성"만 있습니다). |
| 상품고시 **값** | 값이 개별 항목이 아니라 JSON 덩어리(`fields_json`)라 항목별 치환이 안 됩니다. **항목명은 번역됩니다**(아래 참조). 값은 한국어 원문이 법적 기준이므로 그대로 둡니다. |

#### 상품고시 항목명은 이렇게 정해집니다

```
관리자 저장:  { "material": "면 100%", "origin": "대한민국" }   ← field_key 로 저장
store 라우트: 상품유형 템플릿에서 label 을 찾아 붙임 + sort_order 로 정렬
화면(한국어): 템플릿 label 을 그대로 — "제품 주소재"처럼 유형별로 더 정확합니다
화면(영어):   사전(`disclosure.field.*`) — 템플릿 label 은 한국어뿐이라 그대로 두면 한글이 남습니다
```

> 예전에는 화면이 **받은 객체의 키를 그대로 항목명으로** 찍고 있었습니다.
> 그래서 관리자에서 고시를 입력하면 고객 화면에 `material` `origin` 이라고 떴습니다.
> 시드된 두 건만 한글을 키로 갖고 있어 멀쩡해 보였을 뿐입니다(2026-08-11 수정).

> 약관 영문본은 **참고용 번역**입니다. 한국 전자상거래법상 효력은 한국어 원문에 있으며,
> 영어 화면 하단에도 그 사실을 함께 표시합니다. 운영 전 법무 검토가 필요합니다.

## 개발자가 하는 일 — UI 라벨

### 문구 추가·수정

`apps/web/src/lib/i18n/messages.ts` 한 파일만 고칩니다.

```ts
export const ko = {
  "cart.checkout": "주문하기",
}
export const en: Messages = {
  "cart.checkout": "Checkout",
}
```

한국어에만 넣고 영어를 빠뜨리면 **타입 에러**가 납니다. 빠뜨릴 수 없습니다.

### 화면에서 쓰기

```tsx
// 서버 컴포넌트
const t = await getT()          // @lib/i18n
<button>{t("cart.checkout")}</button>

// 클라이언트 컴포넌트
const t = useT()                // @lib/i18n/client
<button>{t("cart.checkout")}</button>
```

값 치환: `t("store.resultCount", { count: 12 })` → `총 12개`

### ⚠️ 함정 (실제로 겪은 것)

**클라이언트 컴포넌트에서 `@lib/i18n` 을 import 하지 마세요.**
`next/headers`(서버 전용)가 클라이언트 번들로 끌려 들어가 **화면이 500** 이 됩니다.
클라이언트는 반드시 `@lib/i18n/client`.

**훅은 조기 return 보다 먼저** 호출하세요. `useT()` 도 훅입니다.

## 전환 현황 — UI 라벨은 **전부 끝났습니다** (2026-08-11)

헤더·푸터·메뉴부터 체크아웃 4단계, 마이페이지, 주문 상세까지 전 화면이 전환됐습니다.
사전은 **1,200여 개 키**(ko/en 각 611)입니다.

영어 화면에서 화면을 직접 긁어 확인한 결과, 남은 한글은 **23건이고 전부 데이터**입니다:

| 남은 것 | 왜 한글인가 |
|---|---|
| 고객 이름·배송지 | 고객이 입력한 개인정보. 번역 대상이 아닙니다. |
| 리뷰 본문 | 고객이 쓴 글입니다. |
| 상품정보 고시 **값** | 전자상거래법 고시. 항목명은 번역되지만 값은 한국어 원문이 기준입니다(아래 참조). |
| 인기 검색어 | 실제 고객이 검색한 말입니다. |

### 날짜·금액도 언어를 따라갑니다

화면마다 `Intl.DateTimeFormat("ko-KR")` 을 따로 들고 있어서, 영어로 바꿔도
날짜만 **"2026년 7월 27일"** 로 남았습니다. `@lib/util/format-date` 하나로 모았습니다.

```ts
formatDate(locale, order.created_at)   // ko → 2026. 07. 27.  ·  en → Jul 27, 2026
```

> 새 화면에서 날짜를 찍을 때 `Intl.DateTimeFormat` 을 직접 쓰지 마세요. 같은 일이 반복됩니다.

### 백엔드가 문장을 만들면 안 됩니다

`/store/coupons` 가 `"5,000원 할인 쿠폰"` 처럼 **완성된 한국어 문장**을 내려줬습니다.
화면은 받은 문자열을 그대로 찍을 수밖에 없어 영어로 바꿀 방법이 없었습니다.

→ 이제 **판단에 필요한 값만** 내려줍니다(`discount_type`·`discount_value`·`currency_code`).
문장은 화면이 만듭니다. 새 store 라우트를 만들 때도 같은 원칙을 지키세요.

같은 이유로 주문 상태·적립금 사유도 **코드**로 내려주고 화면에서 번역합니다.

### 전환하는 법 (새 화면을 추가할 때)

1. `messages.ts` 에 ko/en 키 추가 — 영어를 빠뜨리면 타입 에러가 납니다
2. 화면 파일에서 문자열을 `t("키")` 로 교체
3. `e2e/storefront-i18n.spec.ts` 의 `converted` 목록에 그 영역을 추가
   → 그 영역에 한글이 남아 있으면 테스트가 잡아냅니다

## 설정 (운영 배포 시)

백엔드에 아래가 필요합니다. 하나라도 빠지면 언어 선택기가 화면에 안 나타납니다.

```ts
// medusa-config.ts
featureFlags: { translation: true },   // ← 없으면 관련 라우트가 전부 404
modules: [{ resolve: "@medusajs/translation" }],
```

```bash
cd backend/services/api
npx medusa db:migrate                                   # locale / translation 테이블
npx medusa exec ./src/scripts/setup-translation.ts      # 지원 언어 + 번역 대상 지정
```

지원 언어를 바꾸려면:

```bash
TRANSLATION_LOCALES=ko-KR,en-US,ja-JP npx medusa exec ./src/scripts/setup-translation.ts
```

> 언어를 늘리면 관리자의 언어 탭도 **저절로 늘어납니다**(하드코딩 아님).
> 다만 UI 라벨은 `messages.ts` 에 그 언어를 추가해야 합니다 — 없으면 한국어로 나옵니다.

## 커스텀 모듈을 번역 대상에 추가하려면

이 프로젝트가 만든 모듈(공지·FAQ·배너 등)은 **두 곳을 같이** 고쳐야 합니다.

1. **모델**에 `.translatable()` 표시
   ```ts
   title: model.text().translatable(),
   ```
   > 모듈 옵션(`entities`)에 넣는 방식은 **동작하지 않습니다.**
   > 허용 목록이 모델 정의에서 오기 때문에 `... is not a translatable entity` 로 거부됩니다.

2. **store 라우트**에서 직접 적용
   ```ts
   const localized = await applyTranslations(req, "notice", notices)
   ```
   > 코어는 **자기 엔티티에만** 번역을 자동 적용합니다. 커스텀 모듈은 안 해 줍니다.
   > 필드 목록은 `src/api/_utils/apply-translations.ts` 의 `CUSTOM_TRANSLATABLE` 과 맞춰야 합니다.

3. `setup-translation.ts` 의 `TRANSLATABLE` 목록에도 추가 후 재실행
