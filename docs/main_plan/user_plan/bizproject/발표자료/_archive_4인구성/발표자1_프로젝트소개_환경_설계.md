# 발표자 1: 프로젝트 소개 · 우리가 AI를 쓴 방식 · 전체 설계 (4~5분)

**[자기소개]**

안녕하세요. 지금부터 저희 팀 쇼핑몰 프로젝트 발표 시작하겠습니다. 저는 OOO이고요, 초기 환경 설정하고 전체 설계, 그리고 팀이 AI를 쓰는 방식을 잡는 걸 맡았습니다.

## 1. 프로젝트 배경 (30초)

**[슬라이드: 프로젝트 개요]**

저희는 회사 bizproject 프로그램으로 한국형 쇼핑몰을 만들었습니다. 팀은 4명, 기간은 약 7주였고요.

결과부터 말씀드리면 **코드 8만 줄, 고객 화면 26개·관리자 화면 33개**를 만들었고, **자동 검증 1,100여 개**가 매번 돌아갑니다.

솔직히 저희, 쇼핑몰 개발 경험이 많지 않았어요. 그래서 아예 처음부터 "AI를 제대로 써보자"로 갔습니다. 근데 여기서 중요한 게 있어요. **AI한테 그냥 "쇼핑몰 만들어줘" 한다고 되는 게 아니더라고요.**

그래서 오늘 저는 기능 자랑보다, **"저희가 AI한테 실제로 프롬프트를 어떻게 썼는지"** 그 방식을 먼저 보여드리겠습니다. 이게 이번 발표 전체를 관통하는 이야기예요.

## 2. 우리 팀의 프롬프트 방식 - 발표의 핵심 (2분)

**[슬라이드: 좋은 프롬프트 = 5요소]**

처음엔 저희도 이렇게 물어봤어요. "상품 페이지 만들어줘." 결과가 엉망이었습니다. 매번 다른 구조로 짜고, 우리 프로젝트 규칙은 하나도 안 지키고요.

그래서 팀이 **프롬프트 공식**을 정했어요. 좋은 프롬프트엔 이 다섯 개가 다 들어갑니다.

```
① 맥락       - 어떤 프로젝트·스택·디렉터리에서 작업하는지
② 할 일(하나) - 화면 1개 또는 함수 1개. 절대 여러 개 X
③ 따를 패턴  - "옆에 있는 OO처럼" 기존 코드를 지목
④ 출력 형태  - 타입 먼저 / diff / 파일:라인 등 원하는 결과물
⑤ 검증 요구  - "끝나면 타입체크하고 화면 확인까지"
```

**[슬라이드: 나쁜 예 vs 좋은 예]**

말로만 하면 안 와닿으니 실제 비교를 보여드릴게요. 저희 개발 가이드 문서에 그대로 박아둔 표예요.

```
❌ 나쁜 예
"상품 페이지 만들어줘"

✅ 좋은 예
"products/[handle] 페이지에 리뷰 탭 1개 추가해줘.
 데이터는 lib/data/reviews.ts 경유 (없으면 mock+타입 먼저 제안).
 옆 상세 섹션 패턴 그대로 따르고, 로딩/빈/에러 상태 처리.
 먼저 접근을 제안하고 내 확인을 받은 뒤 구현해.
 끝나면 npx tsc --noEmit 로 타입체크까지."
```

같은 요청인데 결과 품질이 완전히 달라요. 오른쪽처럼 쓰면 우리 규칙대로, 한 번에, 검증까지 된 코드가 나옵니다.

**[슬라이드: 진행 방식 - 2단계 + 계약 먼저]**

여기에 저희가 규칙 두 개를 더 붙였어요.

**첫째, "먼저 접근 제안 → 내 확인 → 그다음 구현."** 바로 코드부터 뽑지 못하게 했습니다. 파일·함수·타입을 어떻게 잡을지 먼저 말하게 하고, 저희가 오케이 한 다음에 구현시켜요. 이 한 줄로 헛구현이 확 줄었습니다.

**둘째, "추측하지 말고 근거를 대라."** 모르면 지어내지 말고 "코드/문서를 먼저 확인하고 파일:라인으로 근거를 대라"고 못을 박았어요.

그리고 실제 개발 루프는 항상 이 순서였습니다.

```
계약(타입) 먼저 → mock → 화면 → 검증
```

기능 코드부터 짜는 게 아니라, 데이터 타입(계약)을 먼저 확정했어요. 백엔드가 아직 없으면 가짜 데이터(mock)로 화면부터 완성하고, 나중에 그 한 줄만 진짜 API로 교체하는 식이죠. 이 방식 덕에 4명이 병렬로 개발해도 충돌이 거의 없었습니다.

이게 저희가 두 달 내내 쓴 방식이에요. 다음 발표자들이 각자 파트에서 이 방식으로 쓴 실제 프롬프트를 계속 보여드릴 겁니다.

## 3. 기술 스택 선정 - AI와의 첫 대화 (1분)

**[슬라이드: 기술 스택]**

자, 이 방식으로 실제로 뭘 했는지 볼게요. 제일 먼저 정할 건 "뭘로 만들지"였습니다. 이것도 맥락을 충분히 주고 물어봤어요.

```
"한국형 단독 쇼핑몰을 만들려고 해. [맥락]

 요구사항: [제약]
 - 관리자·고객 화면 둘 다
 - 상품/주문/재고 관리
 - 결제 연동 가능
 - 쿠폰·적립금 같은 한국 쇼핑몰 기능
 - 빠른 개발

 오픈소스 커머스 프레임워크를 후보로 추천하고, [할 일]
 각 후보의 장단점과 우리 요구사항 적합도를 표로 정리해줘. [출력 형태]
 추천은 근거를 대줘."
```

```
AI: "Medusa.js를 추천합니다.
     (※ Medusa: 커머스 백엔드용 오픈소스 프레임워크)

     - 관리자 화면 기본 제공
     - 기능별 모듈로 나눠서 개발 가능
     - 결제/배송 확장 쉬움

     함께 쓸 스택:
     - 백엔드: Medusa v2
     - 프론트: Next.js (App Router)
     - DB: PostgreSQL / 캐시: Redis"
```

"뭐가 좋아?" 대신 **후보·근거·표**까지 요구하니까, 비교해서 판단할 재료가 나왔어요. v2가 최신이고 모듈 시스템이 개선됐다길래 v2로 정했습니다.

## 4. 개발 환경 & 전체 설계 - 계약 먼저, 근거 대기 (1분 30초)

**[슬라이드: 환경 + 설계]**

환경 설정은 금방이었어요. Docker로 PostgreSQL·Redis 띄우는 설정, `.env` 파일을 맥락 주고 만들게 했고, 첫 실행 에러(DB 연결 실패)도 로그를 그대로 붙여서 바로 잡았습니다.

정작 공들인 건 **설계**였어요. 여기서 "먼저 접근 제안 → 확인 → 구현"이 빛을 봤습니다.

```
"한국 쇼핑몰 데이터 모델을 설계할 거야. [할 일]

 Medusa 기본(User/Product/Order/Cart)은 그대로 쓰고, [제약]
 우리가 추가할 것만 얹어줘:
 등급 / 적립금 내역 / 리뷰 / 문의 / 배너 / 추천상품.

 바로 코드 짜지 말고, 먼저 테이블 목록과 관계를 제안해. [2단계]
 각 테이블에 왜 필요한지 근거도 같이. 내가 확인하면 그때 구현."
```

이렇게 하니 초안을 놓고 저희가 검증할 수 있었어요. 예를 들어 적립금은 "잔액 컬럼 하나" 대신 **거래 내역 테이블(적립/사용/만료)로 쌓고 합산해서 잔액을 계산**하자고 AI가 제안했는데, 이게 나중에 내역 조회까지 그대로 이어져서 좋았습니다.

폴더 구조도 기능별 모듈로 미리 쪼갰어요.

```
backend/services/api/src/modules/
  ├── customer-level/   (등급)
  ├── customer-points/  (적립금)
  ├── review/ · inquiry/ · discount/
  ├── banner/ · curation/ · ranking/
  └── admin-2fa/
```

이 구조를 처음에 잡아두고, 각자 자기 모듈만 담당하니 병렬 개발에서 충돌이 거의 없었습니다. 이게 진짜 신의 한 수였어요.

마지막으로, 이 모든 규칙(컨텍스트 블록, 프롬프트 템플릿, 함정 목록)을 **개발 가이드 문서로 남겼습니다.** 새 AI 세션 시작할 때마다 이 컨텍스트 블록을 붙여넣고 작업했고, 팀원 누구나 같은 방식으로 AI를 쓸 수 있었어요.

## 5. 소감 (30초)

**[슬라이드: 소감]**

초기 설계랑 팀 AI 방식을 잡으면서 느낀 건 이거예요.

**첫째, AI는 프롬프트가 8할입니다.** 똑같은 AI라도 "만들어줘"랑 "맥락·패턴·검증까지 담은 프롬프트"는 결과가 하늘과 땅이에요.

**둘째, 바로 구현시키지 마세요.** "접근 먼저 제안하고 확인받고 구현" — 이 2단계가 헛수고를 제일 많이 줄여줬습니다.

**셋째, 방식을 문서로 고정하세요.** 컨텍스트 블록이랑 프롬프트 템플릿을 문서로 만들어두니, 4명이 같은 품질로 AI를 쓸 수 있었어요.
실제로 저희 저장소엔 개발 가이드·화면 명세·데이터 모델 문서가 그대로 남아 있고, 새 사람이 와도 그 문서만 보면 같은 방식으로 붙을 수 있습니다.

그럼 이 방식으로 실제 주문·결제를 어떻게 만들었는지, 다음 발표자가 이어가겠습니다. 감사합니다!
