## 1. 관리자 2단계 인증(2FA) - 보안은 근거를 요구 (1분 30초)

**[슬라이드: 보안 문제]**

관리자 페이지는 고객 정보랑 주문을 다 다뤄요. 비밀번호 하나로는 불안해서 2FA를 넣기로 했습니다. 근데 보안은 **AI 답을 그냥 믿으면 안 되는** 영역이라, 근거를 요구했어요.

```
"[맥락] Medusa 관리자에 2단계 인증(TOTP) 추가.
 [할 일] 흐름 설계부터:
 1) 활성화 → QR 생성 → 인증앱 스캔 → 백업코드 발급
 2) 로그인 시 → 비밀번호 + 6자리 코드 → 둘 다 맞아야 통과

 [제약] 표준 라이브러리 기준으로, 자체 암호 구현하지 마.
 [근거] 어떤 라이브러리·방식이 표준인지 근거를 대고,
 비밀 키를 DB에 어떻게 저장해야 안전한지도 설명해.
 바로 코드 말고 접근부터 제안해."
```

```
AI: "speakeasy(TOTP 코드) + qrcode(QR 이미지)가 표준입니다.
     비밀 키는 평문 저장 금지 → 암호화해서 저장하고 쓸 때 복호화.
     백업 코드도 암호화, 1회용. [흐름·테이블 설계...]"
```

특히 "비밀 키 평문 저장하면 안 되지 않냐"를 제가 먼저 짚으니, 암호화 저장으로 잡아줬어요. **보안은 이렇게 되물어야** 안전해집니다. 실제 Google Authenticator로 로그인까지 확인했습니다.

## 2. 요청 제한(Rate Limiting) - 함정을 미리 경고 (1분)

**[슬라이드: 서버 남용]**

보안 점검하다 보니 로그인·검색을 무한정 날릴 수 있는 게 걸렸어요. 비밀번호 대입 공격에 취약하니까요.

```
"[맥락] Medusa API에 IP 기준 요청 제한 추가. Redis로 카운트.
 [할 일] 경로별 제한:
 - 로그인 5회/분, 회원가입 3회/시간, 검색 20회/분, 일반 100회/분
 [패턴] express-rate-limit + rate-limit-redis 기준.
 [함정 경고] 프록시 뒤라 req.ip가 프록시 IP로 잡힐 수 있어.
 실제 클라이언트 IP를 쓰도록 신뢰 프록시 설정도 챙겨줘.
 [검증] 로그인 6번째가 막히는 테스트까지."
```

여기서도 저희가 실제로 밟았던 지뢰(프록시 뒤에서 IP가 다 똑같이 잡히는 문제)를 **미리 경고**로 넣었어요. 그러니 처음부터 제대로 나왔습니다. 테스트 돌려보니 6번째에서 딱 막혔고요.

## 3. 베스트 랭킹 최적화 - "느낌" 말고 측정 (1분 30초)

**[슬라이드: 성능 문제]**

베스트 상품 랭킹 때문에 메인이 너무 느렸어요. 근데 여기서 중요한 건, **"느린 것 같다"가 아니라 숫자로 물었다**는 거예요.

```
"[맥락] 메인의 베스트 랭킹(최근 7일 판매량 TOP 10)이 느려.
 [할 일] 먼저 원인부터 측정·분석해줘. 추측 금지.
 - 이 조회가 매 요청마다 어떤 쿼리를 도는지 짚고
 - 느린 지점을 파일:라인으로 근거를 대줘.
 그다음에 개선안을 후보로 제시(각각 장단점)하고, 추천을 골라줘."
```

```
AI: "매 요청마다 7일치 주문을 집계해서 3~4초 걸립니다.
     개선안 3가지:
     1) Redis 캐싱 (10분 TTL) — 가장 빠름·간단
     2) 집계 테이블 사전계산  3) 실시간 카운터(복잡)
     추천: 1번 캐싱."
```

원인을 근거로 짚게 하고, 개선안을 **후보로 비교**하게 하니 판단이 쉬웠어요. 캐싱으로 구현한 뒤 다시 측정했습니다.

**[슬라이드: 3.2초 → 0.05초]**

- 캐싱 전: 평균 **3.2초**
- 캐싱 후: 평균 **0.05초** (약 64배)

"빨라진 것 같다"가 아니라 **전후를 숫자로** 보여주니, 개선이 확실하게 증명됐어요.

## 4. 인기 검색어 - 자료구조를 지목 (1분)

**[슬라이드: 검색어 분석]**

고객들이 뭘 검색하는지 모아서 메인에 띄우고 싶었어요. 이건 적합한 자료구조를 알고 지목했습니다.

```
"[맥락] 실시간 인기 검색어 TOP 10(1시간 기준). Redis 사용.
 [할 일] 검색 시 키워드 집계 → TOP 10 조회 → 매시간 초기화.
 [패턴] Redis Sorted Set으로. (점수순 자동 정렬이라 랭킹에 적합)
 [검증] 검색하면 순위에 바로 반영되는지 확인."
```

"Redis로 알아서 해줘"가 아니라 **Sorted Set을 콕 집어** 주니, 딱 맞는 구현이 나왔어요. 실제로 검색하면 바로 순위에 반영됐습니다.

## [선택] 검증으로 잡은 진짜 버그 — "눈으로는 안 보이는 것들" (1분 30초)

**[슬라이드: 돈이 새던 두 곳]**

기능이 다 돌아가는 것처럼 보여도, 테스트를 짜기 전엔 안 보이는 게 있었어요. 두 개만 소개할게요.

### ① 24시간 뒤 같은 환불 요청 → 환불이 두 번 나갔습니다

환불에는 중복 방지 장치(멱등키)가 있었어요. 같은 번호로 또 요청하면 막히죠. 그런데 이 키에 **24시간 유효기간**이 걸려 있었습니다.

```
"[맥락] 환불 API 에 멱등키가 있는데, 만료(24h) 이후 같은 키로 다시 요청하면 어떻게 되는지 확인하고 싶어.
 [할 일] 추측하지 말고, 코드 경로를 따라가면서 실제로 어떤 순서로 실행되는지 짚어줘.
 [검증] 실제로 두 번 호출해서 응답과 DB 상태를 보여줘."
```

따라가 보니 이랬습니다.
1. 만료된 키 → "새 요청"으로 통과
2. **환불이 실제로 한 번 더 집행**
3. 그리고 키 저장에서 중복 오류 → 호출자에겐 **실패(400)** 응답

즉 **돈은 또 나갔는데 화면엔 실패로 보이는** 상태였어요. 금전 처리는 애매하면 막는 쪽(fail-closed)이 맞으니, 키가 있으면 만료와 무관하게 재실행하지 않도록 바꿨습니다.

### ② 적립금 1,000원 쓰면, 결제액은 1,100원 줄었습니다

"적립금이 부가세 기준이 좀 이상한 것 같다"는 메모만 있고 아무도 숫자를 안 재봤더라고요. 그래서 쟀습니다.

**[슬라이드: 16,500 → 15,400]**

| | 사용 전 | 사용 후 |
|---|---:|---:|
| 결제 총액 | 16,500 | 15,400 |

1,000포인트를 썼는데 총액은 **1,100원** 줄었어요. 할인이 공급가액에 붙으면서 부가세 10%까지 같이 깎인 겁니다. **적립금을 쓸수록 매출이 10%씩 더 새는** 구조였어요.

지금은 옵션 하나로 "1포인트 = 결제액 1원"이 정확히 맞도록 바꿀 수 있게 해두고, 회계 기준을 정하면 켜기로 했습니다.

**핵심은 이겁니다. 둘 다 화면상으론 멀쩡했어요.** 숫자를 재고 코드 경로를 따라가야만 보였습니다.

## 5. 소감 (30초)

**[슬라이드: 소감]**

보안·성능을 이 방식으로 하면서 느낀 건요.

**첫째, 보안은 처음부터, 그리고 되물으면서.** "이거 평문 저장해도 돼?"처럼 짚어야 안전해집니다.

**둘째, 성능은 느낌이 아니라 측정.** "원인을 파일:라인으로 근거 대"라고 하면 진짜 병목을 찾아줘요. 전후를 숫자로 증명하고요.

**셋째, 함정은 미리 경고.** 우리가 밟은 지뢰(프록시 IP 등)를 프롬프트에 넣으니 같은 실수를 안 했습니다.

**넷째, 아는 만큼 지목하세요.** "Sorted Set으로"처럼 구체적으로 찍으면 결과가 정확해요.

## 전체 프로젝트 종합 소감 (30초)

**[슬라이드: 프로젝트 완성]**

약 7주간 AI랑 쇼핑몰을 만들면서, 저희가 몸으로 배운 건 결국 **"어떻게 묻느냐"**였어요. 오늘 발표 내내 나온 방식, 정리하면 다섯 가지입니다.

1. **맥락·패턴·검증을 담아 구체적으로** — "만들어줘"는 실패, 5요소를 담으면 성공
2. **접근 먼저 제안 → 확인 → 구현** — 바로 코드 뽑지 않기
3. **한 프롬프트 = 한 작업** — 통으로 시키지 않기
4. **함정을 미리 경고 + 에러는 통째로 공유** — 우리가 밟은 지뢰를 프롬프트에
5. **검증 없이는 완료가 아니다** — 타입체크·측정·테스트까지

**성과는 이 정도였습니다:**
- **7주 만에 790파일 / 81,000줄**, 4명이 각자 모듈 담당하며 충돌 거의 없음
- 고객 화면 26개 · 관리자 화면 33개 · 백엔드 API 105개
- 자동 검증 **유닛 938 · API 통합 127 · UI E2E 106** 전부 통과
- AI 없었으면 몇 배는 걸렸을 겁니다

결국 **AI는 도구고, 잘 묻는 게 실력**이더라고요. 저희처럼 경험 많지 않은 사람도, 이 방식만 지키면 이 정도는 충분히 만들 수 있습니다.

이상으로 발표를 마치겠습니다. 감사합니다!

## 발표 시 주의사항 (본인 참고용)

- 이 파트 킥은 "측정·근거 요구" + "함정 미리 경고". 3.2초→0.05초는 숫자로 확실히 강조
- 2FA·Rate Limit 용어는 쉽게 풀어주기
- 종합 소감의 다섯 가지는 발표 전체를 관통한 방식 → 천천히, 힘줘서 정리
- 전체 4명 합쳐 20분 넘지 않게 조절
- **B안(검증 버그 단락)을 넣는다면**: "돈이 두 번 나갔다", "1,000원 쓰면 1,100원 깎였다" 두 문장만 확실히 각인시키기.
  세부 원인(공급가액·부가세)은 질문 오면 답하는 용도로 남겨두면 시간이 안 밀립니다.
- 예상 질문 대비: "그건 어떻게 찾았나요?" → **"코드 경로를 따라가게 시키고, 실제로 두 번 호출해서 DB 를 봤습니다."**
