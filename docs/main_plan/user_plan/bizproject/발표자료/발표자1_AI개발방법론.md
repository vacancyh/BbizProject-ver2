# 발표자 1 — AI를 어떻게 썼나 (7분)

> **역할**: 이 발표의 간판입니다. 뒤 두 명이 계속 인용할 방법론을 여기서 세웁니다.
> **한 줄 메시지**: "AI는 프롬프트가 8할이다. 그리고 문서가 곧 컨텍스트다."

---

## 1. 프로젝트 소개 (40초)

**[슬라이드: 만든 것 — 숫자 3개]**

저희가 만든 건 **한국형 온라인 쇼핑몰**입니다. 고객이 쓰는 쇼핑몰, 사장님이 쓰는 관리자 화면,
그리고 그 뒤의 백엔드까지 셋 다요.

숫자로 보면 이렇습니다.

```
고객 화면 26개 · 관리자 화면 33개 · API 110개
자동 테스트 960개 · 보안 점검 52건
```

근데 오늘 하려는 얘기는 **"쇼핑몰을 만들었다"가 아닙니다.**
**"AI를 어떻게 써서 만들었나"** — 이게 저희 발표의 전부입니다.

여러분이 내일 자기 일에 바로 써먹을 수 있는 걸 가져가시게 하는 게 목표예요.

---

## 2. 프롬프트에는 공식이 있다 (2분)

**[슬라이드: 나쁜 예 vs 좋은 예]**

처음엔 저희도 이렇게 물어봤어요.

> "상품 페이지 만들어줘."

결과가 엉망이었습니다. 매번 다른 구조로 짜고, 우리 프로젝트 규칙은 하나도 안 지키고요.
받아서 고치는 시간이 직접 짜는 시간보다 길었습니다.

그래서 팀이 **프롬프트 공식**을 정했어요.

```
① 맥락        어떤 프로젝트·스택·디렉터리에서 작업하는지
② 할 일 (하나) 화면 1개 또는 함수 1개. 절대 여러 개 X
③ 따를 패턴    "옆에 있는 OO처럼" — 기존 코드를 지목
④ 출력 형태    타입 먼저 / diff / 파일:라인 등 원하는 결과물
⑤ 검증 요구    "끝나면 타입체크하고 화면 확인까지"
```

**[슬라이드: 실제 비교]**

말로만 하면 안 와닿으니 실제 비교를 보시죠.

```
❌ 나쁜 예
"상품 페이지 만들어줘"
```

```
✅ 좋은 예
"products/[handle] 페이지에 리뷰 탭 1개 추가해줘.
 데이터는 lib/data/reviews.ts 경유 (없으면 mock+타입 먼저 제안).
 옆 상세 섹션 패턴 그대로 따르고, 로딩/빈/에러 상태 처리.
 먼저 접근을 제안하고 내 확인을 받은 뒤 구현해.
 끝나면 npx tsc --noEmit 로 타입체크까지."
```

같은 요청인데 결과가 완전히 다릅니다. 오른쪽처럼 쓰면 **우리 규칙대로, 한 번에, 검증까지 된 코드**가 나와요.

> 💡 발표 팁: 이 블록은 **읽지 말고 짚으세요.**
> "여기 보시면 맥락, 할 일 하나, 따를 패턴, 그리고 검증까지 다 들어가 있죠."

## 3. 바로 구현하지 못하게 했다 (1분 20초)

**[슬라이드: 2단계 진행법]**

공식에 더해 규칙 두 개를 붙였습니다.

### 첫째 — "먼저 접근 제안 → 내 확인 → 그다음 구현"

바로 코드부터 뽑지 못하게 막았어요.
파일·함수·타입을 어떻게 잡을지 **먼저 말하게** 하고, 저희가 오케이 한 다음에 구현시킵니다.

이 한 줄로 **헛구현이 확 줄었습니다.** 30분짜리 삽질을 30초 대화로 막는 거죠.

### 둘째 — "추측하지 말고 근거를 대라"

모르면 지어내지 말고, **"코드나 문서를 먼저 확인하고 파일:라인으로 근거를 대라"**고 못을 박았습니다.

AI는 모를 때도 아주 자신 있게 답합니다. 그게 제일 위험해요.
근거를 요구하면 확인하고 답하거나, 모른다고 말합니다.

## 4. 계약(타입) 먼저 — 개발 루프 (1분)

**[슬라이드: 개발 루프 4단계]**

실제 개발은 항상 이 순서였습니다.

```
계약(타입) 먼저  →  mock  →  화면  →  실 API 교체
```

기능 코드부터 짜는 게 아니라 **데이터 타입(계약)을 먼저 확정**했어요.
백엔드가 아직 없으면 가짜 데이터(mock)로 화면부터 완성하고,
나중에 **그 한 줄만** 진짜 API로 바꿉니다.

왜 이렇게 했냐면 — 여러 명이 동시에 개발하는데, **타입만 맞춰두면 서로 안 기다려도 되기 때문**입니다.
화면 담당은 mock 으로 계속 진행하고, API 담당은 그 타입에 맞춰 만들면 되니까요.

덕분에 병렬로 개발해도 충돌이 거의 없었습니다.

## 5. ★ 문서를 4층으로 나눈 이유 (1분 30초)

**[슬라이드: 문서 4층 구조]**

이게 저희가 중간에 깨달은 건데요, 꽤 중요합니다.

AI에게 매번 프로젝트를 설명할 수 없잖아요. 그래서 문서를 만들어 붙여줬습니다.
**문서가 곧 컨텍스트**니까요.

그런데 문서를 쌓다 보니 70개가 됐고, 문제가 생겼습니다.
**사람이 읽으려고 쓴 문서를 AI에게 주니까 결과가 나빠지더라고요.**

이유가 있었습니다.

```
사람용 문서              AI용 문서
─────────────           ─────────────
"왜 그렇게 했나"    vs   "정확히 무엇인가"
비유·배경·맥락           타입·경로·제약
읽기 좋게                토큰 효율
```

비유랑 배경 설명이 토큰만 잡아먹고, 정작 필요한 타입 정의는 묻혀버립니다.
반대로 AI용 문서를 사람이 읽으면 사실 나열만 있어서 "그래서 왜?"가 안 보이고요.

그래서 **독자별로 나눴습니다.**

| 폴더 | 독자 | 형식 |
|---|---|---|
| `01_팀원용` | 사람 (합류자) | 설명·비유·"왜 그렇게 했나" |
| `02_AI용` | AI | 사실 나열·정확한 타입과 경로 |
| `03_운영용` | 사장님·운영자 | 개발 지식 0 가정, "무엇을 눌러야 하나" |
| `04_점검기록` | 검증하는 사람 | 결과 + **재현 가능한 실행 도구** |

`02_AI용` 문서들은 아예 **"이 문서를 읽는 AI는 …"** 으로 시작합니다. 사람이 읽으라고 쓴 게 아니에요.

`04_점검기록`도 포인트가 있는데요 — 결과 문서만 남기지 않고 **다시 돌릴 수 있는 스크립트**를 같이 뒀습니다.
"이랬습니다"가 아니라 "이 명령을 치면 지금도 확인됩니다"로요.

> **핵심**: 문서도 코드처럼 **독자가 다르면 다르게 씁니다.**
> 이걸 안 나누면 AI 결과도 나빠지고 사람도 안 읽습니다.

## 6. 마무리 (30초)

**[슬라이드: 정리 3줄]**

정리하면 저희 방식은 세 가지였습니다.

1. **프롬프트 5요소** — 맥락·할 일 하나·패턴·출력·검증
2. **접근 먼저 확인** — 바로 구현 금지, 추측 금지
3. **문서를 독자별로** — 사람용 / AI용 / 운영용

이게 두 달 내내 쓴 방식이고요,
**다음 발표자들이 각자 파트에서 이 방식으로 쓴 실제 프롬프트를 계속 보여드릴 겁니다.**

그럼 이 방법으로 실제 뭘 만들었는지, ○○님이 이어가겠습니다.

## 발표 시 주의사항 (본인 참고용)

- **프롬프트 예시는 읽지 마세요.** 화면에 띄우고 짚어주는 게 훨씬 낫습니다.
- 문서 4층 파트가 이번에 새로 들어간 내용입니다. **여기서 시간 쓰세요** — 다른 팀이 못 하는 얘기입니다.
- "AI가 대신 해줬다"는 뉘앙스는 피하세요. **"우리가 어떻게 시켰나"**가 핵심입니다.
- 시간이 모자라면 4번(계약 먼저)을 30초로 줄이세요. 발표자 2가 실제 사례로 다시 다룹니다.
