  - 프로젝트 배경 및 목표
  - **★ 팀의 프롬프트 방법론(발표 전체의 간판)**: 좋은 프롬프트 5요소 / 나쁜 예 vs 좋은 예 / "접근 제안 → 확인 → 구현" 2단계 / 계약(타입) 먼저 루프 / 컨텍스트 블록·함정 경고
  - 기술 스택 선정 (후보·근거·표로 요구)
  - 전체 설계 (계약 먼저, 근거 대기)
  - 방식을 문서로 고정
- **강조 포인트**: "AI는 프롬프트가 8할" — 이 방식이 뒤 3명 발표를 관통
- **프롬프트 스타일**: 방법론 제시 + 실제 프롬프트 시연
- **소감**: 프롬프트가 결과를 가른다, 바로 구현 금지, 방식을 문서화

### 발표자 2: 주문/결제 시스템 (4~5분)
- **파일**: `발표자2_주문_결제_시스템.md`
- **주요 내용**:
  - 복잡한 주문 프로세스 설계 (Workflow)
  - 엣지 케이스 검증 (동시성, 할인 순서)
  - 단계별 구현 (재고 체크, 할인, 적립금)
  - 관리자 주문 관리 UI
  - 통합 테스트
- **강조 포인트**: 발표자1의 "접근 먼저 제안" + "한 프롬프트 = 한 기능"을 실제로 쓴 사례
- **프롬프트 스타일**: 흐름 먼저 제안받기, 에러 로그 통째 공유, 검증까지
- **소감**: 복잡할수록 접근부터, 한 프롬프트 한 기능, 에러 전문 공유, 테스트 시나리오 직접 지정

### 발표자 3: 상품/회원 시스템 (4~5분)
- **파일**: `발표자3_상품_회원_시스템.md`
- **주요 내용**:
  - 상품 옵션 구조 설계 (사이즈, 색상 조합)
  - 관리자 상품 등록 UI (복잡한 폼)
  - 고객용 상품 상세 페이지 (이미지 갤러리, 옵션 선택)
  - 회원 등급 및 적립금 시스템
  - 재고 관리
- **강조 포인트**: "계약(타입) 먼저 → mock으로 화면부터 → 검증" 루프 + 함정 미리 경고
- **프롬프트 스타일**: 타입 먼저 확정, 백엔드 없이 mock, 실수 목록을 프롬프트에 경고
- **소감**: 타입부터, 함정은 프롬프트에 박기, 꼬이는 조각만 지목, 계산은 경계값 검증

### 발표자 4: 보안 및 성능 최적화 (4~5분)
- **파일**: `발표자4_보안_성능_최적화.md`
- **주요 내용**:
  - 관리자 2FA (TOTP, QR, 백업 코드)
  - API Rate Limiting (Redis)
  - 베스트 랭킹 성능 최적화 (캐싱)
  - 인기 검색어 실시간 트래킹
  - 전체 프로젝트 종합 소감
- **강조 포인트**: "측정·근거 요구"(느낌 말고 숫자) + 함정 미리 경고, 그리고 발표 전체 방식 정리
- **프롬프트 스타일**: 원인을 파일:라인 근거로, 개선안 후보 비교, 전후 숫자 증명
- **소감**: 보안은 되물으며, 성능은 측정으로, 함정은 경고로, 아는 만큼 지목

## 전체 발표 메시지

**"결국 AI는 도구고, 잘 묻는 게 실력이다 — 우리가 실제로 쓴 프롬프트 방식"**

이 발표의 주인공은 완성된 기능이 아니라 **"AI한테 프롬프트를 어떻게 썼는가"**다.
발표자1이 팀의 프롬프트 방법론을 간판으로 세우고, 발표자 2~4가 각자 파트에서
그 방식으로 쓴 **실제 프롬프트**를 계속 보여준다.

### 관통하는 5가지 방식 (발표자1이 심고, 나머지가 재활용):
1. **맥락·패턴·검증을 담아 구체적으로** - "만들어줘" ❌ → 5요소(맥락+한 작업+패턴+출력+검증) ✅
2. **접근 먼저 제안 → 확인 → 구현** - 바로 코드 뽑지 않기(헛구현 방지)
3. **한 프롬프트 = 한 작업** - 통으로 시키지 않기
4. **함정을 미리 경고 + 에러는 통째로 공유** - 우리가 밟은 지뢰를 프롬프트에
5. **검증 없이는 완료가 아니다** - 타입체크·측정·테스트까지

## 발표 시 주의사항

### 전체 공통:
- **말하듯 자연스럽게** - 대본 읽는 티가 안 나게
- **실제 경험 강조** - 에러, 시행착오, 수정 과정 보여주기
- **프롬프트 예시** - 각 파트마다 2~3개 핵심 프롬프트 소개
- **시간 엄수** - 각자 4~5분, 전체 20분 넘지 않기
- **슬라이드 활용** - 코드/구조/UI는 시각적으로 보여주기

### 발표 흐름 (프롬프트 방식이 관통):
1. 발표자 1: 팀의 프롬프트 방법론 제시 — "AI는 이렇게 쓰는 거구나"
2. 발표자 2: 복잡한 로직에 그 방식 적용 — "접근부터 제안시키니 되네"
3. 발표자 3: 계약 먼저 + mock으로 화면 완성 — "함정을 미리 경고하네"
4. 발표자 4: 측정·근거로 최적화 + 전체 방식 정리 — "잘 묻는 게 실력이네"

### 청중 반응 유도:
- 실제 화면/데모 보여주기
- "여러분도 해보실 수 있습니다" 메시지
- 바로 따라 할 수 있게 구체적인 프롬프트 예시로

## 발표 당일 체크리스트 — 데모 환경 띄우기

시연을 한다면 **발표 30분 전**에 아래 순서로 띄워두세요. (자세한 설명: `02_개발환경_구축.md`)

```bash
# 1) DB·Redis (Docker Desktop 실행 후)
docker compose -f infra/docker/docker-compose.yml --project-directory . up -d shop-postgres shop-redis

# 2) 백엔드 (:9000)
cd backend/services/api && npx medusa develop

# 3) 고객 화면 (:8000)
cd apps/web && pnpm dev

# 4) 관리자 화면 (:7002)
cd apps/admin && pnpm dev
```

| 화면 | 주소 | 계정 |
|---|---|---|
| 고객 스토어프론트 | http://localhost:8000/kr | `test@kr-demo.local` / `test1234!` (등급별: silver·gold·vip) |
| 관리자 | http://localhost:7002 | `admin@shop.local` / `admin1234!` |

**데모 추천 동선(3분)**: 홈 → 상품 상세(옵션 선택) → 장바구니(적립금 사용) → 주문 완료
→ 관리자 주문관리에서 방금 주문 확인 → 대시보드

> ⚠️ 데모 직전에 `pnpm build` 를 돌리지 마세요. 실행 중인 dev 서버의 `.next` 를 덮어써서 화면이 500 이 됩니다.

## 예상 질문 및 답변

**Q: AI가 다 만들어준 거 아니에요?**
A: 아니요. 오늘 보여드린 것처럼, 어떻게 묻고 어떻게 검증하냐가 절반 이상이에요. 접근을 먼저 제안받아 확인하고, 검증까지 저희가 챙겼습니다. 잘못된 코드를 받은 적도 꽤 많았고요.

**Q: 그 프롬프트 방식, 정말 그대로 썼나요?**
A: 네. 팀 개발 가이드 문서에 프롬프트 5요소, 나쁜/좋은 예, 컨텍스트 블록, 함정 목록을 정리해두고 매번 그걸 붙여서 작업했어요. 발표에 나온 프롬프트들이 그 방식 그대로입니다.

**Q: 어떤 AI 도구를 썼나요?**
A: ChatGPT, Claude, GitHub Copilot을 상황에 맞게 섞어서 썼습니다.

**Q: AI 없이도 할 수 있지 않았을까요?**
A: 할 수는 있었겠죠. 근데 시간이 훨씬 더 걸렸을 겁니다. 특히 초기 설계랑 반복 작업에서 도움을 많이 받았어요.

**Q: 프롬프트 작성이 어렵지 않았나요?**
A: 처음엔 애매하게 물어봐서 원하는 답을 못 받았어요. 구체적으로, 맥락까지 주면서 물어보니까 확 좋아졌습니다.

**Q: 실제 서비스로 운영 가능한가요?**
A: 기능과 검증은 준비됐고, **외부 계약이 필요한 부분만 남았습니다.** 자동 검증은 유닛 938개, API 통합 127개, UI E2E 106개가 전부 통과합니다. 남은 건 결제 PG·알림(문자/이메일)·본인인증처럼 계약과 비용이 드는 연동이에요. 그것만 붙이면 바로 운영 가능합니다.

**Q: 테스트는 어느 정도까지 했나요?** *(숫자로 답하면 신뢰가 올라갑니다)*
A: 세 층으로 나눠서 했습니다.
- **유닛 938개** — 계산 로직(적립금·환불액·권한 판정 등)
- **API 통합 127개** — 회원가입부터 주문 완료까지 실제 API 왕복. 동시 요청·권한·멱등성까지
- **UI E2E 106개** — 실제 브라우저로 화면 진입·클릭. 접근성(axe)과 모바일 반응형도 포함

**Q: 버그는 없었나요?**
A: 많았고, 그걸 찾는 게 저희 일이었습니다. 예를 들어 **환불 요청을 24시간 뒤 같은 번호로 다시 보내면 환불이 한 번 더 나가는 결함**, **적립금 1,000원을 쓰면 결제액이 1,100원 줄어드는 부가세 계산 문제**를 검증 과정에서 잡았습니다. 이런 건 눈으로 봐선 절대 안 보이고, 테스트를 짜야 나옵니다.

**Q: 4명이 어떻게 충돌 없이 작업했나요?**
A: 담당 모듈을 나누고, 공통 규칙(타입 계약·문서·프롬프트 방식)을 먼저 문서로 고정했습니다. 그리고 CI에서 타입체크·린트·테스트가 자동으로 돌아 깨진 코드가 합쳐지지 않게 막았어요.
