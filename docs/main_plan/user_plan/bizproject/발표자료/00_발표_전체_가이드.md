## 🎯 이 발표에서 전하려는 것

> ### "AI는 도구고, **잘 묻고 검증하는 게 실력**이다."

쇼핑몰을 만든 이야기가 아닙니다. **AI를 어떻게 써서 만들었는지**가 주제입니다.
듣는 사람이 내일 자기 일에 바로 써먹을 수 있는 방법을 가져가게 하는 게 목표입니다.

**청중이 기억해야 할 3가지**

| # | 메시지 | 누가 |
|---|---|---|
| 1 | **처음부터 잘 쓴 게 아니다** — 네 번 깨지고 네 번 바꿨다 | 발표자 1 |
| 2 | **한 번에 하나씩, 접근부터 확인** — 고치면 옆이 깨진다 | 발표자 2 |
| 3 | **AI 결과는 반드시 검증한다** — 우리 점검조차 틀렸다 | 발표자 3 |

> **이 발표의 힘은 “실패를 먼저 말하는 것”에서 나옵니다.**
> 성공 사례만 나열하면 남의 얘기로 들립니다. 각자 파트에 실패 슬라이드가 들어 있으니
> 그 부분에서 속도를 줄이고, **“그래서 이렇게 바꿨습니다”까지 한 호흡**으로 말하세요.

## 왜 이렇게 나눴나

"기능별"이 아니라 **"AI 활용 단계별"**로 나눴습니다.

```
발표자 1              발표자 2              발표자 3
어떻게 물었나    →    무엇을 만들었나   →   어떻게 믿을 수 있나
(방법론)              (적용 사례)           (검증)
```

기능별로 나누면 "저희는 주문을 만들었고요, 저희는 상품을 만들었고요"로 끝납니다.
**단계별로 나누면 하나의 이야기**가 됩니다 — 방법을 정하고, 그 방법으로 만들고, 만든 걸 검증했다.

발표자 1이 제시한 방법론을 **발표자 2·3이 실제 사례로 증명**하는 구조입니다.

## 발표자별 담당

### 발표자 1 — AI를 어떻게 썼나 (8분)

**이 발표의 간판입니다.** 뒤 두 명이 계속 인용할 내용을 여기서 세웁니다.
구조가 **"방법론 나열"이 아니라 "진화 과정"**입니다 — 각 기(期)는 앞 기가 깨져서 생겼습니다.

| 파트 | 시간 | 내용 |
|---|---|---|
| 프로젝트 소개 | 55초 | 무엇을 만들었나 · 오늘 할 얘기 |
| **★ 네 번 바뀌었다** | 45초 | 1기~4기 개요 — "처음부터 이렇게 한 게 아니다" |
| **1기 — 그냥 시켰다** | 45초 | "상품 페이지 만들어줘" → 고치는 시간 > 짜는 시간 |
| **2기 — 프롬프트 5요소** | 1분 55초 | 공식 · 좋은 예 |
| **2기의 한계** | 1분 50초 | 크게 시키면 검증 불가 → 규칙 3개 (접근 먼저 · 한 기능 · 계약 먼저) |
| **★ 3기 — 함정 심기** | 1분 10초 | 겪은 실수를 다음 프롬프트에 경고로 박기 |
| **4기 — 문서 4층** | 1분 50초 | 사람용 문서를 AI에게 줬더니 나빠졌다 → 독자별 분리 |
| **★ 결과** | 1분 | 단계별로 무엇이 달라졌나 |
| 마무리 | 25초 | 뒤 발표 연결 |

**강조**: "네 번 깨지고 네 번 바꿨다" · "깨질 때마다 사람이 아니라 프롬프트·문서에 규칙으로 남겼다"

### 발표자 2 — AI로 무엇을 만들었나 (7분)

발표자 1의 방법을 **실제로 어떻게 썼는지** 보여줍니다.

| 파트 | 시간 | 내용 |
|---|---|---|
| 주문·결제 설계 | 2분 | "먼저 접근부터 제안해" 실제 프롬프트 |
| 엣지 케이스 | 1분 20초 | "추측 말고 근거를 대" — 동시주문·할인순서 |
| 한 번에 하나씩 | 2분 | 재고 → 할인 → 적립금 단계별 구현 |
| 상품·회원 | 1분 20초 | 기존 패턴 지목하기 |
| **★ 고치다 깨뜨렸다** | 1분 | 보안패치가 린터를 죽임 · 첫 설계가 코어에 막힘 · 최적화 켜니 500 |
| 마무리 | 20초 | — |

**강조**: "한 프롬프트 = 한 기능" · "고치면 옆이 깨진다, 그래서 매번 돌려봐야 한다"

### 발표자 3 — AI 결과를 어떻게 검증했나 (7분)

**가장 임팩트 있는 파트입니다.** 실제로 찾은 버그를 보여줍니다.

| 파트 | 시간 | 내용 |
|---|---|---|
| 왜 검증이 필요한가 | 40초 | AI는 그럴듯하게 틀린다 · 검증 3층 |
| **돈이 새던 곳** | 2분 30초 | 적립금 이중사용 · 환불 이중집행 (실측 수치) |
| **★ 저희 점검도 틀렸습니다** | 1분 | 통과 처리했던 항목 · 한 곳만 고침 · 판정 기준 오탐 |
| **보이지만 안 되던 것** | 1분 30초 | 소셜로그인 계정 공유 (원고엔 우편번호 사례도 있음) |
| 자동 검증 체계 | 1분 | 프로브 52건 — 다시 돌릴 수 있는 스크립트 |
| **★ 숫자로 본 결과** | 1분 | 6개 항목 전/후 · 일부러 안 고친 것과 그 이유 |
| 마무리 | 20초 | — |

**강조**: "저희 점검조차 틀렸습니다" · "실측하지 않으면 모른다" · "전부 0보다 왜 남겼는지 설명되는 게 낫다"

> 💡 **"저희 점검도 틀렸습니다" 슬라이드를 겁내지 마세요.**
> 남의 코드만 지적하면 방어적으로 들립니다. 자기 실수를 먼저 인정하면 나머지 주장이 다 믿깁니다.

## 발표 흐름 (연결 멘트)

발표자 사이 연결을 미리 맞춰두면 매끄럽습니다.

**1 → 2**
> "저희는 처음부터 잘 쓴 게 아니고 **네 번 깨지고 네 번 바꿨습니다.**
> 이 방식으로 실제 뭘 만들었는지는 ○○님이 이어가겠습니다."

**2 → 3**
> "이렇게 만들었는데, **AI가 만든 게 진짜 맞는지는 또 다른 문제**였습니다. 검증 얘기는 ○○님이 이어갑니다."

**3 마무리**
> "AI로 빠르게 만들 수 있었지만, **검증하지 않았으면 돈이 새는 걸 몰랐을 겁니다.**
> 잘 묻고, 반드시 검증한다 — 저희가 배운 건 이거였습니다."

## 예상 질문과 답변

**Q. AI가 짠 코드를 그대로 믿나요?**
> 아니요. 그래서 검증을 3층으로 했습니다 — 타입체크 · 자동테스트(960건) · 보안프로브(52건).
> 실제로 AI가 만든 코드에서 **돈이 새는 버그를 3개** 찾았습니다. 발표자 3 파트에서 보여드립니다.

**Q. 그렇게 여러 번 방식을 바꿨으면, 앞에서 만든 건 다시 짰나요?**
> 대부분 안 짰습니다. 바뀐 건 **만드는 방식**이지 결과물 구조가 아니어서요.
> 다만 3기에 정리한 함정 목록으로 **이미 만든 코드를 되짚어 본 건** 있습니다 —
> mock 의 랜덤값, 계산 필드 단독 선택 같은 건 그때 걸러냈습니다.

**Q. 실패 사례를 이렇게 다 공개해도 되나요?**
> 저희가 발표에서 제일 하고 싶은 얘기가 그겁니다. **성공 사례만 보면 따라할 수가 없습니다.**
> 어디서 깨지는지를 알아야 같은 데서 안 깨지니까요. 전부 문서에 실측 수치와 함께 남겼습니다.

**Q. AI 없이 했으면 얼마나 걸렸을까요?**
> 정확히는 모릅니다. 다만 체감한 건 **"코드 작성"보다 "무엇을 만들지 정하는 것"에 시간이 더 들었다**는 점입니다.
> AI가 빨라진 만큼 설계·검증에 시간을 더 썼습니다.

**Q. 프롬프트를 매번 그렇게 길게 쓰나요?**
> 템플릿으로 만들어 재사용했습니다. 문서에 박아두고 복사해서 씁니다.
> 처음엔 길어 보여도, 헛구현 한 번 되돌리는 것보다 훨씬 쌉니다.

**Q. AI가 틀린 걸 어떻게 알아채나요?**
> "근거를 대라"고 요구합니다 — 파일:라인으로. 그리고 **실측**합니다.
> 예를 들어 "동시 요청에 안전하다"는 답을 받으면 실제로 동시 요청을 던져봅니다.
> 그렇게 잡은 게 적립금 이중사용 버그였습니다.

**Q. 문서를 왜 그렇게 많이 만들었나요?**
> AI에게 매번 프로젝트를 설명할 수 없어서입니다. **문서가 곧 컨텍스트**입니다.
> 다만 **사람용과 AI용을 분리**했습니다 — 형식이 달라야 둘 다 제 역할을 합니다.

**Q. 어떤 AI 도구를 썼나요?**
> ChatGPT · Claude · GitHub Copilot 을 상황에 맞게 섞어 썼습니다.
> 도구보다 **묻는 방식**이 결과를 갈랐습니다.

**Q. 실제 서비스로 운영 가능한가요?**
> 기능과 검증은 됐고, **외부 계약이 필요한 부분만 남았습니다** — 결제 PG · 택배사 API · 알림톡.
> 그것만 붙이면 운영 가능합니다. 준비 상태는 명령 하나로 확인할 수 있게 해뒀습니다
> (`preflight-check.ts` — BLOCK 이 0이면 오픈 가능).

**Q. 여러 명이 어떻게 충돌 없이 작업했나요?**
> 담당 모듈을 나누고, **공통 규칙(타입 계약·문서·프롬프트 방식)을 먼저 문서로 고정**했습니다.
> CI 에서 타입체크·린트·테스트가 자동으로 돌아 깨진 코드가 합쳐지지 않게 막았습니다.

## 시간 배분 팁

- **7~8분은 생각보다 짧습니다.** 슬라이드 1장당 40~50초가 한계입니다.
  - 발표자 1 은 14장, 발표자 2 는 11장, 발표자 3 은 13장입니다 (각자 PDF, 표지 포함).
- **실패 슬라이드에서 속도를 줄이세요.** 여기가 이 발표에서 제일 잘 들리는 부분입니다.
  반대로 목록형 슬라이드(5요소, 규칙 세 개)는 빠르게 넘겨도 됩니다 — 화면에 다 적혀 있습니다.
- 프롬프트 예시는 **읽지 말고 짚어주세요** — "여기 보시면 맥락, 할 일, 검증까지 들어가 있죠"
- 숫자는 반드시 말로 하세요 — "10,000원인데 30,000원어치 할인됐습니다"
- 넘어갈 땐 다음 발표자 이름을 부르세요. 전환이 깔끔해집니다.

## 각자 수정 가이드

각 발표자는 자기 파일을 보고:

1. **본인 말투로** — 단어·어미 바꾸기
2. **실제 경험 추가** — 기억나는 에러, 삽질했던 순간
3. **프롬프트 구체화** — 진짜로 썼던 프롬프트로 교체
4. **소감 개인화** — 본인이 진짜 느낀 점으로

이 대본은 **기본 템플릿**입니다. 각자 편하게 고쳐 쓰세요.
