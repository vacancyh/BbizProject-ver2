# 발표자 2: 주문/결제 시스템 개발 (4~5분)

**[자기소개]**

안녕하세요, 두 번째 발표 맡은 OOO입니다. 저는 주문이랑 결제를 담당했어요. 쇼핑몰에서 제일 복잡하고 제일 예민한 부분이죠. 방금 발표자님이 말한 **그 프롬프트 방식 그대로** 제가 실제로 어떻게 썼는지 보여드리겠습니다.

## 1. 주문 프로세스 설계 - "먼저 접근부터 제안해" (1분 30초)

**[슬라이드: 주문 흐름도]**

주문이 생각보다 복잡해요. "구매 버튼 누르면 끝"이 절대 아니거든요. 재고 체크, 쿠폰, 적립금, 배송비, 상태 관리를 한 흐름에서 다 처리해야 하고, 중간에 하나라도 실패하면 전부 되돌려야 합니다.

이런 복잡한 건 **바로 코드부터 뽑으면 안 돼요.** 그래서 발표자1이 말한 "접근 먼저 제안" 방식으로 물었습니다.

### 프롬프트 (맥락 + 한 작업 + 2단계):

```
"[맥락] Medusa v2 백엔드. 한국 쇼핑몰 주문 처리 흐름을 설계할 거야.

 [할 일] 장바구니 → 결제 대기까지의 주문 워크플로우 설계.
 처리 단계:
 1) 재고 확인·차감 (동시 주문에도 안전하게)
 2) 쿠폰 할인  3) 적립금 사용
 4) 배송비 (5만원 이상 무료, 미만 3000원)
 5) 주문 생성  6) 결제 대기
 * 중간에 실패하면 앞 단계 전부 롤백.

 [진행] 바로 코드 짜지 말고, 먼저 단계별 흐름과 각 단계의
 입력·출력·실패 시 보상(rollback)을 표로 제안해. 내가 확인하면 구현."
```

```
AI: "Medusa의 워크플로우로 단계를 나누길 추천합니다.
     (※ 워크플로우: 여러 작업을 순서대로 처리하고, 실패 시 자동 롤백)

     1 장바구니 검증 → 2 재고 확인(동시성) → 3 할인 →
     4 적립금 차감 → 5 배송비 → 6 주문 생성 → 7 재고 예약 → 8 결제 정보

     각 단계 실패 시 앞 작업을 자동 보상합니다. [흐름 표...]"
```

바로 구현 안 시키고 흐름표부터 받으니까, 저희가 검토하고 "여기 순서 이상한데?"를 짚을 수 있었어요.

## 2. 엣지 케이스 검증 - "추측하지 말고 근거를 대" (1분)

**[슬라이드: 검증 과정]**

설계를 받고 바로 코딩 안 했습니다. 애매한 상황부터 던졌어요. 이때도 **추측 대신 근거를 요구**하는 게 포인트였습니다.

### 동시 주문:

```
"재고 1개인데 2명이 동시에 주문하면 어떻게 되지?
 추측하지 말고, Medusa에서 이걸 안전하게 처리하는 방법을
 실제 방식(락/트랜잭션)으로 설명하고 근거를 대줘."
```

```
AI: "DB 락으로 처리합니다. (※ 락: 먼저 온 작업이 끝날 때까지 대기)
     재고 확인 시 해당 행에 락 → 충분한지 확인 → 부족하면 에러.
     첫 주문이 끝날 때까지 두 번째는 자동 대기합니다."
```

### 할인 순서:

```
"쿠폰이랑 적립금 둘 다 쓰면 순서가 중요해.
 한국 쇼핑몰 관행 기준으로 뭐가 먼저인지, 이유까지 설명해줘."
```

```
AI: "쿠폰 먼저(정가 기준) → 적립금 나중(할인된 금액 기준).
     쿠폰은 판매자 혜택, 적립금은 고객 자산이라 이 순서가 일반적입니다.
     예: 100,000 → 쿠폰 10% → 90,000 → 5,000P → 85,000"
```

이렇게 "이유까지"를 붙이니 그냥 답이 아니라 **판단할 수 있는 답**이 왔어요.

> 💡 **한 걸음 더 (여유 있으면 한 줄로)**: 설명만 듣고 넘어가지 않고 **실제로 테스트를 짰습니다.**
> 재고를 1개로 맞춰놓고 3명이 동시에 결제 버튼을 누르게 했더니 **1건만 성공하고 2건은 거부(400)** —
> 오버셀이 안 난다는 걸 말이 아니라 결과로 확인했어요. 이 테스트는 지금도 통합테스트에 남아 매번 돌아갑니다.

## 3. 단계별 구현 - 한 프롬프트 = 한 기능 (1분 30초)

**[슬라이드: 실제 구현]**

구현도 통으로 안 시켰어요. 발표자1이 강조한 "한 프롬프트 = 한 기능" 원칙대로 쪼갰습니다.

### 1단계 - 재고 확인만:

```
"[할 일] 재고 확인 함수 1개만 만들어줘.
 입력: 변형(variant) ID들, 필요 수량들
 처리: 행 락 걸고 재고 조회 → 부족하면 에러, 충분하면 확정
 [검증] 끝나면 이 함수 단위 테스트도 같이."
```

코드 받아 돌렸더니 락이 안 걸렸어요. 에러 로그를 **그대로** 붙였습니다.

```
"락이 안 걸려. [에러 로그 전문 붙여넣기] 원인 찾아서 고쳐줘."

AI: "트랜잭션 안에서 실행해야 합니다. 워크플로우 스텝에
     transaction 처리를 추가하세요. [수정 diff]"
```

로그를 통째로 주니 원인을 바로 짚었어요.

### 2단계 - 할인 계산만:

```
"[할 일] 할인 계산 함수 1개.
 입력: 상품 합계, 쿠폰 코드, 고객 ID
 처리: 쿠폰 검증(유효/기간/횟수/최소금액) → 할인액 계산
 [엣지] 할인액이 주문액보다 크면 최종금액 0으로 클램프.
 이 조건 꼭 테스트에 넣어줘."
```

사실 이 "최종금액이 마이너스면?" 케이스는 제가 먼저 물어서 잡은 거예요. 테스트에 딱 넣으니 안전해졌습니다.

### 3~4단계 - 적립금 차감, 그리고 합치기:

적립금 차감 함수도 같은 방식으로 하나 만들고, 마지막에 **"이미 만든 함수들을 워크플로우로 연결하고, 실패 시 재고 되돌리기·포인트 복구까지"** 붙여서 전체 흐름을 완성했습니다. 작게 만들어 붙이니 문제가 생겨도 어디서 터졌는지 바로 보였어요.

## 4. 관리자 주문 관리 - 기존 패턴 지목 (30초)

**[슬라이드: 관리자 화면]**

관리자 화면은 "기존 패턴 따라"가 핵심이었어요.

```
"[할 일] 관리자 주문 관리 화면.
 [패턴] 기존 상품 목록 화면(admin의 테이블 컴포넌트) 구조 그대로 따라.
 기능: 목록(페이지·필터) / 상태 변경 / 상세(고객·상품·결제·배송지) / 송장 입력
 상태는 색 뱃지로 (대기=노랑, 완료=초록)."
```

"새로 발명하지 말고 옆에 있는 거 따라"라고 지목하니, 다른 화면이랑 톤이 딱 맞는 결과가 나왔습니다.

## 5. 통합 테스트 - 검증까지가 '완료' (30초)

**[슬라이드: 테스트]**

발표자1이 "검증 없이는 완료가 아니다" 했잖아요. 주문·결제는 특히 그래서, 테스트 시나리오를 직접 지정해서 짜게 했어요.

```
"[할 일] 주문 흐름 통합 테스트.
 시나리오: 1)정상 2)재고부족+롤백 확인 3)쿠폰만료 4)포인트부족
 5)동시주문-한 명만 성공
 [검증] 실제 DB로 돌려서 5번(동시성)이 진짜 막히는지 확인해줘."
```

처음엔 5번에서 둘 다 성공하길래 "격리가 안 된 것 같다"고 짚었고, 실제 DB로 다시 돌리니 정상 동작했습니다. 여기서 좀 식은땀 났어요.

**[슬라이드: 지금 남아 있는 검증 자산]**

이때 짠 테스트가 일회성으로 끝나지 않고 계속 돌아갑니다. 지금은 이렇게 쌓였어요.

| 종류 | 개수 | 무엇을 지키나 |
|---|---:|---|
| API 통합테스트 | **127** | 회원가입→주문완료 전 구간, 동시성·권한·멱등성 |
| UI E2E | **106** | 실제 브라우저로 화면·클릭·체크아웃 |
| 유닛 | **938** | 환불액·적립금 같은 계산 로직 |

특히 **환불은 "같은 요청을 두 번 보내도 한 번만 환불"** 되는지를 테스트로 못 박아뒀는데, 나중에 이 덕분에 실제 결함도 하나 잡았습니다. (마지막 발표자가 이어서 설명해요)

## 6. 소감 (30초)

**[슬라이드: 소감]**

주문·결제를 이 방식으로 만들면서 확실히 느낀 건요.

**첫째, 복잡할수록 "접근부터 제안"이 답입니다.** 흐름표를 먼저 받아 검토하니 헛구현이 없었어요.

**둘째, 한 프롬프트엔 한 기능만.** 통으로 시키면 디버깅이 지옥인데, 쪼개니 문제 지점이 바로 보였습니다.

**셋째, 에러 로그는 통째로 주세요.** 요약하지 말고 전문을 붙이면 원인을 훨씬 잘 잡아줍니다.

**넷째, 테스트 시나리오는 내가 정합니다.** 특히 돈 관련은, 엣지 케이스를 직접 지정해서 검증까지 시켜야 안심돼요.

다음 발표자가 상품이랑 회원 시스템을 이어서 보여드리겠습니다. 감사합니다!

## 발표 시 주의사항 (본인 참고용)

- 이 파트 킥은 "접근 먼저 제안" + "한 프롬프트 = 한 기능". 발표자1 개념을 실제로 쓴 사례임을 강조
- 락·워크플로우 용어는 나오자마자 쉽게 풀어주기
- "에러 로그 전문 붙여넣기"는 청중이 바로 따라 할 수 있는 실전 팁 → 짚어주기
- 5분 넘기지 않게 프롬프트는 핵심 2~3개만 자세히
