# 발표자 2 — AI로 무엇을 만들었나 (7분)

> **역할**: 발표자 1이 세운 방법론을 **실제로 어떻게 썼는지** 사례로 증명합니다.
> **한 줄 메시지**: "한 프롬프트 = 한 기능. 복잡할수록 쪼갠다."

---

## 0. 들어가며 (15초)

앞에서 저희 방식 세 가지를 들으셨죠. 접근 먼저 제안하고, 근거를 요구하고, 한 번에 하나씩.

저는 그 방식으로 **실제로 뭘 만들었는지** 보여드릴게요.
주문·결제가 저희 프로젝트에서 제일 복잡한 부분이라 거기부터 갑니다.

---

## 1. 주문 설계 — "먼저 접근부터 제안해" (2분)

**[슬라이드: 주문 흐름도]**

주문이 생각보다 복잡합니다. "구매 버튼 누르면 끝"이 절대 아니에요.
재고 체크, 쿠폰, 적립금, 배송비, 상태 관리를 한 흐름에서 다 처리해야 하고,
**중간에 하나라도 실패하면 전부 되돌려야** 합니다.

이런 건 **바로 코드부터 뽑으면 안 됩니다.** 그래서 "접근 먼저" 방식으로 물었어요.

**[슬라이드: 실제 프롬프트]**

```
[맥락] Medusa v2 백엔드. 한국 쇼핑몰 주문 처리 흐름을 설계할 거야.

[할 일] 장바구니 → 결제 대기까지의 주문 워크플로우 설계.
 1) 재고 확인·차감 (동시 주문에도 안전하게)
 2) 쿠폰 할인   3) 적립금 사용
 4) 배송비 (5만원 이상 무료, 미만 3000원)
 5) 주문 생성   6) 결제 대기
 * 중간에 실패하면 앞 단계 전부 롤백.

[진행] 바로 코드 짜지 말고, 먼저 단계별 흐름과 각 단계의
 입력·출력·실패 시 보상(rollback)을 표로 제안해. 내가 확인하면 구현.
```

돌아온 건 코드가 아니라 **흐름표**였습니다.

```
1 장바구니 검증 → 2 재고 확인(동시성) → 3 할인 →
4 적립금 차감 → 5 배송비 → 6 주문 생성 → 7 재고 예약 → 8 결제 정보
각 단계 실패 시 앞 작업을 자동 보상
```

바로 구현 안 시키고 표부터 받으니까 **"여기 순서 이상한데?"를 저희가 짚을 수 있었어요.**
코드가 나온 뒤에 발견했으면 다 갈아엎어야 했을 겁니다.

## 2. 엣지 케이스 — "추측하지 말고 근거를 대" (1분 20초)

**[슬라이드: 검증 질문 2개]**

흐름은 잡혔는데, 걱정되는 게 있었어요. 그래서 **근거를 요구**했습니다.

### 동시 주문

```
"재고가 1개 남았는데 두 명이 동시에 주문하면 어떻게 되지?
 추측하지 말고 Medusa 재고 처리 코드를 확인해서
 파일:라인으로 근거를 대줘."
```

"안전합니다"라는 답만 받았으면 그냥 넘어갔을 텐데,
**근거를 요구하니까 실제 코드를 확인하고 답하더라고요.**

### 할인 순서

```
"쿠폰 10% + 적립금 5000원을 같이 쓰면 어느 걸 먼저 적용해야 하지?
 순서에 따라 최종 금액이 달라지는지 계산해서 보여줘."
```

이건 **순서에 따라 실제로 금액이 달라지는** 문제였어요.
계산까지 시켜서 확인하고 정책을 정했습니다.

> 💡 이 습관이 나중에 큰 걸 잡습니다. 발표자 3 파트에서 나와요.

## 3. 한 번에 하나씩 — 단계별 구현 (2분)

**[슬라이드: 4단계 분할]**

설계가 끝났으니 이제 구현인데, **한 번에 다 시키지 않았습니다.**

처음엔 "주문 워크플로우 전체 만들어줘"라고 했다가 실패했거든요.
코드는 나오는데 어디가 틀렸는지 알 수가 없었어요. 너무 크니까요.

그래서 쪼갰습니다.

```
1단계  재고 확인만
2단계  할인 계산만
3단계  적립금 차감만
4단계  합치기
```

**[슬라이드: 1단계 프롬프트]**

```
[할 일] 재고 확인 함수 하나만 만들어줘. 다른 단계는 아직 X.
[패턴] 옆에 있는 validateCart 함수 구조 그대로.
[출력] 타입 먼저 제안하고, 확인받은 뒤 구현.
[검증] 동시 요청 2건 테스트 코드도 같이.
```

이렇게 하니까 **각 단계마다 테스트하고 넘어갈 수 있었어요.**
문제가 생겨도 그 단계만 보면 되니까 훨씬 빨랐습니다.

**핵심은 이겁니다** — 복잡한 걸 AI에게 통째로 던지면 그럴듯하지만 검증 불가능한 코드가 나옵니다.
쪼개면 **각 조각을 확인하면서** 갈 수 있어요.

---

## 4. 상품·회원 — 기존 패턴 지목하기 (1분 20초)

**[슬라이드: "옆에 있는 OO처럼"]**

주문 다음엔 상품·회원 쪽을 만들었는데, 여기선 다른 기법을 많이 썼습니다.
**기존 코드를 지목**하는 거예요.

```
"상품 목록에 가격 필터 추가해줘.
 옆에 있는 카테고리 필터(refinement-list/) 구조 그대로 따라가고,
 URL 쿼리 파라미터 방식도 동일하게."
```

"알아서 잘 만들어줘"라고 하면 매번 다른 구조가 나옵니다.
**"저것처럼"이라고 지목하면 일관성이 유지돼요.**

회원 쪽도 마찬가지였습니다. 적립금·등급·위시리스트를 만들 때
이미 만든 모듈 구조를 계속 지목했습니다.

그 결과 **커스텀 모듈 27개가 전부 같은 구조**입니다.
새로 합류한 사람도 하나만 이해하면 나머지가 다 읽혀요.

---

## 5. 마무리 (20초)

**[슬라이드: 정리]**

제 파트를 정리하면,

1. **복잡한 건 설계부터** — 코드 전에 흐름표
2. **걱정되면 근거를 요구** — "추측하지 마"
3. **한 프롬프트 = 한 기능** — 쪼개야 검증할 수 있다
4. **"옆에 있는 저것처럼"** — 일관성은 지목에서 나온다

이렇게 만들었는데요, **AI가 만든 게 진짜 맞는지는 또 다른 문제**였습니다.
검증 얘기는 ○○님이 이어가겠습니다.

## 발표 시 주의사항 (본인 참고용)

- 프롬프트 블록은 **읽지 말고 짚으세요.** "여기 진행 방식을 지정한 부분이 핵심이에요."
- 3번(쪼개기)이 제일 실용적인 내용입니다. 청중이 바로 따라할 수 있어요. **여기 시간 쓰세요.**
- 시간이 모자라면 4번을 40초로 줄이세요.
- 마지막 연결 멘트를 꼭 하세요 — 발표자 3의 임팩트가 살아납니다.
