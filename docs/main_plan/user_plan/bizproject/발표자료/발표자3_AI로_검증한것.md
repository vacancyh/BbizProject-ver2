# 발표자 3 — AI 결과를 어떻게 검증했나 (6분)

> **역할**: 이 발표에서 **가장 임팩트 있는 파트**입니다. 실제로 찾은 버그를 보여줍니다.
> **한 줄 메시지**: "AI는 그럴듯하게 틀린다. 실측하지 않으면 모른다."

---

## 1. 왜 검증이 필요한가 (40초)

**[슬라이드: "동작합니다" ≠ "맞습니다"]**

앞에서 AI로 빠르게 만든 얘기를 들으셨는데요, 저는 반대 얘기를 하겠습니다.

**AI는 그럴듯하게 틀립니다.**

코드는 돌아가고, 화면도 뜨고, 테스트도 통과해요. 그런데 **틀렸습니다.**
모를 때도 아주 자신 있게 답하거든요.

그래서 저희는 검증을 세 층으로 깔았습니다.

```
① 타입체크        컴파일 단계에서
② 자동 테스트     960개 — 계산 로직·화면 흐름
③ 보안 프로브     52건 — 실제 서버에 공격 요청을 던진다
```

이 중에서 **③번이 진짜를 잡았습니다.** 그 얘기를 하겠습니다.

---

## 2. 돈이 새고 있었습니다 (2분 30초)

**[슬라이드: 적립금 10,000원 → 할인 30,000원]**

### ① 적립금을 세 배로 쓸 수 있었습니다

적립금 사용 코드는 "동시 요청에 안전하다"고 되어 있었어요. 락도 걸려 있었고요.
그런데 **실제로 던져봤습니다.**

장바구니를 3개 만들고, 각각에 10,000원짜리 적립금을 **동시에** 써봤어요.

```
카트1: 200 OK  → 10,000원 할인
카트2: 200 OK  → 10,000원 할인
카트3: 200 OK  → 10,000원 할인

보유 적립금 10,000원인데 30,000원어치 할인
잔액: -20,000원
```

**세 건 다 통과했습니다.** 병렬 요청 수만큼 무한정 늘어납니다.

원인은 **락을 잘못된 단위로 잡은 것**이었어요.
락 키가 "장바구니별"이었는데, **적립금 잔액은 고객별 자산**이거든요.
장바구니를 여러 개 만들면 서로 다른 락을 잡으니까 아무 의미가 없었던 겁니다.

주석에는 "동시 차감 방지"라고 적혀 있었어요. 코드만 읽으면 안전해 보입니다.
**실제로 던져보지 않으면 절대 모릅니다.**

**[슬라이드: 환불 1,000원 요청 → 3,000원 지급]**

### ② 환불이 세 번 나갔습니다

같은 방식으로 환불도 테스트했습니다.
같은 요청번호로 1,000원 환불을 **동시에 3번** 보냈어요.

```
3건 모두 성공
DB 환불 기록: 3건 (각 1,000원)
→ 1,000원 요청했는데 3,000원이 실제로 나감
```

이건 더 무서운 게, **순차로 보내면 정상적으로 막힙니다.**
두 번째 요청은 "이미 처리됨"으로 거부돼요.

**동시에 보낼 때만 뚫립니다.** 그래서 지금까지 발견이 안 됐던 거예요.

### 셋 다 원인이 같았습니다

```
검사 → (락 없음) → 집행
        ↑ 여기로 다른 요청이 끼어든다
```

세 건 모두 이 패턴이었고, 고친 뒤 **같은 공격을 다시 던져서** 막히는 걸 확인했습니다.

```
수정 후: 동시 5건 → 성공 1건, 나머지 4건 거부. 잔액 정확히 0
```

## 3. 보이는데 안 되던 것들 (1분 30초)

**[슬라이드: 눌러도 아무 일이 없는 버튼]**

돈 문제만 있었던 게 아닙니다. **화면에 있는데 동작 안 하는 것들**도 있었어요.

### 우편번호 찾기

코드도 있고 버튼도 보이는데 **눌러도 아무 일이 없었습니다.**

원인이 두 겹이었어요.
- 팝업 창 방식이라 **브라우저 팝업 차단**에 걸림
- 차단돼도 오류가 안 나서 **안내 문구조차 안 뜸**

사용자 입장에선 그냥 고장난 버튼이죠.
페이지 안에 뜨는 레이어 방식으로 바꿔서 해결했습니다.

### 소셜 로그인 — 이게 제일 위험했습니다

"카카오로 시작하기" 버튼이 있었는데, 실제로는 **데모용 가짜 로그인**이었어요.
브라우저 두 개로 각각 로그인해봤습니다.

```
방문자 A → kakao-demo@shop.local
방문자 B → kakao-demo@shop.local   ← 같은 계정!
```

**모든 방문자가 같은 계정에 들어갑니다.**
이대로 열었으면 고객 B가 고객 A의 **주문내역·배송지·연락처를 그대로 봤을 겁니다.**

화면 아래에 "※ 데모 환경"이라는 작은 안내가 있긴 했어요.
근데 **고객은 그거 안 읽고 버튼을 누릅니다.**

→ 운영 배포에서는 아예 안 보이게 막았습니다.

## 4. 검증을 자산으로 만들었습니다 (1분)

**[슬라이드: 다시 돌릴 수 있는 도구]**

여기서 저희가 한 가지 더 한 게 있는데요,
**찾은 걸 문서로만 남기지 않았습니다.**

"이런 버그가 있었습니다"라고 적어두면 다음에 또 생겨도 모르잖아요.
그래서 **다시 돌릴 수 있는 스크립트**로 만들었습니다.

```bash
node presale-security-probe.mjs      # 27건 — 권한·인젝션·헤더
node audit2-probe.mjs                # 19건 — 토큰위조·권한상승·입력경계
node audit3-concurrency-probe.mjs    #  6건 — 적립금/환불 동시 이중집행
```

명령 한 줄이면 **지금도 확인됩니다.**
특히 세 번째는 이번에 찾은 버그가 다시 생기면 바로 잡히도록 만든 거예요.

여기에 CI도 붙였습니다. 코드를 올리면 타입체크·린트·테스트가 자동으로 돌아서
**깨진 코드가 합쳐지지 않게** 막습니다.

## 5. 마무리 (20초)

**[슬라이드: 마지막 한 줄]**

정리하겠습니다.

AI로 빠르게 만들 수 있었습니다. 그건 사실이에요.
근데 **검증하지 않았으면 돈이 새는 걸 몰랐을 겁니다.**

- 코드만 읽으면 안전해 보였습니다
- 주석에도 "방지함"이라고 적혀 있었습니다
- **실제로 던져보고 나서야 알았습니다**

> ### 잘 묻고, 반드시 검증한다.
> 저희가 배운 건 이거였습니다.

감사합니다.

### 예상 추가 질문

**Q. 그 버그들은 AI가 만든 건가요?**
> 네. 다만 사람이 짰어도 나올 수 있는 종류입니다.
> 동시성 문제는 **눈으로 리뷰해서는 거의 안 잡힙니다.** 그래서 실측이 필요한 거고요.

**Q. 검증도 AI로 했나요?**
> 네. 검증 스크립트도 AI로 짰습니다. **AI가 만든 코드를 AI로 검증한 셈**인데,
> 중요한 건 "동작하냐"가 아니라 **"실제로 던져봤냐"**입니다.

**Q. 몇 건이나 찾았나요?**
> 돈이 새는 심각한 것 3건, 그 외 기능·보안 문제 10건 정도입니다.
> 전부 문서에 실측 수치와 함께 남겼습니다.
