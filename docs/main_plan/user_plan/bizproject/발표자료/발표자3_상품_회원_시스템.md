# 발표자 3: 상품/회원 시스템 개발 (4~5분)

**[자기소개]**

안녕하세요, 세 번째 발표 맡은 OOO입니다. 저는 상품 관리랑 회원 시스템, 그러니까 고객이 실제로 보는 화면들을 담당했어요. 저희 팀 방식 중에서 특히 **"계약(타입) 먼저 → mock → 화면 → 검증"** 루프를 제일 많이 쓴 파트라, 그 실제 프롬프트를 보여드리겠습니다.

---

## 1. 계약(타입)을 먼저 - 화면보다 데이터 구조부터 (1분 30초)

**[슬라이드: 계약 먼저]**

상품이 은근히 까다로워요. 같은 티셔츠도 색상·사이즈마다 재고랑 가격이 다 다르거든요.

저희 규칙은 **"화면 코드보다 데이터 타입을 먼저 확정한다"**였어요. 이걸 '계약'이라고 불렀는데, 백엔드랑 프론트가 이 타입만 지키면 각자 병렬로 개발할 수 있으니까요.

```
"[맥락] Next.js 15 + Medusa 스토어프론트. lib/data 계층에 데이터 계약을 먼저 만들 거야.

 [할 일] lib/data/products.ts 에 상품 옵션 구조 '타입만' 먼저 제안해줘.
 - 상품 1개에 여러 옵션(사이즈, 색상)
 - 옵션 조합(variant)마다 재고·가격·할인가 다름
 - 이미지 여러 장(순서 있음)

 [출력] export type 만. 필드마다 단위/형식 주석 달아줘.
 아직 화면 코드는 짜지 마. 타입 확정되면 그때 화면 갈게."
```

```
AI: "export type ProductVariant = {
       id: string
       option_values: Record<string, string>  // 예: { 사이즈:'M', 색상:'빨강' }
       price: number          // 원 단위(KRW)
       sale_price?: number     // 할인가(있을 때만)
       stock: number
     }
     export type ProductDetail = { ... images: ProductImage[] ... }"
```

타입부터 잡으니, 이 계약을 기준으로 관리자 등록 화면이랑 고객 상세 화면을 **동시에** 만들 수 있었어요.

---

## 2. 관리자 상품 등록 - 특정 로직만 콕 집어서 (1분)

**[슬라이드: 상품 등록 화면]**

관리자가 옵션만 넣으면 조합은 자동 생성돼야 편하죠. 근데 화면을 통으로 시키니 조합 만드는 로직이 자꾸 꼬였어요. 그래서 **그 함수 하나만** 떼서 요청했습니다.

```
"[할 일] 옵션 조합 생성 함수 1개만.
 입력: 옵션 배열 [{name:'사이즈', values:['S','M','L']}, {name:'색상', values:['빨강','파랑']}]
 출력: 모든 조합 [{사이즈:'S',색상:'빨강'}, {사이즈:'S',색상:'파랑'}, ...] (총 6개)
 [제약] 순수 함수로, 옵션 개수가 늘어도 동작하게.
 [검증] 2개×2개 → 4개 나오는 단위 테스트도 같이."
```

화면 전체가 아니라 **꼬이는 로직 한 조각만** 정확히 지정하니 깔끔하게 나왔어요. UI 껍데기는 어차피 AI가 금방 만들고요.

---

## 3. 상품 상세 페이지 - mock으로 화면부터 완성 (1분)

**[슬라이드: 프론트 상품 상세]**

여기서 저희 방식의 핵심이 나와요. 리뷰 같은 건 **백엔드 API가 아직 없었는데도** 화면을 먼저 완성했습니다. 가짜 데이터(mock)로요.

```
"[할 일] 상품 상세에 리뷰 탭 추가.
 [데이터] store 리뷰 API는 아직 없어 → lib/data/reviews.ts 에
 타입 + '결정적 mock'으로 만들어. (실제 fetch 코드는 주석으로 남겨두기)
 [함정 경고] mock에 Math.random()/new Date() 쓰지 마. 고정 ID·고정 날짜(ISO)로.
 (SSR 스냅샷 흔들려서 하이드레이션 에러 남)
 [UI] 옆 상세 섹션 패턴 따라. 빈/로딩/에러 상태 필수.
 통화는 convertToLocale 써(하드코딩 금지).
 [검증] 끝나면 npx tsc --noEmit."
```

여기서 중요한 게 **함정을 미리 경고**한 거예요. 저희가 실제로 겪은 실수들(랜덤/현재시각 mock, 통화 하드코딩)을 프롬프트에 미리 박아두니, AI가 그 지뢰를 안 밟았습니다.

모바일에서 갤러리가 작길래 이것도 짧게 이어서 교정했어요.

```
"모바일에서 이미지 갤러리 스와이프 되게 해줘. 기존 갤러리 컴포넌트만 수정."
```

새로 길게 다시 쓰는 대신 **대화를 이어서 짧게 교정**하는 것도 저희 방식이었습니다.

## 4. 회원 등급 & 적립금 - 검증을 요구 (1분 30초)

**[슬라이드: 회원 관리]**

등급·적립금은 계산이 얽혀서 "그럴듯한데 틀린" 코드가 나오기 쉬워요. 그래서 검증을 세게 요구했습니다.

### 등급:

```
"[할 일] 등급 계산 로직.
 BRONZE(기본)/SILVER(10만↑)/GOLD(50만↑)/VIP(100만↑), 적립률 1/2/3/5%.
 주문 완료 시 총 구매액 누적 → 등급 재계산 → 오르면 쿠폰 지급.
 [검증] 경계값 테스트 꼭: 총액이 정확히 10만/50만/100만일 때
 어느 등급인지(이상/초과) 명확히 하고 테스트로 보여줘."
```

경계값("10만원 딱 맞으면 실버냐 아니냐")을 콕 집어 물으니, 애매하게 넘어갈 뻔한 버그를 초반에 잡았어요.

### 적립금 - 계약 재활용:

적립금은 발표자1이 설계한 **거래 내역 테이블(적립/사용/만료)** 구조를 그대로 썼어요. `earnPoints / usePoints / getBalance(합산) / expirePoints` 함수를 각각 하나씩, 계약대로 만들었습니다.

### 마이페이지 - 짧은 교정:

```
"등급 탭에 진행률 바 추가. 예: SILVER인데 GOLD까지 20만원 남았으면
 60%(30만/50만) 표시. 기존 마이페이지 컴포넌트 스타일 따라."
```

숫자로만 보던 걸 막대로 보여주니 확 이해가 쉬워졌어요.

## 5. 소감 (30초)

**[슬라이드: 소감]**

상품·회원 화면을 이 방식으로 만들면서 느낀 건요.

**첫째, 타입(계약)부터 잡으세요.** 화면보다 데이터 구조를 먼저 확정하니, 백엔드 없이도 화면을 완성하고 나중에 한 줄만 교체하면 됐어요.

**둘째, 함정은 프롬프트에 미리 박으세요.** 우리가 겪은 실수 목록을 경고로 붙여두니 AI가 같은 실수를 안 반복했습니다.

**셋째, 통으로 말고 꼬이는 조각만.** 화면 전체가 아니라 문제되는 함수 하나만 집으니 결과가 정확했어요.

**넷째, 계산 로직은 경계값 검증.** "딱 맞을 때"를 물어보면 숨은 버그가 나옵니다.

다음 발표자가 보안이랑 성능 최적화를 이어서 보여드리겠습니다. 감사합니다!

## 발표 시 주의사항 (본인 참고용)

- 이 파트 킥은 "계약 먼저 + mock으로 화면부터" + "함정 미리 경고". 실제 문서의 핵심 방식
- 옵션 조합·진행률 바는 화면 캡처/데모로 보여주면 이해 빠름
- "함정을 프롬프트에 박는다"는 청중이 신기해하는 포인트 → 실수 예(랜덤 mock, 통화 하드코딩) 실감나게
- 등급/적립금은 숫자 예시로 설명 (추상적이면 안 와닿음)
