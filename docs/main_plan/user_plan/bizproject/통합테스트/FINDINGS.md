## 다중 방법으로 확인한 핵심 정합성

- **DB 교차검증(응답 아닌 실제 DB)**: 신규 auth identity 링크, 위시리스트 행, 상품 조회수 누적,
  주문 레코드 존재, **적립금 원장 합계 = API 잔액** 일치 — 모두 확인.
- **동시성**: 같은 이메일 5회 동시 가입 → **정확히 1건만** 성공. 같은 상품 5회 동시 찜 → **DB 1행**(유니크).
  적립금 5회 동시 +100 → **정확히 +500**(lost-update 없음, DB 합계 일치).
- **멱등성**: 반복 찜/반복 동의/반복 GET 안전. **권한 매트릭스**: admin 엔드포인트(미인증 401·고객 401/403·관리자 200),
  store-me(미인증 401·고객 200·관리자 401/403) 모두 기대대로.
- **부정·경계**: 잘못된 별점(9)은 4xx 또는 **1~5로 정제** 저장(DB에 범위 밖 값 0건) — 무결성 유지.

## 🟡 참고 — "새 환경 마이그레이션 누락"은 여전히 유효 (별도 조치 필요)

지난 회차 발견과 동일. `product-curation`(위시리스트·조회수)·`customer-dormancy`(휴면) 모듈은
마이그레이션이 누락/stale 이라 **깨끗한 DB에서 해당 테이블이 생성되지 않는다** →
위시리스트/베스트/휴면 엔드포인트가 500.

- 이번 통합테스트는 **임시 DB(shop_test)에만 해당 테이블을 수동 생성**(`setup-test-db.sh` 4단계)하여
  기능 자체를 초록으로 검증했다. **운영 소스는 건드리지 않았다.**
- 근본 해결(권장):
  ```bash
  cd backend/services/api
  npx medusa db:generate productCuration customerDormancy
  npx medusa db:migrate
  ```
  적용하면 `setup-test-db.sh`의 수동 테이블 보강 단계는 불필요해진다.

## 관찰 메모

- 적립금 응답 구조: `{ entries[], summary:{ balance, total_earned, total_used } }` — 잔액은 `summary.balance`.
- 회원가입 직후 `/store/customers` 프로필 생성 → **재로그인**해야 정식 고객 세션 토큰을 얻는다
  (위시리스트 등 일부 라우트는 register 토큰으로도 동작하나, 탈퇴 등은 재로그인 토큰 필요).
- 리뷰 별점 범위초과는 거부가 아니라 **1~5 클램프**로 처리(무결성 OK, 다만 명시적 4xx 검증을 원하면 라우트에 상한 밸리데이션 추가 여지).
- `payment_status=captured` 검색이 0건인 것은 시드에 해당 상태 주문이 없어서(정상). 상태 다양화 시드를 넣으면 강화 가능.
