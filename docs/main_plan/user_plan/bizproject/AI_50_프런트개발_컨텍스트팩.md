# AI_50 · 프런트개발 컨텍스트팩 (마스터 컨텍스트)

> **이 문서의 성격**: 이 파일은 다른 AI(다른 도구/세션)가 **이 `AI_5x` 묶음 문서만 가지고** 스토어프론트를 개발하기 위한 **단독 완결(self-contained)** 컨텍스트입니다.
> 저장소 다른 문서나 코드에 접근하지 못한다고 가정합니다. 그래서 핵심 사실은 이 문서 안에 **직접 박아** 두었습니다. 형제 문서(AI_51/52/53)는 "더 깊은 상세"용 교차링크일 뿐, 본문 이해에 필수는 아닙니다.
> **반드시 가장 먼저 읽으세요.** 그다음 순서: **AI_51(데이터모델) → AI_52(화면명세) → AI_53(플레이북)**.

---

## 1. 역할 / 목표

**너는 이 한국형 쇼핑몰의 스토어프론트(`apps/web`)를 개발하는 시니어 프런트 엔지니어다.**

- **목표**: 손님(고객)용 **Next.js 스토어프론트**를 만든다. 상품을 보고 → 장바구니에 담고 → 결제하고 → 주문/마이페이지를 보는 그 화면 전부.
- 시장은 **한국**, 기본 통화는 **원화(KRW)**, 기본 진입 경로는 **`/kr`**.
- **백엔드(커머스 서버)와 관리자 앱은 이미 완성되어 있다.** 너는 백엔드를 수정하지 않는다. **`apps/web`만** 개발한다.
- UI 텍스트는 **한국어, 존댓말**. 통화/숫자/날짜는 한국 표기(`ko-KR`).

## 2. 시스템 아키텍처

이 프로젝트는 **백엔드 / 관리자 앱 / 스토어프론트** 3개 + **인프라**로 구성된다. 너의 개발 대상은 **스토어프론트뿐**이다.

| 구성 | 위치 | 주소(포트) | 역할 | 우리가 손대나 |
|------|------|-----------|------|----------------|
| 백엔드 Medusa **v2.15.3** | `backend/services/api` | `http://localhost:9000` | 커머스 API 서버(화면 없음). **고객용 `/store` API** + **관리자용 `/admin` API** 둘 다 제공 | ❌ 그대로 사용 |
| 관리자 앱 | `apps/admin` | `http://localhost:7002` | 운영자(사장님)용 별도 Next.js 앱. `/admin` API 호출 | ❌ 직접 개발 안 함(참고만) |
| **스토어프론트** | **`apps/web`** | **`http://localhost:8000`** (`/kr`) | **손님용 화면. `/store` API만 호출. ← 개발 대상** | ✅ |
| 인프라 | Docker 컨테이너 | Postgres `:5434`, Redis `:6381` | 데이터 저장소 / 캐시 | ❌ 띄우기만 |

> Medusa **내장 admin UI는 꺼져 있음**(`medusa-config.ts`의 `admin.disable=true`). 관리자 화면은 별도 `apps/admin` 앱이 담당한다. 스토어프론트는 관리자와 무관하다.

```
   [손님]                                  [운영자]
     │                                        │
     ▼                                        ▼
┌──────────────────┐                  ┌──────────────────┐
│  스토어프론트     │                  │   관리자 앱       │
│  apps/web :8000   │                  │  apps/admin :7002 │
│  (개발 대상)      │                  │  (직접개발 안 함)  │
└────────┬─────────┘                  └────────┬─────────┘
         │ /store API                          │ /admin API
         │ (x-publishable-api-key 헤더 필수)    │ (관리자 로그인 Bearer)
         └──────────────┬──────────────────────┘
                        ▼
              ┌──────────────────────┐
              │  Medusa 백엔드        │
              │  backend/.../api :9000 │
              │  /store + /admin API   │
              └──────┬─────────┬──────┘
                     ▼         ▼
              ┌──────────┐ ┌──────────┐
              │ Postgres │ │  Redis   │
              │  :5434   │ │  :6381   │
              └──────────┘ └──────────┘
```

데이터 흐름의 핵심: 화면에 보이는 **상품/가격/재고/카테고리/컬렉션**은 전부 백엔드 데이터다. 스토어프론트는 데이터를 직접 만들지 않는다. 데이터는 관리자/시드(seed) 스크립트로 생성되어 `/store` API로 노출된다. → **"상품이 안 보여요"는 대개 프런트 버그가 아니라 데이터/키 문제다.**

## 3. 핵심 사실 (facts) — 외워야 할 절대 규칙

1. **기본 통화 = KRW(원화)**. 기본 region = **한국(국가코드 `kr`)**. 기본 진입 = **`/kr`**.
2. **모든 `/store` 요청에 `x-publishable-api-key` 헤더가 필수.** 없으면 **401 또는 상품이 아예 안 보인다.** 이 키는 **sales channel(판매 채널)** 에 묶여 노출 상품 범위를 결정한다. 값은 env `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY`(형식 `pk_...`)로 주입된다. (SDK가 자동으로 모든 요청에 붙임 — `@lib/config`의 `sdk`를 쓰면 됨.)
3. **가격은 `currency_code` 기반**으로 계산되고, **표기는 반드시 `convertToLocale`(locale `ko-KR`)** 로 한다. **금액/통화기호 하드코딩 금지**(예: `"₩" + price` 절대 금지).
4. **퍼블리셔블 키·region ID·product ID·channel ID 등은 DB마다 값이 다르다.** **절대 하드코딩하지 말 것** — env 또는 런타임 조회(`lib/data`)로 주입.
5. **인증 모델 2종 분리**: 고객 로그인 = **고객 세션(JWT 쿠키 `_medusa_jwt`)**. 관리자 토큰(Bearer)과 전혀 다름 — **프런트는 관리자 토큰을 절대 쓰지 않는다.**
6. **관리자 변경 ↔ 프런트 캐시**: 백엔드 변경 시 `revalidateTag` 계약으로 프런트 ISR 캐시를 무효화한다. 신규 화면도 이 캐시 태그 규약을 따른다(§6).

### 라우팅 / 컴포넌트 경계
- **모든 페이지는 `[countryCode]` 아래**에 있다. 링크/리다이렉트 시 country code(보통 `kr`)를 반드시 유지한다.
- **`(main)` vs `(checkout)`**: 라우트 그룹. `(main)`은 헤더/푸터가 있는 일반 화면, `(checkout)`은 결제 전용 레이아웃.
- **서버 컴포넌트가 기본값.** 페이지(`page.tsx`)와 데이터를 가져오는 컴포넌트는 `async` 서버 컴포넌트로 작성하고 `lib/data` 함수를 직접 `await` 한다.
- **클라이언트 컴포넌트(`"use client"`)는 상호작용이 필요한 부분만** 분리한다(버튼 클릭, 폼 상태, 토글 등).
- ⚠️ **client 컴포넌트 내부에 async 서버 컴포넌트를 넣지 말 것.** (자세한 이유와 회피법은 §8 표준 패턴 단계 3 참고.)

## 6. 데이터 호출 규약

**철칙: 모든 백엔드 호출은 `lib/data/*` 함수를 경유한다. 컴포넌트에서 직접 `fetch`로 백엔드를 때리지 않는다.** (키 주입·캐싱·인증을 한곳에서 관리하기 위함.)

`lib/data` 함수는 다음을 표준으로 따른다(실제 `lib/data/products.ts` 기반):

```ts
"use server"
import { sdk } from "@lib/config"                  // 퍼블리셔블 키가 자동 주입되는 js-sdk 인스턴스
import { getAuthHeaders, getCacheOptions } from "./cookies"

export const listX = async ({ ... }) => {
  const headers = { ...(await getAuthHeaders()) }   // 고객 로그인 시 Bearer 자동 부착(없으면 {})
  const next = { ...(await getCacheOptions("x")) }  // Next 캐시 태그 부착

  return sdk.client.fetch(`/store/...`, {
    method: "GET",
    query: { region_id, fields: "...", ... },
    headers,
    next,
    cache: "force-cache",
  })
}
```

핵심 헬퍼(`lib/data/cookies.ts`, 이미 존재):
- **`getAuthHeaders()`** → 쿠키 `_medusa_jwt`가 있으면 `{ authorization: "Bearer ..." }`, 없으면 `{}`. 로그인 필요 호출에 펼쳐 넣는다.
- **`getCacheOptions(tag)`** → `{ tags: [...] }` 반환. **방문자별 태그(`${tag}-${cacheId}`) + 안정 태그(`tag`)** 를 함께 부착한다. 안정 태그 덕분에 백엔드 webhook이 `revalidateTag(tag)` 로 전역 무효화할 수 있다.
- 퍼블리셔블 키 헤더(`x-publishable-api-key`)는 **`sdk`가 모든 요청에 자동으로** 붙인다(직접 손대지 않음). 단, `sdk`를 거치지 않고 raw fetch를 쓰면 절대 안 되는 이유이기도 하다.

**캐시/revalidate 개념**: 데이터 변경 시 Next 캐시가 안 바뀌면 → dev 재시작(+ `apps/web/.next/cache/fetch-cache` 삭제). 운영에선 `revalidateTag` 경로(`lib/data/revalidate-tags.ts`)를 쓴다. 새 화면도 `getCacheOptions(도메인명)`로 태그를 부착해 같은 규약을 따른다.

## 7. 🟢 store API 직접연동 vs 🔴 커스텀 mock

화면을 만들 때 기능이 **둘 중 어디에 속하는지** 먼저 판단하라. 판단이 곧 개발 방식을 정한다.

### 🟢 직접 연동 (표준 Medusa 기능 — `/store` API 존재)
`lib/data/*`를 통해 그대로 호출하면 됨:
- **상품 / 카테고리 / 컬렉션** (products, categories, collections)
- **카트 → 주문** (cart, orders)
- **고객** (customer: 로그인/회원/주소/프로필)
- **지역/리전** (regions)
- **배송** (fulfillment / shipping)
- **결제** (payment — Medusa payment collection/session 흐름)
- **프로모션/쿠폰 코드 적용** (체크아웃 코드 입력 — 표준 promotion)

### 🔴 커스텀 mock (백엔드 store API 없음 — mock 계약으로 선개발)
백엔드에 관리자(`/admin`) 모듈은 있어도 **고객용 `/store` API가 아직 없는** 한국형 커스텀 기능들. 화면을 먼저 만들고 데이터는 mock으로 채운 뒤, 백엔드 준비 시 fetch만 교체:
- **리뷰**(reviews) · **포인트/적립금**(points) · **회원 등급**(grade/VIP)
- **쿠폰함**(내 쿠폰 보관함 — *코드 적용은 🟢, 보관함 조회는 🔴*) · **위시리스트**(wishlist)
- **약관/동의**(consent) · **약관 페이지**(terms) · **상품정보고시**(disclosure/고시)
- **검색**(search) · **타임세일**(time-sale)
- **본인인증**(휴대폰/실명) · **소셜 로그인**(social) · **PG 결제 / 무통장**(실연동 전 mock 흐름)

> 각 기능의 정확한 **필드/타입/관계**는 **AI_51(데이터모델)** 참조. 어떤 화면이 어느 분류인지의 전체 표는 **AI_52(화면명세)** 참조.

## 8. 표준 개발 패턴 (가장 중요) — "리뷰 탭" 복제

🔴 신규(백엔드 없음) 기능은 **항상 아래 4단계**로 막힘 없이 개발한다. **리뷰(reviews)가 이미 완성된 레퍼런스 구현**이다. 다른 신규 도메인은 이 구조를 그대로 복제하라.

> **계약(타입) → 결정적 mock → 서버 컴포넌트 → 배치/검증 → (백엔드 준비 시 fetch만 교체)**

### 단계 1 — 데이터 계약 + 결정적 mock (`lib/data/<도메인>.ts`)
규칙:
- **타입(`export type`)을 먼저** 정의 = 백엔드와의 계약. 화면은 이 타입에만 의존한다.
- mock은 **결정적(deterministic)** 으로. **`Math.random()` / `new Date()`(현재시각) 금지** — SSR 스냅샷이 흔들린다. created_at 등은 고정 ISO 문자열을 쓴다.
- 교체 지점에 **`// TODO(backend): ...`** 로 실제 fetch 코드를 주석으로 남긴다 → 백엔드 준비 시 그 줄만 교체.

실제 `apps/web/src/lib/data/reviews.ts` 발췌:
```ts
export type ProductReview = {
  id: string
  product_id: string
  author: string          // 마스킹된 작성자명 (예: 김**)
  rating: number          // 1~5
  title?: string
  content: string
  created_at: string      // ISO 8601 (고정값 — 결정적)
  has_photo?: boolean
}
export type ProductReviewSummary = {
  average: number; count: number
  distribution: Record<1|2|3|4|5, number>
}
export type ProductReviewsResult = { reviews: ProductReview[]; summary: ProductReviewSummary }

// 결정적 mock — 랜덤/현재시각 미사용
const MOCK_REVIEWS: Omit<ProductReview, "product_id">[] = [
  { id: "rev_mock_1", author: "김**", rating: 5, title: "재구매 의사 100%",
    content: "배송도 빠르고 품질이 기대 이상이에요.", created_at: "2026-05-21T09:12:00.000Z", has_photo: true },
  // ... 고정 데이터 4건 더
]

export async function listProductReviews(productId: string): Promise<ProductReviewsResult> {
  // TODO(backend): store 리뷰 API 준비 시 아래 mock을 교체.
  //   const { reviews } = await sdk.client.fetch(`/store/products/${productId}/reviews`, {
  //     headers: { ...(await getAuthHeaders()) },
  //     next: { tags: [`reviews-${productId}`] },
  //   })
  const reviews = MOCK_REVIEWS.map((r) => ({ ...r, product_id: productId }))
  // ...요약(평균/분포) 계산 후 반환
  return { reviews, summary: { average, count, distribution } }
}
```

### 단계 2 — UI 컴포넌트 (`modules/<도메인>/components/...`)
- 가능하면 **서버 컴포넌트(`async`)** 로 만들어 `lib/data` 함수를 직접 호출. 상호작용 필요한 부분만 `"use client"` 분리.
- **빈 상태/0건 처리 필수**(예: "아직 등록된 리뷰가 없습니다. 첫 리뷰를 남겨보세요.").
- 통화는 `convertToLocale`, 숫자/날짜는 `ko-KR` 표기.

실제 `apps/web/src/modules/products/components/product-reviews/index.tsx` 발췌:
```tsx
import { listProductReviews, type ProductReview } from "@lib/data/reviews"

const ProductReviews = async ({ productId }: { productId: string }) => {   // ← async 서버 컴포넌트

      <h2 className="text-2xl-semi">상품 리뷰 <span className="text-ui-fg-muted">({summary.count})</span></h2>
      {summary.count === 0 ? (
        <p className="text-ui-fg-muted py-10 text-center">아직 등록된 리뷰가 없습니다. 첫 리뷰를 남겨보세요.</p>
      ) : (
        /* 요약(평균 별점 summary.average.toFixed(1) + 별점 분포) + 리뷰 목록 */
      )}
      {/* TODO(backend): store 리뷰 API 연동 시 작성 폼/페이지네이션 추가 */}

```
(디자인 토큰 사용 예: `text-ui-fg-muted`, `text-ui-tag-orange-icon`, `bg-ui-bg-subtle`, `border-ui-border-base`.)

### 단계 3 — 배치 (라우트/템플릿에 연결)
- 서버 컴포넌트는 **서버 템플릿**에 `<Suspense>`로 배치한다(예: `modules/products/templates/index.tsx` — 상품 상세 템플릿).
- ⚠️ **client 컴포넌트 안에 async 서버 컴포넌트를 넣지 말 것.**
  - 실례: 리뷰는 client인 `product-tabs`(탭 UI) **안에 넣지 않고**, 상위 **서버 템플릿**에 직접 배치했다. client 컴포넌트는 async children을 렌더할 수 없기 때문이다.
  - 회피법: async 서버 컴포넌트는 서버 템플릿 레벨에서 렌더하고, 그 결과(또는 직렬화 가능한 데이터)를 client 컴포넌트에 **prop/children**으로 내려준다.

### 단계 4 — 검증 → 문서 체크 → 커밋
- **`cd apps/web && npx tsc --noEmit`** (web에는 `pnpm typecheck` 스크립트가 **없다** — tsc 직접 실행).
- **실제 페이지 1건을 렌더**해 200/화면을 눈으로 확인(날조 금지).
- 화면 완료 시 백로그(진행보드)의 해당 행을 갱신.
- 작은 단위로 커밋/푸시. 커밋 메시지에 검증 결과 한 줄.

## 9. 환경 구동 요약

**하이브리드 구동**: 사내망 TLS 검사(SSL MITM) 환경에서는 컨테이너 빌드가 인증서 오류로 실패하므로,
- **DB(Postgres :5434) / Redis(:6381)는 Docker로** 띄우고,
- **백엔드(:9000) / 관리자(:7002) / 스토어프론트(:8000)는 호스트에서 네이티브로** 실행한다.

스토어프론트 실행 핵심:
- `apps/web/.env.local` 필수 값:
  ```
  NEXT_PUBLIC_MEDUSA_BACKEND_URL=http://localhost:9000
  NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY=pk_...     # ← DB마다 다름. 없으면 401/상품 미노출
  NEXT_PUBLIC_DEFAULT_REGION=kr
  NEXT_PUBLIC_BASE_URL=http://localhost:8000
  ```
- 실행: `cd apps/web && pnpm install && pnpm dev` → `http://localhost:8000/kr`
- **검증: `pwsh ./scripts/healthcheck.ps1`** (백엔드 `/health` 200, 관리자 `/login` 200, 스토어프론트 `/kr` 200, 인프라 포트 5434/6381).
- 데이터가 비어 보이면 프런트 버그가 아니라 시드/키 문제일 가능성이 높다(상품이 안 뜨면 키·region·seed 확인).

> 전체 AI 환경구축 프롬프트(복붙용 절차 전체)는 저장소의 `02_개발환경_구축.md §0-A`에 있다(이 묶음 외부). 스토어프론트 개발만 한다면 위 4줄 env + `pnpm dev`로 충분하다.

## 10. AI 행동 규칙 (반드시 준수)

1. **실제 렌더/응답으로 검증한다. 날조 금지.** "됐을 것"이 아니라 실제 출력/화면으로 판단한다.
2. **`cd apps/web && npx tsc --noEmit` 통과**를 작업 완료 조건으로 둔다(web엔 typecheck 스크립트 없음).
3. **작은 단위(화면 1개)** 로 작업한다. 한 번에 여러 도메인을 건드리지 않는다.
4. **화면 완료 시 백로그/진행보드를 갱신**한다(문서화 규율).
5. **UI는 한국어·존댓말.** 통화는 `convertToLocale`(ko-KR), 숫자/날짜도 ko-KR 표기. 금액/통화기호 하드코딩 금지.
6. **데이터 호출은 반드시 `lib/data` 경유.** 컴포넌트에서 직접 백엔드 fetch 금지.
7. **신규 프레임워크/라이브러리 도입 금지.** §4 스택 안에서 해결한다.
8. **퍼블리셔블 키/region ID/product ID 등 환경 의존 값 하드코딩 금지.**
9. **소유 디렉터리 안에서만 작업**한다(라우트 + `lib/data/<도메인>` + `modules/<도메인>`). 충돌 방지.
10. **같은 에러가 2회 반복되면 멈추고 원인을 보고**한다(무한 재시도 금지).
