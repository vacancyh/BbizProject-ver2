# 쇼핑몰 운영자 매뉴얼

> 대상: 쇼핑몰을 실제로 운영하는 사람(사장님·운영 담당자). 개발 지식이 없어도 읽을 수 있게 썼다.
> 작성: 2026-08-03
>
> **개발 문서가 아니다.** 코드 구조나 설계 이야기는 여기 없다.
> "매일 무엇을 눌러야 하는가", "문제가 생기면 무엇부터 보는가" 만 적었다.

---

## 0. 시작하기 전에 — 지금 열어도 되는지 확인

판매를 시작하기 전, 준비가 끝났는지 **명령 하나로 점검**할 수 있다.

**① 백엔드·데이터 점검** — 약관·시크릿·상품·재고·결제·권한

```bash
cd backend/services/api
npx medusa exec ./src/scripts/preflight-check.ts
```

**② 고객 화면 점검** — 손님 눈에 무엇이 보이는지

```bash
cd docs/main_plan/user_plan/bizproject/보안점검
STOREFRONT=https://내도메인 node storefront-readiness-probe.mjs
```

①은 데이터를, ②는 **실제 렌더링된 화면**을 본다. 둘 다 돌려야 한다.
예전에 이용약관 자리에 `"QA-008 자동화 테스트 약관 본문입니다"` 가 떠 있는 걸
아무도 몰랐던 적이 있다 — ②가 그런 것을 잡는다.

결과는 세 가지로 나온다.

| 표시 | 뜻 | 해야 할 일 |
|---|---|---|
| 🔴 BLOCK | 이 상태로 열면 안 된다 | 반드시 해결 |
| 🟡 WARN | 열 수는 있지만 곧 문제가 된다 | 계획을 세워 처리 |
| ✅ OK | 확인됨 | — |

**🔴 이 하나라도 있으면 오픈하지 말 것.** 법적 문제(약관 미비)나 금전 사고(결제 미연동)로 이어진다.

배포 파이프라인에 넣어도 된다 — BLOCK 이 있으면 종료코드 1 을 반환한다.

## 1. 매일 하는 일

### 1-1. 주문 확인 → 발송

```
관리자 > 주문
```

1. **신규 주문 확인** — 결제완료 상태의 주문을 본다.
2. **상품 준비** — 재고를 확인하고 포장한다.
3. **송장 입력** — 주문을 선택해 운송장 번호를 입력한다.
   - 여러 건을 한 번에 처리하려면 **대량 발송** 기능을 쓴다.
   - ⚠️ 택배사 API 를 연동하지 않았다면 운송장 번호를 **수기로 입력**해야 한다.
     연동하면 자동으로 채워지고 고객에게 배송추적 링크가 나간다(비용 발생 항목).
4. **발송 처리** — 상태를 배송중으로 바꾼다. 고객 화면에도 반영된다.

### 1-2. 고객 문의 확인

```
관리자 > 설정 > 고객센터    (공지·FAQ 관리)
상품 상세 페이지의 문의(Q&A)
```

- 상품 문의는 **답변을 달아야 고객 화면에 공개**된다(답변 전에는 비공개).
- 반복되는 질문은 FAQ 에 넣으면 문의량이 줄어든다.

### 1-3. 재고 확인

```
관리자 > 창고(warehouse)
```

품절 임박 상품을 확인한다. 재고가 0 이 되면 자동으로 품절 표시되고 장바구니에 담기지 않는다.

## 2. 자주 하는 일

### 2-1. 상품 등록

```
관리자 > 상품 > 새 상품
```

빠뜨리기 쉬운 것:

- **대표 이미지** — 없으면 목록에서 빈칸으로 보인다. 구매전환이 크게 떨어진다.
- **상품정보고시** — 전자상거래법상 의무 항목이다(소재·치수·제조국 등). 카테고리마다 항목이 다르다.
- **옵션(사이즈/색상)** — 옵션별로 재고를 따로 관리한다.
- **판매 상태** — `게시(published)` 로 바꿔야 고객에게 보인다. 초안 상태면 안 보인다.

### 2-2. 가격·할인

```
관리자 > 상품 (개별 가격)
관리자 > 쿠폰 (할인 코드)
관리자 > 타임세일 (기간 한정 할인)
```

- 쿠폰은 **기간·최소주문금액·중복사용 여부**를 반드시 확인하고 만든다.
- 타임세일은 시작/종료 시각이 지나면 자동으로 원가로 돌아간다.

### 2-3. 회원·적립금

```
관리자 > 회원
```

- 회원 등급은 **누적 구매금액에 따라 자동 산정**된다. 수동 조정도 가능하다.
- 적립금은 주문 완료 시 자동 적립된다. 수동 지급/차감도 가능하다(사유를 반드시 남길 것).
- ⚠️ 적립금 수동 지급은 **돈을 주는 것과 같다.** 권한이 있는 사람만 하도록 등급을 제한하라.

## 3. 가끔 하는 일

### 3-1. 환불

```
관리자 > 주문 > 해당 주문 > 환불
```

- **전액 환불**과 **부분 환불**(특정 상품만) 둘 다 가능하다.
- 환불하면 **적립금·쿠폰도 함께 되돌아간다**(비례 배분).
- 환불 수단: PG 취소 / 계좌 입금 중 선택.

> ⚠️ 환불은 되돌릴 수 없다. 금액을 두 번 확인하고 실행하라.
> 같은 요청을 여러 번 눌러도 **한 번만 처리된다**(중복 방지 장치가 있다).

### 3-2. 취소 · 반품 · 교환

| 상황 | 메뉴 | 비고 |
|---|---|---|
| 발송 전 취소 | 주문 > 강제취소 | 재고가 자동 복구된다 |
| 청약철회(7일) | 주문 > 청약철회 | 법정 기간. 단순변심도 포함 |
| 반품 | 반품(RMA) | 검수 → 환불 순서 |
| 교환 | 교환 그룹 | 차액이 있으면 추가 결제/환불 |

**반품 배송비**는 사유에 따라 다르다 — 상품 하자면 판매자 부담, 단순변심이면 구매자 부담.
정책은 `관리자 > 정책` 에서 설정한다.

### 3-3. 정산 · 세무

```
관리자 > 정산
```

- 일자별 매출·환불·순매출을 확인한다.
- **세무사에게 보낼 자료**는 CSV 로 내려받는다(아래 4장).
- 세금계산서는 현재 **수기 발행**이다. 자동 발행은 팝빌 등 연동이 필요하다(비용 발생).

## 4. 자료 내려받기 (엑셀)

세무사 전달, 택배사 대량발송 양식, 회원 현황 보고에 쓴다.

### 화면에서 받기

| 자료 | 위치 | 받는 내용 |
|---|---|---|
| 주문(간단) | 관리자 > 주문 > **엑셀 다운로드** | 주문번호·일시·고객명·수량·금액·상태 (현재 화면 필터 기준, 최대 1,000건) |
| **주문(상세)** | 관리자 > 주문 > **상세 내보내기(주소·연락처 포함)** | 위 + **수령인·연락처·우편번호·배송지·상품명** (최대 50,000건) |
| 회원 목록 | 관리자 > 회원 > **엑셀 다운로드** | 이메일·이름·연락처·가입일·등급·누적구매액·보유적립금·주문건수 |

**택배사 대량발송 양식**을 만들 때는 "상세 내보내기"를 쓴다.
버튼 옆에서 기간(시작일·종료일)을 고를 수 있고, 비워 두면 전체가 나온다.

### 공통

- 기간(`from`·`to`)은 생략하면 전체가 나온다.
- **엑셀에서 한글이 깨지지 않도록** 처리돼 있다(UTF-8 BOM).
- 고객이 입력한 값이 엑셀 수식으로 실행되지 않도록 처리돼 있다(CSV 인젝션 방어).
- 자동화 테스트 계정은 회원 목록에서 기본 제외된다(통계 왜곡 방지).
- 권한이 없는 등급은 다운로드 자체가 차단된다(주문=주문권한, 회원=회원권한).

> ⚠️ **내려받은 파일에는 고객 개인정보가 들어 있다.**
> 개인정보보호법상 보관·파기 책임은 내려받은 사람에게 있다.
> 공용 PC 나 메신저로 주고받지 말 것.

## 4-1. 고객 알림 (2026-08-03 신설)

주문·배송 알림 문구를 관리자에서 직접 고칠 수 있다. 코드 수정이나 배포가 필요 없다.

### 지금 상태

**아직 실제 문자는 나가지 않는다.** 발송 업체 계약 전이라 "기록만" 하는 상태다.
대신 **어떤 주문에 어떤 문구가 나갔어야 하는지는 전부 남는다** — 업체를 붙이는 순간 그대로 발송된다.

### 문구 고치기

```
GET  /admin/notifications/templates      현재 문구 목록
POST /admin/notifications/templates      { id, body } 로 수정
```

기본 문구 9종이 **카카오 알림톡 형식**으로 들어 있다:
주문접수 · 입금확인 · 발송 · 배송완료 · 취소 · 환불 · 가입 · 적립금소멸 · 재입고

문구에는 카카오 표준인 `#{변수}` 를 쓴다.

```
[#{shop_name}]
주문하신 상품이 발송되었습니다.

· 주문번호: #{order_no}
· 택배사: #{carrier}
· 운송장번호: #{tracking_no}

배송 조회는 아래 버튼을 눌러주세요.
```
버튼: `[{"name":"배송조회","type":"DS"}]` · 대체문자도 함께 들어 있다.

> 값이 없는 변수는 **빈칸이 아니라 `#{order_no}` 그대로 남는다.**
> 일부러 그렇게 했다 — 조용히 빈칸이 되면 "주문 이(가) 접수되었습니다" 같은
> 어색한 문구가 고객에게 나간다. 그대로 보이면 즉시 알아챌 수 있다.

### ⚠️ 알림톡을 쓰려면 반드시 알아야 할 것

카카오 알림톡은 문자와 규칙이 다르다.

| 항목 | 내용 |
|---|---|
| **사전 심사** | 아무 문구나 못 보낸다. 카카오에 템플릿을 등록해 **승인**받아야 하고, 승인 코드를 발송 시 함께 보낸다. **심사에 며칠 걸린다** |
| **문구 수정** | 알림톡 본문을 바꾸면 **재심사**가 필요하다. (대체문자 문구는 심사 대상이 아니라 자유롭게 수정 가능) |
| **정보성만** | 광고·홍보 문구를 넣으면 반려된다. 할인 안내는 별도 채널로 |
| **1,000자 제한** | 초과하면 발송 자체가 거부된다 |
| **대체발송** | 고객이 카카오톡을 안 쓰거나 채널을 차단하면 알림톡은 **실패한다.** 그때 문자로 자동 대체발송된다(이미 구현돼 있다) |

위 기본 문구를 **그대로 카카오에 등록**하면 된다. 승인받은 코드는
관리자에서 각 템플릿의 `template_code` 에 입력한다.

### "알림을 못 받았다"는 문의가 오면

```
GET /admin/notifications/logs?order_id=order_xxx
```

언제 / 어떤 문구로 / 성공했는지가 남는다.

| status | 뜻 |
|---|---|
| `sent` | 실제 발송됨 |
| `logged` | 업체 미연동 — 기록만 (현재 기본값) |
| `failed` | 발송 실패. `error` 에 사유(번호 형식 오류, 길이 초과 등) |
| `skipped` | 문구가 없거나 비활성이라 건너뜀 |

### 업체를 연결하려면

`NOTIFICATION_PROVIDER` 환경변수를 바꾸고 구현체를 추가한다.
개발자에게 "`modules/notification-kr/provider.ts` 의 `send()` 하나만 구현하면 된다"고 전달하면 된다.

## 5. 문제가 생겼을 때

### 5-1. 사이트가 안 열린다

1. **서버 상태 확인** — 아래 두 주소를 브라우저에 넣어 본다(로그인 불필요).
   ```
   https://api도메인/hc          → {"status":"ok","db":"up"}     이면 백엔드 정상
   https://쇼핑몰도메인/api/health → {"status":"ok","backend":"up"} 이면 화면 정상
   ```
   `degraded` 가 나오면 그 내용이 원인을 알려준다(`db: down` 등).

   > ⚠️ 예전 `/health` 는 **DB 가 죽어도 "OK"** 를 반환했다. 그 주소는 보지 말 것.
2. 200 이 아니면 DB 또는 Redis 문제다. 인프라 담당자에게 연락한다.
3. **점검모드**로 전환하면 고객에게 안내 문구가 나간다.
   ```
   관리자 > 설정 > 점검모드
   ```
   ※ 점검모드 전환은 **최고관리자(super)만** 할 수 있다.

### 5-2. 주문이 이상하다

```
관리자 > 주문 > 해당 주문 > 메모/이력
관리자 > 감사 로그(audit-logs)
```

- 누가 언제 무엇을 바꿨는지 **감사 로그에 전부 남는다.**
- 주문 상태 변경 이력도 함께 확인할 수 있다.

### 5-3. 고객이 "적립금이 이상하다"고 한다

```
관리자 > 회원 > 해당 회원 > 적립금 이력
```

적립·사용·소멸이 시간순으로 남는다. 잔액은 이 이력의 합계다.

문제가 의심되면 아래 쿼리로 **전체 회원의 이상 여부**를 확인할 수 있다(개발자 도움 필요).

```sql
-- 적립금 잔액이 음수인 회원 (정상이면 0건)
SELECT customer_id, SUM(amount) FROM point_ledger
WHERE deleted_at IS NULL GROUP BY customer_id HAVING SUM(amount) < 0;
```

### 5-4. 관리자가 로그인을 못 한다

- 비밀번호 5회 실패 시 **15분간 계정이 잠긴다**(무차별 대입 방어). 기다렸다 다시 시도한다.
- 2단계 인증(2FA)을 켰다면 인증 앱의 시간이 맞는지 확인한다.
- 백업 코드로도 로그인할 수 있다.

## 7. 백업 — 가장 중요한 습관

**데이터를 잃으면 사업이 멈춘다.** 백업은 있을 때가 아니라 없을 때 티가 난다.

### 백업 받기

```bash
# 리포지토리 루트에서 실행
bash scripts/db-backup.sh
```

`backups/` 폴더에 날짜가 붙은 파일이 생기고, **무결성 검사까지 자동으로 한다**
(읽히지 않는 덤프는 복구도 안 되므로 만든 직후 확인하는 것이 중요하다).
14일이 지난 백업은 자동 정리된다.

### 자동으로 돌리기 (권장)

수동 백업은 반드시 잊어버린다. **하루 한 번 자동 실행**되게 걸어 둘 것.

**Linux / macOS (cron)** — 매일 새벽 3시
```bash
0 3 * * * cd /경로/BbizProject-ver2 && bash scripts/db-backup.sh >> /var/log/shop-backup.log 2>&1
```

**Windows (작업 스케줄러)**
```powershell
schtasks /create /tn "쇼핑몰-DB백업" /tr "bash C:\경로\BbizProject-ver2\scripts\db-backup.sh" /sc daily /st 03:00
```

### 확인할 것

- **백업 파일 크기가 0 이 아닌지** — 0 이면 백업이 실패한 것이다.
- **다른 저장소에도 복사되는지** — 서버가 통째로 죽으면 서버 안의 백업도 같이 죽는다.
  외부 저장소(S3 등)에 자동 복사되도록 설정할 것.
- **복구가 실제로 되는지** — 1년에 한 번은 복구 리허설을 하라.
  "백업은 있는데 복구가 안 되는" 경우가 실제로 흔하다.

복구 절차는 `운영_백업복구_런북.md` 에 있다(실제 복구 리허설을 수행한 기록 포함).

## 8. 계정과 권한

```
관리자 > 권한(permissions)
```

등급은 4종이며, 메뉴별로 조회/생성/수정/삭제 권한을 따로 준다.

**원칙**

- **필요한 만큼만 준다.** 모두에게 super 를 주면 권한 관리의 의미가 없다.
- **환불·정산·회원정보**는 특히 조심해서 준다. 돈과 개인정보에 직결된다.
- **퇴사자 계정은 즉시 삭제**한다. 로그아웃만으로는 부족하다.
- 관리자 2단계 인증(2FA)을 켜는 것을 권장한다.

모든 변경은 감사 로그에 남으므로, 사고가 나면 누가 무엇을 했는지 추적할 수 있다.

## 9-0. 화면에 있지만 아직 동작하지 않는 버튼

일부 버튼은 화면에만 있고 기능이 붙어 있지 않다. **눌러도 아무 일이 없으면 고장으로 오해**하므로
비활성 처리하고 마우스를 올리면 사유가 뜨도록 해 두었다(2026-08-03).

| 화면 | 버튼 | 대안 |
|---|---|---|
| 회원 | SMS · 메일 발송 | 알림 서비스 연동 필요(비용 발생) |
| 쿠폰 | 기획전 만들기 / 쿠폰 발급 | 쿠폰 목록에서 개별 관리 |
| 주문 · 배송 | 일괄 송장 등록 | 주문 상세에서 개별 등록 |
| 대시보드 · 통계 | 리포트 내보내기 | 주문/회원 목록에서 엑셀로 받기 |
| 정산 | 정산서 PDF | 정산 화면에서 수치 확인 후 수기 작성 |
| 리뷰 | 자주 쓰는 답변 | 직접 입력 |
| 상품 · 배송 · 통계 | 일부 필터(재고/택배사/기간) | 검색·탭으로 대체 |

## 8-1. 데모 기능 — 운영에서는 자동으로 숨겨집니다

개발·시연 편의를 위해 넣어 둔 기능이 있습니다. **운영 배포(NODE_ENV=production)에서는
자동으로 화면에서 사라지므로** 따로 지우실 필요는 없습니다. 다만 무엇인지는 알고 계셔야 합니다.

| 기능 | 개발에서 | 운영에서 | 왜 |
|---|---|---|---|
| **카카오/네이버 간편 로그인** | 데모 계정으로 로그인 (경고 표시됨) | **숨김** | 실제 OAuth 가 아니라 **모든 방문자가 같은 계정**에 들어갑니다. 그대로 열면 고객끼리 주문내역이 보입니다 |
| **휴대폰 본인인증** | 인증번호 `000000` 고정 (경고 표시됨) | **숨김** | 결과가 저장되지 않아 "인증 완료" 표시만 뜹니다. 안 하느니 못합니다 |
| **공지·FAQ 예시 데이터** | 비었을 때 예시 공지 표시 | **표시 안 함** | 운영에서 공지를 지우면 없는 안내가 고객에게 보입니다 |

> ⚠️ **소셜 로그인·본인인증을 실제로 쓰시려면 연동이 필요합니다**(비용 발생).
> 연동 전까지는 운영 화면에 나타나지 않으니, 고객이 잘못 인증하는 일은 없습니다.

**남아 있는 데모 계정은 지우셔야 합니다.** 버튼은 숨겨져도 계정은 DB 에 남습니다.
`preflight-check.ts` 가 이것을 BLOCK 으로 잡아 줍니다.

## 9. 아직 안 되는 것 (연동이 필요한 항목)

돈이 드는 항목이라 별도 결정이 필요하다.

| 항목 | 없으면 어떻게 되나 |
|---|---|
| **결제 PG** | 실제 결제를 받을 수 없다. **오픈 전 필수** |
| **택배사 API** | 운송장을 수기 입력해야 한다. 배송추적 링크가 안 나간다 |
| **SMS/알림톡** | 주문·배송 알림이 고객에게 안 나간다. 문의가 크게 늘어난다 |
| 세금계산서 자동발행 | 수기 발행해야 한다 |
| 본인인증 | 만 14세 미만 가입을 막을 수 없다 |
| 소셜로그인 | 가입 단계 이탈이 늘어난다 |
| 모니터링 | **사이트가 죽어도 아무도 모른다.** 무료 도구(UptimeRobot 등)라도 붙일 것 |
