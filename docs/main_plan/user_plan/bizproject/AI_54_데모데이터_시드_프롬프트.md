# AI_54. 데모 데이터 시드 프롬프트 (등급별 사용자 + 마이페이지 데이터)

> 📄 **문서 #AI_54** · 팀원이 **동일한 초기 데모 데이터**를 자기 로컬에 깔기 위한 "AI 입력용 프롬프트".
> 아래 **§2 프롬프트 블록**을 통째로 복사해 Claude Code(또는 동급 AI)에 붙여 넣으면, 등급별 테스트 계정과 마이페이지 데이터(주문·적립금·등급·배송지·리뷰·문의·동의)가 재현됩니다.

## 1. 전제 (실행 전 확인)

- 백엔드(:9000)·스토어프론트(:8000)·Postgres(컨테이너 `shop-postgres`)가 **모두 기동** 상태. (구동: [02_개발환경_구축](./02_개발환경_구축.md))
- 관리자 계정 `admin@shop.local` / `admin1234!` 사용 가능.
- 퍼블리셔블 키는 **DB마다 다름** → 스크립트가 자동 조회. 수동 확인:
  ```bash
  docker exec shop-postgres psql -U shop -d shop -t -c "select token from api_key where type='publishable' limit 1;"
  ```
- ⚠️ 데모 데이터는 **로컬 DB 전용**. DB 재시드 시 사라지며, 본 프롬프트를 다시 실행하면 됩니다(멱등 — 재실행 안전).

## 2. 프롬프트 블록 (이 아래 전체를 복사해 AI에게 전달)

````text
역할: 너는 로컬 Medusa 쇼핑몰(백엔드 :9000, Postgres 컨테이너 shop-postgres)에 "등급별 데모 사용자 + 마이페이지 데이터"를 멱등하게 시드하는 작업을 한다.
환경: Windows + Git Bash, NODE_TLS_REJECT_UNAUTHORIZED=0. psql 은 `docker exec -i shop-postgres psql -U shop -d shop`. 한글 INSERT 는 heredoc(<<'SQL')으로 stdin 전달.
목표 계정(비밀번호 공통 test1234!, 도메인 @kr-demo.local): test(일반)/silver(실버)/gold(골드)/vip(VIP).

규칙:
- customer_id 는 절대 하드코딩하지 말고 항상 이메일로 조회/조인해 해석한다.
- 모든 단계는 재실행 안전(멱등)해야 한다: 계정은 이미 있으면 생략, 시드 행은 고정 id 또는 'seed' 접두사로 delete 후 insert.

[1단계] 계정 생성 (이미 로그인되면 생략)
- 각 이메일에 대해: POST :9000/auth/customer/emailpass 로 로그인 시도 → 200 이면 생략.
- 아니면 POST :9000/auth/customer/emailpass/register {email,password} 로 토큰 발급 →

[2단계] 멤버십·적립금·배송지 시드 (psql, 이메일 조인으로 customer_id 해석)
- 등급/누적: 일반 accrued 120000 / 실버 520000 / 골드 1450000 / VIP 3800000.
  (등급 기준: 일반0·실버30만·골드100만·VIP300만 원)

insert into customer_membership (id,customer_id,accrued_amount,current_tier,last_change_reason,created_at,updated_at)
select 'cm_seed_'||split_part(c.email,'@',1), c.id,
  case split_part(c.email,'@',1) when 'test' then 120000 when 'silver' then 520000 when 'gold' then 1450000 when 'vip' then 3800000 end,
  case split_part(c.email,'@',1) when 'test' then '일반' when 'silver' then '실버' when 'gold' then '골드' when 'vip' then 'VIP' end,
  '시드', now(), now()
from customer c where c.email in ('test@kr-demo.local','silver@kr-demo.local','gold@kr-demo.local','vip@kr-demo.local');

-- 적립금(earn/redeem) — balance=sum(amount)
insert into point_ledger (id,customer_id,entry_type,amount,reason,created_at,updated_at)
select 'pl_seed_'||k.label, c.id, k.etype, k.amt, k.reason, now()-(k.days||' day')::interval, now()
from customer c
join (values
  ('test','tst1','earn',1000,'신규가입 적립',30),('test','tst2','earn',600,'주문 적립',10),('test','tst3','redeem',-300,'주문 사용',5),
  ('silver','slv1','earn',2000,'신규가입 적립',60),('silver','slv2','earn',1500,'주문 적립',20),('silver','slv3','redeem',-1000,'주문 사용',3),
  ('gold','gld1','earn',5000,'주문 적립',90),('gold','gld2','earn',4000,'주문 적립',40),('gold','gld3','redeem',-2000,'주문 사용',7),

where c.email like '%@kr-demo.local';

-- 배송지(1개는 기본배송지)
insert into customer_address (id,customer_id,first_name,last_name,address_1,city,province,postal_code,country_code,phone,is_default_shipping,is_default_billing,created_at,updated_at)
select 'caddr_seed_'||a.label, c.id, a.fn, a.ln, a.addr, a.city, a.prov, a.zip, 'kr', a.phone, a.defship, a.defbill, now(), now()
from customer c
join (values
  ('test','홍','길동','서울 강남구 테헤란로 1','서울','서울','06234','010-1000-0001',true,true),
  ('silver','김','민서','서울 마포구 월드컵북로 100','서울','서울','03925','010-2000-0001',true,true),
  ('gold','김','지후','부산 해운대구 센텀중앙로 90','부산','부산','48058','010-3000-0001',true,true),
  ('vip','김','서연','서울 송파구 올림픽로 300','서울','서울','05551','010-4000-0001',true,true)
) as a(acct,ln,fn,addr,city,prov,zip,phone,defship,defbill) on split_part(c.email,'@',1)=a.acct
where c.email like '%@kr-demo.local';

[3단계] 실주문 생성 (store 체크아웃 API — 주문 내역 + 자동 적립)
- 퍼블리셔블 키 = `select token from api_key where type='publishable' limit 1;`, KRW 리전 = `select id from region where currency_code='krw' limit 1;`.
- 판매 변형 id = published 상품의 variant 몇 개 조회.
- 계정별 주문 건수: 일반 1, 실버 2, 골드 3, VIP 3 (등급 높을수록 많게).
- 각 주문은 아래 순서로 store API 호출(헤더 x-publishable-api-key + Authorization Bearer <해당 계정 customer JWT>):
  1) POST /store/carts {region_id, email, items:[{variant_id, quantity}]} → cart.id
  2) POST /store/carts/:id {shipping_address{first_name,last_name,address_1,city,province,postal_code,country_code:"kr",phone}, email}

  4) POST /store/carts/:id/shipping-methods {option_id}
  5) POST /store/payment-collections {cart_id} → pc.id ; POST /store/payment-collections/:pc/payment-sessions {provider_id:"pp_system_default"}
  6) POST /store/carts/:id/complete → order
- 검증: 각 계정 GET /store/orders count 가 위 건수와 일치.

[4단계] 리뷰·상품문의·동의 시드 (psql)

전제: 데모 계정 주문은 store 체크아웃으로 생성되어 payment_status=authorized(결제대기). 아래로 상태를 다양화한다.
필요 값(주문별): orderId, line_item_id(item), 변형의 inventory_item_id(inv)+location_id(loc), payment_collections.payments.id(payId).
  조회: GET /admin/orders?fields=id,display_id,email,fulfillment_status,payment_status,items.id,items.variant.inventory_items.inventory_item_id,items.variant.inventory_items.inventory.location_levels.location_id,payment_collections.payments.id
전이 레시피(모두 admin 토큰, $B=http://localhost:9000):
- 결제완료(captured):   POST $B/admin/payments/{payId}/capture  {}
- 배송중(shipped):      ① POST $B/admin/reservations {line_item_id,inventory_item_id,location_id,quantity:1}
                        ② POST $B/admin/orders/{orderId}/fulfillments {items:[{id:item,quantity:1}]}
                        ③ fid 조회: GET .../orders/{orderId}?fields=fulfillments.id
                        ④ POST .../orders/{orderId}/fulfillments/{fid}/shipments {items:[{id:item,quantity:1}],labels:[{tracking_number:"CJ123",tracking_url:"",label_url:""}]}
- 배송완료(delivered):  위 배송중 후 → POST .../orders/{orderId}/fulfillments/{fid}/mark-as-delivered
- 반품접수(return):     배송중(shipped) 후 → POST $B/admin/returns {order_id:orderId}
- 부분환불(partially_refunded): capture 후 → POST $B/admin/orders/{orderId}/refund {amount:1,refund_method:"pg",nonce:"seed-<orderId>"}
- 취소(canceled):       POST $B/admin/orders/{orderId}/cancel {}
- 결제대기(authorized): 전이 안 함(기본값).
권장 분배(예): silver=[결제완료, 취소], gold=[배송중, 배송완료, 반품접수], vip=[결제완료+배송중, 부분환불, 취소], test=[배송중, 결제대기].

상품/고객 시나리오:
- 품절 변형(OOS): POST $B/admin/inventory-items/{invId}/location-levels/{locId} {stocked_quantity:0}  (admin API=캐시 무효화. DB 직접 UPDATE 는 캐시로 반영 안 됨)
- 재입고 알림 구독: POST $B/store/restock-notifications {variant_id,product_id,email}  (헤더 x-publishable-api-key)
- 검수 대기 리뷰: review insert status='pending' (admin 리뷰관리 큐 노출)
- 미답변 문의:   review insert type='inquiry', reply=null, status='pending'
- 비회원 주문:   3단계 체크아웃을 Authorization 헤더 없이(퍼블리셔블 키만) 실행 → customer_id=null 주문(비회원 주문조회 /kr/order/lookup 테스트용)
- 타임세일:     time_sale 행 starts_at 과거·ends_at 미래·status active (홈 타임세일 섹션)
````

### 3-1. 주문 상태 스펙트럼 (6단계 적용 후 예시)

쇼핑몰에서 나올 수 있는 주문 형태를 데모 계정에 분산해 두면 화면 확인이 쉽습니다:

| 상태 | 배송(fulfillment) | 결제(payment) | 용도 |
|---|---|---|---|
| 결제대기(무통장입금) | not_fulfilled | authorized | 입금 전 주문 |
| 결제완료 | not_fulfilled | captured | 배송 준비 대상 |
| 배송중 | shipped | authorized/captured | 운송장·배송조회 |
| 부분배송 | partially_shipped | - | 일부만 출고 |
| 배송완료 | delivered | - | 구매확정 가능 |
| 반품접수 | shipped(반품 진행) | - | RMA 흐름 |
| 부분환불 | not_fulfilled | partially_refunded | 환불/정산 |
| 주문취소 | not_fulfilled | canceled (status=canceled) | 취소 내역 |
| 비회원 주문 | - | - | customer_id=null, 주문조회 테스트 |

### 3-2. 상품/고객 시나리오

| 항목 | 상태 | 확인 화면 |
|---|---|---|
| 품절 변형 | 특정 옵션 재고 0 | 상품상세 "품절" + 재입고 알림 폼 |
| 재입고 구독 | restock_subscription 1건 | (관리자 후속 알림 대상) |
| 타임세일 | active 2건 | 홈 타임세일 섹션 |
| 검수 대기 리뷰 | review status=pending | 관리자 리뷰·문의 큐 |
| 미답변 문의 | inquiry status=pending, reply=null | 관리자 리뷰·문의 큐 |
| 답변완료 문의 | inquiry + reply | 상품상세 Q&A "답변완료" |

## 4. 한계 (시드 불가/주의)

- **위시리스트**: 스토어프론트는 **브라우저 쿠키** 기반(`lib/data/wishlist`)이라 **서버 시드 불가**. 화면에서 상품 ♥(하트) 버튼으로 직접 담아야 노출됨. (`product_wishlist` 테이블은 관리자 모듈용 — 스토어 미연동)
- **쿠폰 "사용 이력"**: 고객별 쿠폰 사용 이력 화면은 없음. 마이페이지 쿠폰함은 **사용 가능한 활성 쿠폰(전역)** 을 보여줌. 쿠폰 적용은 체크아웃 할인코드에서 수행.
- 시드 데이터는 로컬 DB 전용 — 커밋 대상 아님. 재시드 시 본 프롬프트 재실행.
