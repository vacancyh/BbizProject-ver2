# 백업·복구 / 마이그레이션 롤백 런북 (2026-07-28)

이전까지 **백업·복구 절차와 스크립트가 전혀 없었다.** 장애·잘못된 마이그레이션 시 되돌릴 수단이 없었으므로
스크립트와 절차를 만들고, 실제 복구 리허설까지 수행해 검증했다.

---

## 1. 백업

```bash
bash scripts/db-backup.sh                          # dev DB(shop)
DB_NAME=shop_test bash scripts/db-backup.sh        # 다른 DB
BACKUP_DIR=/mnt/backup RETENTION_DAYS=30 bash scripts/db-backup.sh
```

- `pg_dump -Fc`(커스텀 포맷, 압축) → `backups/<db>-<타임스탬프>.dump`
- 생성 직후 `pg_restore -l` 로 **무결성 즉시 확인**(읽히지 않는 덤프는 복구도 불가)
- 보존기간(기본 14일) 초과 파일 자동 정리
- `backups/` 는 git 비추적

**운영 권장**: 컨테이너 대신 직접 접속 시 `USE_DOCKER=0` + `PGHOST/PGUSER/PGPASSWORD`.
일 1회 자동 실행(cron/스케줄러) + 원격 오브젝트 스토리지 업로드 + 주 1회 복구 리허설.

## 2. 복구

```bash
# 새 DB 로 복구(원본 보호 — 기본 권장)
bash scripts/db-restore.sh backups/shop-20260728-144034.dump shop_restore_test

# 기존 DB 를 덮어쓰기(위험 — 명시적 플래그 필요)
FORCE_DROP=1 bash scripts/db-restore.sh backups/shop-...dump shop
```

- 대상 DB 가 이미 있으면 `FORCE_DROP=1` 없이는 **중단**(실수 방지)
- 복원 후 테이블 수·주문/상품 행 수를 출력하고, 테이블이 비정상적으로 적으면 실패 처리

## 3. 마이그레이션 롤백 절차

Medusa v2 는 `db:migrate` 만 제공하고 **자동 down/rollback 명령이 없다.**
따라서 롤백은 아래 순서를 따른다.

### 3-1. 배포 전(필수)
```bash
bash scripts/db-backup.sh          # 마이그레이션 직전 스냅샷 — 이게 유일한 확실한 롤백 수단
```

### 3-2. 문제 발생 시 선택지
| 상황 | 대응 |
|---|---|
| 마이그레이션 직후 즉시 문제 발견, 쓰기 트래픽 없음 | **직전 백업으로 복구**(가장 안전·확실) |
| 이미 신규 쓰기가 들어간 뒤 | 백업 복구 시 데이터 유실 → 해당 변경을 되돌리는 **역방향 마이그레이션을 새로 작성**해 앞으로 진행 |
| 컬럼 추가처럼 하위호환 변경 | 롤백 불필요(구버전 앱이 무시). 앱만 롤백 |

### 3-3. 역방향 마이그레이션 작성
`src/modules/<모듈>/migrations/MigrationYYYYMMDDHHMMSS.ts` 에 되돌리는 SQL 을 담아 추가한다
(예: 추가한 컬럼 `DROP COLUMN IF EXISTS`). 파일명 타임스탬프가 최신이어야 순서상 뒤에 적용된다.

### 3-4. 안전 원칙
- **파괴적 변경은 2단계로**: ①새 컬럼 추가 + 이중 쓰기 → ②배포 안정 후 구 컬럼 제거.
  한 번에 `DROP` 하면 롤백이 사실상 불가능해진다.
- 마이그레이션은 **fresh DB 에서 먼저 검증**한다:
  ```bash
  bash docs/main_plan/user_plan/bizproject/04_점검기록/통합테스트/setup-test-db.sh
  ```
  (마이그레이션 누락/드리프트를 이 경로에서 여러 번 잡아냈다)
