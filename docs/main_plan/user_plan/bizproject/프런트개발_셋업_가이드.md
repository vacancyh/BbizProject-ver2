## 0. 시작 전 필독 — 백엔드·관리자 컨텍스트

> 관리자/백엔드 개발에 참여하지 않은 프런트 합류자가 **코딩 전에 반드시 알아야 할** 배경.

### 0-1. 시스템 구성
- **백엔드**(`backend/services/api`, :9000) = Medusa v2 커머스 API. **고객용 `/store` API** 와 **관리자용 `/admin` API** 를 모두 제공.
- **관리자 앱**(`apps/admin`, :7002) = 별도 Next.js. ⚠️ **Medusa 내장 관리자 UI는 꺼져 있음**(`medusa-config.ts`의 `admin.disable=true`) → 자체 관리자 앱이 `/admin` API 호출.
- **스토어프론트**(`apps/web`, :8000) = 우리가 개발하는 대상. **`/store` API만** 호출.

### 0-2. 인증 모델 (프런트가 꼭 알 것)
- 스토어프론트 모든 요청에 **퍼블리셔블 키 헤더 `x-publishable-api-key` 필수** (누락 시 401·상품 미노출). 이 키는 **sales channel**에 묶여 노출 상품 범위를 결정.
- 고객 로그인 = 별도 **고객 세션(JWT/쿠키)**. 관리자 토큰(Bearer)과 전혀 다름 — 프런트는 관리자 토큰을 쓰지 않는다.

### 0-3. 데이터는 "관리자/시드에서 생성 → 스토어 API로 노출"
- 상품·카테고리·컬렉션·프로모션·가격·재고는 **관리자(또는 시드)에서 만들어야 프런트에 보인다**.
- 프런트 개발 중 데이터가 필요하면: `seed-test-data.ts` 실행 또는 관리자(:7002 `admin@shop.local`/`admin1234!`)에서 등록.
- **퍼블리셔블 키·각종 ID는 DB마다 다르다** → 하드코딩 금지(env/조회로 주입).

### 0-4. Medusa 핵심 개념(최소한)
- **region**(통화/국가) · **sales channel** · **publishable key** · **product/variant/option** · **inventory**(item/level/**reservation**) · **cart→order** · **payment collection/payment** · **fulfillment** · **promotion**.
- 주문 흐름: 카트 생성 → 아이템/배송/결제세션 → `complete` → 주문(+**재고 예약**). 취소 시 재고 복구, 환불은 **capture된 결제**가 있어야 가능.

### 0-5. 한국형 기능 = 커스텀 모듈 → store API가 없을 수 있음
- 적립금·등급·제재·동의·리뷰/문의·상품정보고시·타임세일·청약철회 등은 **커스텀 모듈**이며, **`/admin` API만 있고 고객용 `/store` API는 아직 없는 경우가 많다**.
- Medusa 코어 미수정 원칙(링크/metadata 활용). → 프런트에서 필요하면 **store 라우트 신설** 또는 **mock 계약 선개발**(회의자료의 ❌/⚠️ 항목 참조).

### 0-6. 관리자 변경 ↔ 프런트 캐시
- `revalidate-contract`(백엔드) ↔ `revalidate-tags`(프런트) 계약으로 관리자 변경 시 프런트 ISR 캐시 무효화. 신규 화면도 이 태그 규약을 따른다.

### 0-7. 더 볼 문서
- 기능 전모: `apps/admin/FEATURE_MATRIX.md`, `apps/admin/docs/기능정의서.md`
- 갭/현황: `apps/admin/docs/gaps/`, [한국이커머스_기능갭분석.md](../한국이커머스_기능갭분석.md)

## 1. 사전 준비물 (설치)

| 항목 | 버전 | 설치/확인 |
|---|---|---|
| **Node.js** | 20+ (검증 v24) | https://nodejs.org → `node -v` |
| **pnpm** | 11.3.x | `corepack enable` 후 `corepack prepare pnpm@11.3.0 --activate` → `pnpm -v` |
| **Docker Desktop** | 최신 | DB(Postgres)·Redis 구동용. 설치 후 **Docker Desktop 실행(데몬 켜기)** → `docker ps` |
| **Git** | 최신 | `git --version` / 작성자 설정 `git config user.name`, `user.email` |
| (선택) PowerShell 7 | — | 아래 명령은 PowerShell 기준 |

> ⚠️ **사내망 TLS 검사(SSL MITM) 환경 주의** — 매우 중요
> 컨테이너 내부 빌드(`docker compose up --build`)는 `apk`/`pnpm`이 **인증서 오류로 실패**합니다.
> 그래서 이 프로젝트는 **DB·Redis만 Docker로, 백엔드·앱은 호스트에서 직접 실행**합니다.
> 호스트는 사내 루트 CA를 신뢰하므로 npm/pnpm 정상 동작(호스트에 `NODE_TLS_REJECT_UNAUTHORIZED=0` 설정돼 있음).

## 2. 로컬 환경 셋업 — 0에서 실행까지 (상세)

### 구성 한눈에 (무엇이 무엇과 맞물리나)
```
[Docker]  Postgres(:5434)  Redis(:6381)
              ▲ DATABASE_URL / REDIS_URL (backend/.env)
[호스트]  백엔드 Medusa(:9000)  ──/store·/admin API──┐
              ▲ NEXT_PUBLIC_*BACKEND_URL              │ x-publishable-api-key
[호스트]  관리자(:7002)        스토어프론트(:8000) ──┘
```
- **백엔드 `.env`** 가 백엔드를 Docker의 DB/Redis에 연결한다(없으면 백엔드가 못 뜸).
- **앱 `.env.local`** 이 앱을 백엔드(:9000)에 연결한다. 스토어프론트는 **퍼블리셔블 키**로 `/store` 호출.

> 모든 명령은 별도 표기 없으면 **저장소 루트(`c:\study\BbizProject-ver2`)** 기준. 새 터미널 3개(백엔드/관리자/스토어프론트)로 띄우면 편함.

### 2-0. 저장소 클론 & 진입
```powershell
git clone https://github.com/vacancyh/BbizProject-ver2.git
cd BbizProject-ver2
corepack enable; corepack prepare pnpm@11.3.0 --activate   # pnpm 준비
```

### 2-1. DB·Redis 기동 (Docker)
Docker Desktop이 켜져 있어야 함.
```powershell
docker compose -f infra/docker/docker-compose.yml --project-directory . up -d shop-postgres shop-redis
docker ps   # shop-postgres(healthy), shop-redis(healthy) 확인
```
→ Postgres `127.0.0.1:5434`, Redis `127.0.0.1:6381`.

### 2-2. 백엔드 환경변수 생성 ⭐ (없으면 백엔드가 DB에 못 붙음)
`backend/services/api/.env` 파일을 아래 내용으로 생성(로컬 개발용 값):
```
NODE_ENV=development
DATABASE_URL=postgres://shop:shop_local_2026@127.0.0.1:5434/shop
REDIS_URL=redis://127.0.0.1:6381
STORE_CORS=http://localhost:8000,http://127.0.0.1:8000
ADMIN_CORS=http://localhost:9000,http://localhost:7002,http://127.0.0.1:9000,http://127.0.0.1:7002
AUTH_CORS=http://localhost:8000,http://localhost:9000,http://localhost:7002,http://127.0.0.1:8000,http://127.0.0.1:9000,http://127.0.0.1:7002
JWT_SECRET=shop-local-jwt-2026-dev
COOKIE_SECRET=shop-local-cookie-2026-dev
STOREFRONT_URL=http://localhost:8000
REVALIDATE_SECRET=supersecret-revalidate
APP_NAME=shop
APP_NAME_KO=쇼핑몰
```
> ⚠️ 로컬 전용 값. **운영 배포 시 JWT/COOKIE/REVALIDATE는 강력한 무작위 값으로 교체.** `.env`는 git 제외됨.

### 2-3. 백엔드 설치 → 스키마/시드 → 계정 → 국내설정 → 실행
```powershell
cd backend\services\api
pnpm install
npx medusa db:migrate                                  # 최초 1회: 스키마 + 기본 시드(상품·리전·퍼블리셔블키)
npx medusa user -e admin@shop.local -p admin1234!      # 관리자 계정(최초 1회)
npx medusa exec ./src/scripts/setup-korea.ts           # 국내(한국/KRW): 통화·리전·세금·상품가·배송(최초 1회)
npx medusa exec ./src/scripts/seed-test-data.ts        # (선택) 테스트 데이터(상품·고객·주문·리뷰·적립금·VIP)
npx medusa develop                                     # 백엔드 실행 → http://localhost:9000
```
- **확인**: 다른 터미널에서 `curl http://localhost:9000/health` → 200.
- **SUPER 전용 기능(점검모드 등)** 쓰려면 admin 계정에 super 역할 부여:
  로그인 후 권한관리 화면, 또는 API `POST /admin/rbac/users/<userId> { "role_key":"super" }`.

### 2-4. 퍼블리셔블 키 확인 (스토어프론트 필수)
```powershell
"select token from api_key where type='publishable';" | docker exec -i shop-postgres psql -U shop -d shop -t
```
→ 나온 `pk_...` 값을 2-5의 `apps/web/.env.local`에 넣는다. (DB마다 다름. 여러 개면 Default Sales Channel 연결 키)

### 2-5. 앱 환경변수 생성 + 실행
`apps/web/.env.local`:
```
NEXT_PUBLIC_MEDUSA_BACKEND_URL=http://localhost:9000
NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY=<2-4에서 조회한 pk_...>
NEXT_PUBLIC_DEFAULT_REGION=kr
NEXT_PUBLIC_BASE_URL=http://localhost:8000
```
`apps/admin/.env.local`:
```
NEXT_PUBLIC_BACKEND_URL=http://localhost:9000
```
실행(각각 새 터미널):
```powershell
cd apps\admin ; pnpm install ; pnpm dev      # 관리자 → http://localhost:7002
cd apps\web   ; pnpm install ; pnpm dev      # 스토어프론트 → http://localhost:8000/kr
```

### 2-6. 동작 확인
| 서비스 | 주소 | 확인 |
|---|---|---|
| 백엔드 | http://localhost:9000/health | 200 |
| 관리자 | http://localhost:7002 | `admin@shop.local`/`admin1234!` 로그인 → 대시보드 |
| 스토어프론트 | http://localhost:8000/kr | 상품 노출(KRW) |

## 3. 자주 겪는 문제 (트러블슈팅)

| 증상 | 원인 / 해결 |
|---|---|
| `docker compose ... --build` 실패(인증서 오류) | 사내 TLS 검사. **컨테이너 빌드 금지** — DB/Redis만 Docker, 앱은 호스트 실행(§2 방식) |
| 백엔드가 DB 연결 실패/안 뜸 | `backend/services/api/.env` **미생성**(2-2) 또는 Docker 미기동(2-1) |
| 상품이 스토어프론트에 안 보임 / 401 | `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` 누락·오값. 2-4로 재조회해 `.env.local` 갱신 |
| 포트 충돌(:9000/:7002/:8000/:5434) | 기존 프로세스/컨테이너 종료. (이전에 같은 `shop-*` 이름 컨테이너 있으면 `docker rm -f`) |
| 점검모드 토글 403 | admin 계정에 **super 역할** 미부여 → 2-3 마지막 참고 |
| 데이터 초기화하고 싶음 | `docker compose -f infra/docker/docker-compose.yml --project-directory . down -v` (DB 볼륨 삭제) 후 2-1부터 재실행 |
| E2E(Playwright) 브라우저 없음 | `cd apps/admin ; npx playwright install chromium` |

> 백엔드 시크릿(JWT/COOKIE 등)은 로컬 외 환경에선 별도 공유 채널로 전달받으세요(문서·커밋 금지).

## 4. 코드 구조 & 규약

### 0) 프런트 표준 스택 (확정)
> 신규 언어/프레임워크 도입 없음 — 기존 코드·Medusa 생태계·SEO·팀 일관성 기준으로 React/Next 유지.

| 구분 | 표준 |
|---|---|
| 언어 | **TypeScript** |
| 프레임워크 | **Next.js 15 (App Router) + React 19** |
| 스타일 | **TailwindCSS + `@medusajs/ui` / `ui-preset`** (공통 디자인 토큰) |
| 데이터 | `@medusajs/js-sdk` + `lib/data` 서버액션 패턴 |
| 렌더링 | 서버컴포넌트 우선 + 필요한 곳만 클라이언트. SEO 위해 SSR/SSG/ISR 활용 |
| 검증/폼 | (선택) zod |
| 테스트 | Playwright(E2E) + Vitest |

### 디렉터리 규약 (도메인 수직 분할)
```
apps/web/src/
  app/[countryCode]/(main)/{store,products/[handle],categories,collections,cart,order/[id],account}
  app/[countryCode]/(checkout)/checkout
  lib/data/*        # 백엔드 호출(서버액션/데이터 페칭) — 도메인별 1파일
  modules/*         # 도메인 UI 컴포넌트(account,cart,checkout,products,...)
  styles/ types/
```
- **신규 도메인**(리뷰·CS·CMS·위시리스트 등)은 `modules/<도메인>` + `lib/data/<도메인>.ts`로 추가.
- 데이터 호출은 **반드시 `lib/data`** 경유(컴포넌트에서 직접 fetch 금지). 백엔드 SDK는 `@medusajs/js-sdk`.
- 공통 UI는 `modules/common` 재사용. 디자인 토큰은 `@medusajs/ui-preset` + Tailwind.

### 계약 우선(contract-first)
1. `lib/data` 함수 시그니처 + `types`를 **인터페이스 PR로 먼저 확정** → 화면 병렬 구현.
2. 백엔드 store API 미구현 기능(리뷰·포인트·본인인증·PG 등)은 **`lib/data`에 mock + 타입 먼저** → 백엔드 준비 시 교체.
3. 관리자→프런트 캐시 무효화는 기존 `revalidate-contract`(백엔드)↔`revalidate-tags`(프런트) 패턴 유지.

### Git / PR
- `main` 직접 작업은 **현 단계(팀 분할 전)** 까지만. 팀 분할 후엔 `feature/<도메인>-<작업>` 브랜치 + PR + 상호리뷰로 전환.
- 커밋: 의도·이유 짧게. PR: 변경범위 / 도메인 / 테스트 방법 / 스크린샷 / 백엔드 의존성.

### 완료 정의(DoD)
화면 구현 + 모바일 우선 반응형 + 로딩/에러/빈상태 + 접근성 기본 + (가능 시) Playwright E2E 1개 + 리뷰 통과.
