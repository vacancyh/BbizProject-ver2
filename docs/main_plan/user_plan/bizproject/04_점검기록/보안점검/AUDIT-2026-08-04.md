## 1. 🔴 레이트리밋이 헤더 한 줄로 뚫렸다

### 무엇이 문제였나

IP 기준 레이트리밋 전부가 `X-Forwarded-For` 의 **맨 앞 값**을 클라이언트 IP 로 신뢰했다.
이 헤더는 요청자가 직접 붙이는 것이라, 매 요청 다른 값을 넣으면 항상 새 버킷이 잡힌다.

```
middlewares.ts:354  clientIp()          ← 로그인 실패 카운터
middlewares.ts:687  orderLookupRateLimit ← 비회원 주문조회
middlewares.ts:733  twoFaVerifyRateLimit ← 2FA 검증
middlewares.ts:750  ipRateLimit()        ← 익명 쓰기·조회수·베스트
store/popular-search-terms/route.ts:23
```

`trust proxy` 설정도 없었다.

### 실측 (수정 전)

```
비회원 주문조회 (분당 30 제한)
  고정 IP 40회   →  404×30 · 429×10     (정상 동작)
  헤더 회전 40회 →  404×39 · 429×1      ← 39건 통과

베스트 상품 (분당 60 제한)
  헤더 회전 80회 →  200×80 · 429×0      ← 전부 통과
```

### 원인이 두 겹이었다

XFF 를 오른쪽에서 읽도록 고쳤는데도 **여전히 뚫렸다.**

Medusa 프레임워크가 `app.set("trust proxy", 1)` 을 **무조건** 켠다
(`@medusajs/framework/dist/http/express-loader.js:68`).
그래서 Express 의 `req.ip` 자체가 XFF 에서 값을 뽑아 온다 — 폴백으로 쓰던 `req.ip` 가 이미 오염돼 있었다.

> 교훈: "위조 불가능한 값" 이라고 믿은 것이 프레임워크 설정 때문에 위조 가능했다.
> 프레임워크가 대신 해 주는 처리는 **무엇을 근거로 하는지** 확인해야 한다.

### 어떻게 고쳤나

`api/_utils/client-ip.ts` 신설. 두 가지를 지킨다.

1. **소켓 주소를 직접 읽는다** — `req.ip` 를 쓰지 않는다(TCP 연결 상대는 위조 불가)
2. **XFF 는 신뢰 홉 기준으로 오른쪽에서** — `TRUSTED_PROXY_HOPS` 대수만큼

```
TRUSTED_PROXY_HOPS=0 (기본)  XFF 무시, 소켓 주소만          ← 로컬·프록시 없는 배포
TRUSTED_PROXY_HOPS=1         ALB/CloudFront/Nginx 한 대 뒤   ← 가장 흔한 운영 구성
TRUSTED_PROXY_HOPS=2         CDN + LB 두 단 뒤
```

⚠️ **운영 배포 시 반드시 설정해야 한다.** 0 으로 두면 프록시 뒤에서 모든 요청이
LB 아이피 하나로 잡혀 레이트리밋을 전체 사용자가 공유한다.
반대로 실제보다 크게 잡으면 위조 값을 읽는다 — 모르면 0.

### 실측 (수정 후)

```
[1] 빈 버킷에 40건 동시 전송      →  404×30 · 429×10   통과 30건 (상한 30)
[2] 버킷 소진 후 헤더 회전 40회   →  429×40            통과 0건
[3] 베스트 상품 헤더 회전 80회    →  200×60 · 429×20   200 정확히 60건 (상한 60)
```

재현 도구: `audit4-ratelimit-probe.mjs` (3/3 PASS)

### 영향 범위 (수정 전 기준)

| 대상 | 뚫리면 |
|---|---|
| 비회원 주문조회 | 주문번호+이메일 대입으로 **주문 정보 열거** |
| 익명 쓰기(리뷰·문의·재입고) | 스팸 무제한 |
| 상품 조회수·베스트 | 순위 조작 |
| 로그인 IP 카운터 | 패스워드 스프레이 |

> 로그인은 **계정별 카운터(5회/15분)가 따로 있어** 특정 계정 브루트포스는 계속 막혔다.
> 계정을 바꿔가며 시도하는 스프레이만 열려 있었다.

## 2. 🟠 시크릿을 교체하면 저장된 데이터가 안 열린다

### 무엇이 문제였나

`C2-시크릿-로테이션-절차.md` 는 소유자가 곧 실행할 P1 작업인데,
**"새 키를 만들어 주입하라"** 만 있고 기존 암호문 얘기가 없었다.

| 대상 | 키 | 키가 바뀌면 |
|---|---|---|
| 관리자 2FA 시크릿 | `ADMIN_2FA_SECRET_KEY` | 2FA 등록한 관리자 **전원 로그인 불가** |
| 세금계산서 사업자번호 | `PII_ENCRYPTION_KEY` | 사업자번호가 **빈 값**으로 보임 |

가장 위험한 지점: 두 전용 키를 따로 안 넣으면 **둘 다 `COOKIE_SECRET` 에서 파생**된다.
즉 **`COOKIE_SECRET` 하나만 바꿔도 둘 다 깨진다.**

게다가 두 복호화 함수 모두 실패 시 **예외 없이 빈 문자열을 반환**한다
(`secret-crypto.ts:61`, `tax-invoice/crypto.ts:46`).
에러 로그가 없으니 관리자가 로그인을 못 하게 된 뒤에야 알게 된다.

### 어떻게 막았나

- **재암호화 스크립트** `scripts/rotate-encryption-keys.ts` 신설
  - 옛 키로 풀어 새 키로 다시 잠근다
  - **안전장치**: 옛 키로 안 풀리는 행이 하나라도 있으면 아무것도 저장하지 않고 중단
  - 이미 새 키인 행은 건너뛴다(멱등 — 중간에 끊겨도 다시 돌리면 됨)
  - `ROTATE_DRY_RUN=true` 로 건수만 확인 가능
- **절차서에 0단계 추가** — 백업 → 옛 키 기록 → 새 키 주입 → DRY RUN → 실행 → 눈으로 확인
- **preflight 에 경고 추가** — "키 파생 의존" 항목. 전용 키가 없으면 운영에서 BLOCK

### 검증 (dev DB, 세금계산서 8건)

```
옛 키 = 현재 COOKIE_SECRET, 새 키 = 다른 값
  → 재암호화 대상 8 · 못 푼 행 0            (복호화 경로 정상)

옛 키를 일부러 틀리게
  → 못 푼 행 8 → 중단, 저장 안 함           (안전장치 정상)
  → 재확인: 8건 모두 원래 키로 여전히 정상    (데이터 무손상)
```

## 4-B. 🔴 레이트리밋이 "고객별"이 아니라 "쇼핑몰 전체 합산"이었다

> 위 1번을 고친 뒤 **실사용 영향을 확인하다가** 나온 것. 보안 구멍이 아니라 **가용성 결함**이다.

### 무엇이 문제였나

스토어프론트의 데이터 계층은 전부 Next.js **서버 액션**(`"use server"`)이다.
로그인·리뷰·문의·주문조회가 고객 브라우저가 아니라 **스토어프론트 서버에서** 백엔드로 나간다.
그리고 스토어프론트는 고객 IP 를 백엔드에 전달하지 않았다.

```
apps/web/src/lib/data/customer.ts     "use server"   ← 로그인
apps/web/src/lib/data/reviews.ts      "use server"
apps/web/src/lib/data/support.ts      "use server"
apps/web/src/lib/data/order-lookup.ts "use server"
apps/web/src/lib/config.ts            X-Forwarded-For 설정 없음
```

→ 백엔드가 보는 요청자는 **항상 스토어프론트 서버 한 대**.
→ IP 기준 한도가 고객 1명당이 아니라 **쇼핑몰 전체 합산**으로 걸렸다.

### 실측 — 가장 심각한 것부터

```
로그인 (IP별 실패 10회 / 5분)
  ① 정상 계정 로그인            → 200
  ② 서로 다른 고객 12명이 각 1회 실패 → 401×10 · 429×2
  ③ 아무 잘못 없는 고객이 올바른 비밀번호로 로그인 → 429 RATE_LIMITED
```

**고객 10명이 비밀번호를 틀리면 쇼핑몰 전체가 5분간 로그인 불가.**
실제 쇼핑몰에서 비밀번호 오입력은 상시 발생하므로, 이대로면 로그인이 사실상 마비된다.

그 외 합산으로 걸리던 한도:

| 대상 | 쇼핑몰 전체 합산 한도 |
|---|---|
| 익명 쓰기(리뷰·문의·지원·재입고) | 분당 20건 |
| 베스트 상품 조회(홈 SSR) | 분당 60건 |

> 계정별 카운터(5회/15분)는 정상 동작하므로 **특정 계정 브루트포스는 계속 막힌다.**
> 문제는 IP 축뿐이다.

### 어떻게 고쳤나

스토어프론트가 **자기가 확인한 고객 IP** 를 백엔드에 알려준다.
아무나 헤더를 넣어 남의 버킷을 조작하지 못하도록 **공유 시크릿**을 함께 보낸다.

```
apps/web/src/lib/util/forward-client-ip.ts   (신규) 고객 IP 산출 + 서명 첨부
apps/web/src/lib/config.ts                   fetch 래퍼에서 자동 첨부
backend .../api/_utils/client-ip.ts          서명 검증 후 그 IP 를 버킷 키로
```

설정(양쪽 모두 필요, 없으면 기능 자체가 꺼짐 = 기존 동작):

```
INTERNAL_CLIENT_IP_SECRET        백엔드·스토어프론트 **같은 값**
STOREFRONT_TRUSTED_PROXY_HOPS    스토어프론트 앞 프록시 대수 (0=전달 안 함)
```

### 검증

```
[4] 내부 IP 전달
  고객 A 가 한도를 다 씀(20 통과 · 5 차단) → 고객 B 는 정상 통과   (버킷 분리됨)
  위조 토큰으로 새 IP 지정 → 429                                  (무시하고 기존 버킷 — 위조 불가)

로그인 프로브
  전달 끔 → 다른 고객 12명 실패 후 정상 고객도 429
  전달 켬 → 같은 상황에서 정상 고객 200
```

재현 도구: `audit5-shared-bucket-probe.mjs` · `audit5-login-lockout-probe.mjs`
단위 테스트: `apps/web/src/lib/util/forward-client-ip.test.ts` (12케이스 — 홉 선택·비활성 조건·위조 방어)

## 7. 남은 것

이번 점검으로 코드에서 나온 결함은 없다. 아래는 **소유자 실행** 또는 **비용 발생** 항목이다.

### 운영 배포 시 반드시

- [ ] **`INTERNAL_CLIENT_IP_SECRET` 를 백엔드·스토어프론트에 같은 값으로** (`openssl rand -base64 32`)
      — 안 하면 고객 10명이 비밀번호를 틀릴 때 **전체 로그인이 5분간 막힌다**
- [ ] **`STOREFRONT_TRUSTED_PROXY_HOPS`** 를 스토어프론트 앞 프록시 대수로 (보통 1)
- [ ] `TRUSTED_PROXY_HOPS` 를 백엔드 앞 프록시 대수로 (0 이면 직접 호출자 구분 불가)
- [ ] `ADMIN_2FA_SECRET_KEY`·`PII_ENCRYPTION_KEY` 전용 키 주입 + 기존 데이터가 있으면 재암호화
- [ ] 프록시 앞단에서 클라이언트가 보낸 XFF 를 덮어쓰도록 설정
      (Nginx: `proxy_set_header X-Forwarded-For $remote_addr;`)

> 위 3개는 `preflight-check.ts` 가 운영 모드에서 BLOCK/WARN 으로 잡는다.

cd backend/services/api
STOREFRONT_URL=https://<운영 도메인> npx medusa exec ./src/scripts/preflight-check.ts
