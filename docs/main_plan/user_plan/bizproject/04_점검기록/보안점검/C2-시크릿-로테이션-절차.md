## ⚠️ 0단계 — 먼저 읽으세요: 키를 바꾸면 **저장된 데이터가 안 열립니다**

> 2026-08-04 점검에서 확인한 함정입니다. 이걸 모르고 교체하면 조용히 망가집니다.

두 곳이 **at-rest 암호화**를 씁니다. 키를 바꾸면 기존 암호문을 복호화할 수 없습니다.

| 대상 | 키 | 키가 바뀌면 |
|---|---|---|
| 관리자 2FA 시크릿 (`admin_totp.secret`) | `ADMIN_2FA_SECRET_KEY` | **2FA 등록한 관리자 전원 로그인 불가** |
| 세금계산서 사업자번호 (`tax_invoice.biz_no`) | `PII_ENCRYPTION_KEY` | 사업자번호가 **빈 값**으로 보임 |

**가장 위험한 지점** — 위 두 전용 키를 따로 안 넣었다면 **둘 다 `COOKIE_SECRET` 에서 파생**됩니다
(`_utils/secret-crypto.ts`, `tax-invoice/crypto.ts`). 즉 **`COOKIE_SECRET` 하나만 바꿔도 둘 다 깨집니다.**

게다가 두 복호화 함수 모두 실패 시 **예외를 던지지 않고 빈 문자열을 반환**합니다.
에러 로그가 남지 않으니, 관리자가 로그인을 못 하게 된 뒤에야 알게 됩니다.

**현재 상태 확인**
```bash
cd backend/services/api
npx medusa exec ./src/scripts/preflight-check.ts   # "키 파생 의존" 항목을 보세요
```

**교체 순서 (이 순서를 지키세요)**
```bash
# 1) 백업 — 되돌릴 수 있어야 합니다
bash scripts/db-backup.sh

# 2) 옛 키를 어딘가에 적어둡니다 (전용 키가 없었다면 옛 COOKIE_SECRET 이 옛 키입니다)

# 3) .env 에 새 키를 넣습니다 (아래 1단계)

# 4) 확인만 — 아무것도 바꾸지 않고 대상 건수만 셉니다
ROTATE_DRY_RUN=true \
OLD_ADMIN_2FA_SECRET_KEY=<옛 키> OLD_PII_ENCRYPTION_KEY=<옛 키> \
npx medusa exec ./src/scripts/rotate-encryption-keys.ts

# 5) 실제 재암호화
OLD_ADMIN_2FA_SECRET_KEY=<옛 키> OLD_PII_ENCRYPTION_KEY=<옛 키> \
npx medusa exec ./src/scripts/rotate-encryption-keys.ts

# 6) 눈으로 확인 — 관리자 1명 2FA 로그인 · 세금계산서 1건 조회
```

전용 키를 안 쓰고 있었다면 4·5단계의 `OLD_*` 자리에 **옛 `COOKIE_SECRET`** 을 넣거나
`OLD_COOKIE_SECRET=<옛 값>` 하나만 줘도 됩니다.

> 스크립트는 옛 키로 안 풀리는 행이 하나라도 있으면 **아무것도 저장하지 않고 중단**합니다.
> 키를 잘못 넣어 멀쩡한 데이터를 덮어쓰는 일은 없습니다.

**2FA 데이터가 없다면**(아직 아무도 2FA 등록 안 함) 이 단계는 건너뛰어도 됩니다.
DRY RUN 이 "바꿀 것이 없습니다" 라고 하면 그런 경우입니다.

## 1단계 — 로테이션 (0단계를 읽은 뒤)
노출된 값을 "이미 유출됐다"고 가정하고 **먼저 교체**합니다. (이력 스크럽 전에 해도 무방)
- **admin 비밀번호**: 관리자 화면 또는 CLI 로 변경
  ```bash
  cd backend/services/api
  npx medusa user -e admin@shop.local -p "<새 강력 비밀번호>"   # 또는 관리자 화면에서 변경
  ```
- **운영 JWT/COOKIE 시크릿**: 환경별 신규 생성 후 시크릿매니저/`.env`(비커밋)에 주입
  ```bash
  openssl rand -base64 48   # JWT_SECRET
  openssl rand -base64 48   # COOKIE_SECRET      ← 0단계 주의
  openssl rand -base64 32   # REVALIDATE_SECRET
  openssl rand -base64 32   # ADMIN_2FA_SECRET_KEY  ← 0단계 주의
  openssl rand -base64 32   # PII_ENCRYPTION_KEY    ← 0단계 주의
  ```
  > `ADMIN_2FA_SECRET_KEY`·`PII_ENCRYPTION_KEY` 는 **처음 주입할 때도** 주의가 필요합니다.
  > 지금까지 COOKIE_SECRET 으로 파생돼 저장된 데이터가 있다면, 전용 키를 새로 넣는 것도 "키 교체"입니다.
  > → 0단계의 재암호화를 함께 하세요(`OLD_*` 에 현재 `COOKIE_SECRET` 을 넣습니다).
- **Postgres 비밀번호**: 운영 DB 는 반드시 신규 값. 로컬 도커는 재사용해도 되나 운영과 분리.

## 2단계 — git 이력 스크럽 (협업자 조율 후)
> 히스토리 재작성 = 강제 푸시. **모든 협업자가 이후 재클론/rebase 필요** → 사전 공지 필수.

**권장: git-filter-repo** (BFG 대안)
```bash
pip install git-filter-repo   # 또는 brew install git-filter-repo

# 백업(중요)
git clone --mirror https://github.com/vacancyh/BbizProject-ver2.git backup-mirror

# 대상 파일 전체 이력 제거
git filter-repo --path apps/admin/e2e/.auth/state.json --invert-paths

# 특정 문자열(비밀번호/시크릿) 이력 치환 (replacements.txt 에 규칙 작성)
#   djemalsdlqslek12!@==>REDACTED
#   supersecret==>REDACTED
git filter-repo --replace-text replacements.txt

# 원격 강제 반영 (협업자 공지 후)
git push origin --force --all
git push origin --force --tags
```
- 스크럽 후 **GitHub 캐시/포크/PR** 에 잔존할 수 있으니, 민감도 높으면 GitHub Support 에 캐시 퍼지 요청.
- 협업자: 기존 클론 폐기 후 재클론(또는 `git fetch` + `git reset --hard origin/main`).
