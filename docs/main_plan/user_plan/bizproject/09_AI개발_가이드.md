# 09. AI 개발 가이드

> 📄 **문서 #09** · AI로 화면 개발하는 법 — 프롬프트 템플릿·함정·문서화 규율. 👉 다음: [10. 디자인·퍼블리싱](./10_디자인_퍼블리싱.md)

스토어프론트(`apps/web`)를 **AI 어시스턴트(예: Claude Code)** 로 개발할 때, 이 저장소 패턴에 맞게 **프롬프트를 어떻게 쓰고 어떤 루프로 진행할지** 정리한 가이드입니다.
함께 보기: [README.md](./README.md) · [02_개발환경_구축.md](./02_개발환경_구축.md) · [06_업무분담_IA.md](./06_업무분담_IA.md)

## 0. AI 개발이 처음이라면 — 환경·기본기·프롬프트 작성법

### 0-1. AI 개발 환경 준비
1. **AI 코딩 도구 설치** — Claude Code(CLI/IDE 확장) 등. 저장소 폴더에서 실행해 **AI가 파일·터미널에 접근**할 수 있게 한다(채팅창에 코드 복붙하는 방식보다 훨씬 효율적).
2. **저장소·로컬 구동 먼저** — [셋업 가이드](./02_개발환경_구축.md)대로 백엔드/관리자/스토어프론트를 직접 띄워 둔다. AI가 만든 결과를 **바로 화면/응답으로 확인**할 수 있어야 한다.
3. **Git 준비** — 작업 전 브랜치 생성. AI가 커밋도 하지만, **변경은 항상 `git diff`로 직접 확인**한다.
4. **계정/키** — 관리자 `admin@shop.local`, 퍼블리셔블 키(DB 조회), 한국/KRW 기본. (셋업 가이드 참조)

### 0-2. AI 개발 마음가짐 (중요)
- **AI는 똑똑한 도구이지 책임자가 아니다** — 결과는 **반드시 사람이 리뷰**한다. 그럴듯해 보여도 틀릴 수 있다.
- **작은 단위로** 시키고 **자주 검증**한다(한 번에 큰 걸 시키면 디버깅이 어렵다).
- **모르면 추측하지 말고 확인하게** 한다 — "추측하지 말고 코드/문서를 먼저 확인하고 근거(파일:라인)를 대라"고 요구.
- **변경 diff를 꼭 본다** — 의도치 않은 파일 수정·삭제가 없는지.
- **검증 없이는 '완료'가 아니다** — typecheck 통과 + 실제 동작 확인까지.

### 0-3. 프롬프트 작성법 기초 (5요소)
좋은 프롬프트 = **① 맥락 + ② 할 일(한 가지) + ③ 따를 패턴/제약 + ④ 출력 형태 + ⑤ 검증 요구**.

| 나쁜 예 ❌ | 좋은 예 ✅ |
|---|---|
| "상품 페이지 만들어줘" | "`products/[handle]` 페이지에 리뷰 탭 1개 추가. 데이터는 `lib/data/reviews.ts`(없으면 mock+타입 먼저 제안). 옆 상세 섹션 패턴 따르고, 로딩/빈/에러 처리. 먼저 접근 제안 후 내 확인 받고 구현. 끝나면 pnpm typecheck." |
| "장바구니 고쳐줘" | "장바구니 수량 변경 시 합계 미갱신. 원인을 코드에서 찾아 파일:라인으로 설명한 뒤 수정하고, /kr 카트에서 확인." |
| "포인트 기능 다 만들어줘" | "오늘은 적립금 '내역 조회'만. lib/data/points.ts 함수+타입 정의(백엔드 없음→mock). 화면은 다음에." |

**팁**
- 한 문장에 여러 작업을 담지 말 것(작업당 프롬프트 1개).
- "기존 ○○처럼"으로 **참고 대상**을 지목하면 일관성↑.
- 막히면 [§5 함정 목록](#5-이-저장소-특유의-함정-프롬프트에-미리-경고)을 그대로 붙여 경고.
- 결과가 어긋나면 **새로 길게 다시 쓰기보다, 무엇이 틀렸는지 짧게 교정**(대화 이어가기).

## 1. 핵심 원칙 (AI에게 반드시 지키게 할 것)

1. **작게 쪼갠다** — "마이페이지 전부" ❌ → "마이페이지 적립금 내역 화면 1개" ✅. 한 프롬프트 = 한 화면/한 함수.
2. **컨텍스트를 매번 준다** — AI는 저장소 규약을 모른다. §3 표준 컨텍스트 블록을 매 세션 앞에 붙인다.
3. **계약(contract) 먼저** — 화면 전에 `lib/data` 함수 시그니처 + 타입을 먼저 확정(인터페이스 PR). 백엔드 미구현이면 **mock으로**.
4. **검증을 요구한다** — "구현했다"로 끝내지 말고 **`pnpm typecheck` 통과 + 실제 화면/응답 확인**까지 시킨다.
5. **기존 패턴을 따르게 한다** — 새 구조 발명 금지. 옆 도메인(예: `modules/products`, `lib/data/products.ts`)을 참고하라고 명시.
6. **담당 도메인만 건드린다** — 분담표(06 업무분담)대로 자기 라우트/`lib/data`/`modules` 디렉터리 안에서만 작업(충돌 방지).

## 2. 진행 루프 (한 작업 = 4단계)

```
① 계획   "다음 화면을 만들 건데 접근/파일/계약을 먼저 제안해줘" → 리뷰
② 구현   합의된 계획대로 구현 요청(작은 단위)
③ 검증   pnpm typecheck + pnpm dev 로 화면 확인 + (가능 시) store API 응답 확인
④ 커밋   feature 브랜치 커밋 → PR(상호리뷰)
```
- 한 번에 ②까지 몰아서 시키지 말고 **①에서 접근을 먼저 합의**하면 헛구현이 준다.
- 막히면(특히 Medusa 데이터 형태) §5 함정 목록을 프롬프트에 같이 붙인다.

## 4. 작업 유형별 프롬프트 템플릿

### A) 신규 화면(페이지) 구현
```
[작업] 상품 상세 페이지(app/[countryCode]/(main)/products/[handle])에 "상품정보고시" 섹션을 추가하라.
- 데이터: lib/data/products.ts 에 고시 조회 함수가 있는지 먼저 확인, 없으면 시그니처를 제안하라.

- 로딩/빈상태/에러 처리 포함, 모바일 우선.

```

### B) 데이터 연동 함수 + 타입 (계약)
```
[작업] lib/data/reviews.ts 를 만들어라(상품 리뷰 목록 조회).
- 백엔드 store 리뷰 API는 아직 없다 → 타입(ReviewItem)과 함수 시그니처를 정하고, 우선 mock 데이터를 반환하는 구현으로 작성하라(주석에 "백엔드 준비 시 교체").
- @medusajs/js-sdk / 기존 lib/data/products.ts 호출 패턴을 따르라.
출력: 타입 + 함수 + 사용 예시.
```

### C) 공통 컴포넌트
```
[작업] modules/common 에 재사용 가격 표시 컴포넌트(Price)를 만들어라.
- 통화는 데이터의 currency_code로 포맷(하드코딩 금지, 기본 KRW 환경).
- 기존 common 컴포넌트 스타일/props 관례를 따르라. Tailwind + ui-preset 토큰 사용.
```

### D) 버그 수정 / 리팩터
```

- 먼저 원인을 코드에서 찾아 설명하고(추측 금지, 파일:라인 인용), 수정안을 제시한 뒤 고쳐라.
- 회귀 없는지 관련 화면을 pnpm dev로 확인하라.
```

### E) mock → 실연동 교체
```

- 엔드포인트/응답을 먼저 확인(없으면 알려달라). 타입은 유지, 내부 구현만 교체.
- 화면 쪽 호출부는 바뀌면 안 된다(시그니처 보존).
```

## 5. 이 저장소 특유의 함정 (프롬프트에 미리 경고)

막히거나 데이터가 이상하면 아래를 AI에 알려준다 — 실제로 겪은 사례들:

- **Medusa 필드 선택 함정**: 주문/상품에서 `items.total`·`items.quantity` 등 계산필드를 **단독 선택하면 값이 null/절반**으로 온다. → `items.*` 처럼 와일드카드로 로드해야 정상.
- **퍼블리셔블 키 필수**: store 요청에 `x-publishable-api-key` 없으면 401·상품 미노출.
- **리전/통화**: 기본 한국/KRW(countryCode=kr). 가격은 항상 `currency_code` 기반 포맷(하드코딩 금지).
- **계산필드 서버필터/정렬 불가**: payment_status·fulfillment_status·집계값은 Medusa 코어가 서버 필터/정렬 못 한다(관리자에선 커스텀 엔드포인트로 우회함). 프런트에서 필요하면 백엔드 협의.
- **검색**: 한글 풀네임 등은 컬럼별 부분일치라 한계가 있다(관리자 회원검색 사례). store 검색 설계 시 유의.
- **캐시 무효화**: 관리자 변경 반영은 `revalidate-tags`(프런트)↔`revalidate-contract`(백엔드) 태그 규약을 따른다.
- ~~**미구현 store API**: 리뷰·포인트·쿠폰(고객)…~~ → **해소됨(2026-06~07)**. 리뷰·포인트·쿠폰·멤버십·동의·약관·타임세일·재입고 등은 이제 **실제 `/store` 라우트**가 있다(목록: `bbizproject-store-routes` 기준, [05 데이터모델](./05_데이터모델_ERD.md) 참조). 남은 mock 은 **본인인증·소셜로그인** 뿐.
- **재고는 Admin API 로만 조작**: `inventory_level` 을 SQL 로 직접 수정하면 재고 캐시가 갱신되지 않아, DB 상 재고가 충분해도 장바구니가 계속 `insufficient_inventory` 로 실패한다. → `POST /admin/inventory-items/:id/location-levels/:location_id`.
- **dev 서버 켠 채 빌드 금지**: `pnpm build` 가 `.next` 를 덮어써서 실행 중이던 dev 화면이 500 이 된다. 빌드 후 dev 재기동.
- **금전 로직은 "총액이 얼마 줄었는지"까지 확인**: 프로모션은 공급가액에 적용되므로 1,000원 할인이 총액에선 1,100원 줄 수 있다(부가세 10%). 적립금·쿠폰 작업 시 반드시 전후 총액을 찍어볼 것 → [금액정합·타임존 점검](./금액정합_타임존_점검.md).
- **멱등키 = 만료돼도 재실행 금지**: 환불처럼 돈이 나가는 요청은 키가 존재하면 만료 여부와 무관하게 막아야 한다(실제로 이중환불 경로가 있었다).

## 6. 검증 명령 (AI에게 시킬 것)

**최소 기준(모든 작업 공통)**
```bash
cd apps/web   && npx tsc --noEmit && npx next lint   # 타입 0 · lint 에러 0
cd apps/admin && pnpm typecheck && pnpm lint
cd backend/services/api && npx tsc --noEmit
```

**바꾼 영역에 맞춰 추가로**
| 무엇을 고쳤나 | 돌릴 것 |
|---|---|
| 계산 로직(적립금·환불·권한 등) | `pnpm test:unit`(백엔드) / `pnpm test`(어드민) |
| `/store`·`/admin` API | API 통합테스트([README](./통합테스트/README.md)) |
| 화면·상호작용 | `pnpm test:e2e`(고객) / `pnpm test:sweep`·`test:qa`(관리자) |
| 금전 관련(적립금·쿠폰·환불) | 위 + **전후 총액/잔액을 숫자로 확인** |

- AI가 "완료"라고 하면 **typecheck·lint 결과 + 테스트 통과 로그**를 근거로 요구한다. 말로 하는 "확인했습니다"는 근거가 아니다.
- CI 도 같은 걸 본다(`.github/workflows/ci.yml`) — 로컬에서 통과해야 머지된다.
- 백엔드·DB가 필요하면 [셋업 가이드](./02_개발환경_구축.md) 구동 절차(+`seed-all.ts`) 먼저.

## 7. 좋은 프롬프트 체크리스트
- [ ] 표준 컨텍스트 블록(§3)을 붙였는가
- [ ] 작업이 화면/함수 **1개 단위**인가
- [ ] 데이터 출처(실 API/mock)와 **lib/data 경유**를 명시했는가
- [ ] 따라야 할 **기존 패턴(옆 도메인)** 을 지목했는가
- [ ] **담당 디렉터리 범위**를 한정했는가
- [ ] **검증(typecheck+화면)** 까지 요구했는가
- [ ] 먼저 **계획 제안 → 확인 → 구현** 순서로 시켰는가

## 9. 팀 문서화 규율 (반드시 지킬 것)

> **AI 개발은 변경이 빠르고 맥락이 휘발됩니다.** 문서 없이 진행하면 ① 다음 AI 세션이 맥락을 잃고, ② 팀원이 무엇이 왜 바뀌었는지 모르며, ③ mock/임시 구현이 방치됩니다. **"기록하며 진행"** 이 팀 AI 개발의 핵심입니다.

### 9-1. 무엇을 문서화하나
| 대상 | 내용 | 어디에 |
|---|---|---|
| **작업 로그** | 오늘 무엇을 했고/막혔고/다음 할 일 (날짜별) | `bizproject/<담당>/작업로그_YYYY-MM-DD.md` |
| **결정 기록(ADR-lite)** | 선택지·결정·이유 (예: "리뷰 정렬은 최신순 — 이유") | `bizproject/<담당>/decisions.md` |
| **mock 계약** | 백엔드 미구현으로 mock 처리한 함수·타입·교체 조건 | 해당 `lib/data/*.ts` 주석 + `bizproject/<담당>/mock목록.md` |
| **공통 변경** | `common`/`layout`/디자인토큰/타입 변경 (전원 영향) | PR 설명 + 사전 공지(채널) |
| **마일스톤 진행** | 대메뉴별 화면 완료/남은 상태 | [06 업무분담](./06_업무분담_IA.md) 분담표 또는 `<담당>/진행현황.md` |

### 9-2. 언제 쓰나 (루프에 녹이기)
- **작업 시작**: 무엇을 만들지 한 줄 + 접근 계획.
- **결정할 때 즉시**: 갈림길에서 고른 이유(나중에 "왜 이렇게 했지?" 방지).
- **mock 만들 때 즉시**: "임시 mock, 백엔드 X 준비되면 교체" 명시(방치 방지).
- **작업 끝**: 로그에 완료/남은 일 1~3줄.

### 9-3. AI에게 문서까지 시키기
프롬프트 끝에 한 줄 추가:
```
작업 후, bizproject/<담당>/작업로그_오늘날짜.md 에 변경 요약·결정·남은 일을 3~5줄로 기록하고,
mock을 만들었으면 어떤 함수가 mock이고 교체 조건이 무엇인지도 적어줘.
```
> AI가 코드와 함께 문서도 갱신하게 하면 "기록 누락"이 크게 줄어든다.

### 9-4. 간단 템플릿

**작업로그 (`작업로그_YYYY-MM-DD.md`)**
```
## YYYY-MM-DD · 담당: <이름/대메뉴>
- 한 일: (예) 상품 상세 리뷰 탭 구현, lib/data/reviews.ts mock 추가
- 결정: 리뷰 정렬 최신순(이유: ...)
- mock/임시: getReviews = mock (백엔드 store 리뷰 API 준비 시 교체)
- 막힌 점: (있으면)
- 다음: 리뷰 작성 폼
```

**결정 기록 (`decisions.md`)**
```
### [날짜] 무엇을 결정 — 한 줄
- 배경/선택지:
- 결정:
- 이유:
- 영향(다른 도메인/백엔드):
```

### 9-5. 규칙 요약
- 코드 PR에는 **반드시 무엇을·왜** 가 한 줄이라도 있어야 한다(빈 설명 금지).
- **mock·임시·TODO는 문서에 등록**(코드에만 두지 말 것) → 출시 전 정리 누락 방지.
- **TODO 는 분류 접두 필수**: `TODO(사장님결정)` / `TODO(후속 사이클)` / `TODO(리팩터)`.
  접두 없는 TODO 는 리뷰에서 지적 대상 — 분류 없는 부채가 다시 쌓이는 걸 막는다.
  (현재 분류 현황: [기술부채·TODO 분류](./기술부채_TODO_분류.md))
- 공통 영역 변경은 **문서/공지 없이 먼저 머지 금지**.
- 주 1회 통합 시 각 담당 **작업로그를 모아 리뷰**.
